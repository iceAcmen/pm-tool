# 多方协作与同步规则 collaboration.md

> **本文件记录什么 / 给谁 / 怎么用**：本文件是 pm-tool「去中心化、多平台协作」的**权威操作规则**——任何编码平台（TRAE、豆包工作、Cursor、其他 IDE/Agent 或人类）在本仓库开工前都必须读懂并遵守：开工前如何同步、改动后如何留痕、知识如何沉淀、冲突如何处理。根 `AGENTS.md` 是简明入口，本文件是其细则；两者冲突时以更严格者为准。

---

## 一、第一原则（重申）

1. **仓库即唯一事实来源**：一切影响继续开发的信息（需求、决策、变更、进展、约定、经验）只以本仓库标准 Markdown 为准；平台对话记录、私有格式、账号缓存均不作数。
2. **平台地位平等**：所有平台均可读写本仓库、互为备份。任何时间点 clone 本仓库，都应得到「最近一次所有平台改动后的完整上下文」，无需口头交接。
3. **以仓库最新状态为准**：平台内旧记忆与仓库冲突时，一律以 `origin/main` 最新文档/代码为准并调整计划。

## 二、平台标识注册表（改动留痕用）

在 `changelog.md`、`knowledge-base.md`、`handoff.md` 等处标注「由哪个平台」时，**统一使用下表标识**。新平台首次参与时，先在本表追加一行（标识用小写英文/数字/连字符）。

| 平台标识 | 显示名 | 首次参与 | 备注 |
|---|---|---|---|
| `doubao-work` | 豆包工作（Doubao Work） | 2026-10-10 | 完成阶段 1/2 与阶段 3 第 0 步、搭建本协作基座 |
| `trae` | TRAE | 2026-10-10 | 已接手并完成首个项目增查业务增量，负责后续编码与验证 |
| `human` | 项目所有者本人（史冰冰） | 2026-10-10 | 人工决策/评审 |
| （新平台在此追加） | | | 命名形如 `cursor`、`codex`、`windsurf` |

> 平台标识只用于标注「改动来源」，不代表任何平台对仓库拥有特殊权限；权限以 GitHub 仓库协作者设置为准。

## 三、开工前必做（任何任务、任何平台，无一例外）

1. **拉取最新**：
   ```sh
   git fetch origin
   git status -sb                 # 确认工作区是否干净、是否落后
   git pull --ff-only origin main # 仅快进合并；若失败说明历史分叉，走第六节冲突处理
   ```
2. **扫描最新档案**（按顺序，至少通读）：
   **`docs/onboarding-prompt.md`（开工前必读，含标准启动提示词与文末「当前交接快照」）** → `docs/handoff.md`（第 0 节）→ `docs/progress.md` → `docs/changelog.md`（**从最新一条往下看，确认其他平台刚改了什么**）→ `docs/requirements.md` → `docs/decision-log.md` → `docs/knowledge-base.md` → `docs/issues-and-solutions.md`。
3. **核对未完成/待办与「由谁继续」**：以 `progress.md` 与 `handoff.md` 写明的下一步为准；发现他人在途改动，先对齐再动手。
4. **阶段 3 起先验证地基**：跑通 `packages/dsh-pm-tool` 的构建与 `node scripts/verify-command.mjs`（退出码 0）。
5. **改代码前先报备**：列出「改哪些文件 / 为什么 / 影响范围」，经项目所有者确认后再动手（见 `AGENTS.md` 第 4、6 节）。

> 禁止：基于平台内旧对话或过期记忆直接开工；禁止在未拉取、未扫描档案的情况下修改代码。

## 四、改动后必做（一次改动的最小留痕闭环）

### 4.1 变更说明（强制）
每完成一次代码/配置/文档改动，在 `docs/changelog.md` **顶部**（最新在最上）追加一条，使用下列模板：

```markdown
## [未发布] — <一句话主题>（YYYY-MM-DD，平台：<平台标识>）

### 改动文件
- path/to/file：<做了什么>

### 为什么 / 背景
- <动机，关联需求编号 R? 或决策 ADL-? / 问题 ISS-?>

### 影响范围
- <影响哪些功能/是否需要重新构建/是否需要数据迁移/对其他平台的提示>

### 验证
- <执行的命令与结果、退出码、可演示证据>
```

### 4.2 需求 / 决策变更（强制联动）
- 改了「做什么」或选定了技术路线：同步更新 `docs/requirements.md`，并在 `docs/decision-log.md` 追加一条 ADL（模板见该文件；含时间、决策、理由、替代方案、结果、平台）。
- 需求文档头部的「最后更新 / 版本」随之递增（如 v0.3 → v0.4），并在该文档末尾或决策日志写明变更原因与时间。

### 4.3 进度与交接（强制）
- 有进展即更新 `docs/progress.md`（已完成/进行中/待办、下一步）。
- 阶段收尾或暂停/移交时刷新 `docs/handoff.md`：当前进度快照、环境依赖、下一步从哪里继续、**「由谁继续」（写平台标识）**、最近改动平台。
- **每次任务完成并提交后，必须更新 `docs/onboarding-prompt.md` 文末「当前交接快照」**（更新时间、改动平台、最新提交短 hash、当前状态、下一步、待确认项），随当次改动一起提交——保证任何新平台拿到该文件即可获得最新上下文。

### 4.4 提交与推送
- 每个任务完成后，必须执行「构建 + 当前插件包内全部 `scripts/verify-*.mjs` + 本批专项功能验证」的完整回归。逐项记录命令、退出码、关键覆盖和失败情况；任一项失败不得标记完成或提交。
- 本地验证「能跑、能演示」且完整回归全部通过后再提交；一个主题一个提交，信息清晰，建议前缀 `feat / fix / docs / chore / test`。
- 最终交付回报必须列出完整测试验证结果和未覆盖边界，不能只给笼统结论。
- 提交信息建议末尾附来源，例：`feat(阶段3): 新增项目实体存储  [trae]`。
- **推送到远程需项目所有者授权**；授权后 `git push origin main`，并确认本地与 `origin/main` 一致。禁止 `--force`、禁止改写已推送历史。

## 五、知识沉淀机制（仓库资产，必须入库）

### 5.1 必须沉淀的四类知识
1. **踩坑与解法** → `docs/issues-and-solutions.md`（ISS 编号）：现象、根因、解决方案、避坑要点。
2. **架构/技术认知** → `docs/knowledge-base.md`（KB 编号）：对 dsh 架构的新理解、真实 API 用法、有效模式、性能/行为规律。
3. **方法/约定** → `docs/knowledge-base.md`：经实践验证的编码规范、命名习惯、协作约定、验证套路。
4. **经验结论** → `docs/knowledge-base.md`：阶段复盘的可操作经验，注明适用场景。

### 5.2 时机与格式
- **一旦总结出即写入，不拖到阶段结束**；平台会话内的临时发现若对他方有复用价值，必须在当次会话内入库，不得只留在平台内部。
- KB 条目模板：

```markdown
## KB-0XX ｜ <主题>（沉淀：<平台标识>，YYYY-MM-DD）
- **结论**：<一句话可执行结论 / API 签名 / 模式>
- **适用场景**：<什么时候用>
- **可复现实例**：<命令或代码片段，注明运行环境；能给则给>
- **来源/佐证**：<上游源码路径或官方文档 URL；不确定标【待确认】>
```

### 5.3 复用
- 开工扫描档案时必须浏览 `knowledge-base.md` 与 `issues-and-solutions.md`，避免重复踩坑、重复造轮子。
- 发现既有知识有误或过时：直接更正条目并在 `changelog.md` 记录，不要新增互相矛盾的条目。

## 六、并发与冲突处理

- **小步快走、勤提交勤同步**：开始一个任务前先 pull；一个可交付小闭环完成就提交，减少长时间分叉。
- 本地落后且无本地提交：`git pull --ff-only` 即可。
- `--ff-only` 失败（历史分叉）时：
  1. 先 `git log --oneline origin/main -5` 与 `changelog.md` 看对方改了什么；
  2. 用 `git pull --rebase origin main` 把本地提交叠到最新之上（解决冲突时**保留双方有效改动**，冲突涉及需求/决策而无法判断时，先问项目所有者）；
  3. rebase 后重新本地验证（构建 + `verify-command.mjs`）再推送。
- **禁止** `git push --force` / `--force-with-lease` 到 `main`、禁止重置/删除他人已推送提交；确需改写历史必须经项目所有者同意并知会所有平台。
- 同一文件尽量避免两平台同时大改；较大改造先在 `handoff.md`/`progress.md` 标注「在途」，降低冲突面。

## 七、可移植性硬要求（所有平台一致）

1. 文档一律**简体中文 + 通用 Markdown**，不用任何平台私有标记（如仅某工具识别的标签）。
2. 关键命令、配置、代码片段**完整可复制**，并注明运行环境（macOS + nvm Node v22.23.3 + pnpm 11.28.5）。
3. 所有核心成果放本仓库；不改上游；`main` 干净、clone 后按 `handoff.md` 即可接续。
4. 每次迭代/变更结束同步提交；真实密钥、令牌、密码绝不入库。
5. 每个文档开头保留一句话说明「记录什么、给谁用、怎么用」。

## 八、新平台首次接入清单（自检）

- [ ] 由项目所有者把 `docs/onboarding-prompt.md` 的「标准启动提示词」整段发来；clone 仓库后读完该文件（含文末快照）、`AGENTS.md`、`docs/handoff.md` 第 0 节、`docs/requirements.md`、`progress.md`、最近的 `changelog.md`、`knowledge-base.md`、`issues-and-solutions.md`。
- [ ] 在本文件「平台标识注册表」登记自己的平台标识（首次改动提交时带上）。
- [ ] 按 `handoff.md` 第 3 节恢复/确认环境，跑通构建与 `verify-command.mjs`。
- [ ] 明确本次接手的任务边界与「由谁继续」，必要时请项目所有者确认。
- [ ] 首次改动即按第四节留痕（changelog 标注平台标识）。
