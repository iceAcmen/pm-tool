## C1 · 模型只读供给面（按需工具查询 / 常驻有界注入）

**核心主张**：把台账变成 agent 在对话里「查得到、看得到」的只读面；产品差别只在供给方式——模型按需调工具查，还是摘要常驻系统提示词不调也看得到。

**成员**：
- D1-01 只读模型工具族 `pm_read_*`；D2-07 纯只读工具 `pm_search/pm_get/pm_list`；D3-01 只读台账工具包；D4-01 只读台账工具组；D5-01 只读工具进 agent loop
- D3-21 按需 pull 只读上下文块（PM 问「当前项目」才喂快照，不每轮注入）
- D1-02 持久轻上下文注入（今日议程+异常 Top N+健康灯，非全量快照）；D2-01 台账摘要作持久模型可见系统提示词段；D4-04 有界只读上下文注入；D5-03 看板摘要推进系统提示词
- D1-32 注入预算治理（上下文小到不挤压主任务，配 compaction/spill）；D1-R3-13 自适应注入水位（随主任务占用伸缩）
- D2-02 台账渲染成可按需加载的 PM skill（不常驻上下文）
- D1-05 会话内多轮副驾（当前项目会话变量+记忆续问，结束即消散）
- D1-R3-01 反向只读工具：台账主动读模型会话（供给方向倒置）；D1-R3-11 模型工作状态常驻推回台账（注入反向）

**边界**：只含「台账→模型」的只读供给，不注册任何写动作（写面归 C2）；不做跨会话持久记忆（那是寿命归属问题，归 C10）。
**与相邻簇重叠**：D2-02/D1-29/D3-16 的 skill 形态同时是 C14 分发载体；D1-R3-01/11 的反向取数同时是 C4 证据采集的另一方向。
**内部张力轴**：
- **按需调用（tool，省 token、可查全量）↔ 常驻注入（不调工具也看得到，但占上下文）**；
- **正向喂（台账→模型）↔ 反向取（台账主动读会话，D1-R3-01/11）**。

## C2 · 写草稿与审批 seam（人裁决的写面）

**核心主张**：模型可以起草改动，但落库必须经过人（或规则）的批准；产品把「草稿—审批—落库」做成对话内的标准 seam。

**成员**：
- D1-03 写动作工具 + interaction 审批 seam（人不在面板也能批草稿）；D2-08 草稿工具+一次性审批 seam；D3-02 `pm_propose` 草稿工具+userQuestions 单选确认；D4-02 写工具+审批 seam；D5-02 写工具走 approval seam，台账仍是唯一事实源
- D1-R3-02 规则化自动审批闸：白名单内自批，人只事后抽查（审批主体从人让位给规则）
- D1-R3-03 事件自更新台账：数据自己写自己，agent 当记录员（无人极）
- D1-R3-10 子 agent 为主体、人远程指挥收发室（自主极）
- **反叛极（只读是半瞎陷阱）**：D1-R2-20、D2-R2-18、D3-R2-17、D4-R2-19、D5-R2-18——单人单写者场景应直接给边界内受限写权，只读+逐笔审批是「半瞎陷阱」
- D4-R2-23 反叛：深双向绑定在单人场景反而对，「无主体所以轻融合」是伪顾虑（更极端端）

**边界**：人始终是落库裁决者（或规则白名单），不含 agent 无人自主执行 PM（那是 C8 自主度极）；与 C1 的分界是「是否注册写动作」。
**与相邻簇重叠**：D1-R3-03/10 的无人/自主端与 C8 班底、C10 事件自写相邻；D4-R2-23 的双向绑定主张同时挑战 C10 的单向镜像纪律。
**内部张力轴**：**逐笔人工点头 ↔ 规则白名单自批 ↔ 事件自写/子 agent 主体（无人）**；以及主流立场「只读最安全」↔ 反叛「单人受限直写更诚实」。
