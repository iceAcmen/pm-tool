### 1.2 处境（已核验的现状，非评价）
pm-tool 是跑在 dsh 宿主里的一个外挂插件，当前版本 v0.7.4（【源码】`packages/dsh-pm-tool/package.json`）。

**已落地的产品面（【源码】`packages/dsh-pm-tool/src/`）：**

- 人直接触发的离线命令族 `/pm ...`，不消耗模型轮次（【源码】`src/index.ts:119-234` 注册单个 `pm` 命令，handler 内部分发各子命令）。
- AI 仅以「一次性草稿」形态存在：`/pm ask` 把当前项目快照压成中文上下文，经 `dsh-llm` 适配器的 provider 候选链一次性调用模型，产出只读诊断 + 多步计划草稿，人在草稿卡上确认才经 `ask-apply` 落库（【源码】`src/core/ask-copilot.ts`（`buildAskContext`/`COPILOT_SYSTEM`）、`src/core/ai-client.ts`（`generateDraft`）、【文档】ADL-054）。

**已核验的接入面（现状用到什么）：**
- Host 入口 `inject = ['commands', 'storageDomain']`；`llm` 不进 inject，运行期 `ctx.reflect.get('llm', false)` 懒读，缺失走中文 NO_LLM 降级（【源码】`src/index.ts:49,101-102`）。
- 全仓 grep 无 `ctx.tools.register` / `defineTool` / `ctx.on(...)` 事件订阅（仅 `src/index.ts:108` 的 `ctx.effect` 做关闭清理）——即：未向 agent 对话循环注册任何模型工具，未订阅宿主任何事件流（【源码】grep 全量 `src/`）。
- Client 运行期注入 `['slots','remote','remote.commands','sessions']`，但 `sessions` 只取第一个会话 id 作为命令投递的传输句柄，从不读取会话消息/历史（【源码】`src/client/index.tsx:21-23`；`package.json` 的 `dsh.client` 仅类型导入 session-controller 等）。

**宿主已有而插件基本未用的能力（【源码】逐一核对 `deepseek-harness/packages/*/README.zh.md`）：**
session（持久会话日志 jsonl）、context（以用户角色消息注入会话历史的模型可见持久上下文）、plan（会话内计划模式）、goal（每会话一个目标状态机）、todo（会话级 `todo_write`）、jobs（进程内后台任务，宿主关闭即结束）、schedule（Host 持久提醒，到期作为 follow-up 消息进入原对话）、mcp（外部服务器工具/资源）、subagent（独立运行时/会话/工具的委派，仅共享工作目录）、workflow（模型编写的扇出编排脚本，会话内）、deliverables（绑定 agent 轮次的交付声明 + git 快照）、interaction（审批/权限/agent 向人提问 seam）、skill（按需加载的会话内指令模板）、compaction、telemetry、document、attachment 等。

## 4. 对命题本身的质疑（本阶段核心）

### 4.1 目的 / 手段 / 症状分层

**命题给出的是手段（且是程度词），不是目的。**【推理】
- 手段：「与宿主深度融合」——动作本身，无目标状态。
- 可能被掩盖的目的（候选，均待所有者确认，本文不选定）：
  - P-a 让台账在宿主的 AI 对话循环里可被读取/起草修改（AI 可达性）；
  - P-b 复用宿主现成能力以减少自建成本（经济性）；
  - P-c 借宿主生态获得存在位置/分发（平台性）；
  - P-d 解决 PM 真实工作中某个尚未被台账覆盖的具体痛点（用户价值）。
- 这四个目的导向的答案互不相同：P-a 指向模型工具/授权边界；P-b 指向成本核算；P-c 指向插件分发与 profile；P-d 指向痛点本身，宿主可能只是其中一个可选载体。

**「深度融合」可能是症状而非问题。**【推理，依据见 1.4】
- 可观察事实：内部增量 backlog 已清空（【文档】`docs/optimization-backlog.md`），台账七实体闭环、甘特/关键路径/人员负载/HITL 副驾/客观进度/备份/CI 均已落地。
- 推理链：当一个产品在自身边界内的可做项被清单化清空后，「向外接宿主」常被当作新方向的默认出口；此时「融合」可能是「内部找不到下一个值得做的问题」的症状，而不是被某个具体未满足痛点推出的答案。
- 检验方式（非方案）：若列不出一个「现在就在发生、发生频率可估、且只能靠加深宿主连接解决」的具体痛点，则 P-d 不成立，命题需要降级为手段或重新归因。

### 4.2 先排除一个伪等式：「宿主有很多能力没用」≠「这些能力都该被用」

【推理】逐一核对宿主能力的作用域后，多数未用能力自带适用前提，而当前用户模型不满足：
- plan/goal/todo/context 都是**会话内（session-scoped）**智能体行为，随一次对话存在（【源码】`packages/plan/README.zh.md`、`packages/goal/README.zh.md`、`packages/todo/README.zh.md`、`packages/context/README.zh.md`：上下文以用户角色消息进入会话历史）；台账是跨会话持久档案，二者生命周期不同。
- jobs 进程内、宿主关闭即结束（【源码】`packages/jobs/jobs-local/README.zh.md`）；与离线、可关可走的定位不天然契合。
- schedule 持久，但到期提醒作为 follow-up 消息**进入原对话**（【源码】`packages/schedule/README.zh.md:12`），投递终点仍是一个会话，而非台账自身。
- subagent 独立运行时/会话/工具，仅共享工作目录（【源码】`packages/subagent/subagent-acp/README.zh.md`）；workflow 在会话内扇出；mcp 面向外部工具生态——它们面向「一个常驻 agent 团队/多人协作」场景，当前单用户单写者下可能没有调用主体。
- deliverables 绑定 agent 轮次与 git 快照（【源码】`packages/deliverables/README.zh.md`）；可行性-map 已记录其依赖模型轮次、不满足无 Key 离线手工台账，故 R10 走了「复用概念、数据层自研」（【文档】`docs/feasibility-map.md` R10 行）。

【推理】结论性质疑：「宿主清单长」只能证明存在可选项，不能证明缺项值得补；按宿主能力清单逐项找用途，有「为用而用」的风险（`src/core/external-skill-router.ts` 注释里作者自己也为 vendored skill 设了「无任何命中→route=none，避免为用而用」的先例，可作为方法论参照，非结论）。

### 4.3 更本质的问法候选（reframing，均为问题，非方案）

#### R1 · 断点问法：「PM 在本机完成一次真实项目动作时，哪一步仍需在工具间搬运信息或重复录入？这个断点位于台账内部、台账与宿主之间，还是台账与宿主之外的系统之间？」
- 推理链：
  1. 已记录的历史痛点证据（【文档】`docs/product/02-ux-evaluation.md`，v0.3.0 时期快照，部分已被后续版本消解，仅作线索）集中在两类：台账与研发日常（Git/MR）两张皮（UX-11）；AI 是固定按钮、非对话（UX-10，已由 `/pm ask` 部分回应）。
  2. 断点若在「台账 ↔ Git/MR/群」一侧，则宿主的 session/plan/goal/subagent/workflow 与该断点无因果关系，加深宿主耦合不消除断点。
  3. 断点若在「人 ↔ 面板」的操作路径上，则属于既有产品的内部可用性问题，与宿主能力无关。
  4. 只有当断点落在「人 ↔ 宿主 AI 对话 ↔ 台账」这条轴上时，「融合」才可能是相关手段。
- 会把探索引向的可能性空间：先定位断点坐标再决定载体；可能的方向包括外部系统对齐、面板内部路径优化、对话可达性——三者并列，融合只是其中一个子集。
- **此问法下「深度融合」常常不是答案**：断点在台账外部或面板内部时，加深宿主连接与断点消除之间无因果链。

#### R2 · 读写边界问法：「宿主的 AI 对话循环在什么条件下可以读取台账、在什么条件下可以起草对台账的修改，且人始终是最终裁决者？哪些操作必须留在显式命令、不进对话？」
- 推理链：
  1. 现状 AI 被锁在 `/pm ask` 一次性命令里：自拼快照、不进 agent loop、对话循环看不到台账、也无法在普通对话中被主动调用（【源码】无 `ctx.tools.register`；`src/core/ask-copilot.ts` 一次性 `generateDraft`）。
  2. 若真实目的是 P-a（对话中随时问项目、随时起草改动），则要回答的本质问题是「可读范围 / 可写草稿范围 / 授权边界 / 人确认卡点」，这是一个权限与可信度问题，「融合」只是它的工程外壳。
  3. 反过来，答案也可能是「维持一次性命令即可，对话循环不应主动碰台账」——此时问题成立但融合被否决。
- 会把探索引向的可能性空间：模型可见的只读面、写草稿面、对话内展示卡片、授权与审批 seam（interaction）、降级与离线复核；同时需要界定**不进对话**的操作清单。
- **此问法下「深度融合」部分是答案、部分不是**：工具注册与授权边界相关；接入 session 历史、subagent、workflow 与该问题无必然关系。

#### R3 · 独立性问法：「抛开 dsh，pm-tool 的最小独立内核是什么？宿主提供的能力里，哪些是可拔插增强、哪些一旦依赖就破坏离线/可读/可逆/可升级这四条既有原则？」
- 推理链：
  1. 产品一贯原则是上游只读、离线优先、人类可读、可逆（【文档】`AGENTS.md:84-89`）；上游处于 alpha，基线锁定 v0.2.1-alpha.2（【文档】`docs/feasibility-map.md`、`optimization-backlog.md`）。
  2. 会话内能力（plan/goal/todo/context/）、进程内能力（jobs）、会话投递能力（schedule→原对话）把产品状态绑定到一个对话运行时；而台账的立身之本是「关闭宿主、文件仍可读可迁移」。
  3. 因此本质问题可能不是「接多少宿主能力」，而是「哪些连接允许断开后内核仍成立」——即把融合反过来审，先划解耦线。
- 会把探索引向的可能性空间：纯文件内核 + 可选宿主适配层；稳定内核与易变会话运行时分离；升级回归成本核算。
- **此问法下答案可能是「刻意保持浅融合」**：融合的深度本身被当作受约束的变量，而非越大越好。

#### R4 · 使用主体问法：「以所有者本人单机、离线、单写者的真实条件，宿主未用能力里有哪些根本没有调用主体？按『宿主有什么』枚举连接，会不会造出无人使用的通路？」
- 推理链：
  1. subagent/workflow/mcp 生态/多人/遥测/compaction 的设计前提是多 agent、多会话、外部工具网络或团队规模（【源码】各 README.zh.md）。
  2. 当前与可预见的未来使用者是同一人、一台机器、一份数据（【文档】`personal-billing-plan.md` 个人单机）。
  3. 无调用主体的能力被「融合」进来后，维护成本落在所有者一人身上，收益侧为空。
- 会把探索引向的可能性空间：以真实高频动作为筛子逐项过宿主能力清单；只保留有主体的连接；明确记录「评估过但不接」的能力及理由。
- **此问法下多数「融合」直接不是答案**：它要求先证明主体存在，再谈连接。

#### R5（补充）· 平台存在性问法：「为什么 PM 台账要活在 dsh 里，而不是独立应用？宿主为产品提供了哪些不可替代的东西（AI 通道、运行时、界面、分发）？哪些只是『恰好在此』？」
- 推理链：若宿主提供的不可替代项只有「一个可调用的 LLM 通道 + 一个本地 Web 壳」，则「深度融合」的必要性需要从这两项是否被用到的角度重新论证；若不可替代项更多，R5 的答案会收缩为对那些项的加深。
- 此问法触及平台选择本身，可能把「融合」问题转化为「去留」问题。

### 4.4 哪些问法下「深度融合」根本不是答案或答案完全不同（汇总）
| 选定问法 | 「深度融合」的地位 |
|---|---|
| R1 断点在台账↔外部系统（Git/MR/群） | 不是答案；答案在外部集成，与宿主会话能力无关 |
| R1 断点在人↔面板内部 | 不是答案；答案是既有产品内部可用性 |
| R2 对话读写边界 | 部分答案（只读/草稿/授权），但融合深度受边界约束，且可能整体否决 |
| R3 内核独立性 | 答案可能反向：保持浅融合、先划解耦线 |
| R4 调用主体 | 多数能力无主体，融合清单被裁掉大半 |
| R5 平台存在性 | 问题可能从「怎么融合」变成「是否继续以宿主为载体」 |

### 4.5 对原命题的总体性质疑（待所有者裁决，非结论）
【推理】「pm-tool × dsh 深度融合」当前是一个**手段被当成目的**的命题：它规定了动作（融合）与程度（深度），未规定要消除的具体问题、成功后的可观测状态、以及不融合时的替代解。在 P-d（真实痛点）被具体指认之前，命题存在「为用而用」「以平台热代替用户痛」的风险；在调用主体与离线约束被核算之前，融合深度可能超过收益。

### 5.1 本阶段在范围内

- 评估宿主能力清单的具体接入实现；
- 改变既有产品决策（离线优先、可读文件、单用户等）。

### 5.3 看似相关、实则是另一个问题（避免在本命题里混谈）
1. **多人协作**：`docs/product/11-collaboration-ready-architecture.md` 的 C2/C3 是独立产品议题，契约已冻结为「现在只留缝、不引入网络/账号/合并」，与「深度融合」不等同。
2. **客观进度 v0.8**：`docs/product/12-objective-progress.md` 产品决策已定，属既定迭代，不是融合议题。
3. **仓库联动（Git/MR）**：是 R1 意义上的外部断点议题，可作为独立方向并列，但与「加深宿主会话能力」是两件事；v0.6.0 已加只读 repoUrl/branch 字段（【文档】`requirements.md` schema v2 批 PROD-21），无实时桥接。
4. **模型成本/Key/车道**：`docs/personal-billing-plan.md`、`docs/model-providers.md` 是独立的成本与接入议题。
5. **上游升级维护**：alpha 基线回归是工程维护议题，不是产品方向议题。
6. **vendored skill 治理**：`docs/external-skills.md` 是既有独立治理体系。
