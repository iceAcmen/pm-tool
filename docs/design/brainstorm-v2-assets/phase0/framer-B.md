## 1. 原命题复述（不带预设）

**命题原文**：「pm-tool × DeepSeek Harness（dsh / Cordis 宿主）深度融合」。

**剥掉「深度融合」这个词之后，可被中立陈述的事实层：**

- **谁**：项目所有者本人（字节在职 PM，单人使用，本地 macOS，仅承诺 Chrome）【文档：`docs/requirements.md` §一、`docs/product/01-current-state-personas.md`】。产品是他自己的工作台，没有第二个登录用户【文档：`docs/requirements.md` §一「MVP 单用户、本地 macOS」；`docs/product/06-tradeoffs-and-risks.md` 三条红线之三「单用户本地」】。
- **处境**：pm-tool 已到 v0.7.4，七类业务实体（项目/任务 WBS/里程碑/风险问题/会议纪要/进度汇报/交付物）+ 人员负载、甘特（只读拖拽）、关键路径只读高亮、健康分、客观进度、备份恢复、口径设置、AI 副驾草稿与多步计划卡均已落地并通过独立验收【源码：`packages/dsh-pm-tool/src/`；文档：`docs/progress.md`、`docs/changelog.md`】。与宿主的现有接触面只有：必需依赖 `commands`、`storageDomain`；`llm` 运行期懒读；Web 侧一个独立顶级面板；客户端只注入了类型与 `sessions/remote/slots`【源码：`packages/dsh-pm-tool/src/index.ts:49,102`；`src/client/index.tsx`；`package.json` 的 `dsh.client`】。
- **与宿主的实际耦合现状（源码核查，非文档转述）**：
  1. **没有把 PM 台账注册为模型工具**：全 src grep 无 `ctx.tools.register` / `defineTool`，agent 在对话循环里看不见、也无法调用七实体 CRUD【源码：`packages/dsh-pm-tool/src/` 全量 grep】。
  2. **没有任何事件订阅**：host 侧 core/commands 无 `ctx.on(...)`，宿主会话事件、领域变更事件均未被消费【源码：`src/index.ts`、`src/core/*`、`src/commands/*` grep 无 `ctx.on`】。
  3. **面板与后端的通道是「命令字符串」**：面板唯一写通道为 `remote.commands.execute(sessionId, '/pm <子命令>')`，唯一读通道为一次性 `web snapshot` 全量 JSON；客户端注入 `sessions` 仅用于取一个 sessionId 作为命令运输句柄，不读会话消息/历史【源码：`src/client/index.tsx`；`src/index.ts:127-147`】。
  4. **AI 是一次性离线生成，不在 agent 循环内**：`/pm ask` 把当前项目压成压缩文本、经 dsh-llm 网关一次性请求，返回只读诊断 + 草稿 plan，写动作必须在面板由人确认；模型在正常对话循环里不持有台账状态【源码：`src/core/ask-copilot.ts`（`buildAskContext`/`askCopilot`）；`src/core/ai-client.ts`】。
- **要解决什么（命题字面）**：让 pm-tool 从「服务级接入 + 上下文级隔离」走向对宿主更多能力（session/context/plan/goal/jobs/schedule/mcp/subagent/workflow 等）的使用【事实包 §4】。
- **为什么现在提**：台账闭环已完成，下一段方向空出；上一轮（v1）脑暴因方法论失败重跑；所有者已开始准备离职后以个人开发者身份维护（`docs/personal-billing-plan.md` 更新于 2026-10-17），平台成本与可持续性进入视野【文档：`docs/personal-billing-plan.md`】。

**未被原命题说出的隐含前提（本阶段只登记、不采信）**：宿主未被使用的能力是「未被利用的价值」，而非「未被需要的复杂度」；以及「融合越深，产品越好」。这两条是待检验假设，见 §4。

### 3.3 可证伪的成功标准（命题级，均可被检验，无「体验更好」类空话）

**A. 本轮脑暴自身的成功标准（阶段 0-2 结束时可判定）**

- A1：对「深度融合」一词给出了至少一种可操作的语义拆解（技术耦合 / UI 无缝 / 商业定位），且每种语义对应可独立检验的命题——若拆解后发现某语义无消费方，该语义被证伪。
- A2：每个 reframing 都配有「什么证据会推翻它」的检验条件，而非停留在主张。
- A3：登记的关键假设中，至少标出哪些可以用现有源码/文档直接核验、哪些必须向所有者提问。

**B. 若未来采纳任一融合方向，方向本身必须满足的可检验命题（本阶段只给检验格式，不选方向）**

- B1（消费方命题）：存在可计数的真实使用场景——例如「一个周期内，agent 循环实际读取台账 N 次且被人采用其结果 M 次」；若 N≈0，该方向无消费方，证伪。
- B2（正确性命题）：在试点期，agent 自动产出的读写建议被人接受的比例、被拒绝/纠正的比例可统计；低于预设阈值则该融合形态不成立。
- B3（约束不破命题）：无 Key 状态下核心台账 CRUD 可用率 = 100%（回归测试可跑）；任何融合层不得在无 Key 时阻断既有命令。
- B4（成本/寿命命题）：上游一次 breaking upgrade 后，融合层修复工时可被记录并与独立层修复工时对比；若融合层修复面系统性更大，「融合提效」主张被削弱。
- B5（价值命题）：融合上线前后，PM 手动录入/维护台账的条数或耗时可被基线测量；无下降则价值主张证伪。

> 以上阈值具体数字留待所有者与后续阶段设定；本阶段只要求命题形式可检验。

## 4. 对命题本身的质疑（本阶段最重要）

### 4.1 目的 / 手段 / 症状分离

| 层级 | 内容 | 依据 |
|---|---|---|
| **目的（待确认，命题未明说）** | 候选目的 P-a：让 PM 更快看到风险、更少手工维护台账、汇报/交付闭环更顺；P-b：让 pm-tool 留在 dsh 内以获得合规低成本 AI 通道；P-c：让产品具备被 agent 自主使用的能力。三者互不等价。 | 【推理】从 `personal-billing-plan.md`（成本动机）与 `product/04-disruptive-concepts.md`（副驾动机）反推，命题未声明是哪一个 |
| **手段（命题给出的）** | 「深度融合」= 更多使用宿主未用能力（session/context/plan/goal/jobs/schedule/mcp/subagent/workflow…） | 【文档】事实包 §4 |
| **症状（可能被误当目的）** | 现状的可观察症状：面板靠命令字符串与后端通信；agent 循环看不见台账；AI 是三个/一次性草稿；台账与研发执行两张皮。症状各自对应不同目的，不必然导向「融合」 | 【源码】`src/client/index.tsx`、`src/index.ts`、`src/core/ask-copilot.ts`；【文档】UX-11 |

**关键质疑 1：「未使用的宿主能力」不等于「有价值的能力」。**【推理】宿主能力清单（事实包 §4）是供给侧列表，不是需求侧证据；现有 S1 级断点（树/排期/概览/人员）全部由本领域数据 + 纯前端解决，未消耗任何未用宿主能力（§2.3）。供给侧丰富不能推出「应当使用」。

**关键质疑 2：两类系统的寿命与归属在结构上不同，「深度」可能是错的耦合方向。**【推理 + 源码/文档】
- 宿主 plan / goal / todo / session / jobs / deliverables 都是**会话级、agent 拥有、随对话生灭**的状态【文档：`packages/plan`、`packages/goal`、`packages/todo`、`packages/jobs`、`packages/deliverables` 各组 README.zh.md；事实包 §4 表】。
- pm-tool 七实体是**跨会话、人拥有、长寿、落盘可 git** 的台账【源码：`src/core/storage.ts`；文档：requirements §五】。
- 把长寿人有事实与短命 agent 状态做双向深度绑定，存在类别错配风险；既有决策已在两处体现这种错配的规避：feasibility-map 判定 plan/goal/todo 不是项目档案故自建实体【文档：`feasibility-map.md` §一/二】；ADL-028 判定原生 deliverables 绑定 agent 轮次+git 快照，不适合离线手工台账，只复用概念【文档：requirements §4.7 ADL-028】。

**关键质疑 3：「深度融合」可能是平台锁定后的合理化，而非需求推导。**【推理】`personal-billing-plan.md` 显示留在 dsh 的一个硬理由是 ¥40/月 Coding Plan 合规与成本；成本约束可以解释「为什么不搬走」，但不能推出「为什么要更深地接进宿主」。把成本约束误当产品价值，是本命题最需要警惕的跳跃。

### 4.2 更本质的问法候选（reframing）

#### Reframing Q1：按「数据寿命 × 归属人」分层，而不是按宿主能力清单逐个配对

- **问法改写**：哪些 PM 事实必须长寿且由人拥有（落盘台账），哪些天然属于短命、agent 拥有的临时状态？在这条寿命轴上，pm-tool 与宿主各自该停在哪一层，层与层之间允许什么方向的流（单向投影？只读引用？禁止双向绑定？）？
- **为什么更本质**：【推理】现状把问题表述为「宿主还有哪些能力没用」，这是从供给出发；Q1 从数据本身的寿命/归属出发，先判类别再判接线。宿主能力清单是杂乱的（会话、定时、后台、多智能体、外部协议混在一起），唯有寿命/归属这一条轴能给出「该不该接」的判据，而不是逐个做功能诱惑测试。
- **把探索引向的不同空间**：分层映射表、单向只读投影、事件单向广播、保持孤岛——而非「把 session/goal/subagent 逐个接进来」的清单式路线。
- **在此问法下「深度融合」的处境**：双向深度绑定大概率不成立；只允许少数单向、只读、短命→长寿的投影。

#### Reframing Q2：真正的缺口是「计划与执行证据之间的闭环」，宿主只是候选通道之一

- **问法改写**：PM 在台账里写了任务，现实中工作发生在 MR/commit/agent 轮次/会议里，两者如何对账（计划 ↔ 执行证据）？证据从哪里捕获、以什么形态回到台账（草稿？只读链接？），与用哪个宿主能力无关。
- **为什么更本质**：【推理】`02-ux-evaluation.md` UX-11（与代码仓库零联动）是 S1 中唯一未被面板内改进解决的断点，也是 Persona D 断点；它指向的是「执行证据缺席」这一目的，而 schedule/mcp/session 日志/git workspace-changes/subagent 都只是捕获证据的可选管道之一。问「接哪个宿主能力」把手段当成了问题。
- **把探索引向的不同空间**：git API、MCP 外部服务器、会话日志作素材、人工链接、暂不做——管道并列评估，宿主集成只是其中一格。
- **在此问法下「深度融合」的处境**：不是答案；答案由「证据从哪来成本最低、最守离线红线」决定，宿主接线可能被外部通道或纯人工方案击败。

#### Reframing Q3：「让一个不看面板的自主工作者能正确读写台账」是不是真实需求？（机器可操作性问题，而非融合深度问题）

- **问法改写**：是否存在这样的场景——agent 在无人逐次指示的情况下，依据台账自主完成 PM 动作并被人接受？若有，需要的是一套机器可操作接口（schema、权限边界、HITL 契约、可校验输出）；若没有，工具注册/上下文注入就没有消费方。
- **为什么更本质**：【源码事实】现状 agent 循环完全看不见台账（无工具注册、无上下文注入，§1），AI 仅以「人在面板点按钮 → 一次性生成草稿 → 人确认」的形态存在。融合讨论常跳过「谁来消费这个接口」直接讨论「怎么暴露接口」。Q3 把场景存在性设为前置门。
- **把探索引向的不同空间**：接口契约设计、权限/HITL、输出可校验性；或证伪后回到「人操作为主、AI 只做一次性草稿」的现状稳态。
- **在此问法下「深度融合」的处境**：若场景不存在，深度融合不是答案；若场景存在，问题也不是「融合多深」而是「接口多严谨」，两者的成功标准（B2 接受率、B3 无 Key 不破）完全不同。

#### Reframing Q4：平台归属问题——dsh 是否是 PM 工作的正确容器？

- **问法改写**：pm-tool 留在 dsh 内，是因为 dsh 最适合 PM 工作，还是因为已经住在里面 + 计费合规？若把「平台」作为变量重新评估，深度耦合与可剥离性各自的代价是什么？
- **为什么更本质**：【文档事实】dsh 明示开发者预览、将有 breaking changes（C6）；计费方案的合规前提是「在官方支持工具内使用」，脱离即需标准 API（成本上升）。成本与惯性是选择留在 dsh 的理由，但与「要不要深度嵌入」是两件事。Q4 防止把「不搬走」误写成「搬得更深」。
- **把探索引向的不同空间**：独立应用、对外暴露的 MCP server（任意客户端消费）、纯开放文件 + 任意前端、维持孤岛插件——平台选项并列。
- **在此问法下「深度融合」的处境**：可能整体被降级为「当前运行时的临时接线」，而非产品方向本身。

### 4.3 哪些问法下「深度融合」根本不是答案（或答案完全不同）

1. 若主导痛点是面板内视图/数据完整性（3 个月 backlog：看板 P2、9 视图重设计、prod Key 稳定性【文档：`progress.md` 下一步】）——宿主未用能力清单里没有对应解，融合不解决该痛点。
2. 若坚持离线优先 + 无常驻进程红线（C2/C7）——schedule 主动推送、jobs 常驻、subagent 扇出等形态与红线直接冲突（ADL-032 已据此暂缓 R11），「更多使用宿主能力」在这些条目上被既有裁决封死。
3. 若真实用户始终只有本人、且每天手动操作——工具化/上下文注入无消费方（Q3），融合是无的放矢。
4. 若目的是离职后低成本长期维护（S2）——耦合越深，面对上游 breaking changes 的修复面越大（B4），轻耦合/可剥离反而更接近目的。
5. 若时间尺度放到 10 年（§5）——宿主必然被替换或废弃，长寿数据不应与短命运行时深度绑定。

## 5. 时间尺度穿透（B 的专项侧重）

> 同一命题在不同时间尺度上，最重要的问题不同，「深度融合」的成立条件也不同。以下每格标注依据类型。

### 5.1 3 个月尺度（当下迭代窗口）

- **最重要的问题**：面板自身完整性——看板 P2、9 视图重设计、视觉基准放行、prod 真实 Key 配置与稳定性（当前 MANUAL_PENDING）【文档：`progress.md` 下一步、`handoff.md` 遗留项】。
- **什么问题会消失/推迟**：需要常驻调度的主动推送（ADL-032 已裁决暂缓，R16 打开面板派生提醒已替代核心诉求）；多智能体编排、外部 MCP 接入在此窗口无触发场景。
- **「深度融合」在此尺度**：收益无证据支撑，多数条目与 C2/C7 冲突；本尺度下它不是答案，而是分心。【推理】依据：现有 S1 断点均由本领域解决（§2.3），无未满足的需求指向未用能力。

### 5.2 2 年尺度（离职、个人开发者维护期）

- **最重要的问题**：可维护性、AI 成本合规、上游能否存活与兼容。约束事实：dsh 处于开发者预览且明示 breaking changes（C6）；个人单机月成本锚定 ¥40 Coding Plan，且合规前提是留在官方支持工具内【文档：`personal-billing-plan.md` §0-1】。
- **什么问题会变化**：单人维护者没有精力为每次上游变更修补深层耦合；融合深度与升级修复工时成反比（B4 可测）。
- **「深度融合」在此尺度**：条件性成立但方向反转——成立的是「刚好 enough 的接线以留在计费合规圈内」，失效的是「尽量深地嵌入宿主内部机制」。【推理】深度嵌入在单人维护 + 预览期平台组合下，维护风险大于收益。

### 5.3 10 年尺度（数据资产视角，平台必然更替）

- **最重要的问题**：项目记录作为长寿数据，如何在宿主消失/重写后仍然可读、可迁移。答案候选空间：开放格式（现状 JSON 已具备）、不依赖宿主 API 的导出、可被任意前端/工具消费。
- **什么问题会消失**：「与当前这版 dsh 的哪个能力对接」作为问题消失——具体宿主机制在 10 年尺度上不存在。
- **「深度融合」在此尺度**：作为目标失效。深度绑定是临时接线，长寿的是数据与格式；在此尺度上，融合越深越是迁移负债。【推理】依据：C6 预览期无长期承诺；requirements §六「可迁移」、ADL-028 只复用概念不复制机制，与这一方向一致。

### 5.4 尺度结论（命题的时间性）

【推理】「深度融合」只可能在 2 年尺度的窄窗口内、且被重新定义为「轻量合规接线」后成立；在 3 个月尺度是分心，在 10 年尺度是负债。把一个条件性、窄窗口的手段升格为产品方向，是本命题需要被检验的核心跳跃。
