# 问题框定书（阶段0 定稿）

> 方法论：两名问题校准者（A、B）在互不可见、无交流条件下独立产出（原文见 `phase0/framer-A.md`、`phase0/framer-B.md`），本文件由组织者合并去重。所有关键判断均带【源码】【文档】【推理】标记，证据路径见原文。本阶段只校准问题、不选方向、不给方案。
> 日期：2026-10-18；基线：pm-tool `dsh-pm-tool` v0.7.4，上游 deepseek-harness 只读（peer 锁 0.2.1-alpha.2 / cordis ~4.0.5-alpha.1）。

## 0. 两独立校准者的共识与分歧

**高度共识（两人独立得出，互不可见）**：
1. 「深度融合」是一个**手段（且是程度词）被当成了目的**：命题规定了动作与程度，没有规定要消除的具体问题、成功后的可观测状态、以及不融合时的替代解。
2. **供给侧清单 ≠ 需求侧证据**：宿主能力多，只能证明「可选项存在」，不能推出「缺项值得补」。
3. 存在**生命周期/归属错配**：宿主 plan/goal/todo/session/jobs/deliverables 多为「会话级、agent 拥有、随对话生灭」；pm-tool 七实体是「跨会话、人拥有、长寿、落盘可 git」。两类状态双向深绑存在类别错配。
4. 已记录的 UX 断点（树打散、排期、概览、人员负载等）**全部由本领域数据 + 纯前端解决**，无一需要宿主未用能力；唯一未被面板内改进解决的是「台账↔Git/MR/群 两张皮」（UX-11），而它的解也不一定在宿主侧。
5. 现状源码事实：agent 对话循环与台账**完全隔绝**——全仓无 `ctx.tools.register` / `defineTool`、无任何 `ctx.on(...)` 事件订阅；面板唯一写通道是 `remote.commands.execute(sessionId, '/pm ...')` 命令字符串、唯一读通道是一次性全量 snapshot；`sessions` 只被借作命令投递句柄；AI 只是 `/pm ask` 一次性草稿，不进 agent loop。

**互补而非分歧的差异**：A 偏重「断点坐标定位 + 调用主体」，B 偏重「时间尺度穿透 + 成本/平台归属」。两份 reframing 可合并为同一组根问题（见 §4）。

## 1. 原命题复述（中立事实）

- **谁**：单一当前使用者——字节在职 PM（所有者本人），单人、本机（macOS）、单写者；数据目录有真实录入（约 84 个 JSON 记录）。演进身份：离职后以个人开发者身份维护自用，成本敏感（个人单机月锚 ¥40 Coding Plan + 本地 Ollama 兜底）。被动相关方：研发/协作方不登录本工具，台账任务最终要落到他们的 Git/MR/群。
- **处境**：pm-tool 已到 v0.7.4，七类业务实体（项目/任务 WBS/里程碑/风险问题/会议纪要/进度快照/交付物）+ 人员负载、甘特、关键路径、健康分、客观进度、备份恢复、HITL AI 草稿、测试/CI 均已落地；内部增量 backlog 已清空，剩余为结构性长期项（常驻推送、生产 Key、多设备/多人、上游升级、外部 skill 毕业），其中没有一项以「融合宿主能力」为既有解法。
- **现状接入面**：Host 必需依赖 `commands` + `storageDomain`；`llm` 运行期懒读、无 Key 走中文 NO_LLM 降级；存储 = storage-domain + storage-json（人类可读 JSON、可 git）；Web 独立面板经 client slot 注入；**无模型工具注册、无事件订阅、无会话读取**。
- **命题字面**：从「服务级接入 + 上下文级隔离」走向更多使用宿主 session/context/plan/goal/jobs/schedule/mcp/subagent/workflow 等能力。
- **命题未声明**：为什么而融合、融合指什么、成功长什么样、不融合的替代解。

## 2. 利益相关者与核心场景

| 相关方 | 关系 |
|---|---|
| 在职 PM（本人，当下） | 唯一用户、唯一维护者、唯一决策者；一人同时是用户/PM/研发 |
| 个人开发者（本人，未来） | 维护者+用户；约束变为 AI 成本合规、单人长期可修 |
| 研发/协作方 | 不登录、不操作；被服务对象；其真实工作（Git/MR/群）与台账零联动 |
| dsh 上游 | 只读依赖，开发者预览期，明示未来将有破坏性变更 |

核心工作流（已落地）：立项拆 WBS → 排期/甘特/关键路径 → 例会纪要与行动项转任务 → 周期快照与 AI 叙述草稿 → 风险问题跟踪 → 交付物验收留痕 → 开面板派生逾期/临期提醒、跨项目人员负载、全局检索；`/pm ask` 一次性诊断+草稿、确认落库。

## 3. 目标 / 约束 / 成功标准 / 决策用途

**阶段0 目标**：把未定义动作「深度融合」拆解为可被确认/否决的问题陈述与根问题空间，供发散阶段覆盖、供后续对抗论证。

**硬约束（不可违背）**：
- C1 纯探讨不改代码；上游只读。
- C2 离线优先：结构化增删改查无 Key 必须可用，生成能力在线增强、失败降级。
- C3 草稿确认制：AI 写库先草稿、人显式确认才落库。
- C4 单用户本地、单写者，不做实时多人。
- C5 人类可读 JSON、可 git、可迁移、可逆。
- C6 上游 alpha 明示破坏性变更；耦合越深升级回归面越大。
- C7 仅承诺 Chrome；不引入常驻后台进程/系统推送（ADL-032/039 已裁决）。

**可证伪成功标准（方向级，先定检验形式）**：
- 消费方命题：能计数真实使用（agent 循环实际读台账 N 次、结果被人采用 M 次）；N≈0 即证伪。
- 正确性命题：AI 读写建议被接受/拒绝/纠正比例可统计，低于阈值则该形态不成立。
- 约束不破：无 Key 下既有七实体 CRUD 与面板可用率 100%，融合层不得阻断。
- 成本/寿命：上游一次 breaking upgrade 后，融合层修复工时可记录并与独立层对比；融合层修复面系统性更大则「融合提效」被削弱。
- 价值命题：上线前后 PM 手动维护台账的条数/耗时可基线测量；无下降则价值证伪。
- 禁止以「体验更好 / 更深度 / 更一体化」作为成功条件。

**决策用途**：阶段0–2 确认「方向空间无明显遗漏」后，进入对抗论证，最终决定与宿主关系的类别（继续轻耦合补面板内完整性 / 选择性接少数能力 / 重新评估平台归属 / 其他）。

## 4. 锁定的问题空间：五个根问题（R1–R5）

> 这是对 A 的 R1–R5 与 B 的 Q1–Q4 的合并。**它们是待回答的问题，不是五个方案方向**；发散阶段产生的想法可以回答其中任意一个、跨多个、或不属于任何一个（「不属于任何一个」的想法尤其要保留）。每个根问题标注：在该问法下，「深度融合」处于什么地位。

**R1 · 断点坐标与「计划↔执行证据」闭环**
PM 在本机完成一次真实项目动作时，哪一步仍需在工具间搬运信息或重复录入？断点位于台账内部、台账↔宿主对话之间、还是台账↔宿主之外的系统（Git/MR/群/会议）？PM 写下的计划与真实执行证据（commit/MR/agent 轮次/会议）如何对账，证据从哪捕获、以什么形态回台账（草稿/只读链接/不回）？
- 开启的空间：外部系统对齐（Git API、MCP 外部服务器、人工链接）、面板内部路径优化、对话可达性；宿主集成只是候选通道之一。
- 「深度融合」地位：断点在外部或面板内部时，融合不是答案；B 进一步指出 schedule/mcp/session 日志/git workspace-changes 都只是「捕获证据的管道」，并列评估。

**R2 · 对话读写边界与机器可操作性（消费方存在性前置）**
宿主 AI 对话循环在什么条件下可读台账、在什么条件下可起草修改、人始终是最终裁决者？哪些操作必须留在显式命令、不进对话？更前置地：是否存在「agent 在无人逐次指示下依据台账自主完成 PM 动作并被人接受」的真实场景？若有，需要的是严谨的机器可操作接口（schema、权限边界、HITL 契约、可校验输出）；若没有，工具注册/上下文注入就没有消费方。
- 开启的空间：模型只读面、写草稿面、对话内卡片/节点、审批 seam（interaction）、「不进对话」清单；或证伪后回到「人操作为主、AI 只做一次性草稿」的稳态。
- 「深度融合」地位：部分相关（接口契约、授权），但接 session 历史/subagent/workflow 与该问题无必然关系；本质是「接口多严谨」而非「融合多深」。

**R3 · 寿命/归属分层与最小独立内核**
哪些 PM 事实必须长寿且人有（落盘台账），哪些天然属于短命 agent 拥有的临时状态？在「数据寿命 × 归属人」轴上，层与层之间允许什么方向的流（单向投影/只读引用/事件单向广播/禁止双向绑定）？抛开 dsh，pm-tool 的最小独立内核是什么，哪些宿主依赖一旦建立就破坏离线/可读/可逆/可升级四条原则？
- 开启的空间：分层映射表、单向只读投影、纯文件内核+可选宿主适配层、稳定内核与易变会话运行时分离；也可能答案是「刻意保持浅融合」。
- 「深度融合」地位：双向深绑大概率不成立，融合深度本身是受约束变量而非越大越好。

**R4 · 调用主体（无人使用的能力不接）**
以所有者本人单机、离线、单写者的真实条件，宿主未用能力里有哪些根本没有调用主体？subagent/workflow/mcp/遥测/多人/常驻 jobs 的设计前提是多 agent、多会话、外部工具网络或团队；无主体的能力接进来后，维护成本由一人承担、收益侧为空。
- 开启的空间：以真实高频动作为筛子逐项过能力清单；只保留有主体的连接；显式记录「评估过但不接」及理由。
- 「深度融合」地位：清单被裁掉大半，融合需先证明主体存在。

**R5 · 平台存在性（dsh 是否是 PM 工作的正确容器）**
为什么 PM 台账要活在 dsh 里，而不是独立应用？宿主提供的不可替代项是什么（AI 通道？Web 壳？运行时？分发？），哪些只是「恰好在此」？留在 dsh 是有意选择还是沉没成本 + 计费合规（¥40/月、脱离即需标准 API）的合理化？
- 开启的空间：维持孤岛插件、独立应用、把 pm-tool 自身暴露为 MCP server（任意客户端消费）、纯开放文件 + 任意前端。
- 「深度融合」地位：可能整体被降级为「当前运行时的临时接线」，问题可能从「怎么融合」变成「去留」。

## 5. 时间尺度穿透（B 专项）

- **3 个月**：面板自身完整性（看板、9 视图重设计、视觉基准、prod Key 稳定性）最重要；现有 S1 痛点均由本领域解决，「深度融合」是分心。
- **2 年**（离职、个人开发者）：可维护性、AI 成本合规、上游存活与兼容最重要；单人维护者没有精力为每次 breaking change 修补深层耦合；「深度融合」只在被重新定义为「刚好够用的轻量合规接线」时条件性成立。
- **10 年**（数据资产、平台必然更替）：长寿记录如何在宿主消失后仍可读可迁移最重要；与当前这版 dsh 的具体对接在该尺度不存在，深度绑定是迁移负债。
- 结论性质：「深度融合」只可能在 2 年尺度的窄窗口、且被重定义为轻量接线后成立；把条件性、窄窗口的手段升格为产品方向，是本命题最需要检验的跳跃。

## 6. 问题边界

**在范围内**：根问题空间与方向探索；现状/宿主能力事实核验；断点、消费方、寿命、主体、平台归属的论证。
**明确排除**：多人协作（11 号契约另案）、客观进度 v0.8（既定迭代）、模型成本/Key 选型（另案）、上游升级回归（工程事项）、vendored skill 治理（另案）、视觉令牌/视图重设计（面板内打磨）、具体功能选型与路线图（后续阶段）。
