## A. 补漏（视角扫描清单空白区）

### D1-R2-01【补漏·规划智能】估算校准闭环：计划工时 vs 实际工时，学会自己的偏差
- **机制**：给任务加一个可选 `estimateHours`（计划工时，新建/WBS 草稿时填），与现有 `effortHours`（实际工时，`core/task.ts` L66 已存在但从不被回填）配对；按任务类型/规模聚合「计划/实际」偏差率，形成个人校准系数，下次 WBS 拆解草稿时把自己历史偏差喂给模型做修正，而不是每次从零拍脑袋。
- **具体场景**：PM 连续拆了 20 条任务后，面板显示「你对『联调类』任务平均高估 40%、对『文档类』低估 25%」；下一次 WBS 草稿里模型自动把同类计划工时按系数收紧，并标注「已按你的历史偏差校准」。偏差只用于提示，不强制改计划。
- **触点**：新增可选字段（estimateHours）；复用 effortHours 回填；completion-history 同套历史聚合；纯本地统计。
- **来源观察**：`task.ts` L66 effortHours 字段在 schema 里、但全仓没有任何代码写它；全仓无 estimate 字段（grep 零命中）；completion-history 只数完成条数不数工时；池内 D4-17 计量的是模型成本，无人做工时估算校准——清单第1区「估时/估算校准」空白。

### D1-R2-02【补漏·规划智能】what-if 排期沙盘：不改库地推演「挪 5 天 / 减 2 条负载」的后果
- **机制**：在面板开一个纯前端沙盘：临时拖动某任务日期、把某人 open 任务减到阈值内，用现有 `gantt.ts` 的 criticalPath/slack 重算关键链移动与里程碑冲击，输出「情景后果」（哪些里程碑滑出、哪条链 slack 被吃光），沙盘结果不落库，可同时对比 2–3 个情景再决定。
- **具体场景**：PM 怀疑 t-12 延期会顶掉 M1，在沙盘里把 t-12 往后拖 5 天，立刻看到「关键链上 M1 从 11-25 滑到 11-30、t-19 slack 由 3 天变 0」；对比「砍一条非关键任务」的另一版，挑一个再正式改计划。
- **触点**：复用 `core/gantt.ts` criticalPath/slack/ES-EF-LS-LF（L506–637 已实现）；纯前端临时状态，不写七表。
- **来源观察**：CPM 关键路径与 slack 已经算出来了（gantt.ts L619–637），但只用于「展示当前」，没有「改参数重算」的推演面；清单第1区 what-if 情景模拟空白；注意无 estimate 时只能按日期差做敏感性，不能做工作量压平。

### D1-R2-03【补漏·规划智能】延期预测：按历史完成速率给里程碑一个区间，不给点估
- **机制**：用 completion-history 的周完成条数序列 + 当前 backlog + 关键链位置，纯派生一个「按当前速度、里程碑预计达成区间（乐观/基准/悲观）」，明确标注低确定性；只在面板只读展示，绝不写进 dueDate。
- **具体场景**：项目跑了 6 周，面板里程碑旁出现一行小字「按近 4 周速度，M1 预计 11-26 ~ 12-02（基准 11-29）」；PM 据此决定要不要提前砍范围，而不是等到期才发现滑期。
- **触点**：completion-history 周曲线；health/derived 只读派生；不接预测模型。
- **来源观察**：KB-100「没有状态事件历史，不能仅凭 updatedAt 宣称本周期完成」，所以本想法只给区间不给点估、只展示不承诺；池内全是状态记录与回看，无延期预测——清单第1区空白。

### D1-R2-04【补漏·项目组合】项目模板库：成熟项目抽成骨架，新建时实例化
- **机制**：把跑顺的项目另存为模板（WBS 骨架层级、标准里程碑节点、常见风险清单、交付物类型、例会节奏），存为独立 templates 目录 JSON；新建项目时选模板实例化成真实记录，模板与实例解耦、可继续维护。
- **具体场景**：PM 做过一个「官网改版」项目后把它存成模板；下一个「小程序改版」新建时选该模板，自动带出三级任务骨架、4 个里程碑节点、3 条常见风险草稿，PM 再删改，不用从零建。
- **触点**：独立模板存储；复用 task-import 的 Markdown 骨架落盘链路；面板新建项目加「从模板」入口。
- **来源观察**：全仓 grep template/模板 零命中，现状项目全部从零建；`task-import.ts` 已验证「外部骨架→结构化→confirm 落盘」可行，可复用；清单第2区「跨项目模板复用/模板库」空白。

### D1-R2-05【补漏·项目组合】组合取舍视图：跨项目排序，给出暂停/合并/砍掉的只读候选
- **机制**：把所有项目按健康分、open 负载、近期承诺产出排成一张组合表，确定性规则标出「长期黄灯/投入产出失衡/可合并」的只读候选清单，PM 决定暂停或砍，系统不自动停任何项目。
- **具体场景**：PM 同时挂 4 个项目，组合视图列出「项目 C 连续 3 周零完成、健康灯红、占用 6 条 open 任务，建议暂停或归档」；PM 看证据后手动归档，系统只给候选。
- **触点**：health.ts 跨项目、people-load 跨项目、completion-history 产出；只读规则引擎。
- **来源观察**：D5-08 的 workflow 并行周审只是让各项目各写一段叙述，不做取舍；池内无 portfolio kill/merge；清单第2区「组合取舍」空白。

### D1-R2-06【补漏·反向写外部】从台账出站写：经外部 MCP 在 GitHub/Jira/飞书建 issue/MR/日历事件
- **机制**：配置一台外部 MCP server（GitHub/Jira/飞书项目），台账里一条任务经确认草稿后，调用 `mcp__<server>__create_issue` 之类工具在外部系统建单/建事件，再把外部 URL 回挂到 evidenceUrl；出站写动作首次需显式授权目标系统，仍走确认制。
- **具体场景**：PM 在面板确认一条任务「同步到 Jira」，模型调外部 MCP 建好 issue，面板里这条任务多了 Jira 链接；反向也能把 Jira 状态只读拉回（与池内 D1-11/D2-30 的只读回流互补，方向反过来）。
- **触点**：`mcp/mcp-client`（外部服务器工具以 `mcp__<serverName>__<tool>` 注册，README 明列 `mcp__github__create_issue` 式命名）；现有 evidenceUrl 字段回挂。
- **来源观察**：池内证据闭环全是「外部→台账」只读回流（D1-06/07/09/11、D5-04/05），零「台账→外部」出站写；清单第3区空白；mcp-client README 确认外部服务器可暴露任意写工具。

### D1-R2-07【补漏·会议实时】会中模式：边开边落行动项草稿，而不是会后粘贴速记
- **机制**：会议进行中开「会中模式」，借助 experimental 的 speech-to-text（sensevoice/api-speech-to-text）实时转写，边说边把决议/行动项抽成草稿行滚在面板一侧，会末一键定稿转任务/风险；区别于现有会后粘贴速记归纳。
- **具体场景**：站会进行中，面板右侧实时滚出「行动项：张三补单测（周五前）」「决议：砍范围 X」；PM 会中随手勾掉不要的，散会即落库，不用会后再翻录音整理。
- **触点**：`experimental/speech-to-text`、`speech-to-text-sensevoice`、`api-speech-to-text`；meeting 实体现有 sourceType/sourceSessionId；meeting-summarize 链路前置到实时。
- **来源观察**：`meeting-source.ts`/meeting-summarize 现状只吃「会后粘贴的速记文本」；清单第4区「会中当场捕获而非会后归纳」空白；语音转写实验包已存在但 pm-tool 未接。

### D1-R2-08【补漏·迁入共存】Jira/飞书项目/Excel 一次性迁入 + 外部 ID 只读共存
- **机制**：一次性导入器读 Jira 导出 CSV、飞书项目导出、现有 Excel，经字段映射成七实体；每条记录保留外部系统 ID 做只读引用，不做实时双向同步，迁入后台账为唯一事实源。
- **具体场景**：PM 从旧 Jira 迁来 60 条任务，导入器映射状态/负责人/截止日，面板里每条挂「Jira PROJ-123」只读链接；之后台账独立维护，旧系统只读备查。
- **触点**：复用 csv-import.ts 的中文表头映射/SheetJS 动态导入；新增 externalRefId 可选字段；遵守 backup-sync 单写者原则。
- **来源观察**：现状只有 Markdown 清单导入与 CSV 导入，无 Jira/飞书适配；清单第5区「从 Jira/飞书项目/Excel 迁入与共存」空白。

### D1-R2-09【补漏·离开电脑】移动端只读 + 手机入站捕获：不在电脑前也能看、能记
- **机制**：只读侧：手机浏览器打开本地只读状态页（见 D1-R2-10）看进度；捕获侧：手机快捷指令/IM 经入站 webhook 发一条文字，落成一条候选任务草稿，回电脑确认；不做手机端写台账。
- **具体场景**：通勤路上想到一件事，手机给 webhook 地址发一句「下周要联系供应商」，回家打开面板草稿箱里已有这条候选；路上也能手机看一眼哪个里程碑快到了。
- **触点**：`experimental/webhook`（注册路由、dispatch、创建根会话）；只读状态页；注意 localhost 需内网穿透才有公网入口。
- **来源观察**：dsh Web 只信本机 loopback、无局域网远程（KB-014、delivery.md §9），现状离开电脑即零访问；清单第5区「移动端/离开电脑场景」空白；池内 D1-15/D4-21 是一次性导出，不是持续可达。

### D1-R2-10【补漏·对外形态】持续只读状态页：给领导/客户一个 URL 自助看，非一次性导出
- **机制**：本地起一个只读小 HTTP 视图（或自动刷新的静态页），按项目开不同只读链接，展示当前进度/里程碑/风险，不暴露任何写操作；快照随读时派生刷新，可设口令或仅局域网。
- **具体场景**：领导要进度，PM 发一个链接，对方随时打开看到的是最新只读看板，不用每周手动导 HTML 发文件；客户只能看自己那个项目的页面。
- **触点**：宿主 webServer（webhook-github 已用注入的 ctx.webServer）；只读派生（health/reminders/里程碑）；与 D1-15/D4-21 的一次性静态 HTML 区别在于持续刷新。
- **来源观察**：池内对外形态全是一次性导出（D1-15、D4-21、D5-11），无持续只读服务；清单第6区「对外持续形态只读状态页」空白。

### D1-R2-11【补漏·多智能体】PMO 角色化常驻班子：风险官/史官/催办员/调度员四个固定角色
- **机制**：不是一次性巡检，而是四个固定职责的角色化 subagent 名册：风险官（定期扫高影响未关闭风险并给处置建议）、史官（维护决策记录与全局审计流）、催办员（只产出临期清单、不主动打扰）、调度员（算关键链与负载冲突）；角色结果统一进一个草稿箱，人统一确认。
- **具体场景**：周一早上草稿箱里躺着风险官的「R-0002 已超期 12 天未处置」、调度员的「王五 open 7 条超阈值」、史官的「本周 3 条决策待归档」；PM 一次过一遍，而不是每次临时起一个子 agent。
- **触点**：subagent spawn-in-process；D4-29 全局审计流（史官写）；people-load/gantt（调度员算）；统一草稿箱复用 ask-apply 确认制。
- **来源观察**：D4-18 是一次性只读巡检、D2-12 是单里程碑审计、D5-07 是单项目常驻、D4-28 是虚拟 assignee 仿真，都不是「固定角色分工名册」；清单第7区「多智能体 PMO 角色化分工」空白。

### D1-R2-12【补漏·认知安全】注入摘要的新鲜度戳与对账：别让模型把陈旧数据当真相
- **机制**：每段注入上下文/工具返回的台账摘要都带 `snapshotAt` 与记录级 updatedAt；模型回答引用时必须标注「截至时间」；当注入块与当前快照不一致（复用 provenance 的 basisFingerprint 思路），面板高亮「此建议基于旧快照，已过期」，并提供一键重取。
- **具体场景**：会话开了两小时，期间台账被改过，模型还在引用旧摘要答「这条没逾期」；面板在该回答旁标黄「基于 10:00 快照，当前已逾期」，避免被陈旧数据误导。
- **触点**：provenance.ts 的 basisFingerprint/fullFingerprint/recheckProvenance 推广到注入块；D1-02/D5-03 注入层加时间戳；纯本地对账。
- **来源观察**：D1-02/D5-03 的持久注入没有新鲜度守卫；provenance 已有指纹重检机制但只用于 AI 草稿、没用于注入摘要；KB-100 陈旧风险；清单第8区「注入摘要过期/错误、陈旧当真相、对账、防误导」空白。

### D1-R2-13【补漏·行为仪式】仪式重构 + 建议疲劳防垃圾化：给建议设配额与沉默期
- **机制**：把站会/周报压缩成固定 3 分钟流水线（一句话今日/阻塞/明日）；系统给 AI 建议设「每日建议配额」与沉默期，当拒绝率高（接 D1-16/D4-16 采纳率）自动降级建议频率；草稿箱设上限与过期清理，防止草稿垃圾化。
- **具体场景**：连续一周 PM 拒绝了 80% 的建议，系统自动把建议频率从每天降到每周，草稿箱里 7 天未处理的候选自动归档；PM 不再被建议淹没，仪式本身也被压到 3 分钟。
- **触点**：feedback/采纳率统计（D1-16、D4-16、D5-22）；草稿箱 TTL；与 D1-24/D4-26 的「彻底沉默」不同，本条是有节制的主动。
- **来源观察**：池内 D1-24/D4-26 是直接关闭一切提醒，没有「建议疲劳/提醒噪音/草稿垃圾化」的失败模式设计；清单第9区「习惯养成、仪式重构、建议疲劳、草稿垃圾化」空白。

### D1-R2-14【补漏·极端吞并/退出】完全吞并极端 + 被宿主原生替代时的退出路线
- **机制（吞并）**：pm-tool 内化自己的 agent runtime（自带模型循环/工具/审批，不借 dsh 循环），dsh 只做文件宿主，走到「产品即完整应用」的极端。
- **机制（退出）**：预设一条退出路线：当 dsh 原生长出项目管理能力时，pm-tool 降级为「数据迁移导出器 + 方法论 skill」，把七实体搬进原生功能，自身退役。
- **具体场景（退出）**：未来 dsh 自带看板/任务，PM 跑一次「导出为原生格式」把数据迁过去，pm-tool 只留下方法论模板与历史档案，不恋栈。
- **触点**：吞并侧=独立 runtime（与 D1-19/D5-14 内核剥离一脉但更彻底）；退出侧=现有 export 通道 + skill 打包（D1-29）。
- **来源观察**：D2-15 面板内嵌对话是半吞并，池内无「完全吞并」极端；也无人讨论「宿主原生长出 PM 能力时本产品怎么退」；清单第10区空白。

### D1-R2-15【补漏·商业分发】开源治理 + 插件市场分发 + 「PM 方法论即产品」分层定价
- **机制**：内核以 MIT/Apache 开源（补 LICENSE、CONTRIBUTING、issue 模板），经 plugin-manager registry 作为外部组合包分发；分层：内核免费、付费卖「模板包/方法论包」（估算校准系数、行业 WBS 模板、仪式 SOP），方法论本身成为商品。
- **具体场景**：其他 dsh 用户从插件市场装上免费内核，再付费买一套「独立开发者项目模板包」；PM 方法论（怎么拆 WBS、怎么开站会）被打包成可售卖资产。
- **触点**：`boot/plugin-manager`（安装/启停外部组合包、registry 检查）；D2-28 的 npm 公开发布；独立模板库（D1-R2-04）作为付费载体。
- **来源观察**：仓库无 LICENSE 文件（grep 零命中）；D2-28 只提 npm 公开发布，无开源治理/市场/定价/方法论产品化；清单第11区空白。

## B. 杂交（≥3，注明来源，产生新机制）

### D1-R2-16【杂交】任务→会话→证据 自动闭环：schedule 到点 × 开工建会话 × workspace-changes 回挂
- **杂交来源**：D1-12（schedule 到点进会话提醒）× D3-13（任务开工自动建带验收口径的会话）× D1-06（workspace-changes diff 回挂证据）。
- **机制**：被选中的任务到点（或手动触发）自动开一个带验收口径的会话；会话结束自动把本轮 workspace-changes 的 diff 收成证据草稿挂回该任务；人只做最后确认。三个原本独立的动作被一条任务生命周期串成自动管道。
- **具体场景**：周五 t-12 到期，schedule 自动唤起、开会话、PM 让 agent 改完代码；会话关闭时面板自动出现「t-12 本轮改 6 文件，是否附证据并确认完成」，PM 点一下即闭环，全程不用自己搬证据。
- **触点**：schedule、session 创建、workspace-changes summary/diff、ask-apply 确认。
- **来源观察**：三条分属调度/工作流/证据，池内各自存在但无人串成管道；新机制=自动串联而非并列。

### D1-R2-17【杂交】可学习的审计履历：里程碑审计员 × 全局审计流 × 采纳率计量
- **杂交来源**：D2-12（里程碑独立审计 subagent）× D4-29（全局 append-only 事件流）× D1-16（采纳/拒绝/纠正计量）。
- **机制**：审计员每次结论写入只增事件流，跨里程碑积累成「审计命中率/误报率」统计；哪些检查项老误报就降权，哪些老命中就前置。一次性审计变成可学习的审计履历。
- **具体场景**：跑过 5 个里程碑后，系统显示「『延期风险』检查命中率 70%、『依赖遗漏』命中率 15%（多为误报）」，下次审计自动把后者弱化，审计员越用越准。
- **触点**：subagent 审计、D4-29 append-only JSONL、provenance/feedback 计量。
- **来源观察**：D2-12 只做单次审计、D4-29 只记录、D1-16 只统计 AI 草稿，三者合流产生「审计自身被校准」的新机制。

### D1-R2-18【杂交】投影→干活→回收 单行道：todo 临时镜像 × goal 单向镜像 × 会话结果回提
- **杂交来源**：D5-20（开放子树临时镜像进 todo、禁止回写）× D1-27（goal 单向镜像）× D3-24（会话 todo 单向导出为完成候选）。
- **机制**：开工时把项目开放子树同时镜像进会话 todo 与 goal；会话结束把 todo 勾选结果单向回提为完成候选（D5-20 原本禁止回写，这里改为带方向的回收），goal 状态仍不回写台账。形成单向投影+回收管道。
- **具体场景**：开工前一键投影，会话里勾掉几项，结束后面板收到「会话中勾掉的 3 条，是否转为完成候选」，PM 确认落库；goal 进度只作会话内驱动、不污染台账。
- **触点**：tool-todo 整表替换、goal、session 结束钩子、完成候选草稿。
- **来源观察**：D5-20 禁止回写、D3-24 只一次性导出、D1-27 只镜像不回写；杂交打破「只投影不回收」，产生方向可控的回收管道。

### D1-R2-19【杂交】自动周报内置「上期承诺兑现表 + 本机工作痕迹」：周期触发 × 承诺对账 × session-query
- **杂交来源**：D1-13（schedule 周期周报自动触发）× D2-21（承诺对账）× D1-07（session-query 反查本机工作轮次）。
- **机制**：自动周报草稿里固定两栏：「上期承诺兑现表」（上期周报承诺了什么、本期兑现/未兑现）+「本周本机为各任务工作轮次/工具调用」（session-query 只读统计）；数字与痕迹自动填，人只写叙述。
- **具体场景**：周五自动草稿里已有「上期承诺 3 项：兑现 2、未兑现 1；本周为 t-12 工作 4 轮、41 次工具调用」，PM 只补两句感想即成稿。
- **触点**：schedule、R9 快照对比（report-diff）、session-query、report-narrate。
- **来源观察**：D1-13 只触发采集、D2-21 只对账承诺、D1-07 只挂单任务痕迹；合流后周报草稿自带两栏事实，是新机制。

## C. 反叛（攻击已成形共识，给成立条件）

### D1-R2-20【反叛】只读工具 + 审批 seam 是单人场景的半瞎陷阱
- **攻击对象**：共识「只读工具进 loop + 每个写动作都走审批 seam」（D1-01/03、D5-01/02、D2-08/09）。
- **机制/主张**：单人单写者场景下，「建议→逐次审批」每一步都要人点头，比「直接写 + 事后撤销」更累、更劝退；应按风险分级：低风险字段（备注、勾选 checklist、状态、证据链接）开直接写口子，只对高风险（删除、改期、改派、里程碑变动）保留审批。
- **成立条件**：① 单写者、无多人误操作风险；② 变更可逆（有 D4-29 全局审计流 + undo postimage 兜底）；③ 低风险动作有明确撤销路径。三者满足时，全量审批是把协作场景的 HITL 错用到单人，制造摩擦而非安全。
- **具体场景**：agent 把一条 checklist 勾上、补一句备注也要弹审批，PM 点烦了干脆全拒，工具回到没人用；改成低风险直接写、错了从审计流撤销，采纳率反而上升。
- **触点**：copilot.ts 白名单分级；provenance undo；D4-29 审计流。
- **来源观察**：池内几乎一边倒「只读 + 审批」，无人质疑单人是否需要每步审批；ADL-036 草稿确认制原本针对 AI 不可信，不等于每个低风险动作都要拦。

### D1-R2-21【反叛】「人类可读 JSON 十年档案」是浪漫错觉
- **攻击对象**：共识「独立内核 + 人类可读 JSON 就是 10 年可读保障」（D1-19/26、D4-23/25、D5-14/18）。
- **机制/主张**：十年后没有人会逐文件打开裸 JSON，真正长寿的是可转换到未来格式的能力与导出的标准化文档/静态视图；把工程力气花在「让人现在舒服读裸文件」不如花在「可迁移转换」；JSON 只是中间态，静态 viewer/开放格式导出才是档案本体。
- **成立条件**：① 承认十年后阅读者几乎不可能手写解析当时的 JSON schema；② 格式漂移/编码/字段重命名比平台更替更致命；③ 因此「可读」应体现在导出物（PDF/静态站/标准 CSV/开放格式）而非裸文件。
- **具体场景**：十年后 dsh 没了，用户面对一堆自己也看不懂的嵌套 JSON 文件反而无从下手；而一份持续导出的静态归档与标准格式，随便一个新软件都能打开。
- **触点**：D1-14/D4-13 导出、D1-R2-10 静态页、D1-19 内核的转换端口。
- **来源观察**：C5「人类可读可迁移」被池内当成终点，但可读≠可被未来的人/工具消费；R5/§5 十年尺度下这是个未被质疑的浪漫假设。

### D1-R2-22【反叛】离线优先正在葬送这个单人产品
- **攻击对象**：共识「离线优先、无常驻、不主动」（ADL-032/039、D1-18/20、D4-22/26、D5-16）。
- **机制/主张**：若消费方命题 N>0（真有人在对话里用台账），离线保守把所有主动价值（提醒、主动建议、自动周报、临期推送）挡在门外，单人产品死于「永远等人来问」；应默认在线主动、离线退化为降级档，而非把离线当原则。
- **成立条件**：① 采纳率计量（D1-16/D5-22）证明 agent 确实在读台账、草稿被采用；② 单人本地有宿主持久 schedule/webServer 可借，不养自己的 daemon；③ 主动动作可随时关闭。满足时「离线优先」是把早期无证据期的保守当成了产品信条。
- **具体场景**：工具永远沉默等 PM 打开，逾期也不吭声，三个月后 PM 忘了它存在——不是功能不好，是它从不主动出现在用户面前。
- **触点**：schedule、webServer、D1-12/13、D1-R2-10。
- **来源观察**：ADL-032/039 暂缓常驻是早期无主体判断，池内把它固化成了原则；问题框定 N≈0 才证伪，N>0 时沉默就是自弃。

### D1-R2-23【反叛】「PM 维护一本台账」本身才是该被消灭的问题
- **攻击对象**：整个前提——所有读工具、审批、证据闭环都在优化「怎么让人更好地记账」。
- **机制/主张**：单人场景下「人负责记全」是工具在伺候旧的多人分工；目标应是账本自己维护自己（事件流自动归集、对话/git 被动捕获、例外才找人裁决），人只做例外；继续打磨「人怎么记」是在优化一个该被消灭的动作。
- **成立条件**：① 被动捕获（D1-25/D5-19）与全局审计流（D4-29）能覆盖绝大多数记录来源；② 自动归集的误报有人工例外裁决兜底；③ 单人无汇报义务需要逐字手写台账。满足时「维护台账」应被趋近于零，而不是被做得更顺手。
- **具体场景**：理想状态下 PM 从头到尾没主动录入过一条任务——对话里的决定、git 里的完成都自动进账，人只在冲突/例外时点一下；工具价值在于让人忘记台账的存在。
- **触点**：D1-25 被动捕获、D5-19 台账吸收对话、D4-29 事件流、D1-R2-17 审计。
- **来源观察**：池内 146 条几乎都在「让人更好地记/查/批」，无人质疑「记」这个动作本身是否该存在；这是对问题前提的正面反叛。

## A. 【补漏】稀疏区新想法

### D2-R2-01 估算校准回路：用历史实际工时给新任务一个区间建议（规划智能·估时）
- **机制**：任务 schema 已有 `effortHours`（明确标注「实际投入工时，非估算」，`core/task.ts` L65-66），但全产品没有估时字段、也没有基线。新机制：完成任务时收实际工时，纯本地按「同级同类任务（同优先级/同 WBS 深度/同负责人）」聚合出历史分布（中位数 + 上下四分位），给新任务一个建议估时区间；估时与实际的偏差随样本逐次自我修正，偏差大的类别单独标记「此人/此类系统性高估或低估」。
- **具体场景**：PM 新建一个 P1 开发任务，面板右侧自动浮出「同类近 12 条任务实际 2–6h，中位 3.5h」，PM 填 4h；三个月后复盘页显示「P1 开发类你估时平均偏长 40%」，校准建议下次压到 2.5–4h。数字全来自本地历史，不联网、不调模型。
- **触点**：纯本地派生（`core/stats.ts`/`completion-history.ts` 范式扩展）；可选 schema v2 增 `estimateHours?`（`docs/product/10-schema-v2-design.md` 预留 optional 新字段口径）；不接宿主。
- **来源观察**：池子 grep「估算/估时/预测」= 0；现状只有事后实际工时、无事前估时、无校准闭环；requirements L103 只冻结了关键路径只读高亮，估时是空白。

### D2-R2-02 what-if 排期沙盘：不改库的「如果这样会怎样」推演层（规划智能·情景模拟）
- **机制**：在面板开一个独立的推演模式，所有操作只改内存里的临时副本：把某里程碑拖到 +2 周、把某任务改派给另一人、删掉一条 P2，纯派生即时算出关键链顺延到哪天、谁负载超载、多少任务变成逾期；点「落库」才写，点「放弃」全部丢弃，库内记录零变化。AI 可被请进沙盘解释后果，但不动正式数据。
- **具体场景**：老板说「里程碑提前 10 天行不行」，PM 进沙盘把日期一拖，立刻看到「关键链上 3 条任务需并行、王五负载 140%、2 条 P2 将滑出本期」，拿着这页推演结果去对话，而不是先在正式计划里试错再回滚。
- **触点**：复用已交付的关键路径只读高亮（GI-CP-01~05，requirements L103）与 `people-load.ts` 负载派生；临时副本层纯前端，不落盘。
- **来源观察**：池子「what-if/情景」= 0；现状关键路径只高亮现状、不回答「改了之后会怎样」；requirements 明确「自动排期/压缩/改期长期观望」，本想法停在只读推演、不自动改期，是观望区内的窄形态。

### D2-R2-03 项目模板库：把跑过的项目沉淀为可实例化的骨架（组合层·模板复用）
- **机制**：「另存为模板」把一个归档项目剥掉实例数据（具体日期、负责人、实际工时、会议记录），保留 WBS 层级骨架、检查清单项、常见风险类型清单、里程碑数量口径、报告周期设置，存为本地模板条目；新建项目时选模板实例化出空骨架，人再填具体值。模板可改名、可增删、可分享为文件。
- **具体场景**：PM 把做完的「官网改版」存成模板，下个季度「小程序改版」新建时选它，自动带出三层 WBS 骨架、5 条常见风险（延期/供应商/资源）、双周汇报节奏，不用从零拆；新模板随项目跑成熟后回写更新。
- **触点**：纯本地新表（templates）；复用 `wbs-ai.ts` 的 markdown 预览/导入计划做骨架实例化；与 D1-29「方法论 skill」不同——那条是给 agent 的操作手册，本条是给项目实例用的数据骨架。
- **来源观察**：池中「模板」6 处均为汇报版式/skill 模板/office 模板，无「项目骨架模板库」；现状每个项目都是裸建，R1 项目创建只有名称/日期。

### D2-R2-04 项目组合取舍视图：多项目并排看健康、投入与争用，只提示不决策（组合层）
- **机制**：纯派生一个组合页：把所有 active 项目排成表（健康灯、本周完成数、临期/逾期数、投入人数、距目标日期余量），跨项目标出同一人在多个项目同时背 P0 的争用点；只给「争用/偏科/停滞」提示条，不做自动优先级裁决。
- **具体场景**：PM 同时跑 3 个项目，组合页一眼看到「张三在两个项目各背 2 条 P0、B 项目连续 3 周零完成」，据此决定砍哪个；视图数字全由现有 `health.ts/stats.ts/people-load.ts` 派生，无新实体。
- **触点**：纯前端派生；复用现有健康分、负载、完成历史。
- **来源观察**：池子「组合」7 处均为多项目周报扇出（D5-08），无跨项目资源取舍视角；UX-07 概览太薄、UX-09 无按人聚合，本想法是两者在组合层的合流。

### D2-R2-05 台账→外部系统的出站写：勾选任务建 Jira issue / 飞书事件，留可撤销出站日志（反向写外部）
- **机制**：与池子里清一色的「只读回流」相反——人在面板显式勾选一条任务/一个里程碑，经 host mcp-client（外部 Jira/飞书项目 MCP）或 web-fetch 向外部系统**写**一条 issue/事项/日历事件；出站动作记入一张 outbound 日志（外部系统返回的 ticket id 回挂到本地记录），提供「撤回/更新」动作；默认全关、逐条显式触发、绝不同步。
- **具体场景**：PM 把本地拆好的 8 条 WBS 任务勾选「同步到飞书项目」，一次建出 8 个事项并回挂 issue 链接；日后某条在本地改了期，面板提示「外部 issue 未同步，是否更新」，人决定才发；本地删除不自动删外部。
- **触点**：`packages/mcp/mcp-client`（调用外部 MCP 的写工具）、`web/web-fetch-http`；本地新增 outbound 日志表；参照 D1-09 的 webhook/轮询是「外部→本地」，本条是「本地→外部」反向。
- **来源观察**：池子 grep「Jira」=0、出站写=0，D1-11/D2-30/D4 全部是只读拉外部；现状 `repoUrl/branch` 只是文本（PROD-21），外部协作系统零写入能力。

### D2-R2-06 会中当场捕获条：边开边记，替代会后粘贴归纳（日历/会议实时辅助）
- **机制**：会议进行中（就在当前会话里）挂一个常驻窄条「当场记」：说到一个承诺/决议/待办就点一下、说半句，条内累积待定行动项草稿；会议结束点「定稿」一次性确认入库为会议行动项，再 promote 成任务；不要求会后翻记录、贴速记、再 summarize。
- **具体场景**：站会进行中，PM 听到「张三周五前交联调」就在窄条点记一句，会末 30 秒过完 5 条草稿确认落库；散会即定稿，不用回头补纪要；说错的条目当场划掉。
- **触点**：会话内窄条（client 侧浮层或命令）；复用 R8 会议行动项结构与 ADL-040 promote 链；与 D3-17/D5-05「会后从历史会话补」方向相反。
- **来源观察**：现状 R8 会议纪要 + summarize 都是会后归纳（`core/meeting-summarize.ts`），池子无「会中实时捕获」；现状依赖人贴速记文件，会中零辅助。

### D2-R2-07 从 Jira/飞书项目/Excel 只读迁入并「镜像共存」，另开无写面只读快照给手机看（迁入共存/离开电脑）
- **机制**：两层。迁入层：现有 CSV/XLSX 导入（`core/csv-import.ts`，ADL-042/043）扩展为读外部系统导出文件或经 mcp-client 只读拉取，落成带 `externalRef` 的镜像记录，此后两边各管各、不自动双向同步；移动端层：生成一份无写面的只读快照（纯 HTML/文本），手机浏览器打开只看逾期/今日清单，不能改。
- **具体场景**：PM 从旧 Jira 导出 CSV 一次迁入 60 条，本地继续管；通勤路上用手机浏览器打开只读快照看「今天 2 条到期」，想改必须回到电脑前；外部系统里的新变化不自动进本地，人手动再拉一次。
- **触点**：csv-import 扩展、mcp-client 只读、Blob 下载通道（ADL-042）；手机只读页无命令面。
- **来源观察**：池子「迁入」=0、「移动/手机」仅 D3-08 一句静态看板泛提；现状只有手工 CSV，无外部系统迁入路径，且任何视图都要求 dsh 在线。

### D2-R2-08 持续对外只读状态页：给领导/客户反复自助看的白名单视图（对外持续形态）
- **机制**：每次本地变更后确定性重渲染一份「对外视图」本地页面：字段白名单（只放允许公开的项目目标、里程碑进度、脱敏风险等级），不显示内部负责人姓名/估算/原始讨论；页面随库更新自动刷新，可放局域网或静态托管，对方随时自助打开，不用每次导一份 HTML 发过去。
- **具体场景**：客户想知道项目到哪了，PM 给一个本地页面地址，客户自己刷新看里程碑完成度；内部只有 PM 自己看的负载/估时/风险应对原文不进白名单；与 D1-15/D4-21 的一次性静态导出区别：持续刷新 + 字段白名单 + 长期可访问。
- **触点**：确定性渲染（复用 `collectProjectReport` 数字）；纯本地文件，无写面；白名单配置存 settings。
- **来源观察**：池子「状态页」=0，D1-15/D4-21 都是一次性导出分享；现状对外只能发 PDF/截图，发完即冻结、无法自助刷新。

### D2-R2-09 角色化常驻 PMO 班底：风险官 / 史官 / 催办员 / 调度员四个固定岗（多智能体 PMO 分工）
- **机制**：区别于一次性巡检（D2-12/D4-18）和单一常驻专员（D5-07），定义四个有专职职责、固定触发条件的角色 subagent：**风险官**专扫 open/monitoring 风险的升级与遗漏；**史官**专把本期承诺-兑现-变更整理成叙事；**催办员**专算临期/逾期并生成措辞克制的提醒草稿；**调度员**专算负载与争用、给出重排建议；各岗产出都进统一草稿箱，人统一批，角色之间不互相写库。
- **具体场景**：周一早，史官已把上周承诺整理成 3 段叙事草稿、风险官标出 1 条该升级的 high 风险、催办员备好 2 条临期提醒、调度员提示张三过载；PM 在一个草稿箱里逐条批，而不是每次临时 spawn 一个通用 subagent。
- **触点**：`subagent-spawn-in-process`（角色化种子提示词）；产出走草稿/审批（D2-08/D1-03 范式）；角色定义纯配置。
- **来源观察**：池子「风险官/史官/催办」=0；D5-07 是一个通用常驻 PM，D4-18/D2-12 是一次性任务式 spawn，无固定角色分工与触发表。

### D2-R2-10 认知安全层：注入摘要带陈旧戳，禁止模型把缓存当真相（认知安全）
- **机制**：所有进入系统提示词/工具返回的台账摘要强制携带「快照时刻 + 记录条数 + 陈旧年龄」戳；超过阈值（如 24h/10 次写）的摘要在工具返回里标注「可能已变更，请重取」；注入区在面板显示最后刷新时间；模型引用旧摘要给结论时，工具层以库内当前值为准并给出「缓存与现状差异」对账；冲突一律以库内为准，不让模型把过期摘要当事实陈述。
- **具体场景**：早上注入段显示「快照 09:12，12 条任务」，中午任务已改，模型若还按旧摘要说「t-12 未开始」，工具返回附「该记录已于 11:40 变更为 in_progress」并纠偏；PM 面板角标看到注入段已陈旧。
- **触点**：context section（D2-01/D1-02）与只读工具（D2-07/D1-01）统一加版本戳；`updatedAt` 墙钟（11 号契约 §二）做陈旧判定；纯派生对账。
- **来源观察**：池子「过期/陈旧/置信/误导」=0；D1-32 只讲注入预算大小，不讲数据时效与防误导；R2 机器可操作性未覆盖「模型读到错误台账怎么办」。

### D2-R2-11 【极端吞并】pm-tool 内化一个最小 agent runtime，dsh 退化成可插拔前端（完全吞并极端）
- **机制**：走到另一个极端——不做 dsh 的插件，而是 pm-tool 自己持有最小模型调用循环（自己的上下文组装、工具注册、单轮/多轮对话），把 dsh 的 llm 提供方当一个可替换的模型后端，面板/对话都长在 pm-tool 自己壳里；dsh 从宿主降级为「可选模型通道 + 可选前端」。
- **具体场景**：pm-tool 直接起自己的进程和窗口，内置台账对话，需要模型时借 dsh 的 provider 或换标准 API；dsh 整个消失，产品照常运行。这是与 D2-24/D1-18「冻结不融合」相对的另一极。
- **触点**：自持有界 loop；模型通道复用 `model-route.ts/ai-client.ts` 适配端口（D5-23 已留端口思想）；不再依赖 cordis 运行时。
- **来源观察**：池子「吞并」=0，现有极端只有反向剥离（D2-05/D3-07/D4-23）和反向嵌对话（D2-15），没有「自己成为 runtime」这一极；问题框定 §R5 平台存在性要求回答离开 dsh 后还剩什么。

### D2-R2-12 【退出路线】dsh 原生长出项目管理能力时，pm-tool 的「被替代」退场脚本
- **机制**：预先写好一条主动退场路径而非对抗：监测宿主/生态原生长出等价能力（原生日程、原生日志、原生任务面板）时，pm-tool 提供①数据标准格式导出包 ②字段映射迁移指引（本地七表→原生能力对应项）③插件 deprecated 公告与只读冻结模式（只看不写、保证历史可读）④维护者退出承诺；产品不与宿主原生功能竞争，完成历史档案使命后下线。
- **具体场景**：两年后 dsh 原生内置了任务/里程碑面板，pm-tool 发布「迁移到原生」指引包，老用户一次性导出 JSON/Markdown 迁入，插件转入只读归档态，不再发新功能。
- **触点**：现有导出/备份链路（`core/export.ts`、`backup.ts`）；只读冻结是配置开关；纯文档+导出。
- **来源观察**：池子「退出/被替代路线」=0，D1-18/D4-22 是「刻意冻结自己」，不是「被宿主替代时怎么体面退场」；R5 平台存在性未回答「宿主长大以后」。

### D2-R2-13 开源治理 + 插件市场分发 + 「PM 方法论即产品」双轨（商业/分发）
- **机制**：双轨：免费轨=七实体内核、方法论 skill、本地模板公开（GitHub 仓库、语义化版本、贡献指南、变更日志、打 dsh-plugin topic 进插件市场，接 D2-28/D1-17）；付费轨=行业模板包、估算校准表、风险登记法与周报仪式的方法论内容、一对一校准服务；方法论本身（怎么估时、怎么登记风险、怎么开站会）脱离软件单独成为可售内容。
- **具体场景**：路人免费装插件看本地台账，需要「软件研发项目模板包 + 估时校准方法」时付费；维护者靠方法论内容而非锁数据赚钱；开源治理文件明确贡献流程、许可证、隐私承诺（接 D1-22 零遥测卖点）。
- **触点**：npm/dsh-plugin 市场（feasibility-map §七）；模板/skill 资产化；与 D5-23 计费合规端口衔接。
- **来源观察**：池子「开源/市场/定价」=0；D2-28 只提公开 npm 包，D1-26 只卖单机定位，无治理/定价/方法论产品化设计。

## B. 【杂交】组合池中机制产生新东西

### D2-R2-14 【杂交】项目时光机 = D4-29 全局审计事件流 × D4-30 备份版本链 × D2-21 承诺对账
- **机制（新机制：把审计事件与承诺绑成因果回放链）**：D4-29 的全实体只增事件流 + D4-30 的备份版本链 + D2-21 的承诺对账三者绑定：每条当初承诺（计划做什么）都挂一条因果链——计划当时长什么样 → 中间被改过几次、谁改的、为什么（事件流）→ 相邻版本 diff → 最终兑现/逾期；报告可直接引用链上某一段「当时 vs 现在」。不是三个视图并列，而是承诺成为回放主线、事件和版本为它供料。
- **具体场景**：季度复盘点开「t-0015 承诺链」，看到 9 月计划时估 3 天、10 月两次改期（事件：AI 草稿改期被拒一次）、最终晚 6 天交付；周报直接摘这段回放，不用手工翻备份。
- **触点**：D4-29 事件流、D4-30 版本链、D2-21 对账纯函数；新机制是三者的主键绑定，非简单并列。
- **来源观察**：三者在池中各自独立（D4-29 审计、D4-30 备份、D2-21 对账），无人把它们收成一条承诺因果链。

### D2-R2-15 【杂交】PMO 三态副驾 = D5-07 常驻 PM subagent × D2-12 里程碑审计员 × D4-27 台账考核 agent
- **机制（新机制：同一个常驻子 agent 按项目阶段在三态间切换，而非每次新 spawn）**：D5-07 的常驻子线程平时处于「辅助态」（回答、出批量草稿）；到里程碑节点自动切「审计态」（D2-12 的独立验收视角、不带辅助偏见）；每周期切「考核态」（D4-27 读执行会话的产出轮次/文件量/feedback 评分）；三态共享同一上下文但职责切换有明确进入/退出条件，切换点写进草稿箱留痕。
- **具体场景**：平时副驾帮 PM 调排期；M1 达成前它自动变成审计员挑证据缺口；月底它切考核态给出「本周期哪些执行会话空转」；全程同一个子线程记得项目历史，不用每次重新喂快照。
- **触点**：subagent 常驻会话（D5-07）+ 角色种子切换（R2-09）+ workspace-changes/session-query/feedback 指标（D4-27）。
- **来源观察**：D5-07 辅助、D2-12 审计、D4-27 考核在池中是三个孤立一次性/单态想法；杂交点是「同一主体按阶段换帽子」。

### D2-R2-16 【杂交】自证周报 = D1-13 周期周报流程 × D2-19/D5-05 session-query FTS5 × D5-04 workspace-changes 证据
- **机制（新机制：证据自动随报告条目绑定，而非事后人工贴）**：D1-13 的 schedule+jobs+快照+narrate 周报流程，在每条「本期完成」条目下自动挂两样东西——本期对应会话轮次链接（FTS5 按任务号/关键词捞出）+ 该轮 workspace-changes 文件/git 证据片段；narrate 只写叙述，数字与证据由确定性层绑定，人确认时一眼看到每条数字背后的证据，不再事后翻会话补材料。
- **具体场景**：周五自动周报草稿里「完成联调」一条下面自带「会话#312 第 4-7 轮、改 6 文件、diff 摘要」，PM 确认即成文；缺证据的条目自动标灰「无执行证据」而不是照常写完成。
- **触点**：schedule/jobs（D1-13）、session-query（D2-19/D5-05）、workspace-changes（D5-04）、R9 冻结快照。
- **来源观察**：周报（D1-13）、会话反查（D2-19）、git 证据（D5-04）各自存在，无人把证据自动绑定到报告条目。

### D2-R2-17 【杂交】自适应沉默提醒 = D2-10 到点议程投递 × D1-24 极致沉默 × 提醒响应历史
- **机制（新机制：提醒频率由个人响应历史自适应，而非固定周期）**：记录每条提醒被打开/被忽略/被延期处理的历史；连续 N 次被忽略，同类提醒自动降频（每日→每周→静默），只在严重度升到逾期/阻塞时冒泡；默认沉默（D1-24），响应历史决定何时重新开口。既不是固定周期打扰（D2-10），也不是永远沉默（D1-24）。
- **具体场景**：「P2 文档收尾」提醒连被忽略 3 次后自动转入静默，只在它变成逾期时再冒一次；「阻塞」类提醒每次都冒泡；PM 在设置里看到「已自动静音 4 条」。
- **触点**：schedule（D2-10）+ 本地响应计数（settings/provenance 范式）+ 静默主张（D1-24）。
- **来源观察**：D2-10 固定到点投递、D1-24 彻底拒绝提醒，池中无「按个人反应自适应频率」；组织者扫描指出提醒噪音/建议疲劳是空白区。

## C. 【反叛】攻击池中共识「只读工具 + 审批 seam + 证据闭环 + 轻融合 + 独立内核 + 离线优先」

### D2-R2-18 【反叛】只读工具 + 审批 seam 是单人场景下的「半瞎陷阱」
- **攻击点**：共识让模型只读、每个写动作都过审批卡。单人单写者场景里，一个人既要当操作者又要当审批者，审批卡的摩擦高于收益，最后模型干脆不建议、人也懒得点，N≈0 被这个流程自我实现——只读工具看似安全，实际让 agent 在台账面前变成半瞎子。
- **成立条件**：单写者 + 操作可逆 + D4-29 完整审计补偿在场时，应反过来：模型直接写台账，人只做**事后抽查 + 一键撤销**；审批 seam 只保留给不可逆动作（删除、对外发布、R2-05 出站写外部系统）。安全不靠「事前每笔拦」，靠「事后可追、可撤」。
- **具体场景**：模型直接把已完成任务标 done、把新承诺记进草稿箱，PM 一天结束时在审计流里扫一眼、错的当场撤销；只有「删项目」「发飞书」才弹审批。
- **触点**：D4-29 事件流（撤销补偿的前提）、goal/workflow 自主执行先例（D2-13/D2-14/D1-23）。
- **来源观察**：池中共识高度一致——D1-01/D3-01/D4-01/D5-01 全是只读工具，D1-03/D3-02/D4-02/D5-02 全是审批 seam，无人质疑单人审批是否有意义。

### D2-R2-19 【反叛】「人类可读 JSON 十年档案」是浪漫错觉
- **攻击点**：共识把「人类可读 JSON、十年可读」当长寿卖点（D1-26/D3-14）。但 JSON 只是工作数据格式，没有查看器、没有工具链、没有当时 schema 的十年后 JSON 和一堆无说明文本没区别；「人类可读」在单人当下成立，在十年后、换人后不成立。
- **成立条件**：把 JSON 重新定位为**易失工作缓存**，真正的长寿档案是归档时刻渲染出的人类直接可打开成品（排版 PDF、静态 HTML 站、印刷本）；JSON 负责当下可改，成品负责十年可看，两者寿命分开。
- **具体场景**：年度归档时系统渲染一份完整静态项目站（接 D2-26）+ 一份 PDF 年报，JSON 只是这次渲染的原料；十年后打开的是站和 PDF，不是 84 个结构未知的 JSON 文件。
- **触点**：D2-26 静态站、D2-31/D1-14 PDF 导出；反驳 D1-26「单机可读硬卖点」与 D3-14「Markdown 唯一真源」。
- **来源观察**：问题框定 §5 长寿记录要求「宿主消失后可读」，池内多数想法把可读等同于 JSON 本身可读，未区分工作数据与档案介质。

### D2-R2-20 【反叛】离线优先正在葬送产品：它是开发期舒适，不是产品定位
- **攻击点**：共识把离线优先当定位基石（UX 评估 L117、D1-18/D4-22）。但离线优先把产品锁死在一台机器、一个 profile、一个人，永远无法被别人使用、无法分发；对一个想成为「产品」的东西，离线不是美德而是原地踏步的借口。
- **成立条件**：个人单机保留离线作为**降级模式**（断网可看可记），但主路径改为可分享/可同步/可被他人访问（接 R2-08 状态页、R2-05 出站、D2-28 分发）；离线是兜底档，不是北极星。
- **具体场景**：日常断网照常用（离线降级），但默认动作里就有「生成对外状态页」「同步到外部」「发给别人看」，产品从第一天就为他人在场设计，而不是永远只服务一个本机用户。
- **触点**：R2-08、R2-05、D2-28；攻击 D1-18/D4-22/D5-16「冻结保持现状」与 requirements 离线基石表述。
- **来源观察**：池子反向一侧（D2-24/25/26/29、D3-09/10/12、D4-22~26、D5-13~18）几乎都以离线/隔离为美德，无人问离线是否限制了产品成为产品。

### D2-R2-21 【反叛】「PM 维护台账」本身才是该被消灭的问题
- **攻击点**：所有现存形态都默认「人要停下来手动维护一本台账」——录任务、更新状态、写纪要、填进度。这本双记账仪式必然腐烂：人忙起来第一件事就是不填，台账随即与现实脱节，然后被废弃。要求人额外维护一个工具，是产品失败的开端。
- **成立条件**：台账不应该是被维护的对象，而应是对话、git、日历流的**自动投影**（D2-16/D5-19 的激进化）：人只在例外处确认/纠正，常态下记录自己长出来；衡量标准不是「台账多完整」，而是「人需要主动填的次数趋近于零」。
- **具体场景**：人全程只对话、只提交代码，台账自动浮现承诺与完成，人每天花 30 秒勾掉明显错的条目；产品里几乎没有「新建任务表单」，录入入口退化成例外修正器。
- **触点**：D2-16 会话投影、D5-19 台账吃对话、D1-25 被动捕获的激进合并；攻击「人是台账维护者」这一未被质疑的前提。
- **来源观察**：池子所有 CRUD 想法（含本 D2 第1轮多数）都保留人工录入主干，D2-16/D5-19 只是补一个捕获旁路，无人主张消灭录入本身。

## D3-R2-01【区域1·规划智能】估时校准回路：用「实际工时 vs 历史同类」给新任务一面镜子

- **机制**：台账只存了 `effortHours`（实际投入工时，task.ts L66），没有估算字段；本想法补一个可选 `estimatedHours` 与纯派生校准报告：新建/排期时，按同类（同模块/同负责人/同规模档）历史任务的「实际工时中位数」给出建议估时，并在任务完成时算出偏差（实际/估算），长期沉淀成每个负责人、每类任务的「估时偏差系数」，下次建议自动修正。
- **具体场景**：PM 给一条新后端任务估 4h，面板侧栏弹出「同类任务过去 6 条实际中位数 9h，你上次估 5h 实际 12h（偏差 2.4×），建议调到 8–10h」；PM 可采纳可忽略。季度末出一张「我的估时准不准」表，而不是只有进度记录。
- **触点**：纯本地派生（effortHours 已存在；新增可选 estimatedHours 字段位，不进写白名单硬校验）；健康/统计纯函数同族；无宿主依赖。
- **来源观察**：池子几乎全是状态记录与回看（D2-21 承诺对账、completion-history 完成曲线都是事后），无人谈向前估时；task.ts L66 只有 effortHours「实际工时」、无 estimate，gantt.ts L3 明确「不做自动排程」；估时校准是规划智能最基础一层。

## D3-R2-02【区域1·规划智能】what-if 推演沙盘：改日期/挪人后先「模拟」，不落库

- **机制**：把 gantt.ts 已有的只读 CPM（predecessorIds 图、slack 松弛、criticalPath 关键路径，gantt.ts L506 criticalPath()）与 people-load 负载读数接进一个沙盒：PM 拖动「M1 推迟 3 天」「把 T-18 从赵六挪给王五」，沙盘在内存里重算关键路径变化、新的逾期面、双方负载，出一份「假设后果预览」；点「应用」才落库，点「放弃」沙盘销毁，台账零变化。
- **具体场景**：PM 想知道「如果这周砍两个低优任务，M1 还来得及吗」，沙盘显示「关键路径不变、slack 从 2 天变 4 天、王五负载降到 3 条」，PM 看后果再决定，而不是改完才发现撞期。
- **触点**：复用 gantt.ts 只读 CPM/环检测、people-load 负载派生；沙盘为内存态；不新增写路径。
- **来源观察**：ADL-051 已落地只读依赖图/环检测/slack（gantt.ts），但池子（D4-19/D2-14 workflow 扇出、D3-25 风险矩阵）都没把它用于「向前推演」；区域1 what-if 情景模拟在 146 条里完全缺席。

## D3-R2-03【区域2·组合层】项目模板库 + 组合取舍视图

- **机制**：(a) 模板库：把一个跑顺的项目「另存为模板」（实体骨架：阶段里程碑集合、标准风险清单、例会节奏、交付物类型，不含具体人名/日期），新项目选模板后实例化，占位日期/负责人留空；(b) 组合取舍视图：跨全部项目汇总同一负责人的负载、同一时间窗的里程碑拥堵、并行项目数，回答「现在同时开 3 个项目现实吗、该先砍哪个」。
- **具体场景**：PM 每接一个同类客户项目，从「交付项目模板」一键长出 4 个里程碑、6 条标准风险、3 个交付物，再填差异；组合视图一眼看到「Q4 你背了 3 个 M1 撞在 11-20 同一周，建议顺延一个」。
- **触点**：现有 project/task/milestone/risk/deliverable 复制纯函数；people-load 跨项目聚合；模板存为一组只读记录；无宿主。
- **来源观察**：池子全是单项目视角（D5-08 多项目周审只是并行叙述，非取舍）；requirements 九实体无模板概念；区域2「跨项目模板复用/组合取舍」在池中空白。

## D3-R2-04【区域3·反向写外部】台账→外部系统：确认后反向建 Git issue/MR、写日历事件

- **机制**：与池中清一色「外部只读回流」（D1-09/D2-30/D4-30 mcp 只读、D5-04 workspace-changes 只读证据）相反方向：PM 在面板确认一条任务/风险后，经已配置的外部 MCP server（GitHub/GitLab/飞书/日历 MCP）**反向发起写**——创建 issue、建 MR 草稿、在日历插入截止事件；写动作同样走草稿确认，外部返回的 issue 号/链接回填到 repoUrl/evidenceUrl。
- **具体场景**：PM 确认「登记一条限流风险」后，面板问「要不要同步建一个 GitHub issue #341 并在日历加 11-20 截止提醒」，勾选后外部系统被创建，issue 号自动回写；台账是发起方，外部系统是执行面。
- **触点**：宿主 mcp-client（已配外部 server 时调其写工具）；现有 repoUrl/branch 字段回填；默认关闭、未配外部时区块隐藏。
- **来源观察**：146 条全部是外部→台账只读（D1-09 webhook 还是只读回填、D2-30 明确「只读、绝不轮询」）；UX-11 两张皮的另一面是「台账里有了、外部还得手工再录一遍」；区域3「反向写外部」空白。

## D3-R2-05【区域4·会中实时辅助】会议进行中的当场捕获槽，而不是会后粘贴归纳

- **机制**：会议开始前在面板/会话开一个「会中模式」持续轻量槽：边开边把口头决定、认领动作随手（或语音转写流）打进速记流，系统当场把每条口头承诺即时转成待确认行动项卡片（谁/做什么/何时），会上逐条扫一眼确认，散会即定稿；区别于 D5-17/meeting-summarize 的「会后贴一段速记再归纳」。
- **具体场景**：站会进行中，PM 每听到「张三领登录改造、下周三给」就点一下记一条，会中列表实时累积；散会时行动项已经在台账里确认完，不用会后回忆、不用翻录音。
- **触点**：现有 meeting actions 增/删/改纯函数、promoteActionToTask 链路；会中槽是临时 UI 态；可借宿主语音/附件（D5-10）喂素材，但核心是「当场」而非「会后」。
- **来源观察**：池子会议想法全是会后（D3-17 会后读历史会话、D5-05 会后捞片段、meeting-summarize 会后归纳、D3-18 会后挂白板照）；区域4「会中当场捕获」空白；ADL-040 promote 链路现成可复用。

## D3-R2-06【区域5·迁入共存 + 离开电脑】Jira/飞书项目/Excel 迁入向导与「离线随身只读包」

- **机制**：(a) 迁入：提供 Jira/飞书项目/Excel 三种来源的只读抽样→字段映射预览→确认导入（复用 csv-import/task-import 的 dry-run→confirm 链路），迁入后台账与原系统只保持单向引用、不双向同步（共存而非取代）；(b) 离开电脑：生成一份可邮件/IM 转发的自包含随身只读包（静态 HTML 或 PDF 合集），手机浏览器打开只看不改，解决「不在 dsh 前也要瞄一眼」。
- **具体场景**：PM 从旧 Jira 迁 60 条任务，预览映射「Jira status→pm 状态、assignee 直填」，确认落库，Jira 链接留作引用；周末在外用手机点开邮件里的只读包看本周完成，不能改。
- **触点**：csv-import.ts/task-import.ts 现有预览落盘；外部经 mcp/web_fetch 只读；随身包复用 D1-15/D4-21 静态导出，但强调「随身/手机/只读」新场景。
- **来源观察**：docs 全仓 grep 无 Jira/飞书项目迁入（仅 csv 手工导入）；移动只在设计稿里出现 390 窄视口（system-ui-spec），无「离开电脑」场景；区域5空白。

## D3-R2-07【区域6·对外持续状态页】给领导/客户自助看的持久只读状态页（非一次性 HTML）

- **机制**：与 D1-15/D4-21「导出一张一次性静态 HTML」不同：维护一个**持续刷新**的只读状态页（本地小站随台账更新，或定时重生成一份只读 HTML 放到约定位置/静态托管），对外只暴露选定项目的健康灯、里程碑进度、本期完成、风险计数，隐藏内部细节与写入口；访问者自助刷新看最新，不需要 PM 每次手动发图。
- **具体场景**：领导每周自己打开一个链接看「官网改版：绿灯、M1 完成 70%、本周完成 5 条、无高影响风险」，PM 不用周报里贴图、不用被追着问；页面只读、无写按钮、看不到内部备注。
- **触点**：本地只读渲染（复用 board bento 快照）；如需跨设备访问才落静态托管；看板 widget 白名单裁剪对外字段。
- **来源观察**：池子导出全是「一次性发出去的文件」（D1-15 单文件 HTML、D4-21 周会前导出、D3-19 PDF 周报），无「持续在场、自助刷新」的对外形态；delivery.md §9/KB-014 现状 Web 只信任本机 loopback、无局域网远程，这正是本想法要正面处理的约束；区域6空白。

## D3-R2-08【区域7·多智能体 PMO 角色分工】四个常设角色 subagent：风险官 / 史官 / 催办员 / 调度员

- **机制**：区别于 D4-18/D2-12 的「一次性临时评审员」和 D5-07 的单个 PM 专员，定义四个**常设、分工明确**的角色 subagent，各有固定职责、触发条件与只读/草稿权限：风险官（持续扫概率×影响漂移、建议升/降级）、史官（负责把会议/决议归档成不可变档案、维护 D4-29 事件流）、催办员（只产出「该提醒谁什么」的草稿、不直接催）、调度员（跑 R2-02 沙盘做排期建议）；角色之间不互相调用，结论都回主会话等人确认。
- **具体场景**：周一早风险官主动交一份「R-0002 概率升高建议升 high」草稿；史官把上周决策会归档；催办员列出「3 条临期该提醒」；调度员给出「M1 拥堵建议顺延」沙盘；PM 在主会话一屏收四路建议，逐条批。
- **触点**：subagent-spawn-in-process（角色种子提示词固定）；只读工具（D5-01 族）；各角色只产草稿；单人主体是否成立先记录待验。
- **来源观察**：146 条里 subagent 全是一次性巡检/审计（D4-18、D2-12、D5-07 单专员、D5-08 workflow 并行），无「角色化 PMO 班子」的分工结构；区域7空白。

## D3-R2-09【区域8·认知安全】新鲜度戳 + 口径版本 + 「可能已变」置信度，防模型把陈旧摘要当真相

- **机制**：任何注入上下文/工具返回的台账事实都带三个元信息：快照生成时间戳、calcVersion/口径版本、记录 updatedAt；模型回答被要求标注「（截至 10-18 09:00）」，超过临期窗口未刷新的摘要在段首显式标「可能已变化，请重新读取」；并提供一个「对账」动作——模型引用的数字与当前快照不一致时，以当前快照为准并提示过期。
- **具体场景**：D5-03/D4-04 注入的看板摘要隔了两天没刷新，模型引用前先看到「此摘要截至前天，可能已变」，主动调只读工具重读而不是拿旧数字回答；PM 问「现在到底几条逾期」时不会得到过期断言。
- **触点**：复用 progress-reports 已有 calcVersion（report-diff.ts 同版本才相减的先例）、reminders 临期窗口；只读工具返回值附 meta；纯本地。
- **来源观察**：池子只谈注入预算（D1-32 spill 预算）和 push/pull（D4-04/D3-21），无人处理「注入的摘要过期/错误、模型把陈旧数据当真相」；区域8认知安全空白；report-diff.ts 已有「口径版本不同不硬减」的防误导先例可扩展到回答层。

## D3-R2-10【区域9·行为仪式层】站会/周报仪式重构 + 建议配额与「建议疲劳」负反馈

- **机制**：把台账嵌进固定仪式节奏（每日站会 5 分钟槽、周五周报槽），同时正面设计失败模式：建议每日配额（一天最多弹 N 条草稿，超限静默）、草稿垃圾桶（被拒草稿不再重复提）、建议疲劳负反馈（PM 连续拒绝同类建议后该类自动降频）、提醒噪音分级（只高影响打扰、其余攒到仪式槽集中看）。
- **具体场景**：副驾一天已经被拒 3 条同类建议，第 4 条自动闭嘴；周五周报槽集中攒着 6 条本周积压建议一次看完，而不是全天被打断；PM 可在设置里调每日建议上限。
- **触点**：纯本地计数（D5-22 采纳率族）+ settings 口径；无新宿主能力；仪式槽是面板内固定视图。
- **来源观察**：D1-24「极致沉默」是反提醒的哲学立场，但没有设计「建议疲劳/草稿垃圾化」的机制层失败模式；146 条无一人谈习惯养成与噪音治理；区域9空白。

## D3-R2-11【区域10·完全吞并 + 退出路线】极端吞并形态 与 dsh 原生长出 PM 能力时的优雅退役路线

- **机制（吞并极端）**：pm-tool 反过来内化一个极简 agent runtime——自己持有循环、工具、模型路由，台账就是操作系统，dsh 只剩渲染；不再借宿主 loop。
- **机制（退出/被替代路线，反向对照）**：预先写好「当 dsh 原生长出项目管理能力时 pm-tool 怎么退役」：功能映射表（宿主能力↔本插件对应功能）、数据迁移出口（导出标准格式给宿主原生 PM）、插件自动降级为只读视图并提示用户迁移，不恋战、不维护双份。
- **具体场景（退出）**：某天 dsh 官方内置了任务看板，pm-tool 检测到后提示「宿主已有此能力，可一键导出台账迁移，本插件转入只读陪伴模式」，作者不用在维护一个被取代的插件上耗带宽。
- **触点（吞并）**：脱离宿主自循环（对照 D4-24 独立 App）；（退出）纯本地导出 + 版本探测；两者是同一区域的两极。
- **来源观察**：146 条全是「往 dsh 里接」或「从 dsh 剥离」，无人谈「pm-tool 吞并 runtime」这个极端，也无人谈「宿主未来自己长出 PM 能力时本产品如何退场」；区域10空白；R5 平台存在性的另一面是被替代风险。

## D3-R2-12【区域11·商业/分发】开源治理、插件市场发布、分层定价与「PM 方法论即产品」

- **机制**：(a) 治理：公开 npm 包（D2-28 已提发布）配贡献指南、issue 流程、版本承诺；(b) 分层：核心离线台账免费，AI 草稿/模板库/状态页作为付费层；(c) 方法论即产品：把 WBS 拆解法、风险 3×3 登记法、周报口径、站会模板从代码里抽成可独立售卖/分发的 PM skill 包（呼应 D1-29/D3-16），买方法论的人不一定买插件。
- **具体场景**：免费用户用离线台账；付费用户拿到模板库+对外状态页；另有人单独买一份「PM 方法论 skill 包」装到自己的 agent 里，与插件销售互不绑定。
- **触点**：npm/bundle 发布机制；skill-filesystem 分发；计费端口（D5-23 model-route 适配端口）。
- **来源观察**：池子商业层只有 D2-28 发 npm、D5-23 计费端口、D1-17 preset 打包，无开源治理/定价分层/方法论独立产品化；区域11空白；personal-billing-plan.md 是成本账而非定价模型。

# B. 杂交（组合池中已有机制，产生原想法不具备的新机制）

## D3-R2-13【杂交 D2-12 里程碑独立审计员 × D4-29 全局只增事件流】审计评级历史曲线：审计员每次判断不丢、可回看趋势

- **机制**：D2-12 的「全新 subagent 独立验收审计」每次结论（达成/证据不足/缺交付物）不只是回面板一次，而是作为一条不可变事件写进 D4-29 的全局只增事件流；同一里程碑多次审计连成一条「评级历史曲线」（首次审计证据 2/5 → 补证据后 4/5 → 达成），看板可回看这个里程碑是怎么被补到达标的，而不是只看到最终状态。
- **新机制点**：单次审计（D2-12）× 只增历史（D4-29）= 审计本身成为可追溯、可累计的评审资产；两者单独都没有「同一对象多次审计的纵向曲线」。
- **具体场景**：M1 三次审计记录在事件流里，复盘时 PM 看到「第一次被指出缺验收报告，补齐后第二次通过」，评审意见的演进留在档案里。
- **触点**：subagent 只读审计 + D4-29 append-only JSONL；审计结论结构化落事件。
- **来源观察**：D2-12 审计报告「只读挂里程碑、不改库」即弃；D4-29 事件流只记普通字段变更，两者从未结合；provenance 有界 20 条会丢最旧（D4-29 已指出）。

## D3-R2-14【杂交 D1-13/D4-09 自动周报 × D5-22/D4-16 采纳率计量 × D3-20 本机计数】自动草稿自带「可信度信封」，低采纳自我静默

- **机制**：周期自动周报草稿（D1-13/D4-09）投递时，信封上同时附上该来源近期的采纳率与数字置信度（D5-22/D4-16 本地计数）：若本类草稿近 10 条采纳率低于阈值，本轮自动不投递、只在后台记录；数字本身附「本期样本 N、与上期口径」的置信说明，PM 一眼知道这条建议值不值得看。
- **新机制点**：自动触发（D1-13）× 采纳率反馈（D5-22）= 一个会根据自己历史命中率自我调节发送频率的草稿系统；纯触发和纯计数各自都没有「命中率驱动的自适应沉默」。
- **具体场景**：副驾周报草稿连续被拒，第三周系统判断「这类建议无人采纳」，周五不再打扰，只在计数页留一条「本周静默」；采纳率回升后自动恢复投递。
- **触点**：schedule 周期触发 + provenance 采纳计数 + 本地阈值 settings。
- **来源观察**：D1-13/D4-09 只解决「到点自动生成」，D5-22/D4-16 只解决「事后统计」，无人把统计结果反馈回触发决策；这也正面回应区域10的建议疲劳。

## D3-R2-15【杂交 D2-15 面板内嵌对话槽 × D3-13 任务反向开工 × D5-20 todo 临时镜像】抽屉内迷你会话自带该任务的临时 todo，散会即焚

- **机制**：D2-15 在任务抽屉里开的迷你对话槽，启动时把该任务的 checklist 临时镜像进会话 todo（D5-20 的临时投影），agent 在抽屉小窗里围着这条任务干，勾选只在会话内、结束即丢弃、绝不回写台账；会话产出经 present 回到任务证据区，人确认才勾正式 checklist。
- **新机制点**：内嵌对话（D2-15）× 任务反向开工（D3-13）× 临时 todo（D5-20）= 一个「围绕单任务、自带临时清单、用完即焚」的微型执行单元；三者单独分别是壳、发起、投影，合体才有完整的局部闭环。
- **具体场景**：PM 点开 T-12 抽屉，底部小窗直接问「这个登录改造怎么拆」，临时 todo 列出 4 个子步，agent 干完小窗关闭，临时清单消失，产出文件进证据区，PM 再勾正式清单。
- **触点**：sessions.create()、tool-todo 临时整表替换、present、checklist 回写确认。
- **来源观察**：D2-15 只开对话槽不携带工作清单；D3-13 反向开工但落在主会话；D5-20 临时镜像但无对话载体；三者互补缺一。

## D3-R2-16【杂交 D4-27 台账考核 agent 会话 × D1-07 session-query 痕迹 × completion-history】执行单元完成曲线：把 agent 会话当可计量资源出趋势

- **机制**：D4-27 把 dsh 会话登记为「执行单元」，D1-07 用 session-query 捞该单元的轮次/工具调用/文件改动，completion-history 的周曲线算法（只认真实完成）复用到执行单元上，形成「每个 agent 会话/每类工作的产出曲线」，进资源负载视图；真人 assignee 与执行单元并列展示。
- **新机制点**：被管理对象（D4-27）× 痕迹回捞（D1-07）× 完成曲线算法（completion-history）= 资源维度的纵向趋势，而非 D4-27 的单次快照罗列。
- **具体场景**：负载视图出现「agent 会话 #312 本周改 8 文件、完成 2 任务」并连成四周曲线，PM 比较哪类会话产出高、哪类空转。
- **触点**：session-query FTS、workspace-changes 计数、completion-history 纯函数移植；只读。
- **来源观察**：D4-27 是单时点考核，D1-07 是单任务证据回挂，completion-history 只给真人任务出周曲线；三者从未组成资源趋势。

# C. 反叛（刻意攻击池中共识：只读工具 + 审批 seam + 证据闭环 + 轻融合 + 独立内核 + 离线优先）

## D3-R2-17【反叛·攻击「只读工具+审批seam」】只读是半瞎陷阱；单人单写者场景应直接给边界内受限写权

- **反叛论点**：146 条几乎一致地选择「只读工具 + 每步审批卡」，但在单人、单写者、无协作冲突的现实里，审批 seam 是纯摩擦——自己批自己、60s 超时默认拒绝、每步打断，模型反而因为怕写错而只敢读不敢动。更对的形态是：在窄边界内（勾 checklist、改自己刚干完的任务状态、补证据链接）给 agent 受限写权，直接写、provenance 全留痕、人只事后审计/回滚，而不是步步举手。
- **成立条件**：① 确实单人单写者，不存在第二个人并发冲突；② 写边界收得很窄（不含删、不含改计划日期/负责人这类高风险字段）；③ 有 D4-29 全量只增事件流可随时回滚；④ 高风险动作（改期、删、提新风险）仍走审批。条件不满足则退回只读+审批。
- **具体场景**：agent 干完一条任务直接勾上对应 checklist 并记证据，PM 晚上一次性扫审计流回滚可疑项，而不是每件事点一次批准。
- **触点**：受限写工具（白名单比 copilot.ts 更窄）、provenance/事件流、事后回滚；对照 D1-23 自主执行的红线探索。
- **来源观察**：共识来自 D1-01/D2-07/D4-01/D5-01 一致只读 + D1-03/D2-08/D4-02/D5-02 一致审批；ADL-036 草稿确认制是为多人/不可信模型时代立的，单人场景是否还需要每步门禁值得反一问。

## D3-R2-18【反叛·攻击「人类可读 JSON 十年档案」】JSON 十年可读是浪漫错觉，真长寿是渲染成品优先

- **反叛论点**：D3-14/D4-25/D5-14/D1-26 把「人类可读 JSON、十年后 grep 得到」当长寿信仰，但 JSON 被 schema 漂移、zod 迁移、字段语义变更绑架——十年后的人拿着旧 JSON 面对新 zod 规则照样读不懂，可读的是文字不是结构。真正十年不坏的是渲染成品：PDF/静态站/Markdown 纯文本，结构反而是会烂的部分。
- **成立条件**：档案目的是「人能读懂历史」而非「机器能再编辑」；若目的是可继续编辑迁移，则 JSON+迁移器仍是对的，两条目的分开。
- **具体场景**：十年后打开的是一份排版完好的项目历史 PDF/静态站，而不是一堆需要理解 v1→v3 schema 变迁的 JSON；JSON 只作为当期编辑源。
- **触点**：D1-14/D4-13/D5-11 成品导出升格为一等档案；本地归档；不依赖宿主。
- **来源观察**：C5「人类可读可迁移」被多方案当硬卖点（D1-26/D4-25/D5-18）；但 domain 已从 v1 九表演进到客观进度 calcVersion，schema 一直在变，反证 JSON 并不自我保鲜。

## D3-R2-19【反叛·攻击「离线优先」】离线优先会把产品葬在一台机器上；联网应是默认，离线是退回选项

- **反叛论点**：C2 离线红线被当成产品主张（D4-26 极致被动、D1-22 零上报卖点、D2-24 隔离门），但单人本地、零网络效应意味着产品永远困在一个人的一台机器里；对外价值（R2-07 状态页、R2-04 反向写外部、分发协作）全部需要默认联网。应把「默认联网可用、离线可降级」反过来，离线是断网时的退回，不是身份。
- **成立条件**：目标包含他人阅读/外部同步/公开分发（H11 潜在他人阅读、R5 去留）；若纯粹自用私有，则离线优先成立。
- **具体场景**：默认状态页可访问、外部 issue 可同步，断网时自动降级为本地只读，而不是默认锁死在本机 loopback。
- **触点**：mcp-client/web_fetch 出站、R2-07 状态页；隐私由可选开关而非默认封锁。
- **来源观察**：KB-014/delivery §9「Web 只信任本机 loopback、无局域网远程」是现状约束却被多条想法当美德；ADL-032 因离线暂缓了大量能力，反叛点在于把约束当原则。

## D3-R2-20【反叛·攻击「PM 维护台账」这个前提】该被消灭的是「维护录入」本身，而不是优化录入表单

- **反叛论点**：所有共识都在优化「人怎么更好地录/确认/维护台账」（表单、草稿、审批、看板），但录入维护成本才是单人工具的真实死因——没人愿意长期另录一本账。正确方向是把录入压到零：自动捕获（D1-25/D5-19/D2-16）到「人只做是/否裁决，从不从零填字」，台账从「要维护的本子」变成「自动长出来、人偶尔纠错的影子」。
- **成立条件**：自动捕获源（会话/git/速记/附件）足够可靠且全进草稿箱等人裁决，零确认不现实但可逼近；人始终保留否决权。
- **具体场景**：PM 全程不填一张表，台账从日常对话和改动里自己长出来，他只在草稿箱里扫一眼勾/删。
- **触点**：D1-25 被动捕获收件箱 × R2-10 降噪；消灭表单而非美化表单。
- **来源观察**：146 条无一质疑「人为什么要维护一本独立台账」这个前提；UX 痛点全是录入/确认效率（UX-05 行内编辑、UX-01 树视图），反叛点是前提本身。

## D3-R2-21【反叛·攻击「抽独立内核」】独立内核是伪独立：换壳等于重写，真正可移植的是开放格式不是代码复用

- **反叛论点**：D3-07/D2-05/D4-23/D5-14 都主张抽零依赖 pm-core，但抽出的包仍绑定「项目/任务/里程碑/风险」这套私有语义和 zod 校验，换一个壳（独立 App/MCP/静态站）照样要重写 UI、适配存储、重新定义交互；代码复用的价值被高估，真正十年可移植的是**开放数据格式 + 成品渲染**，内核代码本就该随宿主一起换掉。
- **成立条件**：评估「独立」时以「换壳后业务代码是否真零改动」为准；若只抽纯函数派生（健康分/对账/CPM）这类无语义件，复用才成立，全实体内核独立是幻觉。
- **具体场景**：换壳时发现七实体语义得重新对着新产品改，抽出的内核只复用了 health/report-diff 几个纯函数，其余白抽。
- **触点**：反面对照 D3-07/D4-23；把投入转向开放格式导出（R2-18）而非代码抽离。
- **来源观察**：product/11「PmDomain 唯一边界、换后端零改动」是存储后端层面，被多条想法推广成「换壳零改动」，二者不是一回事；ADL-034 升级断点全在适配层，但实体语义与壳深度耦合并未被质疑。

## A. 补漏（视角扫描稀疏区，14 条）

### D4-R2-01 【区1 估时校准】从真实完成记录反推个人速度，给新任务参考区间
- **机制**：不引入乐观估时输入，而是用已有的 `effortHours`（实际工时）+ `completedDate`（完成日期），按任务粒度（同层叶子、同优先级、同负责人）聚合出历史中位耗时 P50 与 P80；新任务建档时，模型/纯函数只给一条「同类历史参考：中位 Xh / P80 Yh」的草稿建议，不写死、不强制填；记录样本不足时显示「样本 n<3，证据不足」。
- **具体场景**：PM 给官网改版加一条「支付回调联调」，抽屉里出现一行灰色参考：「同类 P2 叶子近 6 条：中位 6h、P80 11h（样本 6）」；PM 参考着自己填实际计划，系统不替他估。攒满两三个项目后，参考线越来越准，估时从拍脑袋变成对自己历史的校准。
- **触点**：纯本地派生（`core/completion-history.ts` 已按周聚合 completedDate，扩展按粒度聚合 effortHours）；任务已有 `effortHours`/`completedDate` 字段（`core/task.ts` L66-50）；不接宿主。
- **来源观察**：effortHours/completedDate 字段早已存在但全产品无人自动填、无聚合；第1轮池子几乎全是状态记录与回看，没有任何前瞻估时；ADL-051 明确「单用户本地没有权威工作日历，硬算绝对排程会造伪精确」，本想法只给历史区间、不排程，避开该红线。

### D4-R2-02 【区1 what-if 沙盘】延期/挪人的纯本地假设推演，不落库
- **机制**：把已有的只读 CPM `criticalPath(tasks)` 改造成可接受「假设偏移」的纯函数：输入一组假设（任务 A 延期 X 天、负责人 B 减载、某里程碑提前），在内存副本上重算 ES/EF/LS/LF/slack，输出「哪些任务从非关键变关键、哪个里程碑将 missed、新关键链是哪条」，结果只渲染为沙盘对照层，零写库、零持久化。
- **具体场景**：PM 在甘特页开「沙盘」，拖动假设滑块「登录联调延 3 天」，画面即时标出：M1 从 slack 2 天变 slack=0、新增关键链 t-0003→t-0007；PM 看完关掉，台账原日期分毫未动。这是决策前的推演室，不是自动排期。
- **触点**：`criticalPath` 纯函数（ADL-051，已输出 ES/EF/LS/LF/slack/onCriticalPath）加一个内存假设层；面板沙盘浮层；零写。
- **来源观察**：ADL-051 已算好关键链但只吃真实日期、明确「不做自动压缩工期/资源平衡」；池中无情景模拟；persona B 的「资源调配优化、哪个项目要延期」焦虑（product/01）无对应视图。

### D4-R2-03 【区2 项目模板库】完成项目另存为模板，新项目从骨架实例化
- **机制**：新增本地 `templates` 表：把一个 done/archived 项目的任务树骨架（标题/层级/优先级/前置关系，去掉负责人/日期/进度）、里程碑集、常用风险登记项、checklist 检查点冻结成模板条目；新建项目时选模板实例化，编号重排、日期留空、状态复位 todo，产出草稿树待确认；支持「当前项目→另存为模板」。
- **具体场景**：PM 刚完成一个营销活动项目，点「存为模板」；下个活动立项时选「活动项目模板」，秒得到一套三级 WBS 骨架+3 个标准里程碑+风险登记位，只需改标题和日期，不用从零拆。
- **触点**：storage-domain 新增 templates 表；复用 addTask 树/编号/前置校验；纯本地、离线。
- **来源观察**：现状新建项目只有空白七实体；csv-import/task-import 是「外部进」，无「项目→项目」复用；池中无模板概念；requirements R3 项目创建至今无模板路径。

### D4-R2-04 【区2 组合取舍板】有限人力下的「保/缓/砍」聚焦决策视图
- **机制**：跨项目聚合每个 active 项目的健康分、临期里程碑数、未关闭高影响风险、活动天数，纯派生排成一张取舍表；PM 给项目打一个自定义「战略权重」标签，视图辅助列出「同样人力下建议本周期聚焦 Top2、暂缓哪几个」的草稿清单；不自动砍、不改状态。
- **具体场景**：PM 同时管 3 个项目，月底决定资源投向，组合板按健康度+权重排出：「官网改版（黄、临期里程碑 1）建议保；内部工具（绿、14 天无活动）建议缓；实验项目（红、2 高影响风险）建议砍或降目标」，PM 自己拍板后手动调整项目状态。
- **触点**：`core/health.ts`、`war-room.computeKPI`、people-load 聚合；纯面板跨项目派生（现状 GlobalBoard 只读卡片，product/12 §5）。
- **来源观察**：persona B PMO「同时管一组项目、向 leader 报盘子整体健康度、做资源调配」（product/01 五）；现状跨项目只有只读卡片，无取舍辅助；池内无组合层想法。

### D4-R2-05 【区3 反向写外部系统】台账→外部 issue/MR/日历事件的出站草稿
- **机制**：与池中全部「只读回流」反向：经已配置的外部 MCP 服务器（GitHub/Jira/飞书项目）调用其**写工具**，把台账任务生成「要在外部创建的 issue/任务/日历事件」出站草稿（标题/负责人/截止/正文字段预填），人在 approval seam 确认后才发出；外部返回的 issue 号/链接回写任务 `evidenceUrl`/外链字段；未配置外部服务器时该区块隐藏，离线 CRUD 不受影响。
- **具体场景**：PM 在 t-0003 抽屉点「创建到 Jira」，弹出出站草稿卡（标题、负责人、dueDate 已填），确认后 Jira 多出一条 issue，回写链接；反过来不用每天手动把台账任务抄进公司系统。注意：写外部不消耗 Coding Plan key，合规边界在 AI 车道不在出站。
- **触点**：`mcp/mcp-client`（连外部服务器、调用其工具与资源）；`interaction/user-approval`；任务已有 repoUrl/branch（PROD-21）与 evidenceUrl；webhook-github 是入站对照。
- **来源观察**：池内 D1-09（webhook 入站+反向只读轮询）、D2-30/D1-11（MCP 只读拉 MR 状态）全是只读回流，无一条出站写；UX-11「台账↔公司系统两张皮」目前只朝一个方向补；personal-billing-plan §4.1 的合规红线只约束 AI key，不约束对外部系统发写。

### D4-R2-06 【区4 会中实时捕获】麦克风本地转写，会中当场认领行动项
- **机制**：会中打开面板「现场模式」，浏览器麦克风经宿主本地 SenseVoice STT 实时转写，模型边听边从语音流里抽「谁/做什么/什么时候」疑似行动项，逐条弹成可当场认领/丢弃的气泡；散会后这些已认领项直接拼成会议纪要草稿，不再依赖会后粘贴速记。本地转写不外发。
- **具体场景**：站会进行中，PM 说完「赵六今天前补登录单测」，屏幕上立刻浮一条候选行动项，赵六（本人即 PM）当场点认领；散会时纪要里行动项已经齐了，只需补决议。告别「会后对着录音/速记回贴」。
- **触点**：`experimental/speech-to-text`（`ctx.speechToText` 具名 provider、sensevoice-local）+ `voice-input-bundle`（浏览器 mic 控件、默认禁用）；会后定稿仍走 meeting-summarize.ts；attachment 存白板照。
- **来源观察**：R15 现状只吃会后粘贴的静态速记（meeting-summarize.ts 三来源均为粘贴）；池中 D5-10/D3-18/D4-07 都是会后贴图，无会中实时；voice-input-bundle README（本地 SenseVoice、默认关闭、带认证 Remote）说明这条通道现成但从未被 PM 场景使用。

### D4-R2-07 【区5 迁入与共存】Jira/飞书导出格式的列映射导入器 + 增量共存
- **机制**：在现有 CSV/XLSX/Markdown 导入之外，加一层「外部格式列映射适配」：识别 Jira 导出 CSV、飞书项目/多维表格导出的常见列（Issue Key/状态/经办人/截止/史诗链接），映射到我方 schema，导入为草稿并去重；外部 issue 号存进外链字段，支持两种共存姿态——外部继续当主（pm-tool 只读视图）或 pm-tool 当主（外部历史归档）。
- **具体场景**：PM 从旧 Jira 导出一份 CSV，选「Jira 映射」导入，87 条任务进草稿、14 条重复被跳过；Issue Key 留在每条上，日后双向对得上；不是一次性搬家，而是可增量共存。
- **触点**：`core/csv-import.ts` HEADER_MAP 扩展（现状只认少量中英列名）、`core/task-import.ts`；新增 externalRef 字段位；纯本地解析。
- **来源观察**：csv-import HEADER_MAP 仅映射标题/负责人/截止等少数字段；task-import 只认 GitHub 勾选清单；全 docs 无 Jira/飞书格式适配；池中无迁入想法；product/01 自我定位「不是又一个 Jira」但没回答「从 Jira 怎么过来」。

### D4-R2-08 【区5 移动端/离开电脑】手机只读通道：MCP 客户端或静态页看盘，写回电脑
- **机制**：利用本地 MCP server（母本 D4-20/D5-15）或独立静态只读 viewer（母本 D2-26/D5-18），让手机上的 MCP 客户端/浏览器只读取逾期、临期里程碑、高影响风险；手机端不提供批准/写操作，所有确认仍回到电脑。离开电脑时只「看」不「改」。
- **具体场景**：通勤路上 PM 用手机 MCP 客户端问「今天有什么逾期」，读到三条只读清单；想推进时标记「回电脑处理」，不在手机上写。解决「离开电脑完全失联」，又不破坏单写者。
- **触点**：本地 MCP server、静态只读页；sdk JSON-RPC 可作备用通道；KB-014 loopback 限制作为约束记录（外网访问需额外穿透，本想法不解决它）。
- **来源观察**：dsh Web 只信本机 loopback、无局域网远程（KB-014、delivery.md §9）；池中无移动端/离开电脑场景；persona A「随时想知道有没有要炸的」但现状离开电脑就是零信息。

### D4-R2-09 【区6 对外持续只读状态页】非一次性导出的常驻公开看板
- **机制**：在 host webserver 注册一个具名只读路由 `/pm/status/:project`，dsh 运行期间持续渲染该项目的健康灯、里程碑时间线、公开风险（可勾选隐藏敏感细节）；领导/客户从指定入口随时看实时状态，页面只读、无写入口；与 D4-21/D1-15 的一次性 HTML 导出互补（一个快照、一个活页）。
- **具体场景**：客户每周问「项目到哪了」，PM 不再手动发导出图，直接给一个只读链接，对方打开看到当前绿灯/3 个里程碑已达成；PM 在后台更新，页面实时跟着变。
- **触点**：`host/webserver` 具名路由注册（webhook-github 已示范插件在 ctx.webServer 注册路由）、frontend-static 回退席位；只读派生；访问码/token 由宿主 index 机制约束。
- **来源观察**：D4-21/D1-15 都是导出瞬间快照、脱钩台账；feasibility-map H11「潜在他人阅读」长期未满足；webserver README（具名路由互不相交、插件认领各自路由）证明常驻路由可行；loopback 约束决定默认只本机，远程需显式配置。

### D4-R2-10 【区7 多智能体 PMO 分工】角色化班组：风险官/史官/催办员/调度员
- **机制**：用 experimental agent-team 的 Lead+具名 teammate+持久共享任务板，固定四个只读角色：「风险官」只扫 open 高影响风险与预警信号；「史官」只把对话决策抽成纪要候选；「催办员」只产临期/逾期提醒草稿；「调度员」只跑 R2-02 沙盘；各角色只碰自己的域，草稿汇进共享 inbox，主线程人统一确认，无角色有写库权。
- **具体场景**：周一早上 PM 开 PMO 班组，风险官先报「2 条高影响风险未关闭」，史官甩出「上周对话里 3 条待归档决策」，催办员列「明天到期 4 条」，调度员备好延期沙盘；PM 在主线程逐条批，像管理一个小办公室而不是自己一个人全包。
- **触点**：`experimental/agent-team`（Lead/具名 teammate/直接 inbox 消息/持久共享任务板/冷恢复）+ `tool-agent-team`（九个团队工具）；只读工具面；subagent 为对照。
- **来源观察**：池中 D4-18/D3-22/D2-12/D5-07 全是一次性单代理或长会话专员，无角色化分工；agent-team README（具名 teammate、inbox、持久 roster 与任务状态、冷恢复）正是角色化地基；R4 的主体质疑在「分工班组」形态下重新被检验。

### D4-R2-11 【区8 认知安全】摘要新鲜度/口径/覆盖度标注，陈旧即显式警告
- **机制**：每条工具返回值与每段注入摘要都携带三个元数据：`capturedAt`（快照时间戳）、`calcVersion`（口径版本）、`coverage`（有清单叶子占比/覆盖任务数）；模型引用时必须带时间锚；当源记录 updatedAt 晚于 capturedAt 超过 TTL，或 calcVersion 与当前不一致，结果显式标「可能陈旧」并给「一键重取」；禁止把陈旧摘要当现状陈述。
- **具体场景**：模型早上读到的摘要说「2 条逾期」，下午 PM 在面板改了状态，傍晚模型再引用时返回值带「capturedAt=10:12，源记录已更新，可能陈旧」，并附上重取按钮；模型不会把两小时前的数字当现在的事实说出口。
- **触点**：工具 `output.schema` 带元数据；objective-progress 已有的「证据不足 null、calcVersion 不相减」诚实口径（product/12 §5）；report-diff 相邻口径不同不渲染差值先例。
- **来源观察**：D1-32 只治注入预算、不治陈旧；session-reference 有「不受信任背景警告」但无新鲜度；池中无防误导/对账；R2 机器可操作性的暗面正是「模型把过期数据当真相」。

### D4-R2-12 【区9 行为/仪式层】站会/周报仪式卡 + 建议疲劳/噪音/草稿垃圾化的失败模式设计
- **机制**：把站会（每日三问：昨天完成/今天计划/阻塞）、周报（固定节奏）做成显式「仪式卡」由 schedule 触发；同时内置三套反失败模式：①建议疲劳——同类诊断每日封顶 N 条、可按类别静音；②提醒噪音——同一逾期项只在状态变化或窗口跳档时再提，不每天重复轰炸；③草稿垃圾化——被拒草稿单独计数并对该来源降频，拒绝率高的建议不再频繁弹。
- **具体场景**：第一周提醒很勤，第二周系统发现某类诊断被连续忽略，自动降频；PM 感觉不到被催办追着跑；站会仪式卡每天同一时间给三问模板，而不是凭空对着空白写。
- **触点**：schedule 周期触发、suggestion-engine 诊断气泡、provenance 采纳/拒绝计数（母本 D5-22/D4-16）；本地阈值设置；纯读时派生为主。
- **来源观察**：ADL-039 提醒读时派生但无降噪；D4-16/D5-22 只计量采纳率、不做疲劳治理；池中无仪式重构、无失败模式设计；persona A「打开 10 秒答最该盯三件事」反过来说明噪音过多时反而抓不住重点。

### D4-R2-13 【区10 完全吞并 + 退出路线】内化 agent runtime 的极端形态，与原生替代时的平滑退役
- **机制（吞并极端）**：pm-tool 自己持有一个最小执行循环（借 sdk/ptc-runtime 在进程内驱动模型轮次），台账既是计划也是执行环境，不再借主会话；工具、调度、验收全在插件内闭环。
- **机制（退出路线）**：预设「dsh 原生长出项目管理能力」的退役剧本：pm-tool 不再竞争，转为「数据导出器 + 迁移向导」，把七实体按原生模块格式导出、带字段映射说明，自身停维。
- **具体场景（退出）**：未来 dsh 内置了看板/任务能力，PM 点「迁入原生」，七实体经向导映射进原生模块，pm-tool 完成历史使命后只读留存；吞并极端则是反过来：插件把整个 runtime 吃进来，dsh 主对话只是它的一个前端。
- **触点**：`sdk`（另一进程 JSON-RPC 驱动完整 runtime）、`ptc-runtime`；退役复用现有 export MD/JSON；两条方向并列记录。
- **来源观察**：R5 平台存在性问「留在 dsh 是否沉没成本」，但池中无人回答「宿主原生长出该能力时本产品怎么办」；sdk README（从另一进程驱动完整 harness）是吞并极端的技术支点；D2-28/D5-15 只谈对外分发，没谈被原生替代。

### D4-R2-14 【区11 商业/分发】开源治理 + 市场分发 + 分层定价 + 方法论即产品
- **机制**：公开 npm 包（母本 D2-28）补全治理：示例工程、CONTRIBUTOR、license、版本与升级策略、dsh-plugin topic 页面；分层：离线 CRUD 永久免费，AI 车道仅说明配置不代收费；另把「风险 3×3 登记法 / WBS 拆解法 / 周报口径」单独打包成可独立分发的方法论 skill 包，不绑定插件本体。
- **具体场景**：别人在 dsh 插件市场看到干净的 pm-tool，装完有示例工程可玩；哪怕不用插件，也能单独装一份「PM 方法论 skill」让任何 agent 按这套口径办事；产品卖的不只是软件，是这套工作方法。
- **触点**：agent-preset 打包、skill-filesystem、feasibility-map §七发布路径、personal-billing-plan；市场若未来出现则以 topic 对接。
- **来源观察**：D2-28 只提发 npm 包，无治理/定价；D1-29/D3-16 提了 PM skill 但没当独立商品；池中无开源治理、无定价、无方法论产品化；billing plan 已把成本结构算清，缺的是对外售卖形态。

## B. 杂交（4 条，注明母本，产生原想法不具备的新机制）

### D4-R2-15 【杂交 B1】证据新鲜度对账卡 = D4-05（workspace-changes 证据）× D4-R2-11（认知安全）× D4-06（session-query）
- **机制**：新机制是「证据时间戳 ↔ 台账记录时间戳的偏差计算」：每条候选证据（git 改动/会话片段/附件）自动比对自身捕获时间与所挂任务的最新 updatedAt，偏差超窗即标「证据早于记录最近改动 N 天，可能不覆盖最新状态」，三类证据按新鲜度排序，人可一键重取；不是静态挂链，而是会自己「过期提醒」的证据链。
- **具体场景**：t-0003 证据区列三条：①今日 git 改动（新鲜）②上周会话片段（已陈旧，标黄）③白板照（时间最早）；PM 一眼看出哪条还能用来对账周报，哪条需要重取。
- **触点**：workspace-changes summary/diff、session-query、attachment；时间戳偏差纯函数；provenance。
- **来源观察**：母本三条各自孤立——D4-05/D4-06 只静态挂证据，D4-R2-11 的新鲜度治理只用于摘要；杂交把新鲜度口径首次用到「证据」上，池内无此机制。

### D4-R2-16 【杂交 B2】常驻 PMO 班组 × 后台 jobs 轮值 × inbox 汇流 = D4-R2-10（角色班组）× D1-13（jobs 后台周报）× D5-07（PM 长会话）
- **机制**：新机制是「角色职责 × 周期调度 × inbox 汇流」三者相乘：风险官/史官/催办员/调度员各由一个持久 teammate 担任，jobs 在周期点唤醒对应角色跑只读检查，草稿投进共享 inbox，主线程人一次性批，而不是人每次手动叫某个角色。
- **具体场景**：每周五 16:00 jobs 唤醒史官汇总本周决策、催办员列临期项，两条草稿并进 inbox；PM 打开 inbox 一次批完，不用分别唤起。
- **触点**：agent-team inbox/共享板、jobs（JobHandle/完成通知/owner cleanup）、持久 teammate；只读。
- **来源观察**：母本中 subagent 全是一次性、jobs 只跑单任务、agent-team 无周期调度；杂交产生「有班次的虚拟班组」，池内无。

### D4-R2-17 【杂交 B3】冲刺三段链：沙盘 → goal 驱动 → 独立审计 = D4-R2-02（what-if）× D2-13（goal 绑任务续行）× D2-12（里程碑独立审计 subagent）
- **机制**：新机制是「前瞻模拟—执行驱动—独立验收」闭环：先用沙盘算关键链缺口并选出冲刺任务，再把选中任务绑 goal 自动续行推进，完成后派全新无历史审计 subagent 核对证据/checklist 再建议达成；三段各自输出草稿、人在收口处批准。
- **具体场景**：为 M1 冲刺：沙盘选出 3 条关键任务 → goal 驱动 agent 逐条推 → 审计员独立报「证据齐 2 条、1 条缺链接」→ PM 补证后才标 M1 达成。
- **触点**：criticalPath 沙盘、goal/goal-round-driver、spawn-in-process 审计；三段草稿确认。
- **来源观察**：母本三者在池中孤立出现（沙盘无人做、goal 单向、审计单次）；杂交把它们串成一个冲刺生命周期，池内无链。

### D4-R2-18 【杂交 B4】带有效期戳的 AGENTS.md 看板 = D5-13（PROJECTS.md 进 AGENTS.md）× D4-R2-11（新鲜度）× D3-14（Markdown 真源）
- **机制**：新机制是「文件式投影也纳入新鲜度治理」：渲染进工作区的 PROJECTS.md 顶部带 capturedAt 与「建议渲染时间」，agent-instructions 加载时发现文件 mtime 陈旧，自动在注入段加一行「看板已 N 天未刷新」；文件真源与保鲜警告并存。
- **具体场景**：PM 两周没重渲染，新会话里 agent 开场先看到「本看板最后更新 10-04，可能陈旧」，不会把两周前的逾期清单当现状。
- **触点**：agent-instructions 文件加载/刷新、文件 mtime 比对、Markdown 渲染；零宿主 API。
- **来源观察**：D5-13/D2-06 只渲染文件不保鲜，D3-14 把 md 当真源但无新鲜度；杂交让「纯文件路线」也防误导，避开它最大的暗面。

## C. 反叛（5 条，攻击第1轮共识，给出成立条件）

### D4-R2-19 【反叛 C1】只读工具是半瞎陷阱：单人场景应让 agent 在边界内直接写
- **攻击对象**：D1-01/D2-07/D3-01/D5-01/D4-01 五人趋同的「只读工具+写全走审批」共识。
- **反叛机制**：只读工具让模型只能「汇报台账」却永远不能「完成台账」，每次都要模型读→人转述→人动手，两次往返；单人单写者场景下，应允许 agent 在低风险动作集内直接写（勾 checklist、标完成、关已解除风险），审批 seam 只留给改期/删/改负责人/改优先级这类高风险动作。
- **成立条件**：①单写者身份恒定，无跨人冲突；②所有直写进可回滚事件流（母本 D4-29）；③有 auto-review 式逐动作模型审查兜底（experimental/auto-review：每次工具调用前模型先评，被拒转人工）；④直写动作白名单封闭、可一键撤销。四条同时成立时，半只读反而更慢更累。
- **触点**：auto-review 逐调用审查、provenance 事件流、封闭写白名单。
- **来源观察**：auto-review README（Full access 前模型评估、拒绝转审批、默认关闭、耗额外 token）正是单人直写的现成安全网；共识把「安全」等同于「只读」，忽略了单人场景的冲突成本本就为零。

### D4-R2-20 【反叛 C2】「人类可读 JSON 十年档案」是浪漫错觉，长寿靠契约不靠裸文件
- **攻击对象**：D1-26/D2-26/D3-14/D4-25/D5-18 的「人可读 JSON/Markdown 即十年档案」叙事。
- **反叛机制**：per-record 裸 JSON 没有 schema 迁移链、没有索引、没有读取器；十年后字段语义漂移、口径变化，人照样读不懂、更无法机器复用。真正长寿的是「格式契约 + 版本迁移器 + 可执行读取器」三件套，「人能直接打开」只是锦上添花，不是长寿保证。
- **成立条件**：把 formatVersion（备份已有）、逐版本迁移函数、独立 viewer 做成产品一等公民，任何旧版本数据经迁移器升到当前；档案信仰从「裸文件可读」转向「契约可迁移」。
- **触点**：现有备份 formatVersion/manifest、独立 viewer（D2-26）补迁移层；纯本地。
- **来源观察**：现状只有备份格式 manifest，无实体 schema 版本迁移；R3/§5 十年尺度被简化成「文件可读」，跳过了格式演化问题；D3-14 把 Markdown 升格真源尤其脆弱——Markdown  frontmatter 语义十年后同样会漂移。

### D4-R2-21 【反叛 C3】离线优先会葬送产品：默认在线、离线降级为容错而非信条
- **攻击对象**：C2 离线红线、ADL-036 奠定的「离线 CRUD 优先」基调，及池中 D1-20/D3-10/D5-17 的纯离线立场。
- **反叛机制**：离线红线把所有需要外部世界的价值——Git/MR 实时状态、公司日历、Jira 双向、客户可读页、手机查看——全挡在门外；单人练习场可以离线，真实 PM 工作一半发生在系统之间。应反过来：默认在线取外部状态、本地台账为真源、断网时降级为只读/排队，而非以离线为最高原则。
- **成立条件**：外部状态一律只读或出站草稿、不把外部数据当事实源；断网时写操作排队、恢复后同步；敏感台账本地不外发。在线是常态，离线是容错。
- **触点**：mcp-client、web fetch、R2-05 出站、R2-09 状态页；离线排队队列。
- **来源观察**：UX-11 两张皮的本质就是工作在系统之间、台账离线；personal-billing-plan 约束的只是 AI key，不支持把「离线」扩大成产品哲学；池中离线立场是从合规/免费车道历史约束里长出来的，被误当成了产品信仰。

### D4-R2-22 【反叛 C4】「PM 维护台账」本身才是该被消灭的问题，不是该被优化的流程
- **攻击对象**：整个「人录任务、勾清单、写周报」的产品前提（含第1轮所有围绕「更好录账」的接线）。
- **反叛机制**：让人天天录账、勾进度、写周报，是产品在伺候一个记账习惯，而不是消灭记账动作本身；终态是台账成为工作的自动副产品——对话、文件、提交、会议流自动投影成记录，人只做归类与判断，「维护」这个动作本身趋近于零。母本 D1-25/D2-16/D5-19 抽候选还停在「人确认入库」，本反叛要求确认也逐步退场。
- **成立条件**：证据自动捕获密度足够高（git/会话/语音/附件全管道，R2-06/R2-15）、投影准确率可观测（D5-22 采纳率）；当误投影率低于人可接受阈值，自动入库+事后纠错取代事前确认；产品价值在判断与取舍，不在记录。
- **触点**：session-query、workspace-changes、STT、自动投影+纠错流；provenance 事后补偿。
- **来源观察**：R1 断点本质是「工作发生了但台账不知道」，第1轮多数想法仍在让人把工作搬进台账；把方向倒过来——台账自己从工作里长出来。

### D4-R2-23 【反叛 C5】深双向绑定在单人场景反而对，「无主体所以轻融合」是伪顾虑
- **攻击对象**：R4 调用主体顾虑、及由它推出的轻融合/单向只读共识（D4-22/D5-16/D2-24 冻结面）。
- **反叛机制**：共识认为单人单机无主体所以只配轻融合；但正因为只有一个人，不存在跨人冲突、不需要 CAS、不需要冗余审批，深双向（台账↔会话 todo/goal/工作区目录）的协调成本结构性为零，风险也最低。「无主体」限制的是多人协作，却被错用成「什么都别接」。
- **成立条件**：单写者身份恒定；双向所有改动进可回滚事件流（D4-29）；每侧寿命分层标注（会话 todo 短命、台账长寿，单向镜像不污染）；深绑定的唯一真实成本是上游升级回归面，用独立内核（D4-23）隔离即可，而非因噎废食。
- **触点**：todo/goal 双向镜像、workspace 目录锚定（D2-34）、事件流回滚、pm-core 隔离层。
- **来源观察**：R4 原文顾虑是「多 agent 前提不成立」，被第1轮泛化成「单人不该接」；D5-20/D2-13/D2-33 已在试探单向镜像，本反叛主张单人下双向本就安全，轻融合是被多人协作恐惧症吓到的保守选择。

## A. 补漏（稀疏区新想法）

### D5-R2-01 估时校准 + what-if 日期情景模拟（补 A1：面向未来的规划智能）

- **机制**：任务在现有 `effortHours`（实际工时，已落地）旁加一个可选 `estimateHours`（开工前估的）；完成后本地统计「估/实偏差」按任务类型（拆解自标题/优先级）滚动出个人偏差基线；另做一个纯算术的 what-if 面板：拖动某任务的 dueDate，即时重算下游里程碑偏移与关键链 slack（复用 ADL-051 只读 CPM），只给「若 X 滑到 D 日，M2 将顺延几天」的数字，不做黑箱概率预测、不自动改期。
- **具体场景**：PM 估「登录风控 4h」，实际填了 9h；三个月后面板显示「同类联调任务平均高估 2.1 倍，下次可乘 2」；排期会上 PM 把某任务拖到下周三，面板立刻显示「M2 slack 从 3 天压到 0，进入关键链」，PM 自己决定要不要调。
- **触点**：纯本地派生（新增可选 estimateHours 字段、加法式 schema）；复用 `criticalPath(tasks)`（ADL-051，ES/EF/LS/LF/slack 已存在）、`effortHours`（task.ts L66）；不接模型、不预测。
- **来源观察**：池子几乎全是状态记录与回看（completedDate/completion-history/report-diff），无人碰开工前估时与向前模拟；task schema 只有实际工时无估算（changelog v0.7.4 补的是 effortHours 非 estimate）；ADL-051 明确把「自动排期/资源平衡」列为长期观望，what-if 只读模拟正好落在它划出的缝里。

### D5-R2-02 项目模板库 + 组合取舍视图（补 A2：项目组合层）

- **机制**：把一个结项项目「另存为模板」：只存 WBS 骨架（层级/标题占位/里程碑槽位/高发风险清单/交付物类型），不存人名与日期；新项目可从模板实例化，骨架落地后再改。组合层增加一个跨项目派生视图：按人汇总在手任务数、按季度汇总各项目健康灯与里程碑密度，给「这个季度是否同时开太多」的取舍参考数字，不自动砍项目。
- **具体场景**：做过三次「官网改版」后存成模板；第四次开新项目时一键带出 12 条骨架任务、3 个里程碑槽、4 条历史高发风险（如「第三方限流」）；组合视图显示「赵六手上 9 条、3 个项目同时有 at_risk 里程碑」，PM 自己判断推迟哪个。
- **触点**：现有 project/task/milestone/risk/deliverable 实体；模板存为独立只读 JSON（不进运行时七表或作为特殊 projectKind）；people-load.ts 聚合范式扩到跨项目。
- **来源观察**：池子无项目复用/模板概念（D2-17 dogfood、D1-29 方法论 skill 都是单次使用）；requirements 无模板实体；11 号协作契约已把 projectId 当真实归属边界，跨项目视图是现有数据的自然扩展。

### D5-R2-03 【反向写外部】经外部 MCP 把台账任务建成 issue / 卡片 / 日历事件（补 A3：从台账写向外系统）

- **机制**：与 D1-11/D2-30/D1-09 的「只读拉外部证据」反向——配好外部 MCP（GitHub/Jira/飞书项目/日历）后，台账任务可经 MCP 工具**创建**外部 issue/卡片/日历事件，结果回写任务的 `repoUrl/branch/evidenceUrl` 作为双向链接；创建动作仍是草稿→人确认→执行，外部系统失败回滚草稿、不留半截。
- **具体场景**：PM 在任务抽屉点「建到 GitHub」，草稿卡显示「将在 repo X 创建 issue《登录风控》，正文含验收清单」，确认后 issue 生成、任务上记下 issue 编号链接；里程碑目标日期可一键建成团队日历事件，团队在自己日历里看到排期。
- **触点**：`packages/mcp/mcp-client`（调外部 server 的写工具；现状池子里只用来读）；任务现有 repoUrl/branch/evidenceUrl 字段；草稿确认制复用 ask-apply 链路。
- **来源观察**：池子里外部系统全是只读回流（D1-09 webhook 读 PR、D1-11 读证据、D2-30 只读 GitHub），无一条向外写；D1-21 只导出 iCal/CSV 文件让别人消费，不等于主动建事件；UX-11「台账↔Git/Jira 两张皮」目前只在证据侧修补。

### D5-R2-04 会中实时捕获槽：边说边落候选，而非会后粘贴归纳（补 A4：会议实时辅助）

- **机制**：会议进行中，面板/侧边开一条常驻「捕获槽」：PM 边听边敲关键词或点选「决议/行动项/风险」标签，输入即进临时队列；会末不用从头归纳，队列里已是结构化候选，逐条 confirm 成 meeting 决议/行动项；支持拍白板照即贴（接 D3-18 附件）；全程不落正式库直到会末确认。
- **具体场景**：站会 15 分钟，PM 在捕获槽里敲「张三：周五前交登录接口｜风险：第三方额度未定」，随手拍白板照贴上；会末点「收尾」，队列两条已被预填好负责人/日期，PM 改两个字定稿，而不是会后对着空白纪要框回忆。
- **触点**：现有 meeting 实体 + meeting-summarize 解析纯函数（改为吃实时队列而非粘贴文本）；attachment 白板照；临时队列只在面板内存/草稿箱。
- **来源观察**：现状 R8 纪要、R15 归纳全是「会后粘贴速记/文件→模型归纳→confirm」（meeting-source 三来源：粘贴/文件/历史会议），会中那一刻是空白；池子里 D2-16/D1-25 是会后从会话日志抽，都不是会中。

### D5-R2-05 从 Jira / 飞书项目 / Excel 迁入与共存（补 A5：迁入与共存）

- **机制**：除现有 csv/markdown 导入外，提供 Jira 导出 CSV、飞书项目导出、多列 Excel 的结构映射器（列名→字段的可配置映射表，模糊匹配 title/assignee/dueDate/status），导入走 jobs 后台预览→confirm；共存模式：导入后保留外部链接字段，定期「对账」显示外部已关闭而台账仍 open 的漂移，不做实时双向同步。
- **具体场景**：离职前从老 Jira 导出 CSV，映射「Summary→title、Assignee→assignee、Due→dueDate」，预览 87 条、跳过 3 条重复后落库；两个月后对账视图列出「Jira 已 done 但台账 open 的 5 条」，PM 选择同步状态还是保留台账口径。
- **触点**：现有 csv-import.ts/task-import.ts 预览→confirm 链路；jobs 后台（D1-30/D3-23 已提批量导入后台化，本条补的是**外部格式与对账**）；纯本地文件读取，不直连 SaaS。
- **来源观察**：池子里 D1-30/D3-23 只讲「大批量导入走后台」，未讲来源格式与共存漂移；requirements R4 导出已支持，导入侧只有 csv/markdown；11 号契约刻意不做多人实时协作，对账视图比双向同步契合单写者红线。

### D5-R2-06 离开电脑：手机只读看板 + 文字确认回写通道（补 A5：移动端/离机场景）

- **机制**：借本地 MCP server（D2-27/D3-15/D4-20 已提被手机连）或一个极简 HTTP 只读端点，手机浏览器打开本项目健康灯/逾期/今日行动项；确认类动作（勾完成、批准草稿）通过一条经 dsh SDK/消息通道回传的文字指令完成，不做手机端全功能编辑。
- **具体场景**：通勤路上 PM 在手机上看到「2 条逾期、1 条待批草稿」，回一条「t-0007 完成」，到家打开 dsh 已落库；复杂编辑仍回电脑做。
- **触点**：本地 MCP server 只读工具面；`sdk`（D1-31 已提 JSON-RPC 借模型，本条补指令回写）；手机不直连 Coding Plan key（只读不调模型）。
- **来源观察**：D3-08/D2-27 只顺带提了一句「手机浏览器看静态看板」，无回写通道；billing plan 个人开发者成本敏感、场景多为单机；现状 dsh Web 只信任本机 loopback（KB-014），手机无原生入口。

### D5-R2-07 持续只读状态页：给领导/客户自助看的活看板（补 A6：对外持续形态）

- **机制**：与 D4-21「一次性静态 HTML 导出」不同，起一个本机只读 HTTP 端点（自己的极小 http 服务或 webServer 路由），按项目暴露一个免登录只读页面：健康灯、里程碑时间线、本期完成曲线、风险摘要；每次打开实时读当前台账（只读、无任何写控件），可局域网访问或临时生成带过期的分享链接。
- **具体场景**：领导每周不问 PM，自己打开那个地址看「官网项目绿灯、M2 已完成、本周完成 6 条」；页面数据永远是最新快照，PM 不用每周手动导出发邮件；客户侧只暴露指定项目、隐去内部风险细节。
- **触点**：本地只读 HTTP（注意 dsh Web 只信任 loopback、无局域网远程，故需自己的服务或临时隧道）；现有派生视图（health/reminders/completion-history）；只读不接模型。
- **来源观察**：D4-21 是导出瞬间快照发出去即脱钩；池子里无「持续可自助访问」形态；KB-014 指出 dsh Web 无局域网远程，对外分享现状无路，这正是状态页要解的。

### D5-R2-08 角色化 PMO 班底：风险官 / 史官 / 催办员 / 调度员四个常驻只读角色（补 A7：多智能体角色分工）

- **机制**：区别于 D4-18 一次性巡检、D4-28 虚拟 assignee、D5-07 单项目常驻副驾，设四个**角色固定、职责互斥**的轻量子代理，各自只产出指定类型草稿汇入同一个「收件箱」：风险官（每日扫概率×影响矩阵，只提新风险/升级建议）、史官（归档会议决议、周报定稿、结项提炼）、催办员（只整理「到点未动」清单，不发打扰）、调度员（只推演排期冲突与负载，不改日期）；人在收件箱统一批。
- **具体场景**：周一早上收件箱有四张卡片：风险官「R-0002 概率应上调为 high」、史官「上周 3 场会议决议已归档待确认」、催办员「2 条逾期 3 天未动」、调度员「M2 与 M3 资源撞车」；PM 一次清空，角色各自不越权。
- **触点**：subagent-spawn-in-process（按角色喂不同 system 边界）；只读工具面；provenance 账本记每条建议的角色来源；角色清单本身可在设置里开关。
- **来源观察**：池子的多智能体想法都是「一个通用子代理干一次」（D3-22 巡检、D4-18 审计、D5-07 常驻副驾、D4-28 仿真人），无角色分工与职责互斥；R4 主体存疑，但角色班底把「为什么要多个 agent」拆成了四个具体职责问题逐个验。

### D5-R2-09 认知安全：新鲜度戳、置信降级、模型说法与台账自动对账（补 A8：注入数据过期/误导）

- **机制**：所有注入模型的台账摘要/工具返回都带「快照时刻 + 距今天数 + 未覆盖实体数」三个元数据；模型回答引用具体记录时必须带记录 id；面板提供「对账」动作：把模型刚说的（如「t-0003 已完成」）与台账当前值逐条比对，不一致即标红；陈旧摘要（如超过 N 天未刷新）在上下文里自动降级标注「可能过期，需重查」，禁止模型把草稿当已落库事实。
- **具体场景**：模型基于两天前的注入摘要说「风险已关闭」，对账视图显示「台账里 R-0002 仍是 open，模型说法与现状不符」；草稿里被确认前的动作一律显示「未应用」徽标，模型不得声称已改。
- **触点**：buildAskContext（ask-copilot.ts）扩展元数据头；只读工具返回包一层 freshness envelope；provenance 账本的 applied/pending 状态作对账来源；纯本地。
- **来源观察**：D1-32 只讲注入预算/不挤压窗口，未讲数据过期与错误呈现；provenance-store 已有 confirmed/pending/applied/conflict/failed 状态，正是对账原料却没被用于「模型说法 vs 现状」校验；R2 机器可操作性的背面就是误导风险。

### D5-R2-10 仪式与疲劳治理：晨会三行、建议合并配额、草稿箱自动过期、提醒聚合（补 A9：行为/仪式层与失败模式）

- **机制**：正面定义仪式：每天首次打开面板生成「三行晨会」（今日到期/逾期/待批各取 Top），周报/站会有固定模板位；反面设计失败模式：建议合并（同类诊断气泡一轮只出一条，不刷屏）、建议配额（每会话最多 N 条、超了进折叠区）、草稿箱 TTL（7 天未确认的草稿自动归档并提示）、提醒聚合（N 条同类提醒合成一条「共 5 条逾期」而非 5 条通知）。
- **具体场景**：早上面板只有三行，不被 20 条建议淹没；一周后回草稿箱看到「3 条未确认已归档」，不会被旧草稿垃圾淹没；逾期提醒只在晨会出现一次，不整天弹。
- **触点**：现有 suggestion-engine（诊断气泡 kind 五类，D5 池里已存在）加合并/配额规则；reminders.ts 聚合；纯面板行为，不接宿主推送。
- **来源观察**：D1-24 是「极致沉默」的哲学极端，D4-26 同方向；但无人正面设计「建议疲劳/提醒噪音/草稿垃圾化」的具体失败模式阈值；ADL-039 打开即派生 + suggestion-engine 已经是建议源头，缺的是节流机制。

### D5-R2-11 【极端】完全吞并：pm-tool 内化自己的 agent runtime，dsh 对话循环被取代（补 A10 上半）

- **机制**：走到另一极端——pm-tool 不再借 dsh 的对话循环，而是内置自己的执行循环（自带 prompt 装配、工具调用循环、审批中断），dsh 只提供模型通道与存储；面板本身就是工作台，台账驱动的动作在面板内闭环，主对话沦为可选。
- **具体场景**：PM 不开 dsh 聊天窗口，在 pm 面板里直接让内置循环「把逾期任务重排、给我草稿」，循环在面板侧跑完、逐条批准；dsh 的 agent loop 与 pm 互不干扰。
- **触点**：反向于 D2-15（面板嵌对话），本条是面板自带循环；模型通道复用 LlmGateway（ai-client.ts）；存储仍走 PmDomain。
- **来源观察**：池子里融合方向全是「pm 进 dsh loop」（D1-01/D4-01 只读工具注册进宿主 loop）；无人考虑 pm 自己长一个 loop；R5 平台存在性的最激进形态即自我闭环。

### D5-R2-12 退出协议：dsh 原生长出项目管理能力时，本产品如何让位（补 A10 下半：被替代路线）

- **机制**：预先写好一条「退场路径」：检测宿主原生长出项目/任务能力时，pm-tool 转型为「导入器 + 审计器」——把本地台账一键映射成原生实体（迁移工具），并继续作为独立审计/历史层留在旁边；插件本身不与原生功能竞争，版本号停止加功能只修迁移。
- **具体场景**：两年后 dsh 原生带了任务面板，PM 点「迁移到原生」，七实体按字段映射过去，pm-tool 转为只读历史档案 + 迁移校验器；不存在「两套功能硬打」的尴尬。
- **触点**：现有 export/backup 格式作为迁移中间格式；11 号契约的开放字段位；不依赖宿主未来 API（迁移器按当时原生格式另写）。
- **来源观察**：池子全部假设 pm-tool 长期存在，无「宿主原生替代」预案；R5 平台存在性问的是离开 dsh，本条问的是被 dsh 吸收；开源/插件市场（D5-R2-13）也需要退场叙事。

### D5-R2-13 开源治理 / 插件市场发布 / 定价 / 「PM 方法论即产品」（补 A11：商业分发层）

- **机制**：三条并列分发路线：① 开源治理——core 以宽松协议公开、贡献者指南、版本/changelog 透明，单人先自用后公开；② 插件市场——按 dsh 插件打包规范（D2-28 已提 npm 包）发到可发现市场，profile 示例、截图、一句话定位齐备；③ 定价分层：内核/命令/离线 CRUD 免费，模板包、检查单、评分公式、汇报模板作为付费「方法论包」；卖点不是工具而是「一套被用过的 PM 做法」。
- **具体场景**：别人在插件市场搜到「单人 AI 项目管理台」，免费用核心，付费 9.9 买「独立开发者项目模板包 + 周报复盘模板」；方法论（怎么拆 WBS、怎么登记风险）与软件分离可单独卖。
- **触点**：D2-28 npm 包发布；D1-29/D3-16 方法论 skill 可商品化；personal-billing-plan 的成本红线（C2 免费额度、标准 API 计费）决定付费层不能烧模型。
- **来源观察**：池子商业层只有 D4-24（独立应用标准 API）、D5-23（留在 dsh 是合规选择）、D1-26（单机可读当卖点）；无开源治理/市场/定价/方法论产品化；requirements 与 billing plan 均未谈分发。

## B. 杂交（新机制，非并列）

### D5-R2-14 杂交 D4-05（workspace-changes 证据自动采集）× D2-12（全新 subagent 独立验收审计）

- **新机制**：D2-12 的审计员只喂标题+快照，D4-05 只回挂文件清单；杂交后：审计 subagent 启动时直接带上本轮真实 diff 片段与 present 产物清单，让它判断「证据是否足以支持完成」，结论引用具体文件/hunk 而非泛泛而谈；审计意见本身回挂为证据草稿，PM 确认后才标完成。
- **具体场景**：PM 想标 M1 达成，审计员不再只说「1 条任务无证据」，而是指出「t-0003 的 diff 只改了样式、未触及验收清单第 2 条要求的接口，证据不足」，并把对应 hunk 片段附在审计报告里。
- **亲本**：D4-05（session/event 聚合成 workspace-changes 证据草稿）× D2-12（全新进程内子级独立验收审计，无父历史）。
- **触点**：`ctx.workspaceChanges.summary/diff`；subagent-spawn-in-process 喂 diff 文本；provenance 记审计来源。
- **新在哪**：亲本一个只采证据、一个只看标题；杂交让审计结论建立在客观 diff 上，形成「采集→独立评判→回挂」闭环。

### D5-R2-15 杂交 D3-13（任务反向开工建会话）× D4-27（台账考核 agent 会话）

- **新机制**：D3-13 开工时自动把任务号写进会话初始上下文与会话元数据；会话结束后自动聚合该会话的轮次、workspace-changes 文件量、present 产物、feedback 评分，生成一份「本次执行报告」草稿回挂任务——把「任务发起会话」和「会话被台账考核」接成双向自动链，无需人工绑定。
- **具体场景**：点「开工」建的会话结束，任务抽屉自动出现执行报告草稿：「本次 8 轮、改 6 文件、完成清单 3/4、评分 4/5」，PM 确认后补进证据区；哪个任务空转（轮次多但零改动）自动标可疑。
- **亲本**：D3-13（抽屉点开工自动建会话带上下文）× D4-27（把 agent 会话当被跟踪资源、统计轮次/文件量/评分）。
- **触点**：sessions.create() 绑定 taskId 元数据；session-query + workspace-changes + feedback；执行报告草稿落任务 evidenceUrl。
- **新在哪**：亲本一个只管发起、一个只管事后统计；杂交让「发起→执行→被考核→回挂」自动成环，任务与会话的绑定不再靠人工挂关键词（对照 D2-19）。

### D5-R2-16 杂交 D1-24（打开时的差异回顾）× D4-30（备份目录即版本链 + 相邻 diff）

- **新机制**：D1-24 的「你不在的这段时间变化了什么」不再用内存快照对比，而是直接接 D4-30 的自动备份链，把上次打开时点对应的备份副本与当前台账做相邻 diff，差异回顾按实体分组（新增 N 任务/改了 K 字段/关了 M 风险），点开即看每处前后值；没开过备份链也能退化为内存对比。
- **具体场景**：两周没开，再打开首页就是一页基于备份链 diff 的「期间变更回顾」，而不是空白看板；误操作后可直接在同一页看到变更并回退到某份备份。
- **亲本**：D1-24（极致沉默、只靠打开时差异制造回顾）× D4-30（自动时间戳副本 + 相邻副本 diff 视图）。
- **触点**：core/backup.ts 自动副本；相邻 diff 复用 report-diff 口径；纯本地。
- **新在哪**：亲本一个有回顾哲学但无历史来源、一个有版本链但无主动呈现；杂交让沉默回顾有了客观 diff 地基。

### D5-R2-17 杂交 D1-29（PM 方法论 skill）× D4-19/D2-14（WBS 编译成 workflow DAG）

- **新机制**：方法论 skill 在 DAG 编译前加一道「可行性门」：skill 里写明哪类项目（调研/可并行叶子多/验收客观）适合扇出、哪类（强依赖串行/需人判断）禁止编译；编译前先过这道门给出「本项目扇出适配度」判断，不满足就退回普通清单，避免把不适合的 WBS 硬编译成 DAG。
- **具体场景**：PM 拿一个强串行的合规审查项目去「运行 DAG」，方法论门先拦：「本项目 7 条任务全是 FS 串联、无可并行叶子，不建议扇出」，只给出依赖顺序而不编译。
- **亲本**：D1-29（例会/周报/风险/WBS 方法论写成 skill）× D4-19/D2-14（WBS+predecessorIds 编译为 workflow 扇出 DAG）。
- **触点**：skill-filesystem SKILL.md；workflow 编译前的静态判定（读 predecessorIds 连通性/并行度）；不调模型也能算适配度。
- **新在哪**：亲本一个是静态手册、一个是直接编译；杂交让方法论成为编译的准入判据，而非事后参考。

## C. 反叛（攻击本轮池的明显共识：只读工具 + 审批 seam + 证据闭环 + 轻融合 + 独立内核 + 离线优先）

### D5-R2-18 反叛「只读工具是安全的半瞎陷阱」

- **主张**：共识把「模型只读、写全走审批卡」当成安全基石，但在单人单写者、无并发、无外人误操作的前提下，只读让模型永远在台账外面打转：它能看见却不能动，每一步都要 PM 转手批准，摩擦大于收益，最后沦为「模型说得对但落不了地」的半截体验。单人场景下，给模型有限写权限（限定白名单动作：勾完成、关已解除风险、挪自己建议过的日期）+ 自动留痕 + 事后一键撤销，比逐条审批更快，错误成本有 provenance 账本兜底。
- **成立条件**：① 确实长期单人单写者、无多端并发（11 号契约当前状态）；② 写动作白名单极窄（不含删除/不含改他人/不含改交付日期）；③ 每笔自动留痕可撤销、可回滚；④ 用 D5-R2-09 的对账保证模型不把草稿当已落库。任一条件破裂（多人、可删除、无撤销）则回到审批 seam。
- **触点**：挑战 D1-01/D2-07/D3-01/D4-01（只读工具族）与 D1-03/D2-08/D3-02/D4-02（审批 seam 共识）；provenance-store 的 undo 句柄与审计是反叛的安全网。
- **来源观察**：R4 调用主体存疑、R2 读写边界；单人场景下「审批」的防护对象（并发误写、外人篡改）根本不存在，防护成本却始终支付。

### D5-R2-19 反叛「人类可读 JSON 十年档案是浪漫错觉」

- **主张**：共识把「一份人类可读 JSON、十年后照样打开」当长寿信仰（D1-26/D3-14/D4-25）。但可读不等于可用：十年后没人会手工翻陌生目录里几百个 per-record JSON 文件，格式纯洁也挡不住语义腐化（字段名变了、口径变了）；真正长寿的不是存储格式，而是「定期自动导出为当时标准格式 + 附带可重建/可转换工具」，归档应主动放弃实时性、放弃继续被编辑。
- **成立条件**：① 接受「档案是死的快照，不是活库」，不再追求档案可写；② 结项/每年自动导出一份通用格式（Markdown/HTML/PDF 合集）+ 一份迁移说明；③ 把维护精力从「保持 JSON 纯洁」转到「可导出、可重建、可被新工具读」。
- **触点**：挑战 D3-14（Markdown 唯一真源）、D4-25（纯开放文件+静态查看器）、D1-26（10 年可读卖点）；复用现有 export/backup/office-to-pdf 做定期固化。
- **来源观察**：C5 可读可迁移被当成目的；ADL-041 备份恢复只解决「不丢」，没解决「十年后看得懂、用得上」。

### D5-R2-20 反叛「PM 维护台账本身才是该被消灭的问题」兼叛「离线优先哲学」

- **主张**：共识默认「人录入、人维护一本台账」是产品前提，离线优先只是存储约束；真正的低采用根源恰恰是手动维护这本账——没人愿意每天另录一遍自己刚说过/做过的事。离线优先被抬成哲学后，反而把「自动捕获」挡在门外。目标不该是让人维护一本账，而是让账从工作流里自动长出来（D1-25/D2-16 方向推到底），离线只是「数据落本地」的技术约束，不是「拒绝自动采集」的产品立场。
- **成立条件**：① 自动抽取候选 + 人只做确认/丢弃，录入动作趋近于零；② 离线约束只作用于存储（本地 JSON），不作用于捕获（会话日志/git/附件都是本地可得）；③ 确认制保留人对事实的最终签字，自动不等于自动落库。
- **触点**：把 D1-25/D2-16（被动捕获/自动投影）从「疯狂」提为默认形态；session-query/attachment/workspace-changes 全在本地可获，与离线不矛盾。
- **来源观察**：UX-11 两张皮、R1 证据断点本质都是「人要重复录入」；ADL-032 拒绝常驻 daemon 被泛化成了拒绝一切自动化；本条区分「常驻后台进程」（反对）与「本地被动捕获」（不反对）。

### D5-R2-21 反叛「独立内核 / 薄适配层」共识

- **主张**：D2-05/D3-07/D4-23/D5-14 一致主张抽零依赖 pm-core + 薄适配层。但单人维护、生命周期 2 年尺度下，多一层抽象（PmDomain 接口、后端注入、适配层）就是多一份自己维护的代码；上游真 break 时，直接贴合 dsh 重写接线，往往比养一个永不复用的内核便宜。独立内核是为「被多个壳复用」准备的，而复用场景目前并不存在——这是给想象中的需求付现实的维护税。
- **成立条件**：① 明确短期（1–2 年）不打算出第二个壳/第二个客户端；② 上游升级频率低、breaking 少；③ 一旦出现第二个消费端（MCP server/独立 App）再抽内核不迟，接口边界（11 号契约 PmDomain）现在先守住、物理拆分后置。
- **触点**：挑战 D2-05/D3-07/D4-23（抽 pm-core）、D5-14；保留 product/11 §一「域接口唯一边界」作为软约束，反对的是提前物理剥离。
- **来源观察**：R3 最小独立内核被当成默认答案； feasibility-map 主体一栏反复提醒「无主体的能力接进来维护成本由一人承担」，抽象层同理——无复用主体的抽象也是维护税。
