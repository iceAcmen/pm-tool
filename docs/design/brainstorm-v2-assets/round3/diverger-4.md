## S1 · schedule 到点轻提醒（D1-12 / D2-10 / D4-08）

### 【推最大】每个截止、每条依赖、每个临期里程碑都挂一条 schedule，全天候到点进会话
- **极端形态**：台账里每条带日期/前置的记录都自动生成定时器；工作日每 30 分钟扫一次，逾期即冒泡，临期 3 天/1 天/当天/每小时各触发一次；会话里随时插一条「t-0003 还剩 2 小时」。
- **判定：崩。** 推理链：①schedule 到期是作为普通 follow-up 消息进**原会话**，不是 OS 推送/邮件，dsh 没开/会话没活就投递不到，且每个重复任务只补发最近一次错过时点，人离开电脑两天，积压提醒要么只补一条、要么全丢；②免费车道约 50 次/天上限，每条提醒若走模型润色，一天几十条直接烧穿额度；③提醒密度超过人能处理的速率，进入「全部忽略」状态，提醒与没提醒等价。**边界条件**：只对 high 严重度、且人明确在场（会话活跃）时投递，才可能成立；一旦需要 host 常开、headless 环境，schedule 通道本身不可用（需 Web Session controller+持久化后端）。
- **变体 D4-R3-01【分级事件总线】**：提醒分两级——high（逾期/阻塞/里程碑撞期）才走 schedule 进会话；其余（P2 临期、普通到期）不挂定时器，只在人下次打开时由读时派生（ADL-039 现状）攒成一条聚合清单。定时器只服务「人不在场也必须知道」的少数事件，不服务台账全量。

### 【砍最小】只剩一条命令，零 schedule 接线
- **极端形态**：删掉所有定时器，人在会话里说「今天有什么到期」，一条只读命令纯函数算出逾期/临期列表返回；不注册任何 schedule_create。
- **判定：反而成立。** 推理链：现状 reminders.ts 本来就是读时派生、无常驻（ADL-039），砍到最小等于回到现状；单人单写者、自己定的截止自己记得，缺的只是「问的时候能立刻答」，一条命令足够。**成立条件**：人会主动开口问；若人不问就会忘，砍最小把「主动想起来」的责任全还给人。
- **变体 D4-R3-02【零定时器的纯问内核】**：把提醒能力压缩成一个无状态纯函数 `dueNow(records, now)`，任何宿主接线（schedule/面板/状态页）都只是它的不同外壳；内核本身不含时间、不含状态。

### 【倒置】定时任务被禁止：唯一触发是「人打开」，系统永不主动开口
- **极端形态**：产品宪法里写死「不注册任何 schedule、不主动投递」，所有到期信息只在人打开面板/发问时出现；把 ADL-039 的读时派生从「实现选择」抬到「产品禁令」。
- **判定：在短周期/天天在场成立，在长周期/人会离开时崩。** 推理链：倒置后系统零打扰、零 token、零依赖 host 常开；但项目跨月、人休假两周、或人本来就靠系统兜底记忆时，「不问就不知道」等于把遗忘风险完全转嫁给人。**成立条件**：项目周期短（周级）、人每天在场、无对外承诺节点；**崩的条件**：有外部 deadline、人会断联、需要被「推着走」。
- **变体 D4-R3-03【禁令式默认 + 单点例外】**：默认全禁定时器，只允许「硬 deadline 前 N 小时」一个例外槽，且该槽必须由人手动为单条记录显式开启，系统永不自动挂。

## S2 · 周期自动周报（D1-13 / D1-R2-19）

### 【推最大】每周自动生成、自动对账、自动落库，无人介入
- **极端形态**：周五 17:00 jobs 自动跑快照→narrate→承诺兑现表→session-query 痕迹，直接写入 reports 表并归档，草稿确认制也取消。
- **判定：崩。** 推理链：①周报的价值在「叙述与判断」，自动落库的是数字流水，无人读的例行公文；②自动落库绕过 ask-apply 确认，错误口径（calcVersion 不一致、证据不足 null）被固化进档案；③免费车道 50 次/天，narrate 调模型是固定成本，周周烧；④承诺对账需要人对「未兑现」做解释，自动版只会记「未兑现」不记原因。**边界条件**：只自动填数字栏、叙述栏留空等人写（D1-R2-19 本来就是这个姿态），自动落库是越界。
- **变体 D4-R3-04【无变化静默周报】**：周报草稿只在「本期有可量化变化（completedDate 新增/风险升降/里程碑变动）」时才生成；本期零变化则周五静默，只在计数页留「本周无变更，未生成周报」，不产出空文。

### 【砍最小】手动一条命令，无周期、无 jobs、无快照对比
- **极端形态**：`/pm report narrate` 当场读当前台账生成草稿，不存快照、不对比上期、不挂周期。
- **判定：反而成立。** 推理链：现状 collectProjectReport 数字是确定性的，narrate 只是包一层；砍最小丢掉的只是「上期承诺对账」这层增值，核心数字仍在。**成立条件**：人记得自己上周承诺了什么；承诺对账（D2-21）被砍掉后，自我承诺的连续性丢失。
- **变体 D4-R3-05【手动触发的最小周报】**：保留纯函数数字聚合，去掉 schedule/jobs/快照链，作为一条命令存在；周期与快照对比作为可选增强层挂在外面。

### 【倒置】写转拉：周报不由 PM 定时写，而由阅读方（leader/客户）拉状态页触发
- **极端形态**：PM 不写周报；领导/客户打开常驻只读状态页（D4-R2-09）自助看实时数字，周报这个产物被取消，「写报告」动作消失。
- **判定：在对内自助场景成立，在需要向上叙述/承诺时崩。** 推理链：数字可拉，但「为什么延期、下周打算怎么办」的叙述无法从状态页自动长出；倒置消灭了汇报负担，也消灭了向上沟通的固定触点。**成立条件**：阅读方只需要事实数字、不要判断；**崩的条件**：需要解释、承诺、对齐预期。
- **变体 D4-R3-06【拉取式数字 + 触发式叙述】**：状态页永远自助可拉（数字层），仅当 leader 主动问「本周怎么样」时，系统才把数字草稿推给 PM 补两句叙述，叙述不按固定周期生产。

## S3 · jobs 后台批量（D2-11 / D3-23）

### 【推最大】每个小动作都起 job，全后台异步
- **极端形态**：加一条任务、勾一个清单、改个日期都开 JobHandle，进拉取式输出环，完成发会话通知。
- **判定：崩。** 推理链：单人小量数据下，这些操作是毫秒级同步完成，起 job 的句柄管理、owner cleanup、通知环开销远大于收益；通知环每步都「完成了」，制造与 S1 同类的噪音；jobs 是为长任务（批量导入、全库重算）设计的，用在短任务上是大炮打蚊子。**边界条件**：只在操作预计超过阈值（如导入 >50 行、全库重算、跨项目巡检）时才升级为 job。
- **变体 D4-R3-07【阈值升级 job】**：同步快操作当场做完；仅当估计工作量超阈值（行数/实体数/跨项目数）才 spawn job，面板给进度环，完成一条通知而非每条通知。

### 【砍最小】不用 jobs，全同步，面板转圈即可
- **极端形态**：删掉 jobs 接线，导入/重算都在主线程同步跑，UI 转圈。
- **判定：反而成立（小数据量）。** 推理链：七实体本地 JSON、单人几十到几百条记录，同步计算无感知延迟；砍最小省掉 JobHandle/cancel/输出环/owner cleanup 整套机制。**崩的条件**：记录量涨到数百上千、或导入/重算真正需要秒级以上，同步会卡 UI。
- **变体 D4-R3-08【同步内核 + 可选异步壳】**：批量逻辑写成同步纯函数，jobs 只是可选包装；默认同步，量大时由调用方决定是否套 job。

### 【倒置】jobs 不是为「不阻塞人」，而是为「人不在场时也排队等着」
- **极端形态**：重新定义 job 的用途——不是并发提速，而是「人休假两周期间，批量导入/重算任务排好队，等人回来一次性执行」；job 面向缺席，而非面向并发。
- **判定：在异步批处理成立，在「无人时自动跑」崩。** 推理链：倒置把 job 从「并发工具」改成「待办队列」，逻辑自洽；但想让人不在场时自动跑，仍需 host 常开+持久化后端，schedule/jobs 在 headless/纯 SDK 不可用，无人值守自动执行的前提不成立。**成立条件**：job 只是本地排队、人回来再执行；**崩的条件**：期待后台自动完成。
- **变体 D4-R3-09【缺席队列】**：批量任务在 host 关闭期间只登记为待办项，host 下次启动时按序提示执行，不假装自己在后台跑过。

## S4 · 巡检 subagent（D4-18 / D3-22）

### 【推最大】N 个巡检 agent 常驻、高频扫全库
- **极端形态**：为每条风险/每个项目/每个团队派一个常驻 subagent，每小时扫一次，发现异常就出草稿；agent 数量随项目数线性增长。
- **判定：崩。** 推理链：①每次巡检都调模型，免费车道 50 次/天撑不住 100 个 agent 每小时扫；②单人单写者无多主体前提（R4），巡检发现的异常最终还是同一个人看；③大部分异常（逾期、临期、未关闭风险）是确定性规则，纯函数免费就能算，花模型钱巡检是重复付费；④常驻 subagent 的上下文随会话寿命/compaction 漂移，巡检口径不稳。**边界条件**：只对确定性规则覆盖不了的「语义异常」（承诺与实际措辞矛盾、风险措辞自相矛盾）才花模型。
- **变体 D4-R3-10【两层巡检】**：第一层确定性规则（逾期/临期/高影响未关闭/负载超阈值）免费秒出，不调模型；第二层仅当规则命中可疑项时，spawn 一次性只读 subagent 做语义判断，不常驻。

### 【砍最小】零 subagent，全部走确定性 suggestion-engine
- **极端形态**：不 spawn 任何 agent，巡检=现有诊断气泡（kind 五类）纯函数输出。
- **判定：反而成立。** 推理链：现状 suggestion-engine 已经在做规则诊断，砍最小只是承认「单人场景模型巡检边际收益低」；省掉 spawn-in-process 的进程与 token。**成立条件**：异常都能写成规则；语义模糊的洞察（这条计划不合理）被放弃。
- **变体 D4-R3-11【无 agent 巡检内核】**：把巡检抽成规则集合+匹配器，模型层是后期可选插件，内核零 agent。

### 【倒置】不是 agent 巡台账，而是台账「被动冒异常」，agent 不主动扫
- **极端形态**：取消主动巡检；系统不周期性扫描，异常只在「字段被变更、证据被补、承诺被做」的事件发生瞬间被检查并当场冒泡，无事发生即安静。
- **判定：成立。** 推理链：主动扫描的大部分发现是「本来就一直存在、只是这次又扫到」的陈旧异常，价值低；事件触发只对新变化反应，token 只花在变动上。**成立条件**：异常会随动作暴露；**崩的条件**：历史遗留问题（三个月前就没关的风险）不被动作触发，永远不冒泡——需靠 S11 的打开时差异回顾兜底。
- **变体 D4-R3-12【事件触发式巡检】**：检查挂在写动作之后（改期/关风险/标完成瞬间跑对应规则），无定时轮询；陈旧项由打开时一次性补扫。

## S5 · 里程碑独立验收审计（D2-12 / D5-R2-14 / D1-R2-17）

### 【推最大】每个任务每次状态变更都派全新审计 subagent
- **极端形态**：勾一条 checklist、标 in_progress 都 spawn 无历史审计员核对。
- **判定：崩。** 推理链：审计价值集中在「里程碑/交付达成」这一少数高价值节点，逐条审计把单位成本摊到最不值钱的动作上；全新无历史 subagent 每次重新喂快照，重复耗 token；审计员自身有误报率（D1-R2-17），高频审计误报总量被放大，人开始连审计报告都忽略。**边界条件**：审计只在「拟标达成/交付」触发，且用 D1-R2-17 履历给老误报项降权。
- **变体 D4-R3-13【节点审计 + 误报降权】**：审计 subagent 仅在人点「拟达成/交付」时一次性 spawn；审计结论写只增事件流，历史命中率高的检查项前置、老误报项自动弱化（D1-R2-17 履历机制落地）。

### 【砍最小】零审计 agent，人对照 checklist 自验
- **极端形态**：取消 subagent，里程碑达成时人自己逐条对验收清单/checklist，证据自己贴。
- **判定：反而成立（单人、验收客观时）。** 推理链：单人就是验收人，独立审计的「第三方视角」在单人场景缺少真正的独立性——审计员也是同一个模型、同一套台账；自验成本最低。**崩的条件**：验收标准含主观判断、或需要对外背书（向客户证明完成），此时独立视角才有增量。
- **变体 D4-R3-14【自验清单 + 可选背书】**：默认人对 checklist 自验；仅当里程碑对外（有客户/交付物）时，可选 spawn 一次审计员出背书报告，不默认跑。

### 【倒置】黑白反转：审计员不是挑毛病，而是主动为完成「找证据背书」，挑缺口只是副产物
- **极端形态**：审计员的第一任务变成「收集一切支持达成的证据并给出背书」，只在证据实在找不到时才标注缺口；角色从验收官变成吹鼓手。
- **判定：边界内成立，越界即崩。** 推理链：单人自验容易「觉得做完了」，一个主动找证据的角色反而能把散落证据收拢；但如果吹鼓手偏向性太强，会把证据不足也说成达成，丧失验收意义。**成立条件**：背书必须显式列出「已找到的证据 hunk/文件」，缺口单列且不可省略，证据不达标时背书无效；**崩的条件**：背书措辞压倒缺口标注。
- **变体 D4-R3-15【背书型审计报告】**：报告结构=「支持达成的证据清单（逐条引用 diff/hunk/会话）」+「未覆盖的验收项」两栏，前者为主后者必现，禁止只给结论不给证据。

## S6 · 四角色 PMO 班底（D1-R2-11 / D2-R2-09 / D5-R2-08 / D4-R2-10）

### 【推最大】四个常驻 agent 各配定时轮值、各自 spawn、草稿箱四分
- **极端形态**：风险官/史官/催办员/调度员全部常驻持久会话，各挂 schedule 定时扫，结果分四个收件区。
- **判定：崩。** 推理链：①4 个常驻 subagent × 定时扫描，免费 50 次/天远超；②四角色产出高度重叠（催办员的临期清单=规则，风险官的高影响未关闭=规则，调度员的负载冲突=纯函数 CPM），真正需要模型的只有史官归档叙事；③agent-team 是 experimental、无稳定性保证，常驻 roster 冷恢复口径未稳；④单人面对四份草稿，统一确认的摩擦高于自己扫一眼。**边界条件**：四个角色里三个是确定性视图，只留史官一个可选项。
- **变体 D4-R3-16【角色视图而非常驻 agent】**：风险官/催办员/调度员实现为同一只读引擎的四个筛选视图（纯函数），不养 agent；仅史官叙事可选一次性 subagent。「班底」是界面分组，不是四个进程。

### 【砍最小】一个草稿箱 + 人自己分四类，零角色 agent
- **极端形态**：取消角色分工，所有规则结果进同一个列表，人自己看出哪条是风险、哪条是临期。
- **判定：反而成立。** 推理链：单人项目量小，分类认知负担极低；砍最小省掉角色提示词、分触发条件、独立 spawn 整套结构。**成立条件**：项目数 ≤2、风险数 ≤10；项目组合变大（S7 多项目）时分类视图才有价值。
- **变体 D4-R3-17【单箱分组标签】**：单草稿箱内用轻量标签（风险/临期/负载/归档）分组，标签是派生字段，不对应独立 agent。

### 【倒置】班子管理真人，而不是给 PM 提建议
- **极端形态**：角色职能反转——催办员不是提醒 PM「自己的任务到期」，而是替 PM 去盯真人团队成员（谁逾期、谁该交什么）；风险官向真人发升级建议。
- **判定：单人场景崩，多人场景才成立。** 推理链：当前单写者、无真人成员，倒置对象不存在，班子空转；这也正好把 R4 主体问题逼出来——角色班底的真正舞台是未来多人协作，不是单人。**成立条件**：有真实可指派的成员、外部系统可触达（S2 出站写）；**崩的条件**：单写者。
- **变体 D4-R3-18【角色接口预留、单人空转】**：四角色先写成对「成员对象」操作的接口（当前成员只有 PM 自己），单人时班底自动空转不出稿，未来接真人时无需重构。

## S7 · workflow 扇出 DAG（D4-19 / D2-14 / D5-08 / D5-R2-17）

### 【推最大】所有 WBS 自动编译成可执行 DAG，agent 并行自动跑到底
- **极端形态**：一建项目就把任务树编译成 workflow，parallel() 扇出多个 agent 同时执行，pipeline() 串依赖，阻塞父级直到结算。
- **判定：崩。** 推理链：①单人无并行主体，扇出多个 agent 是自己跟自己并行；②强串行/需人判断的项目硬扇出，D5-R2-17 可行性门本来就要拦；③workflow 在 PTC Node 沙箱运行、阻塞父级，自动跑到底会耗尽额度且产出无人验收；④goal/budget 上限到了就停，停在中间态无人收尾。**边界条件**：DAG 只做依赖关系可视化，不执行。
- **变体 D4-R3-19【只读 DAG 视图】**：predecessorIds 编译成依赖图/阻塞链高亮（哪条被前置卡住），纯展示、零 agent、零执行；可行性门（D5-R2-17）作为「是否值得扇出」的静态判定先于任何编译。

### 【砍最小】静态 WBS 树 + 前置关系字段，无 workflow
- **极端形态**：不接 workflow，任务树和 predecessorIds 就是全部。
- **判定：反而成立。** 推理链：现状七实体已含树结构与前置字段，单人串行执行本来就不需要编排器；砍最小去掉模型编写扇出脚本、沙箱运行时整套。**成立条件**：任务在人脑中按序推进；**崩的条件**：多项目并行、需同时跟踪多条流。
- **变体 D4-R3-20【树即 DAG】**：把前置关系直接渲染为树的连线/阻塞角标，不引入 workflow 运行时。

### 【倒置】DAG 不由 PM 事前编译，而由工作实际发生顺序「事后长出」
- **极端形态**：不预先规划 DAG；系统从真实执行轨迹（git 提交先后、会话先后、证据挂接顺序）反推出实际发生顺序，再与计划树对照，画出「计划 vs 实际」偏差图。
- **判定：成立。** 推理链：事后真实轨迹是客观的（workspace-changes/session-query 已有原料），暴露的是「计划以为并行、实际串行」这类真实偏差，比事前编译更诚实。**成立条件**：执行留痕完整；**崩的条件**：无留痕或跨工具。
- **变体 D4-R3-21【事后实际 DAG 回放】**：结项时用完成记录/证据时间戳反推真实执行顺序，与计划树叠加成偏差视图，用于复盘而非指挥执行。

## S8 · goal 绑任务自动续行（D2-13 / D5-21 / D1-27）

### 【推最大】每个 P0 都挂 goal，goal-round-driver 自动多轮续行直到完成
- **极端形态**：所有高优任务绑持久 goal，驱动器自动开 round、调 agent、续行，无需人介入。
- **判定：崩。** 推理链：①自动续行在无人看时空转，轮次烧额度（免费 50 次/天）；②goal 是会话级短命对象，绑长寿里程碑会造成寿命错配（D5-21 实验后即弃的原因）；③续行停在 budget 上限，中间态无人收；④goal 进度只在会话内，回写台账会污染（D1-27 单向镜像就是防这个）。**边界条件**：goal 只挂「单轮可完成的叶子任务」，续行上限 1–2 轮。
- **变体 D4-R3-22【短叶 goal + 硬续行上限】**：goal 仅绑定单条可一轮完成的叶子，自动续行最多 2 轮即停并交回人；里程碑/长目标绝不挂 goal。

### 【砍最小】不挂 goal，人自己推进
- **极端形态**：取消 goal 接线，任务推进靠人在会话里直接做。
- **判定：反而成立。** 推理链：goal 解决的是「会话内聚焦、防止跑题」，单人主动发起的任务本就聚焦；砍最小去掉 create/pause/resume/complete/block 状态机。**成立条件**：单轮可完成；**崩的条件**：一个会话要拆多轮、需要保持目标不漂移。
- **变体 D4-R3-23【可选聚焦环】**：goal 作为人主动开启的一次性聚焦工具，不自动绑定、不自动续行。

### 【倒置】goal 从油门变刹车：偏离即停，而非驱动往前
- **极端形态**：goal 不再用于驱动续行，而是作为「偏离检测」——agent 每轮自报是否还在目标内，跑偏立即 pause/block 并交还人，goal 是停止线不是发动机。
- **判定：成立且与单人安全兼容。** 推理链：自动往前的风险是空转，自动叫停的价值是止损；刹车不需要连续驱动，token 成本低，且可与 auto-review 逐轮审查互补。**成立条件**：goal 描述明确可判定；**崩的条件**：目标模糊到无法判断偏离。
- **变体 D4-R3-24【刹车式 goal】**：goal 只做偏离守卫，命中偏离条件自动暂停并交回，不主动推进；保留 create/block/clear，去掉自动续行。

## S9 · 仪式卡 + 建议疲劳节流（D4-R2-12 / D5-R2-10 / D1-R2-13 / D3-R2-10）

### 【推最大】每分钟都有仪式槽，配额/阈值全调到最严
- **极端形态**：晨会三行、午间复检、下班收口、周报槽、里程碑仪式全天排满；建议配额 1 条/会话、草稿 TTL 1 天。
- **判定：崩。** 推理链：仪式本身变成另一个要维护的负担（仪式主义），三行晨会天天开却无事可报；配额调参地狱（1 条太紧漏掉关键，阈值随人漂移）；TTL 过短把还没来得及看的合法草稿清掉。**边界条件**：仪式只在「有异常可报」时出现。
- **变体 D4-R3-25【静默晨会】**：每日仪式槽默认不开；仅当存在逾期/阻塞/待批时才生成三行，无事则当天晨会缺失，系统不硬造内容。

### 【砍最小】无固定仪式，打开即看
- **极端形态**：删掉所有仪式卡/配额/TTL，人随时打开看现状。
- **判定：反而成立。** 推理链：与 S11 极致沉默同源，仪式是「外部节奏」，单人可自建节奏；砍最小零维护。**成立条件**：人有自己的工作节奏；**崩的条件**：人需要外部结构强迫自己回看。
- **变体 D4-R3-26【无仪式纯看盘】**：仪式层整体可关，只留默认看板。

### 【倒置】无消息本身被观测为信号：连续 N 天零变更触发一次回顾
- **极端形态**：沉默不再是「没发生事」，而是被计量——连续 7 天台账零变更，系统主动给一条「项目静默一周，是否停滞/遗忘」的提示；沉默是要被报告的异常。
- **判定：成立，补 S11 短板。** 推理链：极致沉默只回顾「变化」，变化为零时反而盲；倒置把零活动也当信号，捕捉「项目被遗忘」。**成立条件**：项目本应活跃；**崩的条件**：项目本就是等待期/冬眠期，会误报。
- **变体 D4-R3-27【静默停滞探针】**：可配置项目预期活跃周期，连续 N 天零变更触发一条停滞提示；等待期项目可标记冬眠豁免。

## S10 · 自适应沉默 / 低采纳自静默（D2-R2-17 / D3-R2-14）

### 【推最大】采纳率驱动一切，样本极小也立即降频/静默
- **极端形态**：每条建议记录采纳与否，近 3 条采纳率低就静默，实时调整所有建议频率。
- **判定：崩（冷启动误杀）。** 推理链：①新建议还没被看到，小样本采纳率无意义即被静默；②采纳率低可能是「当时时机不对」而非建议无价值，静默后永不恢复；③自我静默后模型/人都不知道它还存在，等于功能消失。**边界条件**：冷启动保护期 + 静默≠删除 + 严重度升级强制冒泡。
- **变体 D4-R3-28【保护期 + 可唤醒静默】**：新类建议先给固定保护期（如首 10 条）不参与降频；静默只压「主动投递」不删除记录，人可在设置里手动唤醒；严重度升到逾期/阻塞时无视静默强制冒泡。

### 【砍最小】一个全局开关（全收/全静），零学习
- **极端形态**：不要响应历史、不要采纳率、不要降频曲线，设置里只有「接收建议/关闭建议」。
- **判定：反而成立。** 推理链：单人偏好稳定，一个开关覆盖 80% 需求；砍掉本地计数、反馈闭环、阈值调参。**成立条件**：人愿意自己拨开关；**崩的条件**：人懒得调，希望系统自己懂。
- **变体 D4-R3-29【二态开关内核】**：自适应层全部外置，内核只暴露 mute/all 两态。

### 【倒置】采纳率高反而沉默，被反复拒绝的才换方式再提
- **极端形态：因果反转**——最常被采纳的建议默认人已经在做，系统少打扰；被连续拒绝的同类建议，系统换一种表达/时机再试一次，而不是永久静默。
- **判定：反常识但局部成立。** 推理链：奖励「已经做好的事安静」，把注意力预算留给「一直被拒、可能是表达错了」的项；但永久不重试也会漏掉真不需要的项。**成立条件**：拒绝附带简单原因（不需要/时机未到/已完成），系统据此换方式而非消失；**崩的条件**：拒绝无原因，系统无法区分「拒错」与「不需要」。
- **变体 D4-R3-30【奖励安静、重试被拒】**：高采纳类降频至背景；被拒类带一个「重试配额」（同类最多换 2 种表达），仍拒则永久归档；与 D4-R3-28 保护期互补。

## S11 · 极致沉默哲学（D1-24 / D4-26）

### 【推最大】彻底零信号、零常驻、零推送，连打开时差异回顾都关掉
- **极端形态**：产品完全被动，连两次快照差异都不对比，人看到什么就是什么。
- **判定：在短周期天天在场成立，长周期/人离开时崩。** 推理链：推到绝对被动=零打扰零成本，但两周休假后回来，没有任何「期间变化/我落下什么」的线索，项目靠纯记忆；D1-24 的差异回顾正是为了救这个，连它一起关就把唯一的被动信息源也丢了。**成立条件**：项目周级、人每天在场；**崩的条件**：跨月、断联、外部承诺。
- **变体 D4-R3-31【被动回顾保留为唯一出口】**：极致沉默只禁主动投递，保留「打开时基于备份链的差异回顾」（D5-R2-16）作为唯一信息回流，这是沉默哲学的安全网，不可一并砍掉。

### 【砍最小】沉默本身已是最小，无需再砍
- **判定：成立。** 推理链：零接线、零定时器、零常驻 agent，是本簇的最小可行形态；它证明了 PM 工具可以不依赖任何主动能力存在。
- **变体**：无新变体（母本即最小）。

### 【倒置】沉默不是「功能缺失」，而是出厂默认宪法；提醒都是 opt-in 的申请来的特权
- **极端形态**：把沉默写成产品第一原则——默认一切安静，任何提醒/推送/主动建议都必须由人逐条申请开启，系统从不默认替人开。
- **判定：成立，且是 S1/S9/S10 的总开关。** 推理链：把「主动」从默认翻成例外，所有噪音问题在宪法层消解；需要提醒的人自己申请，产品不赌大众偏好。**成立条件**：申请成本低（一键）；**崩的条件**：默认全静让新用户以为产品没有提醒能力。
- **变体 D4-R3-32【沉默宪法】**：产品默认态=全静默；schedule、建议投递、仪式槽、PMO 出稿全部为 opt-in 显式开关，设置页把「默认安静、按需开启」写成首条说明。

## S12 · PMO × jobs 轮值 × inbox 汇流（D4-R2-16）

### 【推最大】四角色按 jobs 轮值表 7×24 跑，inbox 实时汇流
- **极端形态**：排一张角色轮值时间表，jobs 定时唤醒风险官/史官/催办员/调度员，草稿实时进共享 inbox。
- **判定：崩。** 推理链：轮值表本身要维护；jobs/schedule 需 host 常开，headless 不可用；7×24 在单人空转，token 与通知双重消耗。**边界条件**：轮值改为「打开时按需当场跑」。
- **变体 D4-R3-33【打开即轮值】**：取消 jobs 定时轮值，人打开 inbox 时当场按角色规则跑一遍（确定性部分免费，史官可选），出稿即清，零常驻零表。

### 【砍最小】inbox 只是一个列表，无轮值无汇流结构
- **判定：反而成立。** 推理链：汇流的价值是集中确认，单列表即达成；砍掉轮值调度。
- **变体 D4-R3-34【单清单收件箱】**：所有草稿无角色分区进一列表，确认动作统一。

### 【倒置】不是人收建议，而是建议自己按严重度投票排队，人只看 Top1
- **极端形态**：inbox 不按到达顺序列，而按严重度×新鲜度自动排序，只把最该处理的一条顶到最前，其余折叠；人不做分拣。
- **判定：成立。** 推理链：单人确认精力有限，排序省掉分拣动作；排序是纯函数（严重度/逾期天数/未覆盖证据），不调模型。**成立条件**：严重度字段可靠；**崩的条件**：多条同级重要，Top1 机制漏掉次优。
- **变体 D4-R3-35【Top1 收件箱】**：inbox 默认只展开最高优先级一条，其余折叠为「还有 N 条」，人处理完自动降下一条。

## S13 · 冲刺三段链：沙盘→goal→审计（D4-R2-17）

### 【推最大】三段全自动：沙盘选任务、goal 自动驱动、审计自动通过，人只签字
- **极端形态**：what-if 沙盘自动选出冲刺任务，goal 自动续行执行，审计自动判定达成，人只在末尾签字。
- **判定：崩。** 推理链：三段各自的判断（选哪条、跑偏没、够不够格）在单人全自动下无人兜底；goal 空转（S8）、审计误报（S5）、沙盘假设无人拍板，链条把三处风险串联放大。**边界条件**：每段收口都留人批准，自动只做准备不做决定。
- **变体 D4-R3-36【三段备料、人做三个决定】**：沙盘备候选、goal 备驱动、审计备报告，三个收口决策全留人，链条只减少准备工作不代替判断。

### 【砍最小】只留人推 goal，沙盘/审计去掉
- **判定：反而成立（小冲刺）。** 推理链：单任务冲刺不需要沙盘推演和独立审计；砍最小回到 S8 形态。
- **变体 D4-R3-37【按需插拔三段】**：沙盘/goal/审计是三个可独立插拔的配件，按冲刺大小选用，不强制成链。

### 【倒置】验收先于计划：先审计现状缺口，再定沙盘，最后才立 goal
- **极端形态**：冲刺顺序反过来——先派审计员盘点「现状缺什么、证据差什么」，据缺口做沙盘选补项，最后才立 goal 去补；从「计划→执行→验收」翻成「验收→计划→执行」。
- **判定：成立且反常识合理。** 推理链：先看清缺口再选目标，避免为不存在的缺口排期；单人下这是诚实的自审顺序。**成立条件**：审计能给出明确缺口清单；**崩的条件**：从零开始的全新项目无现状可审。
- **变体 D4-R3-38【缺口先行冲刺】**：新冲刺启动第一步=现状缺口审计，第二步沙盘围绕缺口选任务，第三步立 goal；全新无现状项目跳过第一步。

## S14 · 三态副驾：同一常驻 agent 换帽子（D2-R2-15）

### 【推最大】一个常驻 agent 长期记项目全历史，辅助/审计/考核三态随阶段自动切换
- **极端形态**：常驻子线程长期存活，平时辅助、里程碑切审计、月底切考核，共享同一上下文。
- **判定：崩。** 推理链：常驻上下文随 compaction 漂移，长期记忆口径不稳；辅助态的偏见会传染给审计态（D2-R2-15 自己也强调审计要独立视角，同一主体换帽子削弱了独立性）；常驻 token 持续成本；experimental 形态无稳定性保证。**边界条件**：三态各用全新无历史 agent，只共享喂进去的快照。
- **变体 D4-R3-39【无共享上下文的三态】**：辅助/审计/考核三次调用各起全新 subagent，只喂当前快照，防止辅助偏见污染独立审计；「同一主体换帽子」被「三个独立视角」取代。

### 【砍最小】三态都用一次性 subagent，无常驻
- **判定：反而成立。** 推理链：一次性 spawn 成本低、无漂移、无偏见；常驻唯一优势「记得历史」在单人台账里由确定性快照替代。
- **变体 D4-R3-40【一次性三视角】**：需要哪态当场 spawn 哪态，快照由台账喂，不留常驻。

### 【倒置】去共享：三个 agent 互不知晓，人自己综合，而非一个 agent 内部切换
- **极端形态**：取消「同一主体」，辅助员/审计员/考核员互不通气、各自独立出稿，由人在主线程综合三份意见。
- **判定：成立，独立性最强。** 推理链：独立视角不共享偏见，代价是人要综合；单人综合成本可接受。**成立条件**：三份草稿都短；**崩的条件**：意见冲突时无人裁决（单人即裁决人，故不崩）。
- **变体 D4-R3-41【三独立稿 + 人裁决】**：三态并行独立出稿，主线程人对照裁决，系统不替人做一致性合并。

## S15 · 任务→会话→证据自动闭环（D1-R2-16）

### 【推最大】到点自动开会话、自动干活、自动回挂 diff、自动标完成
- **极端形态**：任务到期 schedule 自动开会话，agent 自动执行，结束自动把 diff 挂回并标 done。
- **判定：崩。** 推理链：无人在场时空转；证据被当成完成（D5-R2-14 审计的必要性）；自动标完成绕过确认；host 不开则到点无会话；免费额度被自动会话消耗。**边界条件**：自动只到「开会话+收证据草稿」，标完成留人。
- **变体 D4-R3-42【半自动闭环】**：到点/手动只自动开会话并在结束时收 diff 证据草稿，「附证据+确认完成」必须人点；自动只搬运，不判定完成。

### 【砍最小】手动点开工，单步，无自动串联
- **判定：反而成立。** 推理链：D3-13 手动开工建会话已是现状；砍掉 schedule 触发与自动回挂，证据人自己贴。
- **变体 D4-R3-43【单步开工】**：保留手动开工，证据回挂作为可选一键动作。

### 【倒置】会话找任务，而非任务找会话：结束时会话反向认领它服务过的任务
- **极端形态**：不预先把任务绑给会话；会话结束时由 session-query 反查本轮内容，自动匹配它可能服务的任务，提出「本轮是否服务 t-0003」的认领候选，人确认后挂证据。
- **判定：成立，补绑定难题。** 推理链：反向认领避免「开工时人工挂任务号」的漏绑；匹配是只读+草稿，人确认。**成立条件**：会话内容含任务号/关键词；**崩的条件**：一轮跨多任务，认领歧义（此时出多个候选等人分）。
- **变体 D4-R3-44【会话反向认领】**：会话结束生成「本轮疑似服务任务」候选列表（FTS5 按任务号/关键词匹配），人确认绑定后回挂证据，免除事前人工绑定。

## 压测中反复出现的边界条件（供后续轮次取用，不评分）
1. **host 常开依赖**：schedule/jobs/自动轮值都需 Web Session controller+持久化后端，headless/纯 SDK/关机期间全部失效；这是「推最大」类想法最集中的崩点。
2. **免费车道 50 次/天上限**：任何「N 个常驻 agent × 高频扫描/自动续行/自动会话」组合先在此撞墙；确定性规则是免费替代层。
3. **单人主体（R4）**：多角色/多 agent/并行扇出/班子管真人在单人单写下空转，它们的真实舞台是未来多人。
4. **会话寿命错配**：goal/常驻 subagent 是短命对象，里程碑/项目是长寿对象，绑定即漂移。
5. **冷启动与样本**：采纳率自适应在小样本/新类上误杀，需要保护期与可唤醒。
6. **自验独立性幻觉**：单人下「独立审计」独立性有限，背书/自验/三独立视角是不同补法。
