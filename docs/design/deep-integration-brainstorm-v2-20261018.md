> 方法：两名问题校准者（A、B）在互不可见、无交流条件下独立产出（原文

## 0. 两独立校准者的共识与分歧

**高度共识（两人独立得出，互不可见）**：



1. 「深度融合」是一个**手段（且是程度词）被当成了目的**：命题规定了动作与程度，没有规定要消除的具体问题、成功后的可观测状态、以及不融合时的替代解。

2. **供给侧清单 ≠ 需求侧证据**：宿主能力多，只能证明「可选项存在」，不能推出「缺项值得补」。

3. 存在**生命周期 / 归属错配**：宿主 plan/goal/todo/session/jobs/deliverables 多为「会话级、agent 拥有、随对话生灭」；pm-tool 七实体是「跨会话、人拥有、长寿、落盘可 git」。两类状态双向深绑存在类别错配。

4. 已记录的 UX 断点（树打散、排期、概览、人员负载等）**全部由本领域数据 + 纯前端解决**，无一需要宿主未用能力；唯一未被面板内改进解决的是「台账↔Git/MR/ 群 两张皮」（UX-11），而它的解也不一定在宿主侧。

5. 现状源码事实：agent 对话循环与台账**完全隔绝**—— 全仓无 `ctx.tools.register` / `defineTool`、无任何 `ctx.on(...)` 事件订阅；面板唯一写通道是 `remote.commands.execute(sessionId, '/pm ...')` 命令字符串、唯一读通道是一次性全量 snapshot；`sessions` 只被借作命令投递句柄；AI 只是 `/pm ask` 一次性草稿，不进 agent loop。

**互补而非分歧的差异**：A 偏重「断点坐标定位 + 调用主体」，B 偏重「时间尺度穿透 + 成本 / 平台归属」。两份 reframing 合并为同一组根问题（见 §4）。

## 1. 原命题复述（中立事实）



* **谁**：单一当前使用者 —— 字节在职 PM（所有者本人），单人、本机（macOS）、单写者；数据目录有真实录入（约 84 个 JSON 记录）。演进身份：离职后以个人开发者身份维护自用，成本敏感（个人单机月锚 ¥40 Coding Plan + 本地 Ollama 兜底）。被动相关方：研发 / 协作方不登录本工具，台账任务最终要落到他们的 Git/MR/ 群。

* **处境**：pm-tool 已到 v0.7.4，七类业务实体（项目 / 任务 WBS / 里程碑 / 风险问题 / 会议纪要 / 进度快照 / 交付物）+ 人员负载、甘特、关键路径、健康分、客观进度、备份恢复、HITL AI 草稿、测试 / CI 均已落地；内部增量 backlog 已清空，剩余为结构性长期项（常驻推送、生产 Key、多设备 / 多人、上游升级、外部 skill 毕业），其中没有一项以「融合宿主能力」为既有解法。

* **现状接入面**：Host 必需依赖 `commands` + `storageDomain`；`llm` 运行期懒读、无 Key 走中文 NO\_LLM 降级；存储 = storage-domain + storage-json（人类可读 JSON、可 git）；Web 独立面板经 client slot 注入；**无模型工具注册、无事件订阅、无会话读取**。

* **命题字面**：从「服务级接入 + 上下文级隔离」走向更多使用宿主 session/context/plan/goal/jobs/schedule/mcp/subagent/workflow 等能力。

* **命题未声明**：为什么而融合、融合指什么、成功长什么样、不融合的替代解。

## 2. 利益相关者与核心场景



| 相关方          | 关系                                   |
| ------------ | ------------------------------------ |
| 在职 PM（本人，当下） | 唯一用户、唯一维护者、唯一决策者；一人同时是用户 / PM / 研发   |
| 个人开发者（本人，未来） | 维护者 + 用户；约束变为 AI 成本合规、单人长期可修         |
| 研发 / 协作方     | 不登录、不操作；被服务对象；其真实工作（Git/MR/ 群）与台账零联动 |
| dsh 上游       | 只读依赖，开发者预览期，明示未来将有破坏性变更              |

核心工作流（已落地）：立项拆 WBS → 排期 / 甘特 / 关键路径 → 例会纪要与行动项转任务 → 周期快照与 AI 叙述草稿 → 风险问题跟踪 → 交付物验收留痕 → 开面板派生逾期 / 临期提醒、跨项目人员负载、全局检索；`/pm ask` 一次性诊断 + 草稿、确认落库。

## 3. 目标 / 约束 / 成功标准 / 决策用途

**阶段 0 目标**：把未定义动作「深度融合」拆解为可被确认 / 否决的问题陈述与根问题空间，供发散阶段覆盖、供后续对抗论证。

**硬约束（不可违背）**：



* C1 纯探讨不改代码；上游只读。

* C2 离线优先：结构化增删改查无 Key 必须可用，生成能力在线增强、失败降级。

* C3 草稿确认制：AI 写库先草稿、人显式确认才落库。

* C4 单用户本地、单写者，不做实时多人。

* C5 人类可读 JSON、可 git、可迁移、可逆。

* C6 上游 alpha 明示破坏性变更；耦合越深升级回归面越大。

* C7 仅承诺 Chrome；不引入常驻后台进程 / 系统推送（ADL-032/039 已裁决）。

**可证伪成功标准（方向级，先定检验形式）**：



* 消费方命题：能计数真实使用（agent 循环实际读台账 N 次、结果被人采用 M 次）；N≈0 即证伪。

* 正确性命题：AI 读写建议被接受 / 拒绝 / 纠正比例可统计，低于阈值则该形态不成立。

* 约束不破：无 Key 下既有七实体 CRUD 与面板可用率 100%，融合层不得阻断。

* 成本 / 寿命：上游一次 breaking upgrade 后，融合层修复工时可记录并与独立层对比；融合层修复面系统性更大则「融合提效」被削弱。

* 价值命题：上线前后 PM 手动维护台账的条数 / 耗时可基线测量；无下降则价值证伪。

* 禁止以「体验更好 / 更深度 / 更一体化」作为成功条件。

**决策用途**：阶段 0–2 确认「方向空间无明显遗漏」后，进入对抗论证，最终决定与宿主关系的类别（继续轻耦合补面板内完整性 / 选择性接少数能力 / 重新评估平台归属 / 其他）。

## 4. 锁定的问题空间：五个根问题（R1–R5）

> 它们是待回答的问题，不是五个方案方向；发散想法可回答任意一个、跨多个、或不属于任何一个（「不属于任何一个」的想法尤其保留）。每个根问题标注「深度融合」在该问法下的地位。

**R1・断点坐标与「计划↔执行证据」闭环** — PM 在本机完成一次真实项目动作时，哪一步仍需在工具间搬运信息或重复录入？断点位于台账内部、台账↔宿主对话之间、还是台账↔宿主之外的系统（Git/MR/ 群 / 会议）？PM 写下的计划与真实执行证据（commit/MR/agent 轮次 / 会议）如何对账，证据从哪捕获、以什么形态回台账（草稿 / 只读链接 / 不回）？



* 开启的空间：外部系统对齐（Git API、MCP 外部服务器、人工链接）、面板内部路径优化、对话可达性；宿主集成只是候选通道之一。

* 「深度融合」地位：断点在外部或面板内部时，融合不是答案；schedule/mcp/session 日志 /git workspace-changes 都只是「捕获证据的管道」，并列评估。

**R2・对话读写边界与机器可操作性（消费方存在性前置）** — 宿主 AI 对话循环在什么条件下可读台账、在什么条件下可起草修改、人始终是最终裁决者？哪些操作必须留在显式命令、不进对话？更前置：是否存在「agent 在无人逐次指示下依据台账自主完成 PM 动作并被人接受」的真实场景？若有，需要严谨的机器可操作接口（schema、权限边界、HITL 契约、可校验输出）；若没有，工具注册 / 上下文注入就没有消费方。



* 「深度融合」地位：部分相关（接口契约、授权），但接 session 历史 /subagent/workflow 与该问题无必然关系；本质是「接口多严谨」而非「融合多深」。

**R3・寿命 / 归属分层与最小独立内核** — 哪些 PM 事实必须长寿且人有（落盘台账），哪些天然属于短命 agent 拥有的临时状态？在「数据寿命 × 归属人」轴上，层与层之间允许什么方向的流（单向投影 / 只读引用 / 事件单向广播 / 禁止双向绑定）？抛开 dsh，pm-tool 的最小独立内核是什么，哪些宿主依赖一旦建立就破坏离线 / 可读 / 可逆 / 可升级四条原则？



* 「深度融合」地位：双向深绑大概率不成立，融合深度本身是受约束变量而非越大越好。

**R4・调用主体（无人使用的能力不接）** — 以所有者本人单机、离线、单写者的真实条件，宿主未用能力里有哪些根本没有调用主体？subagent/workflow/mcp/ 遥测 / 多人 / 常驻 jobs 的设计前提是多 agent、多会话、外部工具网络或团队；无主体的能力接进来后，维护成本由一人承担、收益侧为空。



* 「深度融合」地位：清单被裁掉大半，融合需先证明主体存在。

**R5・平台存在性（dsh 是否是 PM 工作的正确容器）** — 为什么 PM 台账要活在 dsh 里，而不是独立应用？宿主提供的不可替代项是什么（AI 通道？Web 壳？运行时？分发？），哪些只是「恰好在此」？留在 dsh 是有意选择还是沉没成本 + 计费合规（¥40 / 月、脱离即需标准 API）的合理化？



* 「深度融合」地位：可能整体被降级为「当前运行时的临时接线」，问题可能从「怎么融合」变成「去留」。

## 5. 时间尺度穿透



* **3 个月**：面板自身完整性（看板、9 视图重设计、视觉基准、prod Key 稳定性）最重要；现有痛点均由本领域解决，「深度融合」是分心。

* **2 年**（离职、个人开发者）：可维护性、AI 成本合规、上游存活与兼容最重要；单人维护者没有精力为每次 breaking change 修补深层耦合；「深度融合」只在被重新定义为「刚好够用的轻量合规接线」时条件性成立。

* **10 年**（数据资产、平台必然更替）：长寿记录如何在宿主消失后仍可读可迁移最重要；与当前这版 dsh 的具体对接在该尺度不存在，深度绑定是迁移负债。

* 结论：「深度融合」只可能在 2 年尺度的窄窗口、且被重定义为轻量接线后成立；把条件性、窄窗口的手段升格为产品方向，是本命题最需要检验的跳跃。

## 6. 问题边界

**在范围内**：根问题空间与方向探索；现状 / 宿主能力事实核验；断点、消费方、寿命、主体、平台归属的论证。

**明确排除**：多人协作（11 号契约另案）、客观进度 v0.8（既定迭代）、模型成本 / Key 选型（另案）、上游升级回归（工程事项）、vendored skill 治理（另案）、视觉令牌 / 视图重设计（面板内打磨）、具体功能选型与路线图（后续阶段）。

## 3. 五人高度趋同的 5 条反叛（阶段 3 必须重点论证的候选命题）

> 它们是 5 名发散者在互不可见条件下独立提出、随后被多人强化的对产品现状信条的反叛，直接挑战既有裁决（C2/C5/C3/ADL 等），但发散期不适用证据制度，成立与否全部留待阶段 3。



* **反叛 a（写边界）**：单人单写者下「只读 + 每步审批」是半瞎陷阱 —— 没有第二双眼睛，审批是橡皮图章。成立形态可能是「窄白名单直写 + 事后审计抽查 + 可撤销事件流」，只有高风险动作才拦截审批。（K2 张力轴）

* **反叛 b（档案长寿）**：「人类可读 JSON 十年可读」是浪漫错觉 ——schema 会漂移、JSON 没有渲染器、十年后没人找到当初的解释。长寿靠的是固化渲染成品（PDF / 静态站）+ 格式契约与迁移器，而非裸文件纯洁。（K16 张力轴）

* **反叛 c（在线立场）**：离线优先作为信条葬送产品 —— 应默认在线取外部能力、离线降级为容错而非设计中心。（K14 张力轴，与 C2 直接冲突）

* **反叛 d（录入本体）**：该被消灭的是「PM 维护台账」这件事本身 —— 录入趋近零，台账从会话 / 痕迹自动投影，人只做例外裁决。（K4 主张，同时是 C3 草稿确认制的边界问题）

* **反叛 e（独立内核）**：抽独立 pm-core 是伪独立、提前付维护税 —— 抽象应后置到出现第二个真实客户端；真正可移植的是开放格式而不是代码。（K14 张力轴）

## 4. R3 极端化反复暴露的成立 / 崩点边界（阶段 3 攻防素材，已在池内逐条留痕）



1. schedule/jobs/ 自动轮值需 host 常开（Web Session controller + 持久化后端），headless / 纯 SDK / 关机即失效；

2. 免费车道约 50 次 / 天上限且模型随机、function-calling 不保证（KB-034），常驻 agent× 高频扫描先撞墙 —— 确定性规则是免费替代层；

3. 单人主体（R4）下多角色 / 多 agent / 并行扇出 / 班子管真人空转，真实舞台是未来多人；

5. 采纳率自适应在小样本冷启动误杀，需保护期 + 可唤醒；

6. 单人下「独立审计」独立性有限，背书 / 自验 / 三独立视角是不同补法；

7. undo 句柄 TTL 仅 10min / 最多 3 条 / 一次性 / 重启失效（provenance-store.ts L28-29），接不住事后撤销；

8. dsh Web 只信本机 loopback（KB-014），状态页 / 手机无公网入口；

9. 单写者无 CAS/rev，任何双向同步 / 多端写崩；

10. webhook-github 是 experimental 且 [localhost](https://localhost) 无公网入口；

11. 估时校准同类样本 N<10 是噪声、沙盘无工作量数据是日历幻觉、预测前 6 周方差无信息。

## 2. 淘汰方案附录（撤并/撤除/归并，各含四段）

### 2.1 K5 会议流三段捕获（会前应读包/会中槽/会后 60 秒认领窗）

- **原方向**：会前按议题聚合历史决策/未决项的应读包；会中当场捕获槽（含本地 STT）；会后 60 秒认领窗，取代会后空白回忆。

- **撤并去向**：会前包→K1 时间触发变体；会后会话内认领→K4 候选箱同一机制；分段 STT→meeting-summarize 输入方式；会中槽、连续监听、STT 自动 owner、60 秒硬窗前两轮已放弃。
- **不推荐理由**：剥离后 K5 名下无独立机制、无独立 schema/命令/视图，不满足「独立方向需不可被相邻方向吸收的机制增量」（E4）；FTS5 可选挂载边界由承接方 K1 承担，残留为零。

### 2.2 K10 多 agent 角色组织（PMO 四角色班底/常驻副驾/巡检/考核 agent）

- **原方向**：PMO 四角色班底、常驻副驾、巡检 agent、考核 agent；对立极是角色退化为纯函数筛选视图、一次性 spawn。
- **致命攻击**：C-K10-01 常驻班底/副驾在宿主运行时内无可挂常驻载体（C7 禁常驻，致命）；C-K10-02 四角色在单人空台账上无产出对象，且同读一份数据导致结论重叠，多角色独立性来自独立信息集而非进程隔离（E2，致命）。
- **撤并去向**：4 项新规则集（①里程碑偏差趋势 ②风险超期 SLA 未处理 ③跨周期承诺未闭环 ④已完成但缺证据）并入规则方向承载（②依赖 slaDays 字段，现有 risk-issue schema 无，随并入补或借 dueDate 近似）；低频 spawn 作可选插件 E6 登记，接入 K3 外部证据后才产生第二信息源。
- **不推荐理由**：放弃常驻班底/副驾/三独立稿/考核/预埋后，唯一含 agent 的成分为低频可选 spawn，规则扫描全部纯函数完成，独立方向机制增量不成立（E4）；H3 日常跑会话解除 N≈0，但不解除「无独立信息集」与「无第二被考核对象」。

### 2.3 K15 商业与生态分发（npm 市场/开源治理/分层定价/方法论即产品/preset 打包）

- **原方向**：npm 市场发布、开源治理、分层定价、PM 方法论即商品、preset/skill 打包；对立极是开源履历路线与套餐即商业模式。
- **致命攻击**：K15-01 付费分层在合规层与技术层同时空心化——各持 key 则作者对 AI 消耗无收费权，代持/转售套餐额度违 personal-billing-plan §1.1 红线，方法论文本零边际成本、无 DRM、MIT 允许再分发，付费墙不可闭合（致命）；K15-02 无已核验公开插件市场、npm 包从未发布（package.json private、npm view E404、无 LICENSE/CONTRIBUTING），渠道第一环缺失（致命，E1 Taylor et al. 2020 arXiv:2003.03471 npm 长尾旁证）。

### 2.5 K20-X4 对外举证/法务证据链（第三方可采信/法定留存/不可篡改/独立出示）
