K2 写边界

自主度光谱：本期只点亮第 3 档

五档从「人只写」到「全自治」连续排列。第一期只开放「AI 限内直写」一档中的窄集 2 项；第 4 档（规则自批）、第 5 档（全自治）不开放，第 2 档（AI 提议、人点确认）为现状 ask-apply 路径，保持不变。

L1 人只写 所有写动作由人在面板完成，现状基线。 现状
L2 AI 提议 · 人确认 ask-apply 草稿流：人点确认即即时落库，provenance 记已应用历史。 现状保留
L3 AI 限内直写 · 本期 服务端双层闸放行窄集 2 项，落库留痕、可事后撤销。 本期开放
L4 规则自批 需 approved-pending 持久批准队列建成后评估，本期挂起。 挂起
L5 全自治 越过 C3 人裁决，第一期不开放，扩界须另行论证。 不开放

第一期字段级白名单（类型闸 + 字段闸双层约束）

类型闸回答「这是哪类动作」，字段闸回答「该动作允许改哪些字段」；两层缺一不放行，未知/非允许字段直接拒收。标完成、状态流转、排期、依赖均不在白名单。

白名单动作允许修改的字段集明确拒收的字段状态
① 纯文本 / 备注修改 notes / description（字段级白名单内的自由文本） status、progress、dueDate、predecessorIds、assignee 开放
② 补挂证据链接 evidenceUrl / repoUrl（单链，max 2048） 标题、状态、排期、归属、依赖 开放
③ 采纳已批草稿落库 —（无服务端可验的已批准持久状态） 整体动作本期不放行，回 L2 人点确认即时落库 挂起
标完成 / 状态流转 — 完成判据归 K6，状态机写全部留人裁决 移出白名单

闸门演示：三条 agent 动作样本（点击运行观察判定）

样本为虚构示例。判定顺序：先类型闸（动作枚举 ∈ 白名单），再字段闸（载荷字段 ⊆ 允许集）；任一层拒收即退回 L2 人裁决草稿，不静默落库。

样本 A · 备注补写（合规） action=update-notes · target=t-118
notes「与研发确认评审窗口改到周四下午，待补会议纪要。」
类型闸通过 · 字段闸通过 · 限内直写落库

动作类型 ∈ 白名单，载荷仅含允许字段 notes；落库成功并写一条 provenance（kind=auto-whitelist-write），本人可在台账记录上事后撤销。

provenance: auto-whitelist-write · t-118.notes · 2026-10-18 14:02 · 可撤销
样本 B · 夹带排期字段（类型过、字段拒） action=update-notes · target=t-118 · 夹带 dueDate
notes补充备注正文（允许字段）
dueDate改为 10-25（非允许字段，类型闸看不出）
类型闸通过 · 字段闸拒收 · 退回人裁决草稿

类型层「改备注」合法，但载荷夹带非允许字段 dueDate；字段闸整体拒收，不部分落库。动作转 L2 草稿流，由人决定是否修改排期，模型声明「只是顺手」不作放行依据。

样本 C · 第 3 项「采纳已批草稿落库」（挂起拒收） action=apply-approved-draft · 无队列记录
声明模型侧称「该草稿已被人批准」，但服务端查不到 pending 队列项。
无持久批准事实 · 拒收 · 回 L2

现状 ask-apply 确认即即时落库，provenance 仅记已应用历史，不存在「已批准未落库」队列；规则只重放 status=pending 且未过期的队列项，模型侧「已批准」声明不作放行依据。

挂起后续件 · approved-pending 待落库队列（本期不开放，待用户拍板）

队列建成前第 3 项保持挂起，第一期 2 项不依赖它。放行唯一依据是服务端持久队列记录，而非模型声明；落库成功转 applied，过期惰性转 expired。队列快照与当前白名单一致性、惰性过期时机为实现口径。

边界与残留登记

1. H5（期望 agent 代执行）与 C3（保留人裁决）的张力未由用户一锤定音，直写扩界须阶段5 再论证；
2. 字段集随实体 schema 演进同步维护（局部）；规则异常检测只能覆盖已枚举模式，新模式落在盲区，扩界前需补规则（局部）；
3. 第一期直写限定为即时可核验、错误可手动重填的低风险写；错误补偿事务后置，一旦扩大直写范围须先补补偿层；
4. 本页为设计原型，全部条目为示例数据，不调用生产 API。
