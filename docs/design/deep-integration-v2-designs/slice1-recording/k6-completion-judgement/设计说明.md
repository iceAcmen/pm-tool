# K6 完成评判层 · 设计说明

> 裁决档位：**修正采纳（L1 并入 due/health；L2 寄生 K3/K4）**｜推荐组合内（依赖 K3/K4 原料，排其后）｜证据等级：E5（`core/reminders.ts` overdue/due-soon、`core/health.ts`、状态机现状）+ E4（未覆盖≠未完成、不下完成裁决）
> 原型：`原型.html`（示例数据；含 L1 派生表、L2 待命占位/缺口清单切换；浅/深两态）

## 1. 该方案改变了什么

**场景改变**：回应 H4（自己判断是否完成不准），但把「评判」收敛为两层、且都不下完成裁决——完成与否的裁决权始终在人（C3）。

**结构改变（L1 并入、不另建体系）**：
- 现状 `reminders.ts` 已派生 overdue/due-soon，`health.ts` 已给项目健康灯；K6 **不新建完成评分/状态机/独立评判引擎**（B6-K6-01 否决项）；
- L1 只补 **2 条净增纯函数规则**并入既有 due/health 派生列表：①到期未动（过 dueDate 仍 todo、无进展/改期痕迹）；②承诺日期与状态机不符（原料来自 K4 留痕）；两条都只是「提示」，不自动改状态。

**L2 寄生而非独立**：
- 一致性复核、证据否证、缺口清单全部以 K3 证据原料、K4 承诺原料为输入；上游未落地时保持待命占位，不凭空生成结论；
- 输出边界 = 一致性 + 缺口，**不背书完成、不下完成裁决**；
- 「未覆盖 ≠ 未完成」：只说明本次原料里没看到对应证据/承诺，不等于判定没做完；
- 重复缺口合并为一条持续项，按出现期数升级提示等级；同源叙述（present 声明与会话自述）不作互证。

**交互改变**：L2 初始为待命空态，模拟原料到达后才展开缺口清单，清单每条只列事实缺口，无「判定完成/未完成」按钮。

**视觉改变**：既有派生项与 K6 净增规则用 chip 区分（existing / new）；缺口清单用持续项编号 G1–G3；「未覆盖≠未完成」用 warn callout 固定在 L2 区内，防止被读成裁决。

## 2. 采用的专家方法

- **design-human-ai-workflow**：AI 只做「retrospective review（事后复核）」，不做 decide（裁决）；缺口清单是可撤销的观察，不是结论；异常态（原料未到）安全空转。
- **review-product-plan**：可核验性收敛为纯函数规则（L1）与可追溯原料（L2），不引入模型打分；非目标（不评分、不背书完成）显式写出。
- **ux-ui-audit**：区分「观察/提示」与「裁决」两种语义，界面不给后者留按钮，避免用户误读为自动验收。

## 4. 残留与待补

- 依赖：L2 启动以 K3/K4 本机样本进入为前提；规则②的承诺日期原料来自 K4 留痕，K4 未启用时该条不派生。
