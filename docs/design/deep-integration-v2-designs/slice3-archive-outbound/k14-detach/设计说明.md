# K14 宿主解绑独立形态 · 设计说明

## 终局定位
- **台账判定**：饱和（本期零投入登记）；裁判 A「采纳（本期零投入登记；格式层消费 K16 快照，合并单元评估）」；裁判 B「条件性采纳（本期登记件，零投入）」。
- **推荐档位**：**登记层（零或低主动投入）**，不进本期路线图；与 K16 作为单一交付单元合并计分，不分别计分、不重复计功。

## 设计前提（事实 / 假设 / 推断区分）
- 事实（E5 本机/一手）：插件 `inject = ['commands','storageDomain']`，`llm` 懒读；core 层存在大量无 I/O 纯函数（health / derived / people-load / completion-history / report-diff / progress-derivation）；备份为带 manifest 的人类可读 JSON（`core/backup.ts`）。
- 用户假设（H9，E5 用户确认版）：有意留在 dsh，2 年尺度 API 稳定为**用户预期而非上游保证**；H7 默认在线、C2 解除，离线信条权重下调。
- 设计推断（E4）：无验收标准的工作项不可完成、不可关闭——登记件必须带完成态与复查触发，否则与「不做」无法区分。
- 红线：不得把 H9 的稳定预期写成上游承诺；不虚构 MCP server / 独立 App / 换壳交付物；系统内核类只展示用户可见的登记项、控制与证据出口。

## 改变点（相对现状）
1. 在设置区新增一条**登记项**（非新页面、非新视图）：「独立形态 · 韧性保险」，当前状态=登记中、本期零投入。
2. 登记项内固化两项**未来完成态**：①脱离成本清单（可独立模块/适配点数量/迁移工作量）；②导出快照在脱离 dsh 环境独立打开的验证。
3. 固化两个**复查触发**：dsh 不可用信号（停更/弃用/API 破坏）或年度例行，二者其一启动重估；不预写常驻监测器。
4. 「生成脱离成本清单」按钮为未来态，触发未满足前禁用并给原因，避免登记件被误读为进行中任务（anti-zombie）。
5. 显式声明依赖方向：K14 格式层 ← 消费 K16 固化快照；K16 收缩/延期则 K14 同步不独立交付。

## 采用的专家方法
- product-design §4 经验模型：把「未来选项」建模为登记件 + 完成态 + 触发条件（intent/condition/completion），而非功能队列。
- ux-ui-audit 证据纪律：区分 observed（现状纯函数可抽）/ inferred（保险价值在风险发生时兑现）/ unknown（脱离概率 E6），未虚构收益数字。
- design-human-ai-workflow 责任分配：本期「人不动作、系统不动作」，触发后才进入人主导的核对，无自动化承诺。
- 视觉：沿用 dsh 中性板（近黑主按钮、#4868b2 链接、灰阶层级、8/12px 圆角、4 的倍数间距），浅深两态均为独立定义的 token，非反色。

## 与攻防结论的关系
- R2-D-K14-01（无完成态/复查点易成永久挂起）：由「完成态两项 + 两个触发 + 禁用未来按钮」闭合。
- R2-D-K14-02（与 K16 跨候选耦合、不可独立关闭）：由「单一交付单元、依赖方向单向、合并计分」闭合。
- 首轮已撤回项（全量抽七实体内核、自建 MCP server、独立 App、通用多客户端、静态站直读活目录、CLI 写面、双壳）不在原型中出现。
- H11 收窄：通用多客户端前提不成立（有阅读受众、无实时多写协作），仅余导出格式小增量，由 K16/K18 承载。


## 验证结果（shot.py 实测）
- 浅态 desktop/mobile pass（blocker0/error0）；深色态 pass；禁用未来按钮、登记件三行表、两触发卡渲染正常，无文字溢出。
