# K18 对外接触面 · 设计说明

## 终局定位
- **台账判定**：采纳（出站写单向只增；外部为唯一事实源；两类日志；分受众只读导出）；裁判 A/B 一致采纳。
- **推荐档位**：**核心层（纳入本期最小交付）**；H11（存在外部团队/朋友/公开阅读受众）下，只读导出/状态页是重点。

## 设计前提
- 用户假设（H11，E5 用户确认版）：外部受众为团队/朋友阅读与汇报分发；示例数据须显式标注虚构，禁止真实业务数据/生产 API。
- E6 悬空：具体目标平台（GitHub/Jira/飞书等）名称与 MCP 可用性待核验，原型用「目标平台（待核验，E6）」占位，不写死。
- 攻防事实（R2-D-K18-01）：双向同步承诺不成立——外部为唯一事实源，本地镜像必然过时、误导决策。
- 攻防事实（R2-D-K18-02）：审计只增流与动作已发日志保留期不同，合并会让长期审计被日常噪音淹没。

## 改变点
1. **分受众只读导出/状态页**：技术读者 MD（含 ID/枚举/依赖，可解析）、非技术在线增强档（状态色+一句话进展，无写操作）、纯文本兜底（无格式依赖）；导出时刻冻结，不随活库刷新。
2. **出站写单向只增**：任务卡留静态关联位「已发 #编号」；发出后不拉回外部状态、不双向同步；失败留痕无伪成功。
3. **两类日志分置**：审计只增流（长期保留，含已发/已撤回/失败）；动作已发日志（TTL，到期折叠归档），不合并。
4. 事实源边界明示：外部系统是自身状态唯一事实源。

## 采用的专家方法
- design-human-ai-workflow：出站动作由人触发（演示按钮），系统只负责留痕与失败可见，不自动代表用户对外承诺。
- ux-ui-audit：失败态（不可达）与撤回态都在审计流可见，不留静默成功。
- product-design §4：分受众对应三种成功条件（可解析 / 可阅读 / 任何环境可打开），共用同一冻结快照。
- 视觉：三档导出用 tabs 切换预览，避免建三套页面；日志状态用语义色 + 文字双编码（不仅靠颜色）。

## 与攻防结论的关系
- R2-D-K18-01（双向同步被拒）：由「外部唯一事实源 + 静态关联位」闭合。
- R2-D-K18-02（两类日志合并被拒）：由分置 tabs 与不同保留期闭合。
- 撤回项：活看板实时镜像、双向状态同步、拉回外部评论/时间线、自动汇报日历。


## 验证结果（shot.py 实测）
- 浅态 desktop/mobile pass；深色态 pass；三档受众 tab、单向出站静态位、两类日志（已发/已撤回/失败）、事实源边界正常。
