# 01 · 产品现状 & 用户画像复盘

> 本文回答两件事：「这个东西现在到底做到哪了」和「我们究竟在为谁解决什么问题」。给接手的产品/研发/编码 Agent 看，3 分钟建立全局正确认知，避免凭标签臆测。

## 一、一句话定位

**dsh-pm-tool** 是跑在 DeepSeek Harness（dsh，「一切皆插件」的 Cordis 架构）之上的一个**离线优先、单用户、本地文件持久化**的项目经理工作台插件。它不改上游源码，以独立插件包 `packages/dsh-pm-tool/` + 专属 `pm` profile 的方式挂载；数据是人类可读的 JSON（dsh `storage-domain` + `storage-json`），可 git 管理、可迁移、可备份。

它不是「又一个 Jira」，而是 **dsh 这个 LLM 智能体框架里的一个 PM 外挂**：结构化台账完全离线可用，只有 WBS 生成 / 汇报叙述 / 会议纪要归纳这类「生成型」动作才调模型，且一律先出草稿、确认才入库。

## 二、产品形态与技术骨架（读代码确认）

- **宿主**：dsh Web UI（http://127.0.0.1:3080）。本插件通过 `clientBundle` 注入一个**顶级面板**，稳定入口是左侧栏「项目管理」。
- **为什么主用面板而不是斜杠命令**：宿主限制——首页斜杠补全**不显示第三方 `/pm` 命令**，发送后主区**不自动跳转到面板**（ADL-038 / KB-037 / ISS-026）。所以 `/pm xxx` 命令面虽全，但**真实操作都发生在 Web 面板**。这一点是后面所有 UI 评估的前提。
- **前后端通道**：面板只有一个 RPC `execute(line)`，把面板动作翻译成 `/pm <子命令>` 字符串；初始化时一次 `web snapshot` 拉全量七实体 JSON 到浏览器内存，之后所有派生（提醒、看板、全局搜索、概览）都在**前端基于 snapshot 计算**，不额外请求。

```
面板(React, panel.tsx 2619 行)
  └─ execute("/pm task update t-1 {..}")  ← 唯一写通道
  └─ execute("web snapshot")              ← 唯一读通道（全量快照）
        ↓
commands/*.ts → core/*.ts → storage-domain 表（projects/tasks/milestones/risk_issues/meetings/reports/deliverables）
```

## 三、七张业务表（数据实体，读 zod schema 确认）

| 实体 | 表名 | 关键字段 | 生命周期/枚举 |
|---|---|---|---|
| 项目 Project | `projects` | name/owner/status/startDate/targetDate/tags | planning·active·paused·done·archived |
| 任务 Task（WBS 节点） | `tasks` | parentId/title/assignee/status/priority/startDate·dueDate/progress/milestoneId；自动 `code`(1.2.1) 与 `order` | todo·in_progress·blocked·done；P0/P1/P2 |
| 里程碑 Milestone | `milestones` | title/targetDate/status/achievedDate | planned·at_risk·achieved·missed |
| 风险问题 RiskIssue | `risk_issues` | type/概率/影响/应对(responsePlan)或解法(solution)/owner/dueDate/status | risk·issue；open·monitoring·closed |
| 会议 Meeting | `meetings` | title/meetingDate/主持人/记录人/参会人/议题/决议/summary + 内嵌 `actions[]`(行动项，可挂 taskId/riskIssueId) | draft·final；行动项 todo/in_progress/done/cancelled |
| 进度汇报 Report | `reports` | 周期 + **冻结 snapshot**(任务/里程碑/会议计数+异常项) + 人工摘要/已完成/下期计划/阻塞 | draft·final；快照不随后续数据漂移 |
| 交付物 Deliverable | `deliverables` | name/version/status/location/dueDate + **只增不改的变更历史 history[]** | planned·in_progress·submitted·accepted |

另有两张系统表：`checks`（自检）、`settings`（自由键值，如 AI 车道模式）。领域版本固定为 **v1**，layout=per-record，每实体一个 JSON 文件。

## 五、目标用户画像（国内一线 PM）

> 注意：requirements 里写的目标用户是「项目经理，含非纯技术背景」，MVP 单用户本地。我们的评估以此为准，但要还原国内一线 PM 的**真实一天**。

### Persona A：交付型项目经理（主力，占比最大）
- **背景**：互联网/软件公司，背 1–3 个并行项目，带研发/设计/测试小团队，常夹在业务方和研发之间。
- **一天**：早上看「昨天谁卡了、今天谁要交」→ 站会过任务状态 → 午前写周报/向上汇报 → 随时记风险问题 → 下午拉会出纪要和行动项 → 下班前盯交付物验收。
- **核心焦虑**：①「到底有没有要炸的地方我没看见」；②「周报别让我从零写」；③「会上说的事别到下周没人跟」。
- **对本产品的期待**：打开面板 10 秒内能答「现在最该盯哪三件事」。

### Persona B：项目负责人 / PMO（多项目视角）
- **背景**：同时管一组项目，要向 leader 报盘子整体健康度，要做资源（人）调配。
- **核心焦虑**：①「张三是不是过载了」；②「这几个项目哪个要延期」；③「跨项目的风险有没有共性」。
- **对本产品的期待**：一个跨项目的健康/负载视图，而不是一个个项目点进去看。

### Persona C：非技术 PM / 新手上手者
- **背景**：不写代码，但要维护这套台账。
- **核心焦虑**：界面别让我填命令、别藏太深、空了知道下一步干嘛。
- **对本产品的期待**：纯鼠标、少出错、有 AI 帮我起步。

### Persona D（被服务但不直接操作）：研发/协作方
- 不直接登录本工具，但 PM 的任务状态、交付物、行动项最终要落到他们的日常（代码仓库、MR、群里）。
- **当前断点**：本产品台账和他们真正干活的地方（Git/MR）完全脱节——这是后面「代码仓库联动」颠覆性方向的由来。

## 六、当前产品的「心智模型匹配度」快照

| PM 心智动作 | 产品现状 | 匹配度 |
|---|---|---|
| 立项/建项目 | ✅ 完整 CRUD + 面板切换 | 高 |
| 拆 WBS（分层看任务树） | ⚠️ 有父子与编号，但 Web 表格**按状态分组打散了树** | 低（见 02-UX-01） |
| 排期/看时间安排 | ❌ 只有两个日期文本列，无甘特/时间线 | 缺 |
| 盯进度/抓风险 | ⚠️ 提醒条有，但点了不直达；概览很薄 | 中 |
| 例会→纪要→行动项→转任务 | ✅ 闭环已通（含 AI 归纳、转任务） | 高 |
| 写汇报/向上报告 | ✅ 快照+AI 叙述，可编辑落盘 | 中高 |
| 交付物验收留痕 | ✅ 四态 + 变更历史 | 高 |
| 跨项目/跨人协同 | ⚠️ 有总览看板，但无「按人」视图 | 低 |
| 与代码仓库联动 | ❌ 完全没有 | 缺 |
| AI 辅助日常 | ⚠️ 三个一次性固定模式，非对话式 | 中 |

> 结论先行：**台账骨架（增删改查 + 七实体闭环）已经很扎实，短板集中在「看」和「连」——可视化排期、跨人/跨项目透视、以及与研发日常的联动。** 这正是 02~05 文档要解决的。
