# 04 · 颠覆性创新构想（功能 + UI）

> 增量方案是「把现有的事做得更顺」，本节是「换一种产品形态」。判断标准：是否利用了本产品**独一无二的禀赋**——它跑在一个 LLM 智能体框架（dsh）里，手里又握着七实体的结构化台账。多数 PM 工具（Excel/Trello/飞书项目）缺这两样的交集。
> 这些方向多数需要**架构演进**（新表 / 领域 v2 / 外部桥接），与增量方案分开排期。

---

## 构想一：AI 项目副驾（Conversational PM Copilot）—— 最值得做的颠覆性方向

**现状的天花板**：现在 AI 是「三个固定按钮」（拆 WBS / 写周报 / 记纪要），PM 得先知道自己要用哪个按钮、填什么输入。

**颠覆性设想**：把整个工作台变成一个**可对话的副驾**。PM 用自然语言下达意图，副驾读全量 snapshot、给结论、并把「要改的东西」做成草稿让 PM 一键确认。

它能回答/能做的事（举例）：
- 「**这个项目下周三前会不会延期？风险最大的三件事是什么？**」→ 副驾综合任务进度、逾期、临期里程碑、未关闭高影响风险，输出一段诊断 + 直接在概览标出这三项。
- 「**谁过载了？帮我把王五手上两个低优任务挪给赵六**」→ 先分析跨人负载，再把「挪任务」做成确认草稿（批量 `task update`）。
- 「**帮我把这周周报按公司模板写好**」→ 自动汇总本周完成/阻塞/下周计划，出草稿。
- 「**上周会议决议里那条『做登录风控』跟进了吗？**」→ 反查 meeting action → task 状态，闭环回答。

**为什么这是颠覆而非修补**：从「PM 操作台账」变成「PM 问问题、AI 起草、PM 确认」。台账是 PM 唯一事实源，AI 只是读它、写草稿——完全契合现有「草稿→确认入库」范式，风险可控。

**UI**：顶栏保留 AI 按钮，但抽屉从「三模式」升级为**底部一个对话输入框**，上面是消息流；每次副驾要动数据，都渲染成一张「操作草稿卡」（影响 N 条任务）+ [确认执行]。
```
┌─ AI 副驾 ──────────────────────┐
│ 副驾: 官网改版下周有 2 项风险:    │
│  ① 登录接口联调逾期1天(张三)      │
│  ② 支付里程碑 target 10-25 仅60% │
│ ┌─ 建议操作草稿 ─────────────┐  │
│ │ 把「埋点」从王五挪给赵六?   │  │
│ │ [确认执行] [再聊聊]        │  │
│ └────────────────────────────┘  │
│ > 输入: 帮我把下周排期拉一下____  │
└────────────────────────────────┘
```

**落地前提**：core 已有 `collectProjectReport` 式确定性聚合 + `ai-client`；需要一个「提问→读 snapshot→生成结论/草稿」的新命令（如 `/pm ask "..."`）。不新增表。
- 用户收益：把 PM 从「维护台账」升维到「管理例外」。
- 成本：**L**。风险：中（免费 PoC 车道输出不稳，结论类只读可容忍；写操作严格走确认草稿）。
- 优先级：**P1（长期旗舰）**。适用：所有重度 PM，尤其配合生产车道（官方 Key）。

## 构想二：代码仓库联动 / 研发协同塔（Repo Bridge）

**现状断点**：PM 台账和研发的 Git/MR 是两张皮（UX-11）。

**颠覆性设想**：让任务成为「需求→代码→交付」的追踪单元：
- 任务可挂 `repo` + `branch` + 关联 `commit/MR 链接`；
- 约定提交信息含 `#t-0003`，副驾/桥接把对应任务状态推进（如 MR 合并→任务自动建议「已完成」草稿）；
- 交付物 location 可直接是可点的 Git Release / MR 链接。

**UI**：任务详情抽屉加「代码」区块：分支 chip、关联 MR 列表、最近 commit；概览加「本周合入 MR 数」。

**为什么是颠覆**：本产品从「PM 自己记的本子」变成「连接 PM 计划与研发执行的控制塔」，这是国内 PM 最痛、现有离线工具没人做的缝。

**重大分支 A/B 对比**：

| | 方案 A：手工关联（PM/MR 手填链接） | 方案 B：Git 桥自动同步（读本地仓库/远端 API） |
|---|---|---|
| 做法 | 任务加 repo/branch/MR 文本字段，UI 渲染成可点链接，状态变更人工 | 插件读本地 git 仓库或调 GitHub/GitLab API，自动拉 commit/MR 状态回写任务草稿 |
| 离线优先 | ✅ 完全离线，手填即可 | ⚠️ 要联网拉 API 或常驻 watch，与离线优先有张力 |
| 开发成本 | **S–M**（加字段+链接渲染） | **XL**（凭证、轮询、冲突、webhook） |
| 风险 | 低 | 高（凭证安全、写回误判、网络） |
| 推荐 | ✅ **先做 A 作为 MVP** | 作为 B 长期可选增强，且做成「只读建议草稿」而非自动写库 |

**推荐**：**先 A 后 B**。先在任务/交付物上加 `repoUrl`/`branch` 可选字段（domain v2 兼容），把链接渲染出来、副驾可引用；B 仅在生产车道、用户主动配置仓库后，以「草稿建议」形式存在，绝不自动改库。
- 优先级：A=P2（低成本铺垫），B=长期观望。

## 构想三：可视化甘特排期台 + 关键路径

**现状断点**：无排期视图（UX-02）、无任务依赖（UX-12）。

**颠覆性设想**：把「排期」从两个日期文本列，升级成一条可拖拽的甘特带：任务按起止日期画条、里程碑菱形落在时间轴、拖拽改条即改 startDate/dueDate；引入前置依赖后高亮**关键路径**。

**UI**：
```
        10-14  10-18  10-22  10-26  10-30
需求确认  ████●
原型设计      ███████●
前端开发           ███████████●
联调                     ████◆M1 首版发布
(拖拽条=改期；依赖线=A→B；红色=关键路径)
```

**前置**：任务要加 `predecessorIds[]`（依赖）与自动排期。这是 domain v2 演进。

**重大分支 A/B 对比**：

| | 方案 A：只读甘特（只画条，拖拽=改日期） | 方案 B：可计算关键路径（加依赖+自动排期） |
|---|---|---|
| 数据 | 仅用现有 startDate/dueDate | 需新增 predecessorIds 并做排期算法 |
| 成本 | **M–L**（纯前端时间轴渲染+拖拽写回日期） | **XL**（依赖图+关键路径+冲突检测） |
| 离线 | ✅ | ✅（本地算） |
| 推荐 | ✅ **先做 A**（立刻解决「看不见排期」） | B 作为专业 PM 的进阶，等 A 被验证需要依赖再加 |

**推荐**：A 先行（PROD-22a），它直接补 UX-02 这个 S1；关键路径（B）标记为长期、按需。
- 优先级：A=P1，B=P2。

## 构想四：项目健康度评分 + 自动周报机器人

**设想**：把散在各处的信号（完成率、逾期数、逾期增长率、未关闭高影响风险数、里程碑达成率、临期交付物）合成一个 0–100「健康分」与红黄绿灯，并按周自动生成可直接发出去的周报草稿。

**为什么有价值**：PMO（Persona B）和向上汇报场景，要的就是一个「一眼健康度 + 一份能发的稿子」。

**落地**：健康分是 snapshot 的确定性公式（可解释：哪些因子扣分），不调模型；周报草稿复用现有 narrate。
- 用户收益：汇报自动化、跨项目健康度可比。
- 成本：**M**（评分公式 + 一个灯号组件 + 周报模板）。风险：低（公式可调、透明）。
- 优先级：**P2**。

## 颠覆性方向汇总与推荐

| 构想 | 解决 | 成本 | 离线兼容 | 优先级 | 推荐度 |
|---|---|---|---|---|---|
| AI 项目副驾 | UX-10 + 整体升维 | L | ✅ | P1 | ★★★★★ 最该做 |
| 代码仓库联动 A（手填链接） | UX-11 | S–M | ✅ | P2 | ★★★★ 低成本铺垫 |
| 代码仓库联动 B（Git 桥自动） | UX-11 | XL | ⚠️ | 长期 | ★★ 观望 |
| 甘特排期台 A（只读拖拽） | UX-02 | M–L | ✅ | P1 | ★★★★★ 直接补 S1 |
| 甘特 B（关键路径） | UX-12 | XL | ✅ | P2 | ★★★ 按需 |
| 健康度评分+自动周报 | Persona B | M | ✅ | P2 | ★★★ |

> **一句话推荐**：颠覆性方向里，**AI 项目副驾**（最能发挥 dsh+结构化台账的独有优势）和**甘特排期台 A**（补最核心的「排期」缺失）是两个真正值得押注的方向；仓库联动先以「手填链接」低成本占位，不急于做自动桥。
