# 12 · 客观进度（Objective Progress）产品决策（v0.8 第一版）

> 一句话：任务进度不再靠人手填百分比，改由任务上的 checklist 勾选**客观派生**；没有清单就诚实显示「证据不足」，不凑一个看起来精确的数字。
> 本文只做**产品口径**；用例与技术形状以 `docs/testing/objective-progress-acceptance.md` 冻结版为唯一验收依据，本文与矩阵冲突时以矩阵为准。

## 1. 背景与问题

- 现状：任务上的 `progress 0~100` 是纯手填、凭主观估；汇报快照 `averageProgress` 对**全部任务（含父节点、含手填值）**求平均，口径含混，且无法回答"这个数从哪来"。
- 目标：进度从**可勾选的检查点记录**确定性派生，收敛到单一真源；无客观信号时宁可为空，也不输出伪精确百分比。

## 2. 所有者已确认的两条最终规则（产品红线）

1. **清单完成度 = checked/total，全勾即 100%**；全勾但任务尚未 `done`，只挂独立「待验收」标签——**不封顶、不自动把 status 改成 done**。
2. **父/项目只汇总「有非空 checklist 的后代叶子」并等权求均值**；历史手填 `progress`（含 0）单独旁注「原手填 x%」，**永不混入客观均值**；任务无清单 → 客观值为 `null`（证据不足）。

## 3. 产品语义边界（必须对用户讲清的四件事）

- **清单完成度 ≠ 工时比例**：勾选项是"交付物检查点"的完成记录，不代表人天投入。v1 一律**等权**，不按工时/优先级加权；前提是清单粒度相近（拆到"勾得完/勾不完"的粒度），粒度悬殊时等权只是诚实近似，不是精确度量。
- **验收状态独立**：全勾只说明"清单检查点全部过"，任务闭环仍由人把 status 置 `done`；系统不自动闭环、不自动补勾。
- **覆盖不足不称整体完成率**：有清单的后代叶子少于全部后代叶子时，界面只能叫「**已覆盖任务清单完成度**」；全部后代叶子都有清单时才可称「整体完成率」。
- **不做"客观证明"宣传**：本工具是单用户本地台账，**没有真实权限身份审计**；清单勾选是用户自陈记录，不构成对外部的客观证明，也不具备分布式安全/多人审计能力——界面与文档不这样宣称。

## 4. legacy 手填进度

- 用户手填值**仍可编辑、原值保留**，但只作旁注展示（「原手填 x%」），不参与清单派生、不进父汇总均值；系统**不做任何自动迁移/回写**，首开旧库零写。
- 新任务默认无清单 → 客观值 `null`（证据不足）；不拿手填 0% 或默认 0 冒充客观进度。

## 5. 汇报快照口径

- 新快照写入 `calcVersion=1`；历史旧快照缺该字段按 `0` 对待（旧口径 = 全任务手填均值，与新口径不可比）。
- 相邻两份口径不同、或任一侧 `averageProgress` 为 null 时，相邻对比徽标**不渲染差值**；历史快照**不回填重算**。

## 6. 一页纸适配结论

本能力落在**现有单项目概览（作战室）**内改造：用单一真源派生替换其任务完成率口径，加「待验收 / 证据不足 / 原手填」三类诚实标签；项目汇总若没有任何带清单叶子，就显示证据不足，**无源不造一个默认完成率撑场面**；跨项目总览沿用既有 GlobalBoard 只读卡片，不在本批扩展。
