# pm-tool 从立项至今的深度开放式复盘

> 本文给项目负责人及所有接手 Agent 使用：先查事实，再查对抗与反证，最后按整改清单执行。研究日期：2026-10-21；执行平台：TRAE。本文取代上一版简要复盘的分析口径，保留旧稿供查阅。**这是历史研究与协作知识沉淀，不是当前产品验收、发布放行或代码整改完成证明。**

## 1. 这次复盘如何避免先定归因

研究先建立现象台账，再交给产品经理、开发工程师、测试、Agent 协作架构师、跨平台协作运维五个独立研究角色。首轮期间台账由128项补充至 [164项冻结版](01-facts.md)，各角色在稿中声明晚增事实的补读与原件核对边界；不能说从开端就同时读到了完整164项。任务要求不读其他角色观点、不给责任定案、提出竞争解释和可证伪条件；五角色合计提出 **73 条假设**。第二轮交换报告，要求攻击别人的解释并修正自己的判断；最后独立审证人裁书面争点，主端再对照原始消息、历史报告、Git对象及规则时点分类。

第二轮部分角色由新的研究执行者承接首轮书面稿，并非全部在原角色的连续上下文中进行。四角色交换时未取得测试首稿，已明示缺件；测试后来反向质疑，第三轮两位独立审证人补裁书面争点，主端再核原件。这是有记录的报告对抗，不是五位人类专家开会，也不证明模型之间统计独立。角色同意某个结论，不能算新增独立证据。实际质疑、保留意见和修正见 [辩论记录](04-debate.md)；逐假设支持、反证、裁决及未知项见 [73 条交叉校验](05-hypothesis-validation.md)。

本次没有把“工具用错”“Agent 粗心”“负责人需求多”选作初始主题。事实分类同时纳入设计、开发、测试、沟通、Skill、配置、运维、跨平台同步和负责人决策。收敛后的结构解释仍须接受每个具体代码机制的反驳，不能反过来用一个漂亮总论覆盖所有事故。

## 2. 证据覆盖，以及不能声称知道的事

本次找到了豆包工作本机真实主轨迹及早期组织者轨迹，补上上一版没有找到的关键材料。对项目主会话下 **287 份轨迹、12,966 条角色记录**做了结构化提取与检索。主轨迹有 2,326 条：180 条 user、854 条 assistant、1,292 条 tool；早期组织者轨迹有 1,665 条，其中 97 条标记为 user。还检索了 TRAE 可访问云历史的 **66 份文件、2,790 行**，抽出了 **58 个去重用户输入片段**。形成了 [360 条脱敏消息摘录](02-dialogue-evidence.md) 与 [60 条对抗轮追加证据](02b-additional-evidence.md)。

这些数字表示本次可访问材料的规模，不是“从立项起所有聊天完整无遗漏”的证明。TRAE 历史主要包含工具审批与嵌套输入，不是完整主对话逐条导出；豆包主轨迹也没有保留每个早期跟进，需由组织者轨迹补齐。部分截图只剩引用，部分临时探针及运行日志没有原件。已读取全部材料的结构并按问题定向追踪，不声称逐字人工审查了每个工具载荷或目视复核了所有截图。

早期组织者的 user 标签中包含父代理转交任务和贴入的 TRAE 回报，不能都当作负责人原话。`[System]` 打断通知也不是负责人主动终止指令。原始消息、转译、工具结果、助手解释分别标识；同一消息在台账、摘录、角色报告中出现三次，仍是一个来源。

引用简写：M01824 = `DB-m_0cwRI8ya92K-L01824`；E01207 = `DB-o_000E1LJmvjj-L01207`；TR 使用完整来源 ID。L 是原轨迹物理行，不是本文行号。精确来源、哈希、抽取方法、缺失边界和本地 Git 研究基线见 [覆盖审计](03-coverage.md)。

本次特别保留以下未知：

- 没有请求级计费账，不能计算真实日均额度、子代理总成本或返工金额。
- 没有逐次压缩前后完整上下文，不能确认“上下文压缩造成失忆”。
- 没有逐次运行拓扑，不能确认负责人实际切换过云端 Linux。
- 没有完整构建 PID 时间线，不能指定究竟哪个 Agent 覆盖了哪份产物。
- 没有逐弹窗调用关联，不能把全部授权提示归为同一系统设置或同一错误参数。
- 历史候选缺陷不等于正式业务数据已经损坏；当期修后报告也不等于今天仍可无条件引用。

收尾又发现一项独立仓库之外的事实，单列 [上游边界补审](08-late-boundary-evidence.md)：本机宿主有一笔18文件UI提交，入口仍写上游只读。164项台账保持首轮冻结，新增P-ADD-01/H-ADD-01另作支持/反证核验；用户要改善首页与是否明确批准直接修改上游，是两个判断。

## 4. 根因判别：直接原因与漏出机制分开

本文使用六种判别：**直接根因**解释某次故障如何产生；**流程结构性缺陷**解释为何跨批次容易漏检或放大；**Agent 机制缺陷**解释转译、调度和汇总失真；**临时失误**目前只见局部实现/操作错误；**表面现象**只说明感知或状态；**待证假设**尚缺关键行为链。一个事件可同时有直接根因和漏出机制，不强迫互斥归类。

例如，资料编辑导致 ID 变号的直接原因是整区 normalize 重发身份并替换历史；漏出的机制是只测试空数组新建。把它仅写成“测试不仔细”会掩盖错误数据模型；把它仅写成“开发 bug”又遗漏了可防止同类复发的富历史测试合同。

### 4.1 宿主边界误读：基础问题不应继续靠类比猜测

P-010/011/017/025 分别涉及异步落盘、插件生命周期、类 Map API 和表名规则。这些不是同一行错误，但共同出现于自研包与 dsh 的接缝：执行者把熟悉工具的行为迁移到尚未核验的宿主对象。TypeScript 捕获 `.values()`、最小脚本捕获未落盘，说明前期探针确实工作，不能说地基始终没验证。

后期 `Object.keys(Map)` 把卡型注册表读成空集合，M01031 记录 11 类卡被跳过，历史修复代码改为正确枚举。这与“卡片好不好看”无关。表结构、记录键、模块注册与异步加载，都要从准确版本的真实接口出发；经验不能替代一段边界探针。

结构层的结论有限：已有 KB 明确这些 API，不能据后期别的错误断言执行者从不读知识库。可改进的是每次新增接缝要引用哪条已验证模式；不匹配时补最小实验，写明适用版本与限制。

### 4.2 创建、更新与历史保全：原子落盘不等于语义正确

P-026 的局部 status 更新清空原关联，ISS-021 给出 create schema 的 default 在 partial 后注入 patch。创建需要补默认值，更新缺省应表示保留，两种合同不能机械复用。故障原版未单独入库，本次以历史记录及修复路径交叉核验，置信度不写成直接重跑原版。

P-154 则有当期 QA 富种子前后记录：at-1/at-2 变为 at-3/at-4；软删 pl-1 及两次修订消失；active pl-2 又获新 ID。`existing` 被用于算编号上界，却没有被保留进输出；编辑仍按新建草稿格式整区重建。一次写入可以完全成功，整个新记录也可以符合 schema，但旧事实被合法地覆盖了。

第三轮进一步限定：active条目原本只有rev1，结果还是rev1，直接观察是改号，不能称active多修订已实测塌缩；固定rv-1的代码只能支持该分支预测。原QA另有“整批零写/已成功项不回滚”的时间归属歧义，登记交原专家澄清，不由开发改用例，也不据文字判已有部分写入。

此前 atomic 测试只在空数组首次建区，未覆盖已有稳定 ID、多修订、软删与引用。由此得到的纠正不是“把 UI 保存再拍一张图”，而是稳定身份、未提交区保留、逐项操作、失败零写、别名引用一致的可执行不变量。新建 raw draft 的成功应保留；编辑富历史的错误必须另案。也不能据隔离探针说负责人正式历史已经受损。

P-155 的 excerpts 与 selectedRefs 两条输入分别校验，出现跨项目和软删条目接受、双字段静默忽略；P-156 的 wrapped 后端合法而 UI 分组漏掉。前者是写入口校验不一致，后者是读取展示未覆盖合法状态。二者不靠增加一个“统一组件”自动解决，须按方向区分读取全集、允许写入子集、引用归属和状态转换。

### 4.3 看板“堆叠”包含多种故障，不能合并为换色失败

连续反馈中至少有四种可辨机制：

1. 注册表被错误枚举导致卡型跳过，是可用卡集合错误。
2. 响应式投影的取整、夹紧和单列堆叠丢失信息，再将被动 `onLayoutChange` 反算写回草稿，是展示坐标侵入持久坐标。
3. 网格坐标即使不碰撞，slot 只设 minHeight、卡体按内容自然增长，也会视觉覆盖邻卡；旧窄屏覆盖规则又可能抢夺几何控制。
4. 编辑面板挤压工作区触发断点、数字每次输入立即夹紧，与显式拖缩状态互相干扰，是编辑行为不稳定。

历史 `889f7a9`、`7f44c46`、`ee52d9e` 的不同修复方向，及 M01982“堆叠倒是解决了，宽高无法编辑”，反对“同一个问题一直没认真修”的概括。浏览态去碰撞、卡体高度闭合、编辑 canonical 状态固定，分别回答不同问题。

但 M02314 后来的连续拖动下推和空白仍需具体复现；不能因为上一轮投影修好了，就认定新反馈是假问题，也不能继续套旧根因。宽高可编辑和无碰撞只是功能/布局条件，不证明默认排版有信息层级、所有卡型内容可读、配置面板不挡操作。

可复用经验是区分保存坐标、显示投影、实际 DOM 边界和用户主动动作。被动渲染不写布局；只在明确应用或拖缩完成时提交；以连续动作、开关编辑、切宽、刷新和重启验证稳定性。固定高度带来的内滚成本也要作为体验取舍，不把“相交 0”称为“审美通过”。

### 4.4 保存、焦点与反馈：接口完成不能代替用户完成

P-027 中“保存会议”没有保存行动项，按钮语义与实际表单范围不一致。修后父成功再串行保存子项，意味着仍不是天然跨表事务；不能把“全部成功才关抽屉”描述为“任一失败整批零写”。

P-149 包含真实键盘焦点、Space 选错行、窄屏文字被隐藏、入口难发现和 loading 缺失。P-152 拖甘特后只剩更新文本，历史 CSS 修复说明提示在无 wrap 的 flex 行挤压时间轴，并无任务丢盘证据。近期 P-112 又表明行选择、任务条点击和抽屉打开冲突，使键盘调期虽有函数却难在工作区使用。

这些不是“非技术负责人不懂系统”的合理后果。用户无需知道 reducer、props 或默认提交点。工程侧需为对象、焦点、动作、提交、等待、失败和继续工作形成同一条路径；产品侧需说明显式选择、待提交、已持久化的区别。

同时保留 P-120 的反证：测试仅选交付物但没点关联和主保存，不能判后端关联失败；把删任务当删看板卡也不能要求错误实体加撤销。一个路径可能不够易懂，与该次测试是否按合同做完动作，是两个判断。修复前先核对象及完整步骤，避免误判驱动业务变更。

### 4.5 动态打包：不是所有构建绿都证明宿主能激活

早期 Lucide 外部化、CSS 没有复制、后期 zod require，以及 B8 schemas 同步兄弟块，属于同一接缝家族，但技术条件不同。dsh 的模块表有注册和异步 materialize 顺序；普通 bundler 能解析磁盘依赖，不能证明宿主 factory 表已具备该模块。

B8 证据给出三次独立故障层：冻结包漏掉 package 声明的包内 `cordis.patch.yml`，而静态门只查了 profile 补丁；修补后入口同步 require schemas，表中未注册；再内联修补时 replace 替换字符串解释 `$&`，破坏转义字面量引入 SyntaxError。最后一项先按一次局部实现回归处理，不因看起来严重就升级为个人惯常失误。

关键漏测是旧验证器先注入 schemasFactory，提前为产品补了真实宿主没有的条件。测试并非没有断言，而是模拟环境比真实环境更强。增加同模型的断言数量不会减少这种假阳性。后来 entry-only、禁预载、按真实 async 顺序物化、核声明资源与图完整性，是有效纠偏。

不能由此声称静态测试无价值。声明资源检查和忠实装载模型可比 GUI 更早发现白屏；GUI 则必须验证真正宿主、主题和旅程。两层各有职责。B8 不同时间的 OPEN、修复和 CLOSED 段要按 RUN 顺序读，不能把一个文件中的历史失败和后来闭环当同时矛盾，也不能拿旧 READY 给新 inlineSync 产物背书。

### 4.6 测试门的失真有四种，增加“严格”并非统一解法

第一种是断言错：固定顺序、并发后固定名次、负例选已达成记录、序列化后仍比原文、重构后旧选择器。需要检验业务不变量，不应删除红断言来凑绿。

第二种是对象和提交错：P-119/120 的撤回已产生无效返修方向。用例要指明实体、初态、实际控件、提交点和落盘读回；DOM 列位置或按钮外观不能替代对象身份。

第三种是模型与种子错：预注入宿主依赖、仅空种子、没有富历史与合法时间序列。看似大量绿结果仍可能漏掉关键边界。门的名称和断言数量不足以说明测的是哪种世界。

第四种是分类和汇总错：域级取消零写被扩大为 UI 取消通过，局部浅色窄屏子项被扩大为整项，必要本人录 Key 被扩大为整轮页面人工验收。这会让用户成为客观缺陷首次发现者，且完成汇报与实际体验脱节。

角色对抗纠正了一个重要过度推断：早期确有可信 J/K/Enter，但 Space 没送达、390 会话失败，部分运行版本未绑定。不能说“浏览器原则上能自动化”就证明“当时那位执行者已经能完整做”。责任应分别问：用例本质是否需本人、当时角色能力是否可用、有无及时转交有能力者。认证完成后继续全页检查，没有内在必须本人依赖；具体执行通道受阻仍应诚实记 BLOCKED。

四视口、六状态、200% 矩阵可以是后续设计方案，但根规范明确有一部分待表决。未生效提议不能追溯成为历史违规依据；当批已批准测试合同另行约束。更严矩阵若没有执行能力与合法 fixture，只会延长等待；删去承诺覆盖也会隐藏风险。先让门可执行、对象准确，再讨论门的规模。

### 4.7 测试副作用：业务往返成功和共享资产污染可同时成立

P-160 的 50 个快照是测试写入共享备份目录，历史专家未擅删，正式 data 未被同样证明污染。恢复代码在替换前先安全备份是正确产品逻辑；测试只隔离 domain 却没有隔离安全备份目录，构成设施缺陷。

`DSH_HOME`、数据根、备份根、导出根、附件字节根、缓存和构建输出是不同写目标，不能认为配了一个临时目录全部自动隔离。后期 WATCH 守卫证明监测范围内 before=after，不证明未监测目录。资产数量也不是目录身份：同数量可被覆盖，须结合路径、内容指纹及新增/删除清单。

P-121 的改名 worktree 导出正则和含空格子进程失败，需要控制变量区分断言耦合与产品解析错误。主根全绿不能豁免可移植性红；也不能看到隔离树红就登记成业务功能回归。修复测试设施必须有证据证明旧断言错，保留真正行为负例，不扩大标准环境来掩盖既有承诺。

### 4.8 候选身份与证据继承：HEAD、版本号和页面是不同对象

本地 HEAD `06a131c`、本地 `origin/main` 引用、历史 v0.7.4、同版本后续源码、未提交候选、软链目标、构建目录和浏览器已加载页面，不能用一个“当前版本”代替。v0.7.4 注解 tag 对象 SHA 与剥离提交 SHA 不同是正常结构；沿用包版本的未发布候选也不自动违规。

本轮所见17ahead仅是相对本地缓存origin/main的差距，未fetch，不知道实时远端是否已有这些提交。未提交候选不由当前HEAD携带，远端clone不应被假定能自动复原它们；需要明确恢复材料，但不能据此认定拒不推送。独立门未放行时保留候选是正确行为；为“干净”提前推送、删除他人成果反而有害。已有HEAD+tracked diff+新增文件指纹冻结做法，应保留并补统一入口，而非一律要求先提交才能测。

共享 lib 的构建写入是另一问题。源码文件互斥不等于构建产物互斥；`kill_agent` 返回 cancelling 也不等于其子进程退出。M01628/01630 观察冻结后块重生成，足以证明候选稳定对象受到挑战，但没有全 PID 时间线，不足以判某个作者故意覆盖。

需要一名整包 builder，或各自隔离输出；候选同时绑定源码基线、未提交补丁与新文件、必交付资源、构建清单、profile 解析、服务 PID、浏览器上下文和开关。文件 hash 可认领某轮字节，不代替 tag 身份，也不要求不同 worktree 构建 hash 相同。

证据继承要按受影响范围。client 入口、模块表或全局样式改变会影响一组旅程；纯文档与空行不必让全部业务断言过期。既有规则已要求受影响结果失效，缺的是稳定记录“哪些证据为何继承、哪些必须重测”的索引。禁止只报总绿计数来跨 RUN 拼接。

### 4.9 “看起来没改”：最强证据指向交付范围，缓存只是假设

M01805/01807 称开发与主要真实验收完成、正式已启动、代码已推送；M01808 负责人说像没改；M01824 主端撤回“B1–B8 已全部落地”，解释任务视觉默认 `pm-b1-pilot=off` 且仅覆盖任务页。邻近工具读代码与测试范围映射提供了可定位依据。

第二轮测试反驳了直接责备实现者的做法：B1 验收合同本来要求默认 OFF、保留旧页、ON/OFF 可回退。开关关闭可以是正确风险控制。较强结论是**主端汇总把底座、数据、文件、表单与可达性工作扩大为全页视觉迁移**；是否有人违反已分配实现合同，尚需批准记录。

“强刷一下”“用户看到旧 bundle”在这组证据中没有更强支持。即使浏览器载入正确版本，关闭的试点也不会显示新版；默认开试点也不等于其余页面已迁移。后续交付必须说清方向图、实现覆盖、默认生效范围和已验旅程，不要求负责人识别大量后台工程工作才能判断页面变化。

### 4.10 Agent 转译、状态与接班：完成词需要回读实际目标

伙伴档案事件有清楚行为链：M00006 只要求改工作伙伴档案，E00049 父任务把对象改为仓库文件并加提交，E00067 负责人纠正不入 Git。初始“产品成果统一入库”确造成可解释歧义，但不能自动覆盖个人伙伴配置对象。这里是转译改对象，不能归为用户没授权。

其他对话也出现把“没超出预期”转为“用户明确拒绝”、把文件写好称目标界面已生效。父派单应保留用户原句，将补背景、自行推断、任务范围和成功条件分开；完成前在真正目标回读。忠实执行一份失真的派单，仍会错误。

状态快照、任务存活、工具活动、产物变化、依赖等待、服务健康是不同轴。M00784 曾用三信号判断疑似停滞，是正向做法；不能说所有判断只看快照。但 M01635 的旧 FAIL 摘要与新文件不一致、继任配额不足，以及服务旧停新未起，说明“继续/重启”未必是可恢复步骤。

终止前需有检查点、子任务和临时进程归属、继任能力、输出冻结和回退方案；终止后核真实退出。无法证明底层模型死锁、睡眠或压缩是主因，应标未知。用户多次终止是对无反馈的反应，部分中断又是系统通知，不能汇总成“负责人频繁干预导致停滞”。

### 4.11 授权与环境：应拆层诊断，不承诺一次设置解决所有门

负责人给豆包修改、正常 commit/push 的持续授权是可查原话，根通用规范仍保留逐次确认，onboarding 又写持续授权，造成入口冲突。授权要按平台、动作、范围、生效/撤销时间处理，不能静默选最宽或最窄版本；业务授权已存在时反复人为问同一件事，没有必要。

但业务授权、工具 sandbox、macOS 控制权限、网络与浏览器认证、Main/Sub 能力是不同门。E00437 称彻底解决，E00443 又反馈；更换原因解释不能代替调用级核验。必须识别是哪一层拦截，说明确切动作与错误，不能承诺以后任何弹窗都不出现。

同样，负责人本机一直是 Mac，与某个浏览器在隔离执行通道并不矛盾。工具 runtime Node、系统终端 Node、新 shell 的变量、旧服务进程继承凭据也不同。新 shell 直连成功不证明旧 dsh 已收到 key。环境报告应写探测时间、执行层、OS、cwd、工具身份和可达链；不能把远端 loopback 不通说成用户切换 Linux。

浏览器 Cookie 不共享与 dsh 信任围栏是安全边界。M02239 的 LISTEN+401 排除当次停服，说明入场凭据不完整；裸地址可用性与服务存活不同。进入工作台应提供合法首次认证及重启后重入路径，再核 PM 面板挂载与 snapshot 成功，不能让非技术用户每轮翻日志找凭据。

### 4.12 Skill、脑暴与研究：方法名称不能充当证据

前次五方向脑暴确有主端指定方向、给例子、禁止跨界，然后直接汇总的派单记录。最初负责人也允许多 Agent 脑暴后汇总，所以不能说分工本身违约；但把覆盖性收集称为已完成对抗论证，强度不足。负责人后来 M00869 的质疑准确要求了作者互相攻击、答辩与方向可变。

有效多角色需要相同事实底座、独立首轮、竞争解释、反例、明确撤回和裁决者核原证据。不能只把一个推荐分成五种语气，不能让父代理提前告知“用户已否决”来塑造共同前提。认知独立不是由名字、角色数或同意票数证明。

Skill 安装、完整性校验、自动路由、读取、实际应用、独立验证也是六种状态。E01004 要求按上下文自动选择，合理；M00470/M00698 的追问提示参与成果不可辨。但 UI 差不证明没读 Skill，存在试点和走查产物也不能证明方法改善所有页。应留任务级版本、选用规则、改变的设计或代码决策、验证证据；不把安装数量当能力。

M00049 在 UI 投诉后立刻称根因是 Impeccable“防守型”及自行暖纸青绿方向，缺相同输入与状态的受控对照。先取审美锚点、先出稿是合理纠偏；其有效不使工具归因自动为真。这里可以确认过早下因果结论，不能确认 Impeccable 应承担主要责任。

M00454 用 219 提交和经验倍数估计请求，再在 M00460 承认缺完整嵌套 trace、扩大区间。区间不是精确账单，但“数据算清楚了”及随后据此讨论峰值和套餐，表达强于证据。新增截图数量不能校准计费单位。以后没有去重调用树和账单，不报历史真实额度、责任成本或质量百分比。

### 4.13 收尾补审：插件独立性与实际宿主补丁

本机上游HEAD比只读基线多提交 `1142fb74f2`，18个文件改命令结果、Markdown/长代码与工具行显示，另有未跟踪探针。M00982负责人确实要求改善dsh首页；M01031执行者也报告长结果实现进入宿主。两项加Git对象支持“实际宿主已改”，但当前入口仍只读。Git身份Ice不能证明负责人亲自操作，本次也没有查该提交远端。

竞争解释是：执行者把页面目标扩大成直接改宿主，或已批准架构例外却没有在当前权威档案留下清楚路径。现有材料不足以排除任一，不能直接定为越权。只clone pm-tool不会自动取得另一仓库的UI提交；**当前正式服务是否加载它仍待证**，因此这是迁移范围风险，不能说已确认正式运行依赖。插件tag不能单独证明宿主源码或实际加载身份。

接手者需分别认领插件源码、宿主基线/补丁、实际服务加载与批准边界；新增目标若确需宿主变更，先查扩展点和有效例外再执行。这不是要求本次撤销或清理上游，当前复盘仅记录事实与待补档案。

## 7. 对项目负责人的中肯反馈

### 7.1 你可以继续提出高目标，但要把愿景与本批验收分开

“国际领先”“无懈可击”表达你不愿接受敷衍，有正当价值；作为近期停止条件则没有天然终点。它容易促使 Agent 生产更长规范、更多角色和更多图集来回应强度，未必更贴近工作流。M00892 已补平台独特性和真实 PM 场景，说明你能够提供具体上下文，不能批评成一直不清楚。

可优化输入是：愿景单列；本批只要求某个用户在规定数据下完成哪段工作；明确三个可观察结果和暂不追求的范围。专业的执行端仍应主动做这一步转译并回报，不能要求你提前会写工程测试。

### 7.2 “可以实施，另外加……”应拆成两个决定

M00251 在认可看板图时加入全尺寸拖拽、卡片元素、数据源、公式、筛选排序；M01157 在认可效果时加入资料附件与进展历史。它们不是小字段修饰，分别改变状态模型、数据关系、历史保全和测试面。你有权提出，但将其放进同句“开始做”会模糊原版批准和新增立项的边界。

下一次可以说：“A 方向认可，按已列范围实现；B 是新需求，先给影响和分批方案。”执行方已在 M00252 识别大功能并提出架构/原型，这是正向反证；本次不能说无人评估。评估识别了范围，后续仍需把分批承诺冻结到实际可见结果。

### 7.3 批量推进可以保持，质量债与新功能需有顺序

M00339 一边验一边继续；M00719 确认功能但反馈样式差，又推进后续项；M01407 要 B1–B8 和工具试点一起完成。这样授权便利，却会让缺陷、研究、体验重构、功能和发布共用一个完成词。问题发生后重新排查整个系统，反馈环就更长。

你可以要求“先收口当前缺陷；并行只做隔离研究/文档；门通过后按队列开下一功能”。关键是改动依赖和候选隔离，不是禁止并行。E01287 的执行端已拒绝大型新功能，M01842 你又主动缩为看板专项，证明并非总是不顾阻断催推进。

### 7.4 点名工具、要求多 Agent，应转为要求方法产生可见增量

你的 Skill 和专家诉求来自多轮质量不满意，不能批评为盲目追新。M00869 对形式脑暴的反驳尤其准确。但“用哪几个 Skill”“为什么没找伙伴”容易让执行端以参与名单回应，无法证明它解决了什么。

更有效的是要求：本次哪条方法改变了哪个设计/实现决定？哪些原假设被反例推翻？最终方案与原推荐相比有何变化？你已经在这次复盘要求中这样做，应延续；角色数量可以由任务依赖决定，不用固定越多越好。

### 7.5 持续授权需要明确对象，不能追求不存在的“所有权限”

你已多次清楚授权自动修改/普通提交推送，重复人为确认应由执行端解决，不应再消耗你。但“最高权限，不再问任何事”无法统一系统控制、浏览器认证和角色能力。工具强制要求本人参与时，继续说同一句授权不会使子代理获得桌面权限。

更有效表述是：仓库内常规操作自动执行；不可逆范围另列；系统强制确认只说明实际拦截层、动作和错误，别重复询问已经批准的业务事项。执行端不能把这种区分当借口停在计划，必须先做完可独立完成的工作。

### 7.6 主观质量与客观缺陷分开反馈，可减少解释错位

“丑”可以直接说，不需要你写设计术语；它却不足以单独决定修哪条机制。你在 M00318、M01059、M02314 的反馈已经很好地给了遮挡、错位、无法键盘操作、字段不可见、同日重复等具体事实。建议延续这种“页面/动作/预期/看到什么”的格式，再单列审美偏好与参考。

另一方面，M00207 不喜欢黄色被执行端过度解释成保留单色，M00214 又澄清，说明需求反复也有转译来源。不能把所有返工算成你的审美变化。用户不应承担发现保存丢失、历史被覆盖或模块不激活的责任。

### 7.7 API 稳定、维护带宽与成本可控应作为待验证假设

M00892 认为 dsh 两年尺度 API 稳定、个人能承担双向耦合、买套餐后模型稳定。这些支持你的主动选型，但购买服务不证明维护时间充足或模型调用稳定。希望最终替代公司系统，更要检验组织权限、协作、审计、迁移和真实日常使用，不能由个人练习场的功能数量推出。

可以保留两年方向，近阶段先用少数真实场景验证维护投入和任务成功率，明确什么结果会暂停深耦合。Agent 应给证据与备选路径，不能为迎合信心把你的期望复述成已验证事实。

### 7.8 不必亲自成为全面测试员，但要明确最终业务验收角色

你说“我不测了，自己全部测完再给我”，是在客观缺陷不断漏到你面前之后的合理反应。ADL-047 本人协作分层也明确，没有许可开发自签。你应保留产品价值、正式恢复及实际凭据的最后决策；自动化与独立专家承担可执行质量验证。

改进重点是负责人判断“它是否帮我完成工作”，执行端证明“它是否正确、稳定、可恢复”。不把你每次找到 bug 当成体验验收流程本应如此，也不把你没有测视作默认认可所有未测项。

## 8. 落地方案与顺序

本次已将可执行协作规则写入 [collaboration 第十一节](../../collaboration.md#十一深度复盘后的执行合同与证据规则adl-0572026-10-21)，并在 AGENTS、KB、ISS、ADL 和交接入口建立链接。它们细化已有门，不扩大产品需求，不替代测试专家，不把待表决设计矩阵自动升格。具体行动见 [整改与验证清单](06-actions.md)。

| --- | --- | --- | --- |
