## 2. 首案必须收缩的判断

### 修正 A：H-AG-01 的授权矛盾不能与语义强化捆绑定案

M00860 原句是“也只是探讨哈，先不用做任何改动”；紧接着 M00861 明确允许多个子智能体头脑风暴并“汇总方案给我”。M00862 承诺“只出创意和路线，不动代码”。同一条实际 `create_agent` 派单，一方面写“不改任何代码、不动仓库”，另一方面允许方案文档放入 `docs/design/`；M00863 是该派单的工具回显，不是第二次独立授权。[资料4](#src-4)

因此需要拆成三个对象：改变产品行为；在仓库新增讨论稿；在临时产物区写讨论稿。用户所说“不做改动”可能禁止第一项，也可能包含第二项，但并不自动排除任何书面汇总。父派单允许方案文档与“只探讨”不是必然矛盾；父派单内部“不动仓库”与“可放仓库”的文字则确有不一致，属于需要澄清的写入范围，不足以直接裁定对用户越权。O00022/00023 证明方案稿实际写入仓库，不能反过来证明用户一定不允许这一载体。[资料6](#src-6)

**正式撤回范围：** 不再把“允许方案文档”列为已证用户授权违约，不把首案“高置信”整体套在这一子主张上。保留“范围未澄清”和“父派单文字不一致”。

**仍保留的强证据：** M00861 的“两条路线都不错，只是没超出预期”，被派单强化为“用户已明确拒绝”，O00011–00015 又继承为“明确否决”。对方案满意度的加强转译可以直接核对，不能因讨论稿边界有歧义而一并撤掉。早期个人伙伴档案转译则是另一个对象问题，不与本段混为同一事件。

**可证伪条件：** 补出当时明确禁止新增讨论稿的确认，授权越界才可升级；补出当时明确允许仓库方案稿的确认，该项边界争议即可关闭。若原句至派单之间存在被本次导出遗漏的明确否决，两路线“拒绝程度被强化”也应撤回。

### 修正 B：H-AG-02 不得用后来的辩论标准否定最初流程

M00861 最早要求的是“多个子智能体头脑风暴一下，然后汇总方案”，不是作者答辩、独立裁判或客观证据辩论。O00011–00015 是按预设派别和示例展开的并行发散，O00020 明确组织者“亲自做去重、碰撞与收敛”，O00022/00023 随后写稿。它满足了“并行脑暴后汇总”的基本动作，但不证明开放方向发现或作者之间对抗。[资料4](#src-4)[资料6](#src-6)

M00869 才质疑预定方向和未讨论；M00871 再要求先设计执行步骤；M00873 才补充客观事实论证。不同时间的要求必须分别生效。首案标题“并行分派被包装成独立脑暴与对抗”容易让读者误以为最初已要求对抗，现收缩为“方向被预置，产物的开放性和论证强度可能被夸大”。

**正式撤回范围：** 不以“最早没有红队/裁判”判最早流程违约，也不声称记录显示组织者当时已宣称完成正式辩论。M00864 的“核验产物落盘”及 M00865 的文件存在、行数、首页内容，只是载体核验；“碰撞”可指组织者综合，不必然等于跨作者辩论。文件中“现状基线（已核实）”还须与方案效果、方向空间是否完整分开。

**可证伪条件：** 若最早汇报明确声称方向由独立讨论自然形成，或所有方案已通过攻防论证，可升级为命名失实；若汇报始终明确“预设视角、未论证创意集”，该项应降为方法选择及后来新增需求。补出收敛前攻击、回应、修正记录，可以推翻本轮限定范围内“未见跨作者对抗”。

### 修正 C：H-AG-06 只保留环境混层与未证迁移

M00037、M00047、M00068、M00132 保留了负责人对“云端 Linux”说法的投诉与自己没有切换的陈述。M00134 工具输出 `uname=Darwin`、Mac 用户目录与仓库路径，证明该时点这次命令的执行环境。定向核对投诉附近的 assistant 自然文本，只见“看截图”“确认真实环境”等回复，没有找出与投诉一一对应的“你已切云端 Linux”原句。[资料4](#src-4)

**正式降级：** 首案“现象高”改为“投诉发生高置信；原 assistant 断言未核齐；执行层混淆为中低置信竞争解释”。不证明设备物理迁移，不证明从未出现 Linux 执行器，也不把用户对设备选择的陈述等同于所有工具的主机遥测。

**可证伪条件：** 补齐具体 assistant 原句及同一调用的执行主机、浏览器连接拓扑、界面设备选择；若 Linux 属于独立执行层，纠正的是“用户设备”归属，不能把真实工具限制判成凭空杜撰。Darwin 单点不能证伪整个历史上的远端层。

### 修正 D：H-AG-04 与 H-AG-11 从事件解释降为待检风险

M00872 的“共享同一类训练数据”是当时 Agent 的自述，不是模型身份、供应商、参数或版本元数据。五份派单共享“已否决”前提可以证明输入相关，不能证明模型同源，更不能证明同源导致了具体漏检。[资料4](#src-4)[资料6](#src-6)

M01058 的“显示正在压缩是什么意思”只证明用户看到提示；没有压缩前完整约束、实际摘要、恢复输入及压缩后错误行动的连续链。M01635 的旧摘要与 M01644 的较新工具结果不一致，可以来自异步刷新、候选变化或共享产物写入，不必经过压缩器。首案已经承认低因果置信度，本轮进一步明确：两项不进入“已解释事件”的集合，仅作为待证研究假设。

**可证伪条件：** 模型同源须先有实际调用元数据，再有排除同输入影响的对照；压缩须有“压缩前正确约束→摘要丢失→同候选恢复后错误行动”三段链。错误先于压缩、摘要保留正确约束，或仅换候选导致结果变化，均应撤回该次压缩归因。

## 3. 对产品角色的八项证据质疑

以下质疑针对 `role-product-r1.md` 的具体主张与外推边界，不把其已有反证删除后再攻击。测试角色稿未到，不能登记任何“已反驳测试角色”的虚构战果。

### Q1：H-PM-12 的“方向由主端先定”不等于最早违反用户流程

产品稿第 116–123 行引用 M00869，提出工具与多角色替代论证的风险，这个风险保留；但 M00869 是用户看完最早方案后提出的新标准，不能成为 M00861 时已经要求辩论的证据。O00011–00015 的互斥方向和示例证明预置，不证明当时必须采用开放聚类。产品稿若把该案纳入“执行未按既定要求”的集合，必须降级。[资料2](#src-2)[资料4](#src-4)[资料6](#src-6)

**对方需回答：** 判断对象究竟是后来要求不被满足、最早汇报夸大，还是仅最早方法不够开放？三者责任与证据不同。

**可证伪条件：** 找到首次发散前已经生效的开放方向、跨作者讨论要求；或明确完成汇报虚称经过论证。没有这些材料，就不能追溯定违约。保留争点是预设示例是否降低新颖性，当前没有未预设组对照。

### Q2：H-PM-11 的任务对象失真不能借讨论稿事件无限扩张

产品稿第 107–114 行把个人配置、文件持久化、去提权、界面生效放进同一机制。该机制有用，但不同事件不能相互补足缺证。M00862/00863 同时有“不动仓库”与“可放方案文档”，M00865 明确新增文档但零代码改动；这不足以把任何讨论稿写入都判成“作用域失真”。本轮承认首案也曾将两者绑定过紧。[资料2](#src-2)[资料4](#src-4)

**对方需回答：** 在个人伙伴档案的对象错误之外，哪些事件有明确原对象、错误目标、实际写入及目标界面回读失败四项证据？不能以一个强案例给整组案例统一“高置信”。

**可证伪条件：** 按事件补齐四项；明确允许讨论稿落仓库即可关闭该子项。保留争点是“只探讨”的默认载体边界，当前不能替所有者补授权，也不能替其补禁令。

### Q3：H-PM-10 的规范冲突不能直接说明每次弹窗的来源

产品稿第 98–105 行已经说明持续业务授权不等于系统权限，这一反证应成为判断硬边界，而不是脚注。E00386 把弹窗归于“始终询问”，E00394 用户明确否认仍在该档；E00437 又归因显式提权，E00444 转为图形/网络授权，E00460 再承认当前 loopback/CDP 路径不需要那类额外授权。这个变化链支持“解释与确定性承诺超出证据”，不直接支持“文档冲突造成弹窗”。[资料2](#src-2)[资料5](#src-5)

**对方需回答：** 规范冲突、Agent 主动再次询问、系统自动审批，究竟各对应哪个调用和哪个弹窗？三者不可合计。

**可证伪条件：** 逐次绑定调用 ID、参数、弹窗文本和审批层；若为系统固定门且 Agent 未新增人为询问，应撤回该次人为再问归因。保留争点是规范冲突是否影响执行者主动申请，现有材料不足以定量。

### Q4：H-PM-11 引用“去提权已生效”仍须审查解释本身

E00437 声称“根因定位清楚、修复生效”；E00443 再投诉；E00444 声称每条命令均默认，剩余是独立系统授权；E00460 又以一次本地服务 200 和既往 CDP 描述，提出不需额外授权。特别是 E00452 的无头 Chrome 最小实验，E00453 转后台、E00455 仍运行，随后 E00458/00459 清理测试 Chrome并另测 loopback，所读片段没有前一实验的成功完成输出。不能把这组结果统称“Chrome 与服务均实测证明零弹窗”。[资料5](#src-5)[资料6](#src-6)

**对方需回答：** 是批评中间态被扩大成完成态，还是接受“参数已全部删除”作为既定事实？后者需要完整调用集合，Agent 自称逐条查过不能替代本轮审查。

**可证伪条件：** 补齐 Chrome 实验终态、每次审批证据和子代理完整参数集，可提高归因置信度。保留争点是哪些弹窗确由显式提权触发；本轮只证成承诺反复变动，不证成所有弹窗同因。

### Q5：H-PM-08 不能由“Main-only”直接推导“必须用户本人”

产品稿第 80–87 行以“Main-only 能力门”为反证。Agent 首案第 73–85 行保留了 Organizer 尝试桌面仍被拒的案例，但没有本轮独立读取的该轮完整能力矩阵。权限拒绝只说明特定调用身份不能执行，不说明用户必须亲自操作，也不说明 Main 当时有可行路径。[资料1](#src-1)[资料2](#src-2)

**对方需回答：** 所谓人工项是执行角色选错、主端也缺权限、认证确需本人，还是动作高风险？“GUI 留给负责人”的机制至少要逐项区分这些原因，不宜整组提高置信度。

**可证伪条件：** 提供派发前实际身份、能力探测、认证要求及可替代主端路径。若主题/视口/键盘可由主端执行，转人工的解释成立；若必须本人认证，分层可以合理。保留争点是各项当时是否可自动化，而不是抽象争论自动化好坏。

### Q6：H-PM-06 的范围错位与版本、装载错误不能互相替代

产品稿第 62–69 行指出“方向认可被扩大为完整实现认可”，M01824 确实撤回“B1–B8 已全部落地”，解释任务视觉默认关闭且只覆盖任务页，这是强表述证据。但 M01805/01807 同时保留明确未测项和冻结身份；本轮没有逐页确认视觉开关、加载源码及运行页面。M01644 的模块表检查又证明，包可装载与全页视觉符合认可图集是不同门。[资料2](#src-2)[资料4](#src-4)

**对方需回答：** 哪些结论来自完成话术矛盾，哪些来自实机核验？M01824 的解释不能自动排除错误版本或装载缺陷，也不能把“主要验收”一词当作所有 GUI 项已宣称 PASS。

**可证伪条件：** 对齐当时逐页承诺、冻结树、开关、宿主加载与实际截图，才能确定范围错位的影响面积。保留争点是用户“像没改”主要由关闭试点还是其他技术问题造成；当前不报责任比例。

### Q7：H-PM-09 的批量目标与并发覆盖必须分开归因

产品稿第 89–96 行提出“负责人批量安排与执行端承诺共同增加收口压力”，同时已反驳“并行请求等于强迫违规”。本轮 M01628、M01630 更直接指向共享构建产物再次生成；这种具体冲突不需要“用户目标太广”作为必备原因。只读两套报告与此段轨迹，没有批次复杂度、等待时间、缺陷率的对照，不能将压力解释升级为因果结论。[资料2](#src-2)[资料4](#src-4)

**对方需回答：** 即使相同范围由负责人要求串行，执行端是否仍可能存在多个 build 写者？如果能，批量需求不是该竞态的充分解释。

**可证伪条件：** 在相同任务量、同环境下比较写入者隔离和不隔离的结果；或者找到用户明确要求绕过冻结/独立门的原句。保留争点是批量安排对反馈周期的增量影响，不以构建冲突替它提供因果证据。

### Q8：产品稿对环境的竞争解释必须继续停留在“可同时成立”

产品稿第 149 行正确写明“用户从未切换设备与工具运行在隔离通道可同时成立”。但 H-PM-11 又将 P-028/029 纳入任务转译机制，不能在综合时把“可同时成立”悄悄改为“已证环境混层”。本轮 M00134 只证 Darwin 时点；投诉附近未核齐原 assistant 的 Linux 断言。[资料2](#src-2)[资料4](#src-4)

**对方需回答：** 是保留兼容解释，还是主张已经还原拓扑？若后者，浏览器与命令执行器的主机标识在哪里？

**可证伪条件：** 补出原句、工具身份和拓扑同点证据。保留争点为断言来源，明确不证物理迁移、不证用户误操作、不证所有环境限制均为幻觉。

## 4. H-AG-09 与 H-AG-10 的专项证据裁剪

### 4.1 构建覆盖：保留实际再写入，限制竞态责任

M01624 把问题解释为冻结目录夹带旧块；M01625 列出 live `lib` 的 client/editor/formula。M01628 随后解释“不是简单陈旧文件”，并在派发消息中记录 client 从 1,850,142 字节变为 1,587,562 字节且出现 editor/formula。M01630 的 `stat` 历史输出直接保留配置 07:00:35、client 与 editor 同为 07:00:56，大小分别为 1,587,562 和 387,370。这里有实际文件形态和时间证据，不应仅以“独立构建 hash 不可复现”排除再写入。[资料4](#src-4)

但冻结前 1,850,142 字节在本轮定位段中属于 Agent 当时记录，M01630 是后态工具输出，尚未具备同等直接性的前后文件清单。M01636 是 `[System]` 打断通知，虽然再次提及互相覆盖，也不是独立第三方取证，不算负责人主动打断或独立竞态证明。本轮只支持“共享构建产物再次写入的证据较强；并发覆盖值得保留；具体写者及输入版本未锁定”。

另须区分两种 hash：隔离 worktree 各自构建结果不同，不能单独证明污染；同一被冻结产物在冻结后变更，才是冻结身份失效问题。前者构建不可复现，不会自动免除后者的变化。M01644 的平台模块表与 bundle 检查通过，只说明该时点加载契约检查通过，不能追溯证明 M01635 的旧 FAIL 当时错误，更不能替代 GUI。

**可证伪条件：** 取得冻结前后清单、精确 build PID/cwd、输入提交与 dirty diff；若为单一 owner 有意重建且及时重新冻结，应撤回“并发互相覆盖”，保留候选更新；若独立目录间只有 hash 差异而没有共享写入，应撤回污染归因。当前不指认哪个 Agent 写坏。

### 4.2 授权：只统计真实参数，不统计全文关键词

本轮对 JSONL 中 assistant 的 `tool_calls` 字段使用结构化 JSON 解析，逐调用读取 `function.name` 与 `arguments.sandbox_permissions`，没有把全文出现 `require_escalated` 的次数当作调用数。定向读到 E00352 确有 `Bash` 的 `sandbox_permissions=require_escalated`，但它早于 E00358 持续授权，不能拿来证明后续仍反复显式提权；E00444、E00452、E00458 的外层 Bash 调用为 `use_default`，只能证明这几条。[资料6](#src-6)

E00436 是 `peek_agent_progress` 的工具结果，其文本嵌套子 Agent 回合、参数、工具 schema；其中 schema 的 `require_escalated` 枚举不是实际取值。其嵌套文本在本轮尝试按完整 JSON 解析时失败，故没有据此作“所有子命令均默认”的结构化结论，也没有修造源文本或降为关键词统计。首案用 E00436 证明抽样默认调用仍须降格为“待完整嵌套载荷核验”；本轮可引用的默认参数来自前述可解析外层实际调用。

**保留结论：** 业务授权、仓库范围、执行模式、应用控制、浏览器认证不是一个开关。E00437/00444/00460 的确定性解释连续改变，足以批评“全部不会再弹”的承诺没有匹配可审计范围；但不能证明每次弹窗均由 Agent 主动索权，也不能宣布所有系统权限已解决。工具成功输出没有弹窗遥测，不能直接推出零弹窗。

**可证伪条件：** 完整调用与审批事件一一绑定，先去掉工具声明、进度回显和重复嵌套，再按时点比较授权生效前后。若同一实际调用只有系统强制门，应撤回该次人为再问；若承诺后来被明确限定为当前测试批次，需缩小“全局保证”的批评范围。弹窗归属仍未定案。
