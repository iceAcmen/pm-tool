# pm-tool 深度开放式复盘：开发工程师第一轮独立假说

日期：2026-10-21。性质：盲评研究稿，供第二轮交换反对意见；不是根因定案、测试结论或整改授权。

## 1. 研究边界与证据规则

本轮读取指定事实台账 P-001 至 P-164、消息摘录、豆包主轨迹脱敏 JSONL、主对话、TRAE 用户摘录和补充早期对话。应用户后续指定，追加读取四份当期独立 QA 原始发现，不读取其他复盘角色报告或上一版复盘。只读 Git 与必要历史源码；没有修改仓库、产品、测试、上游或配置，没有 fetch/pull、构建、测试、服务启动、提交、推送或加载 vendor。唯一写入为本报告。

历史证据按版本分层：上游 API 使用 `dsh-v0.2.1-alpha.2`；产品使用具体提交及其父版本。当前 HEAD `06a131c` 及未提交改动只说明本次研究环境，不用于反推当时产品。初版 schema 等缺陷在首个入库提交中已经修好，修复后的源码只能核验写入路径，不能充当缺陷原版的直接复现。

事实台账是索引，不是独立于其引用材料的第二份证据。主对话与 JSONL 是同源转写，也不算两份独立证明。ISS、QA 报告里的“根因”在本轮均视为待核验陈述。下面置信度分别针对直接机制和流程解释；“高”不代表已完成跨角色根因判定，缺原始复现时明确保留单源限制。

身份尤其需要谨慎：早期 `user` 消息包含父代理转译，例如 DB-o-L00049 的任务编排语句；DB-o-L00190 明确是在转贴 TRAE 返回结果。不能把这 97 条角色标签全部计为负责人原话。本文引用 `DB-m-Lxxxxx`、`DB-o-Lxxxxx` 分别对应指定主轨迹和早期轨迹原有完整 ID；TR-Uxx 对应 TRAE 摘录中的用户序号。

## 2. 独立假说

### H-DEV-01：将熟悉的容器与插件习惯迁移为未核验的宿主 API 假设

- **P 编号**：P-010、P-011、P-017、P-025；关联 P-079、P-085。
- **机制**：同步读不代表同步写；挂插件不代表裸 Context 已完成 effect 生命周期；类 Map 表不代表完整 Map API；记录键规则不代表表名规则。后来的 `Object.keys(Map)` 又把合法卡型集合变为空集合。这些都是对象形状与生命周期的不同误读，不是一行相同代码反复出错。
- **支持证据**：ISS-005/006/012/020；上游基线 `storage-domain/src/domain.ts:42-89` 明示 `keys/entries`、同步 `get`、Promise 写入。DB-m-L01031 报告注册表误枚举，`bb5ff2a` 的 BoardBento 修复注释与 `knownWidgetTypeSet()` 接线对应。
- **反证**：TypeScript 已在 P-017 阻止继续构建；多个错误被最小验证及时捕获，没有证据说明每项都流入正式产品。Map 误枚举只是看板现象的一条原因，不能解释全部重叠。
- **可证伪条件**：若当时已逐项核实准确 API，而失败来自依赖版本漂移或类型声明错误，此假说需降级；若注册表实际上不是 Map，则后段解释不成立。
- **置信度**：直接机制高；“缺少统一边界核验习惯”为中。属于重复假设家族，不足以证明个人长期粗心。

### H-DEV-02：交接材料未区分建议、已实现和已验证，增加错误 API 的传播机会

- **P 编号**：P-130、P-012、P-132；关联 P-125、P-127。
- **机制**：需求建议目录与技术骨架的实测目录并列，已修正命令仍残留在入口文档，服务旧名继续传播。执行者可能把“曾出现过的文字”当作当前合同。
- **支持证据**：DB-o-L00190/00193 分别列出接手发现与核验；`871f838` 实际修正三个启动命令位置、服务名并定稿布局；`38ad1a9` 又修正 progress 残留 `--profile pm web`，与 P-132 相符。
- **反证**：旧目录明确标为“建议、开发前确认”，不是两个已定方案相互冲突；不存在 conventions.md 也不等于规范缺失，已有 AGENTS/协作规则/知识库。TR-U2 明确区分 Host 自检与 R5 浏览器待验证，说明澄清确实发挥了作用。
- **可证伪条件**：若错误启动命令来自用户自行另写、没有来自文档的传播链，只能判为孤立输入错误；后期规范滞后也不能自动证明早期 API 错误由它引起。
- **置信度**：文档残留与修正高；导致具体开发错误中低。建议布局定稿是正常设计演进，不应与过期命令混为一类。

### H-DEV-03：创建 schema 的默认值侵入局部更新语义

- **P 编号**：P-026；对照 P-016。
- **机制**：patch 未提交某字段应表示“不修改”；若 create schema 的 `default(null)` 经 partial 仍补值，`{...current,...fields}` 会把关联清空。防删保护失效是下游结果，不是保护代码首先坏了。
- **支持证据**：ISS-021 描述只改 status 后 taskId/riskIssueId 被清空；`64187b0` 的 `meeting.ts` 已改为独立 optional 更新 schema，`meetings.ts:updateMeetingAction` 可核验解析后合并与关联检查路径。P-016 是另一种“未改变名称却重新授权名称”的更新边界错误。
- **反证**：未取得入库前错误 schema，不能声称本轮直接运行证实；P-016 没有默认值注入机制，二者只共享 patch 意图边界，不能合并为同一缺陷。
- **可证伪条件**：若故障版本的实际解析没有生成 null，而是表单主动提交 null，应改判前端载荷问题；需以当时依赖锁定版本和解析结果区分。
- **置信度**：直接机制中高、原版证据单源；流程解释中。不是简单拼写手误，是创建与更新合同的语义差异。

### H-DEV-04：父记录按钮与子记录保存范围不一致

- **P 编号**：P-027；相关 P-043、P-111。
- **机制**：“保存会议”在用户心中是保存抽屉全部改动，原实现只取父表单 FormData。子表单独立意味着父成功不证明子落盘；五列固定最小宽还超过 520px 抽屉内容区。
- **支持证据**：TR-U52 直接反馈溢出与漏保存；ISS-022；`64187b0:panel.tsx:1259-1275` 的修复读取 `form[data-action-form]` 并逐一执行子命令。
- **反证**：修复是父写入成功后串行子写入，不是一个事务；不应把“全部成功才关闭”说成“失败时全部零写”。本轮没有证据证明该阶段实际发生中途失败或重复新增。
- **可证伪条件**：若原版父按钮已统一提交子项、故障实际为后端拒绝或按钮命中错误，需改判；若设计明确让子项独立保存且用户已得到清晰提示，责任边界也需调整。
- **置信度**：直接机制高；“完整保存旅程未被验证”中高。跨页面表单难看只能提示共性调查，不能证明都漏保存。

### H-DEV-05：操作按钮、焦点与等待态没有组成可完成的用户路径

- **P 编号**：P-149、P-150、P-077、P-091、P-092、P-112、P-162。
- **机制**：逻辑存在但只有难发现图标；键盘状态变化未连接视觉焦点；点击行与热键当前行不一致；窄屏主动藏标签；慢请求无等待反馈；恢复 dry-run 没有 confirm 入口。代码可调用与用户能完成是不同属性。
- **支持证据**：DB-o-L01207 八项验收反馈及 L01216 技术回执；`38f3512` 前后差异实际补了高亮、文字按钮、模型选择和等待态，删除窄屏 `color:transparent/width:32px`。P-162 仅以事实台账为单源。
- **反证**：八项反馈包含“深色通过”和“生产未测”，不能写成八项全失败。图标存在不等于入口完全未接；模型切换从助手移到副驾也可能是新体验要求，需核对当时合同。
- **可证伪条件**：同一被测版本、视口与输入步骤能稳定找到并完成动作，会削弱“缺入口”；热键若被宿主截获，则需把焦点接线与宿主事件边界分开。
- **置信度**：窄屏标签直接机制高；其他项中；把这些全部归为用户不会操作低且不成立。

### H-DEV-06：动态 bundle 合同被误当成普通打包器的依赖解析

- **P 编号**：P-021、P-022、P-157、P-158、P-161。
- **机制**：声明目录不是 JS 入口；打包成功不代表 roster 能回答外部 require；文件在磁盘也不代表 factory 已注册；profile 根补丁不等于包内 manifest 声明的补丁。
- **支持证据**：ISS-016/017；B8 原始 QA 中 patch ENOENT、schemas 同步 require 失败；DB-m-L01517/01524/01531。上游基线 `modules/src/client/system.ts:325-377` 只同步查 seed/cache/factories，异步块才经过拉取、登记、materialize。
- **反证**：宿主机制不是任意坏工具，它在依赖不满足时明确报错；B8 后续闭环恢复了 editor/formula 两个异步块，不能依据中途单包方案声称“最终已永久取消懒加载”。P-161 未额外展开原始提交，仅作重复现象索引。
- **可证伪条件**：证明故障时 factories 已注册相应模块、声明补丁确实完整，或版本已切换到另一加载器，则这条链应拆分重查。
- **置信度**：直接机制高；“工程验证沿用普通 bundler 心智”中高。存在跨日期重复家族，但不是所有白屏的唯一解释。

### H-DEV-07：验证器提前提供缺失能力，产生构建假阳性

- **P 编号**：P-158；对照 P-005、P-018、P-019、P-020、P-023、P-119、P-120。
- **机制**：先把 schemasFactory 塞入 requireMap，再调用入口，实际上替产品完成了宿主没有做的注册。验证的环境比生产更强，因此入口错误被遮住。另一类测试错误来自固定顺序、错误初始状态或选错操作对象，应分别看待。
- **支持证据**：B8 QA 的 FAIL2 与 entry-only 新门明确记载禁预载；上游基线的 makeRequire 没有这种注入步骤。早期 ISS 和事实台账列出了测试预期错误，与生产缺陷有明确区别。
- **反证**：发现问题后验证器和原始报告主动撤回旧 READY，这证明独立审查有纠偏能力，不支持“所有测试都是假的”。本轮未运行验证器，不能将修后静态结论扩大成 GUI PASS。
- **可证伪条件**：若真实宿主确实在入口前注册相同 factory，预注入不算假阳性；若当时验证对象就是已预载环境，也要重定验证范围，而非指控伪造。
- **置信度**：B8 直接机制高、原 QA 单源加宿主合同核验；流程解释中高。误判家族不等于所有误判具有同一原因。

### H-DEV-08：字符串替换修打包错误引入生成代码损坏

- **P 编号**：P-159；相关 P-022、P-158。
- **机制**：JavaScript replace 的替换字符串会解释 `$&` 为整段匹配。若内联正文也含此字面量而未隔离，替换可能注入旧 require 文本、破坏转义，形成语法非法 bundle。
- **支持证据**：B8 QA 的“构建回归”给出 escapeRegex、注入内容、SyntaxError 与证据过期时间关系。`2aaffcb:tsdown.config.ts` 可见后续复杂字符串剥壳、内联共享块插件，但不能拿该修后版本复现旧回归。
- **反证**：目前只证实一次具体替换失误；不能据此认定所有构建插件都不可靠。手写转换在当前工具约束下可能是合理选择，关键是语法与加载顺序有没有验证。
- **可证伪条件**：若故障版使用函数替换且原样返回正文，或 SyntaxError 已在替换前存在，`$&` 解释应撤回。
- **置信度**：直接机制中高、原版单源；把它升级成流程结构性缺陷中低。先按局部实现回归处理，第二轮再讨论为何旧绿证据仍被引用。

### H-DEV-09：响应式显示投影不是持久布局的可逆编辑格式

- **P 编号**：P-056、P-079、P-085、P-101、P-102、P-107。
- **机制**：canonical 是保存的 12 列坐标；投影只是适配当前宽度。四舍五入、minW 夹紧和单列堆叠会丢失信息。RGL 被动 onLayoutChange 再反算，可能把展示重排写回草稿；配置面板缩小容器又触发断点，数值输入立即夹紧进一步互相干扰。
- **支持证据**：`ee52d9e^:projection.ts:28-79` 可见缩放及单列信息丢失；`ee52d9e` 去掉 ResizeObserver 编辑列切换、被动回写，改显式 drag/resize stop 和数字应用；DB-m-L02007/L02038/L02068 记录症状与修后保存链路。
- **反证**：P-107 在该补丁后仍被用户报告，说明补丁不等于全部拖动策略正确；RGL 碰撞下推本身可能是既定行为，问题还包括可控性与连续操作。旧布局靠左也可能真实来自已保存坐标，不能擅自判数据已坏。
- **可证伪条件**：若无操作切宽、开配置、挂载均不改变 draft，或故障只源于 CSS 高度越界，应撤回对应回写解释。
- **置信度**：代码机制高；对每次历史堆叠的覆盖程度中。属于布局状态所有权家族，不是纯换色问题。

### H-DEV-10：网格不相交不能保证实际卡体不覆盖邻卡

- **P 编号**：P-079、P-085、P-101、P-102；相关 P-033。
- **机制**：投影后两个矩形可能相交；即使坐标已去碰撞，slot 只有 minHeight、内部内容自然高度不受约束仍会越界。旧窄屏 `!important` 又可推翻内联坐标，形成第三个布局决定者。
- **支持证据**：`889f7a9` 先做展示坐标去碰撞；`7f44c46` 再把 minHeight 改明确 height，闭合卡体 100% 高度链并移除旧规则；DB-m-L01965 解释渲染覆盖，P-102 随后明确说堆叠已解决但宽高仍不可编辑。
- **反证**：固定高度与内滚会改善覆盖但可能恶化阅读，不能把“无相交”当成“美观通过”；单张截图不证明密集、长内容和所有视口。
- **可证伪条件**：同版实测 slot/card bbox 一直受限且没有实际相交，需转查投影、层叠或截图版本；只修坐标即可消失的实例不归高度链。
- **置信度**：直接机制高；同屏压力未被充分验收中高。相似用户措辞包含不同机制，必须分案而后归家族。

### H-DEV-11：就地反馈在正常页面旁出现时改变了布局，而非业务数据消失

- **P 编号**：P-152；相关 P-149、P-080、P-114。
- **机制**：甘特 flex 首行包含固定 labels、可缩 scroll，以及新增 `flex-basis:100%` hint；没有 wrap 时，提示挤占时间轴空间，使画布宽度近零。刷新清提示后图恢复，符合状态依赖渲染错误。
- **支持证据**：DB-o-L01497 的准确更新字串；`eb41b30` 的 CSS 差异增加 flex-wrap 并解释 shrink；同补丁 quiet 成功反馈、去二次 refresh，显示确有多条反馈路径。
- **反证**：quiet、定时清除和去重复刷新是一起落地的，不能只看成功补丁就证明各项都必要。既有证据没有说明任务写入丢失，不应称数据白屏。
- **可证伪条件**：故障版 DOM 中时间轴已卸载而非宽度归零，或者关闭 hint 仍不恢复，应转查快照与条件渲染。
- **置信度**：直接机制高；“未测试反馈出现时布局”中高。是状态组合遗漏，未证明属于宿主故障或用户拖错。

### H-DEV-12：整区草稿替换把新增格式误用于已有历史实体

- **P 编号**：P-154；对照 P-026、P-027。
- **机制**：编辑现有资料/进展时 normalize 只从已有数组取 max，然后从空 out 数组重新发 at/pl ID、只建 rv-1。覆盖完整记录时，未提交的软删项和旧修订一并消失。单次写入原子性只能保证整批落盘，不能保证内容语义正确。
- **支持证据**：B2-P3 QA 的富种子 before/after 和 `commitTaskDraft/normalize*Drafts` 路径定位；B8 后续源码快审明确编辑改 ops、raw 限 create，构成同批修复方向的交叉记录，但两报告的独立性仍不能仅按文件数认定。
- **反证**：空数组首次创建使用 raw draft 并非同样破坏；报告记录的是候选故障，不证明负责人正式数据已被损坏。后续修复状态不能抹掉历史，也不能据历史断言当前仍坏。
- **可证伪条件**：故障版本编辑载荷若已带逐项 ops 且 normalize 保留 IDs/revisions/deletedAt，需重新定位；富数组 round-trip 不变可直接挑战此机制。
- **置信度**：机制高但本轮依据 QA 单源复现；“只测空种子导致漏出”中高。与 schema patch 不是同一错误，只共享“未提交内容不得当作空值”的不变量。

### H-DEV-13：同一业务的多条输入路径校验与前后端枚举不一致

- **P 编号**：P-155、P-156；相关 P-116、P-153。
- **机制**：selectedRefs 校验严格，不代表 excerpts 路径也做同项目、软删检查；双字段并存没有互斥就静默忽略意图。交付物写选择器可以省略 wrapped，但展示分组不能因此丢失后端合法记录。
- **支持证据**：B6 backup QA 的 D1-D3 修前接受与修后拒绝；enum gap 的 backend 五值与 UI 四值、STATUS_ORDER 缺 wrapped；B8 后续记载 wrapped 分组已修。
- **反证**：写入口有意不提供 wrapped 可接受，不能强制全枚举都可写；单一路径通过不说明跨项目一定发生数据泄露。后端拒绝复验与 UI 待测是两种状态。
- **可证伪条件**：若两条输入当时共用同一校验器，或 wrapped 通过兜底分组可见，需撤回对应缺口。
- **置信度**：直接机制高、取证主要依赖当期 QA；“多分片没有共享可执行合同”中。不能从枚举漂移推定整个数据模型错误。

### H-DEV-14：源码存在、路由可达和默认用户可见被当成同一种完成

- **P 编号**：P-077、P-091、P-092、P-100、P-101、P-162；对照 P-130。
- **机制**：服务端实体、组件、导航、父 props、收件区形状、默认 feature flag、宿主 slot 分属不同连接点。漏一处即可形成“已实现但看不到”；列表只读也不等于新增编辑入口完整。
- **支持证据**：`8f668bb` 已有 OKR/习惯视图，但 `6b0d2a3` 又补桌面导航、收件区透传与队列项目字典适配；原 queue 误按 top/rest 读取项目字典会假空态。`2aaffcb:panel.tsx:665-668` 默认 pilot off，DB-m-L01824 撤回“全落地”；L01681 记录习惯点击仍在 OKR。
- **反证**：保留旧布局、不自动加新卡可能是保护个性化的正确选择；对话内卡可能只在插件副驾，未承诺宿主全局聊天。不能把未找到等同未编码。
- **可证伪条件**：同版本默认配置、正确导航下能完成旅程，且发布说明清楚限定试点，则应改判交付表达而非接线缺陷。
- **置信度**：部分直接机制高；每次“没改”的具体运行态归因中。入口证明必须独立于函数存在证明。

### H-DEV-15：共享构建输出破坏候选冻结与证据的稳定对象

- **P 编号**：P-099、P-157 至 P-159；相关 P-124。
- **机制**：不同分片即使只改各自源码，整包 build 仍写同一 lib。冻结前后再次覆盖 client.js/chunks 会让源码、候选、扫描和 GUI 证据不再指向同一对象，旧绿结论被误用于新产物。
- **支持证据**：DB-m-L01625 输出 editor/formula/client 的体积，L01628 明确观察“client 大小变化、块重生成”，L01636 系统通知报告整包构建覆盖；B8 QA 多次标注检查在最终 inlineSync 之前、旧 RUN expired。
- **反证**：系统打断不是负责人指令；仅有文件变化不能定位哪个代理，也不能排除单 owner 的后续合法重建。HEAD 领先远程或工作树脏也不自动证明构建竞态。
- **可证伪条件**：若进程记录证明只有一个 builder、不可变候选从未变化，且各次检查均绑定自己的 manifest，流程解释需缩小为快照沟通过期。
- **置信度**：构建共享机制高；具体并发主体与管理责任中。不能以用户允许并行为“允许共享输出互相覆盖”的同义词。

### H-DEV-16：客观进度不是多画一个百分比，而是派生值来源与消费者迁移

- **P 编号**：P-153；相关 P-034、P-093。
- **机制**：父子任务平均会重复计数，状态 done 不等于证据充分，时间消耗不等于完成量。新增 derive 函数后若旧图仍用 legacy progress/status，数字虽可渲染却与用户要的“符合实际”相冲突。
- **支持证据**：DB-o-L01527 明确提诉求；L01534 是执行者方案，不应当作负责人已逐条确认。`9ef27f6` 实现 checklist/叶子汇总、null 证据不足，同时保留 deprecated progressRatio 并注明阶段三迁移；后续 `8759e53`、`ef80674` 提交说明记录 UI 切换和死代码删除。
- **反证**：阶段式后端先行本身合理，不等于虚报交付；清单仍需人定义，不能称统计已还原真实世界。负责人提出新的数据价值要求不等于推翻此前全部功能。
- **可证伪条件**：若旧消费者在声明上线时已全部迁移且有 calcVersion/覆盖范围说明，此项仅是正常演进；若用户实际接受主观百分比，则需重查诉求。
- **置信度**：派生合同机制高；上线期间口径漂移中。第二轮应讨论缺证据值的展示与汇报历史，而非只争论算法。

## 3. 对单一责任解释的反驳与负责人侧证据

“工具是唯一责任”解释不了 create 默认覆盖、整区重发 ID、错误枚举、CSS flex shrink 与预注入测试：这些是执行者编写或连接出来的直接机制。动态模块表和浏览器认证也有明确安全、加载合同，不是因为不方便就可判工具有错。P-164 中执行者把 Impeccable 定为“防守型”并直接认作根因，缺少同需求、同状态、同验收下的对照；本轮不接受这一工具效果结论。

“负责人是唯一责任”同样不成立。TR-U4/U5/U15、DB-o-L00258 和 P-143/P-146/P-149 反复要求自行功能验证、独立专家与自动/人工分层；P-118 明确要求举一反三。不能把用户未亲自发现所有缺陷当作开发免责条件，也不能将系统停滞通知算作他频繁干预。

负责人侧仍有可讨论的贡献因素：P-041 在设计认可同时加入高自由度配置、公式与数据源，明显扩大工程范围；P-098 增加资料/进展的历史与引用义务；P-048/P-151 允许验收与开发并行，可能增加候选归属和优先级压力；P-067 的“每页每按钮、国际领先”缺少稳定比较尺度。这些支持“范围与评价边界需要共同明确”，但没有证据证明负责人要求删去历史、绕过测试、假注 factory 或发布失败版本。

反证也应保留：DB-m-L00252 执行者自己已识别配置看板是大功能并提架构方案；设计偏好经选图逐步具体化，功能障碍并不随审美变化而消失。应检验开发是否把新增诉求拆成可验收增量、主动报告限制，再谈负责人是否承担需求节奏责任。宽泛授权不等于缺陷豁免，授权矛盾也不等于代码错误的直接原因。

## 4. 第二轮待挑战的证据与判断边界

| 议题 | 目前不能定案 | 需要的挑战证据 |
| --- | --- | --- |
| schema/草稿 | 候选故障是否伤及正式历史数据 | 缺陷版 SHA 或冻结文件、实际解析载荷、富种子原始前后记录 |
| 看板连续拖动 | P-107 是否仍来自投影回写，还是下推策略/状态滞后 | 同版连续操作、draft/canonical/DOM 三层差分，不能只看坐标单测 |
| 构建共享 | 谁写入、是否同时写、冻结对象有没有被改 | 构建 PID/时间线、输出目录归属、候选 manifest 与被测 SHA |
| 发布可见性 | pilot、能力门、导航、运行版本各自占比 | 默认用户配置下逐入口证据，正式服务对应 worktree/tag |
| GUI与测试 | 哪些属于误判，哪些是真缺陷漏测 | 同版本、同 fixture、同动作的原始证据，不使用撤回结论作现行证据 |
| 客观进度 | 迁移期是否被误称全部上线 | 版本公告、消费者清单、calcVersion 与无证据展示合同 |

本轮保留的共同候选解释是：**边界合同、状态所有权、交付物身份和完整旅程的证明经常没有对齐**。它只是跨案例待检验的流程假说，不能替代上面各条直接代码机制。已捕获的手误、重复缺陷家族、真实工具能力限制、合法需求演进以及负责人节奏选择必须分别保留；根因排序与责任分配留待反方交换之后。
