本轮限定六个目标：开发初案、PM 初案、QA 初案（缺件）、P154 的 B2-P3 原始 QA、P157/P158/P159 的 B8 原始 QA、包含 P149 的早期对话。实际完成五个目标的读取，没有追加其他角色初案、现行业务源码或新的测试报告。规则与技能读取、目标文件存在性和只读 Git 身份核对不作为扩展研究目标。

原始报告优先于复盘概括。本轮通过 `git log`、`git show 2aaffcb:<报告路径>` 与只读差异核对确认，两份当期 QA 报告已在 `2aaffcb` 入库，当前文件与 HEAD 无差异。但入库版本已经包含后续修复叙述，仍不是最初故障源码；不能把其“源码快审”段或当前业务源码反推成故障当时已经正确。B8 的中途 OPEN、证据 expired 与文首 fix2 闭环必须按时间分别阅读。

事实编号是检索 ID，不是新增独立证据。早期对话是原轨迹的转写：保留 `DB-o_000E1LJmvjj-Lxxxxx`，不把 Markdown 文件行号当作原轨迹行号。QA 报告包含的复现结果属于历史证据，本轮未重新执行探针。同一报告中的定位、回顾、修复要求不是三份独立来源。

全程只研究。未 fetch/pull、安装、build、test、运行 verify、启动或停止服务、提交、推送、加载 vendor；未改产品、仓库、`docs/testing/`、上游或系统配置。唯一写入是本文件。原有脏工作树和本地领先提交不作为错误或责任证据。

## 2. 第二轮核心立场

开发的具体机制解释“怎样坏”，系统假说解释“为何多次没有挡住、为什么证明被扩大”。两层不互相取代。漏 `await`、patch 默认值注入、编辑重建稳定 ID、展示枚举漏 `wrapped`、替身预载 factory、`$&` 损坏生成代码，各有可检验的输入和失效路径。把它们全部改名为“需求不清”“测试不足”或“管理失序”，会失去修复对象；只列代码错误而不追查为何反复以局部绿宣称整体就绪，也不能解释返工链。

目前保留的系统候选是：**不同层的合同、验证对象与完成表述未持续对齐**。它能同时容纳“合法宿主依赖如何加载”“已存历史如何局部修改”“用户入口如何完成”“哪次构建对应哪次证据”，但尚不能定为唯一根因。没有逐批合同、候选身份和实际执行记录，不给责任比例，也不把所有案例塞进一个因果链。

静态检查、离线脚本和替身均有合法用途。失效的是部分检查声称能证明、实际上没有检查的范围，以及部分替身替产品补上的缺失行为。真实 GUI 也不能替代历史数据不变量；构建语法门也不能替代真实宿主激活。证据应按层相互补充，而不是选择一种方法宣布其余无用。

## 3. 九条跨角色质疑

### Q-DEV2-01：向 PM H-PM-07/08 质疑，旅程遗漏不等于所有脚本无效

**被挑战判断。** PM 将接口验收漏掉完整旅程、GUI 分派扩大化列为重要假说，方向成立；若进一步推为“离线脚本无用”或“必须全部改成人工目视”，则超出证据。PM 初案并未明言所有脚本无用，因此这里挑战的是假说的推广边界，不把不存在的主张强加给 PM。

**证据。** P149 对应 `DB-o_000E1LJmvjj-L01207`，包含键盘、窄屏、等待反馈和可发现性问题；同一早期对话 `L00799` 则记载焦点回退选择器根本不存在、此前没有真实焦点断言。后者说明一个具体 DOM 假设和一个断言缺口，不说明存储读回、零写回滚或入口语法检查失去价值。P154 QA 第24-26行明确指出空数组种子覆盖不到富数组往返，也是覆盖不足，不是自动化天然无效。

**开发异议。** 应区分静态文本命中、选择器存在、事件发出、焦点实际落点、界面反馈、持久化结果。静态选择器失败只能推翻依赖该选择器的证据；按键 reducer 单测正确也只能证明 reducer，不证明页面焦点接线。脚本若真正读取焦点、可见状态和保存后数据，可以给独立专家有效原始证据。

**可证伪条件。** 若相同故障版本、合法步骤和原始日志表明焦点实际正确且用户没有遵循前置条件，应撤回该实例的接线归因；若既定脚本已经断言真实焦点却仍放行，需核查断言与被测构建绑定，而不是继续归为“缺断言”。

**保留未知。** 本轮只有早期回执和用户结果，未读取当时 E2E 脚本全文；不能评估全部脚本的真假阳性率。置信度：局部覆盖边界高，整体测试策略归因中。

### Q-DEV2-02：向 QA 原始 P154 质疑，三个失效结果不能扩写成正式历史已损坏

**被挑战判断。** B2-P3 报告给出的 HARDFAIL 和稳定 ID 要求有直接机制支持；“修订塌缩”须进一步拆开其实际证明对象，不能顺势宣称所有现存进展历史已被业务数据永久破坏。

**证据。** 原报告第5-15行：隔离临时 domain、零正式数据；at-1/at-2 变为 at-3/at-4；软删 pl-1 原有两次修订，提交后整项消失；active pl-2 原本仅 rev1，提交后变为 pl-3/rev1。第19-22行定位 `out=[]`、新发 ID 和固定 `revisions:[rv-1]`；第26行说明此前只测空数组。

**开发异议。** 此富种子已经直接证明 ID 变号及软删记录连带历史丢失，是足够严重的候选数据完整性缺陷。但 active pl-2 的修订数是 1→1，不能单凭该行直接证明“active 多修订被塌缩”。固定 rv-1 的代码定位支持该机制预测；更强的独立实验还需 active 多修订种子。软删记录两修订全部丢失与 active 多修订压成一条应分开记录。

**可证伪条件。** 缺陷版本的富数组往返若保留既有 ID、deletedAt 和全部 revisions，整区覆盖归因应重查；另以 active 两次以上修订的种子单独验证，若不塌缩，就撤回该分支预测。无需触碰正式数据即可判断。

**保留未知。** 临时探针已删除，本轮没有原版载荷或故障源码冻结文件；未知正式数据是否受影响、多少记录受影响、后续是否恢复。历史缺陷成立不等于当前仍开放。置信度：已报告的隔离损坏高，实际正式影响未知。

### Q-DEV2-03：向 QA 原始 P154 质疑，原子性要求存在一处待澄清的文字冲突

**被挑战判断。** 报告第32行要求“同事务校验失败整体零写”；第50行又写“整批零写，已成功项不回滚、未成功项不落库，basic 原值保持”。若“已成功项”指本次同批已写项，两句不能同时成立。

**证据。** P154 原始报告第30-33行、第49-52行。该冲突只属于报告的验收文字，不是已证明业务实现违反原子性。

**开发异议。** 开发不能用模糊验收词自行选择“失败后保留本次前半批”。较一致的解释是：事务前已存在的成功事实不变，本次失败批次不落库；但这是待 QA 确认的解释，不能代为改写专家用例。stable ID/历史保留与失败零写也是不同不变量，必须分别验证。

**可证伪条件。** 若原探针或 QA 澄清证明“已成功项”明确指本批前的既有数据，文字歧义解除；若指本批新操作，则必须明确合同是全原子还是允许部分成功，不能同时标两种结果通过。

**保留未知。** 未取得专家澄清或当时事务级载荷。本轮不修改 QA 报告，不给其复验 PASS。置信度：文本冲突高，实际行为未知。

### Q-DEV2-04：向 QA 原始 P158 质疑，替身允许宿主依赖，但不得替业务补注册

**被挑战判断。** P158 旧验证器预载 schemas 确实掩盖真实宿主失败；不能把该发现扩大为“不得使用任何替身”或“替身不得提供任何依赖”。

**证据。** B8 第56-61行记录入口同步 `require('./client.schemas.js')`，真实模块表没有该 factory；旧 `verify-client-bundle.mjs` 先 `loadChunkFactory`，再向 `requireMap` 注入 schemasFactory。第70-78行的新门仍允许平台 react 系模块和按真实 `require.async` 序列登记 factory；第81-86行承认私有 require 不可导入时可用公开 bench，但须标明不是真实宿主。

**开发异议。** 判据是替身是否提供合同允许的外部依赖及真实时序，而不是有没有 mock。平台正常预置 react 可以；真实宿主入口前并未登记 schemas，测试却先登记它，就替包补上缺失的装载能力。只有运行产品自己的入口或异步加载路径能获得的能力，不应由 fixture 在测试前免费提供。

**可证伪条件。** 若找到当时真实宿主确实入口前预置同一 schemas factory 的原始记录，旧注入不能再被称为该故障的假阳性原因；若替身与宿主在同一包、同一加载顺序下对漏模块结果不同，忠实模型要求没有满足。

**保留未知。** 真实宿主私有实现未在本轮重读，也未执行新门；B8 原报告与初案引用的历史宿主核验可共同约束解释，但不是本轮新复现。置信度：预载越界高，替身全面等价未证明。

### Q-DEV2-05：向 PM H-PM-06/09 与 QA 原始 B8 质疑，一次 `$&` 触发可以属于重复的结构性家族

**被挑战判断。** PM 提示“看不见新版”可能有装载原因而不只范围错位，开发接受。初案对 `$&` 仅按局部回归处理仍偏窄；但同样不能把 `$&` 扩写成所有构建失败的共同根因，或因 B8 中途 OPEN 宣称当前仍阻塞。

**证据。** P157 对应 B8 第16-25行：冻结遗漏 package-local patch，profile 根补丁不能替代；P158 对应第56-61行：入口 schemas 同步 require 与人工预载错配；P159 对应第11-14行：替换字符串解释 `$&`，把旧 require 文本注入 zod 字符串，生成 SyntaxError。第47-54行明确旧绿在最终转换落地前；第5-9行记 fix2 静态闭环、两块异步加载恢复，但旧94/94不作为该新候选证据。

**开发异议。** 三次直接机制不同，家族共同点是“声明、产物、宿主序列、检查范围和候选身份没有一致证明”。一次 `$&` 是局部触发器；其发生在连续包修复、生成转换和旧证据过期链中，使结构性构建合同假说值得上调。当前材料不能定位为“并行必然互相覆盖”，单人合法重建也会使旧证据失效。

**可证伪条件。** 若逐次不可变 manifest 证明每次新转换都在宣称 READY 前重新做语法、入口加载及冻结核对，则结构性“证明错位”需缩小为独立局部缺陷；若原替换使用函数回调原样返回、错误早在转换前存在，则 `$&` 直接归因需撤回。

**保留未知。** 本轮未取故障 inlineSync 原文件、构建进程和完整时间线，不能证明实际责任人、并发次数或所有历史 bundle 问题同源。fix2 静态关闭不等于 GUI PASS，历史过期94/94也不等于 fix2 完整隔离已完成。置信度：家族候选中，唯一系统根因低。

### Q-DEV2-06：向 PM H-PM-09 质疑，负责人增加范围不能解释基础不变量被违反

**被挑战判断。** PM 合理地保留批量目标、广泛配置与收口压力的贡献因素；但范围增加不是漏 `await`、patch 默认覆盖、合法 `wrapped` 展示丢行的机制解释，更不是免责理由。

**证据。** 开发初案 H-DEV-01 引 P010/P011 与历史 API 写入 Promise；H-DEV-03 引 P026/ISS-021 的局部 status 更新清空关联；H-DEV-13 引 P156 的后端五值与 UI 分组四值。此三项本轮未展开新原文件，严格标为书面初案继承证据。新核对的 B8 第102行记载 wrapped 分组已修，不反推过去从未遗漏。PM H-PM-04 本身承认执行端此前已识别看板为大功能并给出阶段估算。

**开发异议。** 复杂度可提高犯错机会，却不能推出负责人要求异步落盘不等完成、未提交字段被清空、既有合法记录不可见。写选择器不允许 wrapped 与读展示必须保留 wrapped 是两种合同；不能用简化写操作的需求解释读侧丢行。要把范围压力升级为实际因果，至少要有明确要求删减哪些验证、错误如何由该删减漏出的链路。

**可证伪条件。** 若当时确认合同明确允许先返回未持久化结果、status-only 也清关联，或 wrapped 是故障版本非法值，开发机制须调整；若有负责人明确否决已报告的必要验证，可讨论具体风险接受，但不能自动豁免其他未告知缺陷。

**保留未知。** 未量化规模、投入、期限与错误概率；没有证据证明负责人强制跳过独立门。这里反对单因免责，不否认需求节奏可能贡献收口压力。置信度：责任边界高，压力因果中低。

### Q-DEV2-07：向 PM H-PM-08 与早期执行回执质疑，P149 必须保留原组数和状态

**被挑战判断。** PM 已写“八类不等于八类失败”，应进一步固定为原八组6 FAIL、1 PASS、1 NOT_RUN，而不能沿用下一条助手的“7 条失败”。

**证据。** `DB-o_000E1LJmvjj-L01207` 的1/2/4/5/6/7组失败，3组深色通过，8组生产模型未测。`L01208` 却称“你的7条失败全部重开”，是原始回执的计数错误。第6组又包含移动入口、行动项、甘特、等待态等多个现象，不能将八组、缺陷数和复验用例数混算。

**开发异议。** 六个失败组足以支持当期旅程存在问题，无需夸大为七或八个失败。原未测状态应记录 NOT_RUN，不倒改成历史 PASS 或历史 MANUAL_PENDING；后续因本人凭据需协作可另记分层状态。深色单组通过也不能推出全站所有状态对比度通过。

**可证伪条件。** 若完整原输入在当前转写之外另有第七失败组，应另行核验并登记新增来源；不能以助手总结覆盖当前明确八组。若有凭据且自动化本可完成生产验证，则“需本人参与”分类也需重查。

**保留未知。** 用户报告不是开发根因复现；`L01216` 的技术回执也是执行者陈述，不能单独替专家判定每个分项。置信度：原组数与计数错误高，逐分项根因不一。

### Q-DEV2-08：向 PM H-PM-09 质疑，并行授权不等于取消冻结或错误由并行必然导致

**被挑战判断。** 收口压力和共享输出是合理研究方向，但不能把负责人“先做一部分开发任务并行”译成“同意修改冻结 UI、互覆 lib 或带病发布”。

**证据。** P151 对应 `DB-o_000E1LJmvjj-L01286`；紧随 `L01287/L01291` 明确不开发大型新功能，先补自动回归和规划、不碰冻结 UI。`L01295/L01297` 将数据安全修复单独分批；`L01303` 执行回执称撞上另一 Agent 修改/构建出现中间态失败，随后统一收口。

**开发异议。** 这些原文反对“负责人要求无门禁并行”的概括，也显示执行端知道隔离风险。`L01303` 可以支持共享工作区中间态的调查，但不能仅凭一句回顾证明构建竞争的精确主体、时长和正式影响。新增后端改动虽不碰 UI，也可能影响集成证据；“不改 UI”不是“所有旧证据自动有效”。

**可证伪条件。** 若有清楚逐批依赖图、不可变输出及各自 manifest，证明后端改动未影响被冻结用例，则证据扩大失效应缩范围；若负责人另有明确取消门禁指令，须按真实时间和作用域重新评估。

**保留未知。** 本轮未查构建 PID、输出时间戳和候选 manifest，不能确认实际并发因果。置信度：授权语义高，具体竞争归因中低。

### Q-DEV2-09：向 PM H-PM-14/07 质疑，数据价值问题与历史保存问题不可互相替代

**被挑战判断。** “可计算不代表真实世界完成”的产品提醒成立，但 P154 是保存语义直接破坏，不是仅缺进度解释或来源展示；增加覆盖率、来源标签不能恢复被覆盖的历史。

**证据。** P154 原始 QA 第7-22行记录已有 ID、软删与修订的变化；PM H-PM-14 引 P153 与 ADL-050 区分清单比例、验收状态和外部证明。二者关注的对象不同。P154 第32-33行提出逐项操作与富种子，不是改百分比公式。

**开发异议。** 应先保留事实，再计算和展示事实。一次事务写得完整，不代表写入内容保持历史语义；一个百分比可复算，也不代表证据覆盖真实工作。两种不变量都重要，不能用“增加用户解释”替代数据修复，也不能用“数据不丢”代替进度定义被用户理解。

**可证伪条件。** 若缺陷版本保持全部事实而仅展示过滤掉历史，应改判读侧可见性；若进度合同本来就声明只计算当前清单且用户能正确理解，产品语义风险应降低。

**保留未知。** 本轮未验证任何现行进度页面或导出，不能判断当前仍误导。置信度：两层区别高，现行残余风险未知。
