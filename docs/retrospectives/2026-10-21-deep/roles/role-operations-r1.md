## 运维与协作假设

### H-OPS-01：临时进程没有可靠所有权，清理动作越过正式边界

- **P 编号**：P-001、P-133。
- **可能机制**：隔离了业务数据，却未隔离进程身份；正式与临时实例共享 argv 主体及 cwd，模糊匹配把“同类程序”误当“本任务创建的程序”。直接触发是杀进程命令选择，结构风险是清理缺少所有权凭证。
- **原证据**：ISS-027 记载误杀 3080/3091、仅端口不同、从 v0.7.1 恢复。早期 L00349–354 也出现验收结束后服务残留；但当次报告明确定位 PID 32599 再停止，不能倒推那次也误杀。[cite:3](#source-3)[cite:6](#source-6)
- **反证**：事故恢复记录称业务零损；后续 progress 多次记录隔离端口与单 PID 收尾。此次原轨迹 L02239 仍有多个实例，只说明需要分辨，不证明它们均是泄漏。
- **证伪**：补查事故实际命令与 PID 命中集；若停服来自无关崩溃，或两正式实例未被信号命中，需撤回该触发归因。未来以创建记录、端口、PID、启动时间共同验证。
- **置信度**：事故机制高，但原执行命令未在指定主轨迹找到；“目前仍普遍误杀”无证据。

### H-OPS-02：服务切换缺少连续执行能力和中断恢复点

- **P 编号**：P-140、P-141、P-144、P-103。
- **可能机制**：停止旧服务与启动新服务跨越任务/执行层；中断发生在两步之间，用户看到停滞，组织者仍用“重建”统称构建、重启、浏览器验收。问题可能是切换非连续，而非构建耗时。
- **原证据**：早期 L00582 说先停旧服务，L00584 用户称一晚未完；L00587 自述代码与构建已完成、服务因取消停着。L00648 明确“旧服务已停、新版尚未启动”；L00785–786 则把剩余动作交回用户前台终端。[cite:3](#source-3)
- **反证**：上述解释多为助手自述，无完整时间线；睡眠、工具会话退出或前台终端能力不足都可能参与。P-103 的 L02239 实测 LISTEN 加 HTTP 401，不能归为又一次服务停机。
- **证伪**：对齐停止、构建完成、启动、取消和反馈时间；若无服务空窗，撤回停服机制。再判断执行层是否确实无法自行启动，而非默认要求用户接续。
- **置信度**：中高；空窗有明确记载，“一晚”的实际持续时间未量化。

### H-OPS-03：工具链、shell 环境与服务凭据被混为一次配置

- **P 编号**：P-004、P-006、P-009、P-132。
- **可能机制**：工具内能运行 Node，不等于系统终端已安装；新 shell 能读 key，不等于旧 dsh 进程继承了 key。把配置文件、shell 和存活进程当作同步状态，会误判模型不可用。
- **原证据**：ISS-001/004/024 分别记载注入 PATH、新 shell 需加载 nvm、旧进程不含变量。早期 L00283–288 的全新 zsh/curl 成功，之后 L00303 仍反馈失败，说明直连成功不能代表宿主调用链成功。[cite:3](#source-3)[cite:6](#source-6)
- **反证**：随后录入 credentials service 与重启成功，说明 key 本身并非持续失效；免费模型的真实响应失败也可能来自限流或能力，不全是配置。
- **证伪**：仅检查服务凭据是否存在、凭据来源和 provider 路由，禁止输出值；若失败进程已正确取到同一路由凭据，转查模型与网络。档案中打印完整进程环境的诊断范例应另做安全审查，不在本轮执行。
- **置信度**：已记载旧进程机制高；对后续所有 AI 失败的解释力低。

### H-OPS-04：浏览器认证隔离是安全边界，交付入口却没有覆盖它

- **P 编号**：P-015、P-103–105、P-123、P-145–146。
- **可能机制**：执行端已认证的标签页被误当成用户所有浏览器可用；裸 URL 丢失入场凭据。另一层问题是子代理桌面能力不能由用户口头授权扩展，认证权限与工具能力被混称“授权不足”。
- **原证据**：主轨迹 L02239/244 有 PID 44388、LISTEN、401 和明确 authentication required；L02240 承认先前裸地址不完整，L02241 的接管请求因未先开网页被拒。早期 L00904 明确区分桌面不支持和 3080 未认证；当前 progress §最新接续仍将 Finder E2E 标为 Main 采证待办。[cite:2](#source-2)[cite:3](#source-3)[cite:7](#source-7)
- **反证**：不共享 Cookie 本身不是缺陷，也未证明 token 只能使用一次；助手后来明确保留认证、只优化入口。工具能力也随执行角色和时间变化，不能认定平台永远做不了。
- **证伪**：用独立浏览器上下文核对合法入场、重启后的认证生命周期及 PM 真挂载，不跨浏览器复制会话。若同一未经认证上下文裸地址可进入，应重新核查服务策略。
- **置信度**：入口遗漏高；token 寿命、桌面端完整体验仍未验证。

### H-OPS-05：tag、源码与运行构建缺少足够精细的对应关系

- **P 编号**：P-119、P-124–125、P-077、P-100–101。
- **可能机制**：包版本同为 0.7.4，却跨越历史发布与大量后续源码；HEAD、实际构建目录、软链目标和已加载页面不是同一概念。只用一个版本号易把测试或“没变化”反馈归错对象。
- **原证据**：Git 显示 v0.7.4 注解对象为 `30c99e7077ad38538265d5025b35cce3b97a998f`，剥离提交为 `5fdb2d7525b669244a735c8e3018306c299c1b91`，与当前 HEAD 不同；两提交中的 package version 均为 0.7.4。ISS-027 记录软链版本归属，主轨迹 L01403 明确未提交候选不能只由 HEAD 代表。[cite:6](#source-6)[cite:9](#source-9)
- **反证**：注解对象与提交 SHA 不同是正常结构，未打新 tag 的候选沿用版本也不自动违规。L01807 已报告冻结与推送，用户 L01808 仍觉得没改，可能只是变化不显眼。
- **证伪**：绑定运行实例、源码提交及脏补丁、构建目录、实际下发产物和浏览器上下文；若完全同批仍不符，则查功能/视觉实现，不能继续甩给缓存。
- **置信度**：身份描述不足高；“用户看到旧 bundle”仅待证假设。产物 hash 可作同轮证据，不能替代 tag 身份或假设跨 worktree 必须相同。

### H-OPS-06：17 ahead 与脏候选扩大迁移缺口，但冻结不等于失控

- **P 编号**：P-124、P-119。
- **可能机制**：远端 clone 看不到本地 17 个提交及未提交产品、launcher 变更；同机接手还需理解多个 worktree 和在途所有权。“仓库唯一事实源”未明确是远端、主树还是冻结候选。
- **原证据**：本轮 `git status`、`git log origin/main..HEAD` 与 `git worktree list`；17 个本地提交集中在 10 月 20 日晚，工作树还有新补丁。onboarding 最新区明确未提交、未放行、最终 Git 由组织者安排。[cite:8](#source-8)[cite:9](#source-9)
- **反证**：这些可能是待独立复验的合理暂存；盲目 push 或为“干净”删除补丁反而违规。早期 L00221 转译任务已明确保护未提交 R9、不直接 pull，说明并非从未治理。
- **证伪**：请另一平台仅凭现有可移植交接恢复同一候选；若有完整补丁、文件指纹及所有者映射，风险下调。此次未 fetch，17 不是实时远端落后统计。
- **置信度**：本地缺口高；丢成果、未授权提交或历史分叉未证实。

### H-OPS-07：多个“当前”增加歧义，已修知识没有稳定进入下次指令

- **P 编号**：P-130、P-132、P-125、P-127。
- **可能机制**：知识条目更新，模板、正文和当前快照仍各自保留旧值；“最新/更严格”不足以判断历史规则何时失效。错误命令可从旧模板重新进入用户路径。
- **原证据**：早期 L00190/193 发现布局建议与已选骨架不一致、旧服务名和启动命令。Git `871f838` 记录修正文档；之后早期 L00282 又给 `--profile pm web`，L00292 用户运行报错，形成具体复发链。当前 onboarding L71、78、83、98–102 及 progress L340–345 仍有多个时期的“当前”。[cite:3](#source-3)[cite:7](#source-7)[cite:8](#source-8)[cite:9](#source-9)
- **反证**：首次布局明确是待确认建议，不全是冲突错误；conventions 缺失也不证明有断链。档案提供日期、历史与最新入口，细读可以识别。
- **证伪**：新平台只读引导文件能否一致识别当前命令、候选、规则生效状态；若能，重复只是冗余。对原错误命令，需查是否来自外部输入而非所示助手命令。
- **置信度**：启动命令复发高；多个快照导致某次实际误改的因果仍中等。

### H-OPS-08：业务审批、工具提权和桌面能力没有分开承诺

- **P 编号**：P-134–138、P-126、P-145。
- **可能机制**：所有者持续授权可解决业务决策许可，不能改变工具参数、OS 安全闸或 Main-only 能力。组织者承诺所有层“再不弹窗”，再用未经核查的原因解释复发。
- **原证据**：早期 L00358/385/431/434/443 多次直接要求不再问；L00386 归于系统询问模式，L00437 改称显式提权参数，L00444 又改称图形/网络授权。TR-U55 有针对豆包修改、提交、推送的持续授权；collaboration §4.4 与 onboarding L92 的口径不同。[cite:3](#source-3)[cite:4](#source-4)[cite:5](#source-5)[cite:8](#source-8)
- **反证**：确可同时存在不同闸门；后续“默认作用域跑通”说明部分修复可能真实有效。持续授权不是不存在，也不能把所有询问都定为 Agent 故意不执行。
- **证伪**：拿每次弹窗实际发起者、原工具参数、当时模式及动作逐一配对；若全是不可代办安全确认，撤回“审批执行失配”，只保留错误承诺。
- **置信度**：混层承诺高；具体提权标记致因中等，早期摘录无完整工具请求，不能认证其自述。

### H-OPS-09：备份污染风险来自隐式默认路径，路径不清又是另一问题

- **P 编号**：P-149、P-121、P-125、P-160（收口补入）。
- **可能机制**：测试隔离主数据而恢复前安全备份仍走默认目录，污染共享备份；默认路径依赖模块位置，又易与包根、仓库根混淆。用户“不知道备份在哪”则是交付反馈，不等于污染。
- **原证据**：Git `0f852d0` 提交正文记载增加注入 directory，“测试备份目录不再用真实 backups”；onboarding L85 更正 builtin 为仓库 `packages/backups/`。早期 L01207 直接投诉备份路径无提示。冻结台账新增 P-160 明确记载恢复测试向共享 `packages/backups` 写入 50 个测试快照，产品往返正确但隔离失败；该历史污染不能再仅称“风险”，本轮未读其测试原件或污染清单。[cite:1](#source-1)[cite:3](#source-3)[cite:8](#source-8)[cite:9](#source-9)
- **反证**：主轨迹 L01786/1800 的 guard 记录 228 资产 before=after、污染 0。没有指定证据证明目前备份仍遭污染；50 个是新增台账报告数量，不是本轮独立清点。
- **证伪**：未来先列全部有效写目录及优先级，再以目录集合、hash、mtime 检查；若所有备份早已注入临时目录，撤回当前污染假设。零污染只适用于守卫实际监测范围。
- **置信度**：历史污染按台账与修复记录增强至高；具体写入调用链待原件核对，当前污染无证据。路径可发现性问题高。

### H-OPS-10：worktree 的名字与空格成为隐藏环境合同

- **P 编号**：P-121、P-130、P-122。
- **可能机制**：导出断言绑定 `/pm-tool/exports/` 而非实际导出 root；子进程入口或 cwd 含空格处理不当。主根绿但迁移树红，是可移植性缺口，不必是业务回归。
- **原证据**：主轨迹 L02203 记录 export 路径断言和 settings reopen 失败；当前 progress L35 将后者定位为含空格 cwd，并否定缺文件猜测。worktree 清单确有多个 `Application Support` 路径。[cite:2](#source-2)[cite:7](#source-7)[cite:9](#source-9)
- **反证**：尚未只读产品/测试源码或复跑；后者仍可能涉及环境变量、fixture 或入口解析，不能确定就是 shell 引号。P-122 合法回填不足也不等于代码有错。
- **证伪**：后续独立执行同提交在普通、空格、改名目录的配对验证，固定数据与 env，仅变路径。若失败不随路径变化，应撤回路径机制。
- **置信度**：路径耦合中高；具体代码根因待查。不得删除失败断言或把主根绿冒充迁移通过。

### H-OPS-11：可移植成果存在，但原始证据与指令来源仍不可完整迁移

- **P 编号**：P-128–130、P-124–126。
- **可能机制**：Markdown/Git 足够接着编码，却不足以重建审批、失败和决策来源；会话 ID、平台绝对路径及截图引用未组成可独立读取的脱敏证据包。父指令转译丢失谁决定“写哪里”。
- **原证据**：早期 L00049 将伙伴档案指定在仓库，L00067 用户纠正不入 Git；L00070/79 对持久路径的说法又发生变化。TR-U56 请求读豆包对话；U57 要求全量复盘。当前事实 P-128 只能作为上一轮证据覆盖不足的报告，本轮没有读旧复盘。[cite:1](#source-1)[cite:3](#source-3)[cite:4](#source-4)
- **反证**：现有证据已脱敏、有消息 ID；仓库多次成功交接。原始聊天不必全部进 Git，尤其不能为了移植保存秘密或个人画像。
- **证伪**：由无平台历史权限者只凭脱敏包复核关键主张、授权范围和原始发言；全部能复核则缺口缩小。需要区分直接用户、父转译、系统通知，不能把资料重复当独立来源。
- **置信度**：关键证据迁移不充分中高；不是“仓库文档毫无价值”。

### H-OPS-12：状态观察把无新快照、能力阻塞和真实卡死混为一种

- **P 编号**：P-068–070、P-076、P-099、P-140–141、P-144、P-147。
- **可能机制**：快照滞后、执行无反馈与服务切换等待共用“卡住”词，重启组织者可能丢上下文或重复构建；反过来只相信百分比，又可能错过真实停滞。
- **原证据**：主轨迹 L00784 综合快照、文件产出和消息无回应判断；L00882 用户则看到子任务已完成；L01636 为系统打断通知，不能算负责人主动取消。早期 L00647/785/987 是用户直接因无反馈终止，性质不同。[cite:2](#source-2)[cite:3](#source-3)
- **反证**：L00784 已使用多信号，并非只盯百分比；中断可能是在解死锁。未见 caffeinate 只能说明当时守护不在，不能单独证明睡眠造成某次停滞。
- **证伪**：对齐执行事件、等待条件、最后产物、消息回执和取消时间；若子任务确在持续有效运行，则撤回“卡死”；若无有效推进，再审重启是否保存所有权和候选身份。
- **置信度**：观测分类不足中高；各次具体死锁、睡眠因果待证。没有延迟分布，不报告“通常滞后多久”。

### H-OPS-13：负责人授权常把设计认可与实施扩界放在同句，执行端需拆分边界

- **P 编号**：P-041、P-048、P-067、P-071、P-074、P-098、P-151。
- **可能机制**：认可效果同时新增完整自由配置、认可设计同时新增资料/进展字段，改变实现和测试面；“验一下同时下一步”易被解释成验收未完也开新功能。负责人可改善批准粒度，执行端应回报原范围、新范围、暂停范围与服务切换许可。
- **原证据**：主轨迹 L00251/1157、早期 L01286 的并行诉求。但 P-151 未证明当时仍有阻断门，不能单据这句判违规。[cite:2](#source-2)[cite:3](#source-3)
- **反证**：TR-U2 要求最窄纵切与先报文件；早期 L00176 明确验收、推送、暂停三项；L01324 明确验收后升级。主轨迹 L00858 要求只探讨，L00722 明确“前面完成之后”，L00892 提供详细约束；这些都反驳“负责人从不明确”。设计探索的偏好变化也合法。
- **证伪**：若执行端已拆开范围并获确认，却仍失败，则主因转向代码、设计或测试。若相同冻结范围可稳定交付、扩界后反复漂移，才增强此假设。
- **置信度**：范围变化事实高；对返工的净贡献中低。不能把拖拽算法、信息层级或审美试验一概归罪流程。

## 第一轮边界与对抗交换请求

### H-OPS-14：冻结交付完整性与入口装载顺序未被测试模型忠实覆盖

- **P 编号**：P-157–159、P-161。
- **可能机制**：测试环境预先提供 schema 工厂，掩盖真实入口同步 require 的先后约束；冻结文件集合又漏掉包声明的 patch。尝试内联修复时字符串替换 `$&` 具有替换语义，可能进一步破坏字面量。三者是不同失败层，不能统称“运维部署没做好”。
- **原证据**：冻结至 164 的台账分别记载 patch 缺失导致 ENOENT、预载 requireMap 假阳性、inlineSync 构建后 `node --check` SyntaxError，以及离线全绿但 zod require 导致真实浏览器不激活。[cite:1](#source-1)
- **反证**：P-158/159 可能是试验性修复暴露的问题，不能未经时间核对说已进入正式服务；源码声明 patch 不等于本轮已核查冻结包。测试原件均未读。
- **证伪**：第二轮对齐冻结清单、package 声明、真实入口装载顺序和修复前后产物；若真实入口也已先注册工厂，则预载不构成因果；若 `$&` 所在替换并未触及出错字面量，应撤回该解释。
- **置信度**：按台账报告的失败现象高，独立机制复核中等；当前版本是否仍存在未知。

### H-OPS-15：自责式原因说明不能替代受控证据

- **P 编号**：P-164、P-030、P-128。
- **可能机制**：助手在用户投诉后先认责，再将工具定位、自己选择风格直接称为“根因”；这种答复降低争论，却可能把设计实现、内容和真实用户偏好排除得过早。
- **原证据**：主轨迹 L00049 已实际读取，先说“想清楚了根因”，随后把 Impeccable 称为防守型工具；新增 P-164 明确登记未先展示受控对照。[cite:1](#source-1)[cite:2](#source-2)
- **反证**：助手提出先取审美锚点、先做设计稿，是合理的下一步，不证明工具无效；用户多轮改变偏好也不自动证明其需求表达导致失败。
- **证伪**：比较相同内容、范围和数据条件下不同方法的真实产出；若换方法而不换实现仍显著改善，才增强工具解释。第二轮保留代码、信息结构及审美探索的竞争原因。
- **置信度**：过早下因果结论高；所述工具特性是否真实、对失败贡献多大，未证实。

收口纳入 P-154–164：P-154–156 涉数据修订、跨实体校验与前后端枚举合同，P-162 涉确认入口不可达，优先交开发/测试视角，运维不擅自给出根因；P-163 的 219 提交和经验倍数不是请求级额度账，不用于推算卡死、并行成本或本轮研究预算。相关原件反证全部留第二轮，不继续检索。

当前最值得优先对抗核查的是进程所有权、切换空窗、身份绑定及授权混层；均不要求把正常浏览器隔离、安全校验或独立测试门删除。P-119/120 的旧误判撤回和 P-122/123 的阻塞仅按指定台账、progress 的转述引用，没有越权审查测试专家原件或重新判 PASS。

下一轮应补证，而非先加更多规范：事故实际命令；重建至认证的时间线；每次弹窗的发起层；冻结源码到实际页面的对应记录；测试完整写目录；父指令与用户原话配对。可考虑单一生效快照、候选可移植包、服务所有权记录、分层授权表，但这些只是待辩建议，本轮未写入项目规则。

尤其保留两个竞争解释：用户“没变化”可能是正确版本的设计效果不足；反复界面失败可能是组件和布局实现问题。运维只能排除版本、会话与执行环境误归因，不能替设计和开发证明产品质量。
