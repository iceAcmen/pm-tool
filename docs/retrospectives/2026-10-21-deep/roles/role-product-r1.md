# pm-tool 深度复盘：产品经理视角首轮盲评

> 本报告供多角色对抗轮逐条攻击、补证和撤回假设使用。仅研究，不给根因或责任定案；全部假设的分类暂不判定。日期：2026-10-21。P-129 至 P-153 已结合早期对话核对；最终冻结的 P-154 至 P-164 已登记竞争解释与补证边界，保留原问题编号。

## 1. 证据范围与独立性

本轮未读取本次其他角色报告或上一版复盘结论；只读事实台账、脱敏摘录、主轨迹提取、追加的早期组织者对话及历史产品与协作文档。未修改仓库、产品、测试，未构建、启停服务、提交、推送或加载 vendor 指令。

证据记号：`M-Lxxxxx` 指 `DB-m_0cwRI8ya92K-Lxxxxx`；`E-Lxxxxx` 指 `DB-o_000E1LJmvjj-Lxxxxx`；TR 保留完整 ID。行号是原轨迹物理行，不是 Markdown 行。文档引用另标实际行号。

现有 JSONL 是保留来源、行号、角色和文本的提取物，不是全部原始运行载荷；图片引用不等于已查看图片，Agent 宣称“核验通过”不等于本轮核验。早期组织者的 `user` 角色含父 Agent 转译，例如 E-L00049，不能当负责人逐字原话；TR 云历史含审批嵌套，不能把系统说明当用户意见。M-L00786、M-L01636 的 `[System]` 打断通知不用于证明负责人主动打断。

不能以记录条数宣称完整：缺少部分上游对话、审批上下文、完整子代理链、请求级成本与耗时、部分设计图和运行态对照。台账、摘录、Agent 回顾可能同源，不算三份独立证据。以下置信度仅指“机制值得保留的程度”，不代表已证实因果，更不代表责任比例。

## 2. 产品侧可证伪假设

### H-PM-01：阶段目标更新与当前承诺没有充分区分

- **对应 P**：P-071、074、077、125、127、153。
- **可能机制**：初期“本地离线最小闭环”与后期“代执行、技术耦合、UI 无缝、潜在团队用户”是不同阶段目标。若旧约束仍作为当前总纲，执行者会按旧边界交付，新目标却被表述为已满足。
- **支持证据**：`requirements.md:12-25` 定义 MVP；M-L00892 明确离线原则可让渡、当前为练习场而未来希望代替公司系统。文档 `requirements.md:5-8,46-57` 同时保留“生成型暂缓”和已实现 R13–R15。
- **反证**：M-L00972 明确 H6 常驻推送不急；不能把暂缓推送判成违约。初期 MVP 决策本身合理，目标演进不是错误。
- **可证伪条件**：找出每批当时有效、经确认的阶段目标与交付边界，证明用户看到的交付说明始终准确引用它们，差异仅来自后续新增目标。
- **置信度**：中；**分类**：暂不判定。

### H-PM-02：愿景级语言缺少可判定的近期成功标准

- **对应 P**：P-035、067、073、074、075。
- **可能机制**：“国际领先”“无懈可击”适合表达期望，却无法直接成为完成条件。执行端若不追问近期参照、代价和停止条件，容易用图集数量、规范篇幅或多角色数量替代产品效果。
- **支持证据**：M-L00722 要求逐页逐控件领先；M-L00871 要求先设计严谨脑暴流程；M-L00932 要求最终方案通俗、可见亮点。
- **反证**：M-L00892 的 H10 已给出“平台独特性”参照，不能说负责人始终未表达目标。H8/H9 关于维护带宽与 API 稳定性是期望或判断，不是已验证事实。
- **可证伪条件**：补出当时明确的核心使用旅程、取舍和停止条件，且证明执行与验收都按这些条件而非数量评价。
- **置信度**：中；**分类**：暂不判定。

### H-PM-03：反馈被过度翻译为视觉规则，造成看似反复的需求

- **对应 P**：P-036 至 040、094、097。
- **可能机制**：执行端把局部“不喜欢黄”翻译成保留单色方向，把“简洁清爽”扩大为变更信息架构或隐藏卡片能力。用户纠正解释时，就容易被误读为审美变化。
- **支持证据**：M-L00207 反对偏黄；M-L00208 保留“单色图表”方向；M-L00214 澄清并非必须单主色，M-L00215 承认过度收敛。M-L01120 追问旧卡片，M-L01121 承认未完整展示个性化卡片模式。
- **反证**：TR-6aca242effde095bd0adb94c-L0001-U30 希望酷炫，M-L01096 后来要求抛弃旧偏好，确有探索变化；但不能推导重叠、不可编辑也是偏好变化。
- **可证伪条件**：还原每轮完整方案和确认语境，证明单色及卡片能力的范围变化均由负责人明确要求。
- **置信度**：高（局部解释偏差），中（解释全部返工）；**分类**：暂不判定。

### H-PM-04：灵活能力与简单操作没有被拆成不同使用层

- **对应 P**：P-041、079、102、106 至 108。
- **可能机制**：用户要“必要时足够灵活”，实现却可能将所有数据源、公式、筛选、几何参数同层暴露。可配置性越多，默认路径越复杂；自由画布的碰撞、尺寸和持久化又是独立难题。
- **支持证据**：M-L00251 提出广泛配置能力；M-L02314 抱怨配置繁琐、面板挡卡；M-L01982 区分“堆叠已解决”与“宽高仍不能编辑”。
- **反证**：M-L00252、00263、00267 已明确这是大功能，给出三阶段及 20–26 人日估算和编辑态原型，不能断言完全未评估范围。该估算也不证明真实投入与排期。
- **可证伪条件**：证明普通用户的最短编辑路径已隐藏高级配置，复杂度反馈只来自高级模式；另以真实旧布局排除几何实现问题。
- **置信度**：中高；**分类**：暂不判定。

### H-PM-05：信息丰富被当成决策有效，产生重复和主次失衡

- **对应 P**：P-033、034、038、040、052、093、109、113、116。
- **可能机制**：按实体或组件增加卡片，缺少“现在判断什么、随后处理什么”的排序。同一指标多处出现，关系却不可见；提醒反而不显眼。多加图表不能自动补上行动价值。
- **支持证据**：M-L00175 指人员上下卡片无增量；M-L00237 指逾期和关注清单重复；M-L01059 指概览重复计数、提醒不显眼；M-L02314 要求任务与里程碑、交付物双向关系。
- **反证**：概览和钻取中的重复可能必要；M-L00231 主动要求同时保留两个模块，显示用户也在通过预览探索组合。
- **可证伪条件**：为每块信息补出不同使用者、决策问题与后续动作，实测证明重复块支持不同决策且不妨碍扫描。
- **置信度**：中高；**分类**：暂不判定。

### H-PM-06：设计方向认可被扩大为完整实现认可

- **对应 P**：P-041、095 至 098、100、101。
- **可能机制**：效果图只覆盖代表页或关闭态，认可后执行与完成回报却覆盖全页面、抽屉、下拉和编辑态。功能底座完成进一步被等同于用户已看到新版。
- **支持证据**：M-L01119 质疑只做三类页面，M-L01157 明确全部页面、抽屉和下拉都要出图。M-L01805/01807 宣称主要真实验收完成；M-L01808 表示像没改；M-L01824 随后说任务视觉默认 `pm-b1-pilot=off`、只覆盖任务页，撤回全量落地表述。
- **反证**：试点关闭可能是正确风险控制；它是否违约取决于承诺是否标明试点。Agent 的后续解释不是本轮代码验证。
- **可证伪条件**：补出当时承诺清单、运行版本、开关及逐页设计对照，证明交付一直明确为底座或局部试点。
- **置信度**：高（完成表述前后冲突），中（技术原因）；**分类**：暂不判定。

### H-PM-07：领域动作存在，但用户旅程与可发现性没有闭合

- **对应 P**：P-027、077、091、092、112、116、117、149、152。
- **可能机制**：命令、关联字段和 reducer 正确，不保证用户能找到入口、理解术语、保存子记录、看到反馈后继续原操作。按接口验收容易遗漏用户整段动作。
- **支持证据**：`issues-and-solutions.md:264-269` 记会议主保存未提交行动项；E-L01207 报移动和转任务入口、键盘与等待反馈问题；M-L01059 不知道如何维护 OKR/习惯；E-L01497 拖甘特后只剩更新字串；M-L02314 的抽屉干扰键盘调期。
- **反证**：E-L01216 说部分动作已存在于小图标，属于不可发现而非未开发；P-120 的“选择交付物”也不等于执行关联失败。
- **可证伪条件**：按初见用户的合法完整路径复核，证明入口明确、草稿/保存语义清楚、操作反馈不替换工作区。
- **置信度**：高（旅程缺口线索），中（当前是否仍存在）；**分类**：暂不判定。

### H-PM-08：验收分层被扩大成把可执行 GUI 工作留给负责人

- **对应 P**：P-084、119 至 123、131、143、145、146、149。
- **可能机制**：执行角色能力受限，被转译成“必须用户本人参与”；局部自动化通过又被扩大为整项通过，用户不得不重新发现本可自行测试的问题。
- **支持证据**：E-L00258 要求先自行目视；E-L00908 列出待人工键盘和窄屏；E-L00909 只豁免需本人配合项；E-L01207 提交八类结果，其中深色通过、生产模型未测、多项失败；E-L01208 承认分层扩大化。`collaboration.md:166-172` 明确不是豁免所有 BLOCKED。
- **反证**：P-123 确有 Main-only 能力门；P-122 长历史不能绕两天补记窗造数。P-119/120 还提示测试本身会误判，不能把每个 FAIL 直接算产品缺陷。八类结果不等于八类失败。
- **可证伪条件**：逐项证实当时确须本人认证或不可逆决策，且 GUI 子项没有被写成整项通过。
- **置信度**：中高；**分类**：暂不判定。

### H-PM-09：负责人批量安排与执行端承诺放大可能共同增加收口压力

- **对应 P**：P-048、066、067、098、101、151。
- **可能机制**：“继续下一步”“全量优化”“同时试点工具”混合缺陷、功能、研究和发布目标，若没有冻结范围与先后门，会拉长反馈循环。负责人侧可优化的是批次目标和停止条件，不是禁止提出新需求。
- **支持证据**：M-L00339 一边验一边继续；M-L00719 功能 OK 但样式差仍推进后项；M-L01407 让 B1–B8 与工具试点同时完成；E-L01286 请求并行。
- **反证**：E-L01287/01291 明确不做大型新功能，先补测和规划；E-L01295/01297 将数据安全修复单独分批。M-L00707、00868 要先清技术债，M-L01842 主动缩为看板专项。不能把并行请求等同强迫违反门禁。
- **可证伪条件**：逐批证明冻结、写文件归属、单一构建和放行状态完整，扩大范围不影响旧证据；或证明反馈周期延长只发生于环境阻塞。
- **置信度**：中；**分类**：暂不判定。

### H-PM-10：有效授权、规范提议和历史状态缺少统一生效口径

- **对应 P**：P-124 至 127、134 至 138。
- **可能机制**：授权更新已经发生，根规范仍保留逐次确认；建议门禁在一处待表决，另一处写成必须。执行者读不同入口，就得到不同许可与完成条件。
- **支持证据**：TR-6aca4c31ffde095bd0adc813-L0001-U55 明确对豆包持续自动修改、提交推送；E-L00358、00385、00443 反复授权并追问。`onboarding-prompt.md:92-94` 记持续授权，`collaboration.md:74-76` 仍为逐次确认；`AGENTS.md` §6A.1 待表决与 `system-ui-spec-20261017.md:306-326` 强制措辞不一。
- **反证**：持续业务授权不等于系统权限，更不允许绕过安全边界。未推送 17 提交也可能是正确冻结，不能单凭数量判同步失责。
- **可证伪条件**：补出明确优先级、生效日期、适用平台、撤销范围和每次确认来源，证明不同执行者实际得到同一规则。
- **置信度**：高（文本冲突），中（具体阻塞原因）；**分类**：暂不判定。

### H-PM-11：任务转译缺少对象、作用域与生效证据

- **对应 P**：P-028、029、060、076、129、133、138、140、141。
- **可能机制**：把个人伙伴配置转成产品仓库文件，或把“文件已写”“命令已去提权”当成用户界面已生效，主端到子端的语义丢失就会制造反复确认和不可信快照。
- **支持证据**：M-L00006 原要求改伙伴档案；E-L00049 父转译明确加上仓库落盘、提交；E-L00067 纠正“不进 Git”。E-L00070 说已持久生效，00072 用户仍看不到，00079 才定位云端入口。E-L00437 称授权问题已解决，00443 用户再问。
- **反证**：早期“产品成果入库”要求确可造成歧义；截图页、沙箱与云端也是能力事实，不全是转译问题。但歧义不能使中间态自动成为完成态。
- **可证伪条件**：出示原指令到子任务的对象/作用域校验，以及“完成”之前在真正目标界面的回读证据。
- **置信度**：高（个人档案局部），中（扩展到全部协作）；**分类**：暂不判定。

### H-PM-12：工具与多角色被当成质量保证，替代了问题论证

- **对应 P**：P-061 至 065、072、073、075、128、148。
- **可能机制**：选择某 Skill 或派多个同方向角色只能改变方法，不能证明设计适用、判断独立或结论正确。若方向由主端先定，再汇总同向建议，可能增加材料而不增加可检验认识。
- **支持证据**：M-L00869 质疑五方向预置且没有辩论；M-L00932 要专业过程但通俗成果；E-L01004 要 Agent 自行按上下文选 Skill。M-L00049 关于 Impeccable 是防守型工具的说法只是 Agent 归因，不是工具失效证据。
- **反证**：负责人引入专家和方法，是合理的质量诉求；M-L00873 要客观材料、00892 回答关键假设，表明不是只要更多角色。未经任务输入、引用与互相质疑记录，不能判全部多角色无效。
- **可证伪条件**：补出首轮独立任务输入、候选变化、反例、撤回与来源核验，证明方法确实改变选择而非包装原推荐。
- **置信度**：中；**分类**：暂不判定。

### H-PM-13：进入工作台也是产品交付，却被拆成运维说明

- **对应 P**：P-001、002、004、015、024、103 至 105、123、131、132。
- **可能机制**：“已起服”“HTTP 可达”“已有认证浏览器可用”不同于非技术用户能稳定进入。裸地址、环境变量和跨浏览器认证的解释成本，可能在每轮验收前重复消耗信任。
- **支持证据**：M-L02237 报无法访问，02240 自述裸链接 401，02249 要用户翻日志找 token；E-L00292 启动命令多余 `web`；`issues-and-solutions.md:37-45` 说明新 key 没进入旧进程。
- **反证**：浏览器 Cookie 不共享、loopback 限制和缺凭据是安全边界，不能直接叫工具坏。P-001 的误杀另属精确进程问题，也不是认证体验所致。
- **可证伪条件**：固定版本和权限条件下，已有清楚、可复现的首次进入与换浏览器路径，实际失败全部来自用户偏离已确认环境。
- **置信度**：中高（交付链缺口），中（各事件原因）；**分类**：暂不判定。

### H-PM-14：“客观百分比”需要界定证明对象，不能靠换公式解决

- **对应 P**：P-038、074、093、098、153。
- **可能机制**：清单勾选比例可复算，但不证明真实工作量、价值或外部验收完成。若界面只强调客观 100%，不显示覆盖率、待验收和资料依据，会把“可计算”误认成“真实完成”。
- **支持证据**：E-L01527 追问实际进度而非主观填数；`decision-log.md:36-43` 已区分清单完成、验收状态、覆盖率与用户自陈。M-L01157 要进展记录及附件，M-L00892 的 H1 指现实沟通和文档不实时入账，均显示只看数值不足。
- **反证**：ADL-050 已明确无清单为 null、拒绝全勾封顶 90%、不声称外部客观证明；E-L01572/01574 有修订过程。这是正向控制，不能判需求错误或当前一定误导。
- **可证伪条件**：实机各页和导出稳定展示证明对象、覆盖率、来源及待验收；用户能正确区分“清单全勾”和“交付验收通过”。
- **置信度**：中（残余语义风险）；**分类**：暂不判定。

## 3. 跨类别扫盲与竞争解释

| 类别 | 应保留的其他解释 | 产品视角不能越界下的结论 |
| --- | --- | --- |
| 开发与数据 | P-010/011 存储生命周期，P-016/017 API 与校验，P-021/022 bundle/主题，P-025/026 patch 与表名 | 接口错误可直接造成失败；不能一律归为需求不清。需开发对实际改动、首发与复发取证。 |
| 测试与证据 | P-005、018–020、023 的断言问题，P-119/120 的对象误判，P-121/122 环境与合法造数 | 增加测试数量不自动提高有效性；错误断言也不能被借来否认用户实测。 |
| 配置与工具 | P-006/008/009/012/013、015/024；P-028/029/031/032 的环境陈述 | 用户从未切换设备与工具运行在隔离通道可同时成立；不能把 Agent 的云端推断算用户操作事实。 |
| 研究与模型 | P-007 官方来源混淆，P-061 适用政策，P-062/063 子链成本，P-139 用户估计失败率 | 订阅投入不等于维护带宽、额度或模型稳定性实证；无请求级日志不报成功率、平均成本。 |
| 协作与运维 | P-060/068–070/076/099、124/130、133/140/144/147、151 | 静默不等于卡死，快照不等于真实进度；共享构建可能污染证据。系统打断也不等于负责人误操作。 |

“用户审美多变”只能解释部分方向探索，解释不了保存丢失、重叠、键盘失效和未呈现新版。“工具不好”解释不了 E-L00049 的对象转译和 M-L00214 的解释纠正；工具权限确有独立限制，不应否认。“自动测试不足”解释不了已经明确人工分层却错误分派、旧运行版本与新源码未绑定、设计认可范围被扩大。三种解释都只能作为局部竞争假设。

负责人侧也不免于检视：批次中混入愿景、修复与试点，广泛“都做”需要明确优先级；维护带宽及 API 稳定预期需要验证。但反复授权、要求先自测、缩小看板专项、回答关键假设、认可局部修复，都是反对“负责人只催进度、拒绝澄清、不断推翻需求”的证据。执行方应承担需求解释和风险说明职责，不能把非技术用户补反馈视为失职。

## 4. 对抗轮补证重点

首轮优先送审 H-PM-03、06、08、10、11，因其有较直接的指令或表述对照；其余不降格为附会，也不升格为根因。后续需要四组证据：

1. 每次“认可”对应哪版图、哪些页面和状态；原型、源码、开关、实际服务逐项如何绑定。
2. P-146 分层前后，每个人工项为何必须本人参与；P-149 实测失败为何此前被留出，是否真正与被测版本一致。
3. 授权和规范何时生效，父端怎样转译给子端；P-151 并行有没有跨批写入、共享构建或改变冻结候选。
4. 可配置看板与客观进度的真实完整旅程：旧布局、长内容、撤销、保存重进、关系下钻与来源解释。

可讨论的改进方向是“变更对象卡、阶段目标与本批非目标、设计覆盖对照、有效授权与门禁状态、用户旅程证据”，不是此轮立即加规则或开发。分类与方案均留待对抗；证据不足时应撤回或降置信，而非靠更多报告填满空白。

### 最终冻结补充的反证边界

P-154 至 P-164 在首稿落盘后补齐，本轮只核对冻结台账描述，未再展开其独立测试报告、提交或全部运行证据；以下是第二轮核验方向，不冒充已复现：

- P-154 稳定 ID/历史丢失、P-155 跨项目及软删校验、P-156 wrapped 前端丢行，是数据完整性和前后端合同的直接竞争解释。它们反对将返工全部归为审美、需求表达或负责人范围变化；H-PM-07/14 应与开发解释竞争，不将这些错误反推为用户要求有错。
- P-157 冻结包缺 patch、P-158 mock 预载假阳性、P-159 `$&` 替换破坏产物、P-161 zod 运行时，提示 H-PM-06 的“看不见新版”还可能有装载原因；不能只凭 Agent 承认范围错位排除它们。P-160 的 50 个共享备份污染指向隔离，不证明产品恢复往返失败。
- P-162 恢复缺确认/取消入口可补强 H-PM-07；P-163 无完整 trace 的额度倍数估算要求 H-PM-12 限制成本结论；P-164 正是“工具直接归因而无受控对照”的证据线索。台账冻结为 164 项，只表示索引范围固定，不表示原始记录完整、164 项均已独立复验或因果已明。
