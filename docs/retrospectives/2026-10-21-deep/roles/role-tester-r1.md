## 2. P-149 门分类专项核对

P-146/L00909 的负责人原句是：“除了需要我配合的测试用例，其他能够自动化完成的测试用例通过，则视为测试通过，把需要配合的测试用例记录下来发给我即可”。这是分层授权，不是让所有 GUI 变成人工项，更不是把未执行项改成 PASS。

## 3. 第一轮假设

### H-QA-01：临时工具受限被扩大成用例固有人工属性

**关联 P 号：P-131、P-145、P-146、P-149。支持：** A-L00906 已提出 Playwright 可覆盖键盘、视口、焦点、主题；L01206 却仍交付整组人工检查。L01208 明确认可“测试分层做错了”。Q 的人工登记与后来的 14 项自动/隔离 GUI 回归形成前后对照。机制可能是按最弱角色的能力划分门，而非按用例是否确须本人参与划分。

**反证：** Q `reverification-round2.md` §64 记录 Space 入口不送达、视口工具受限及正式认证缺口，并非凭空编造；后续 R3/R4 仍由用户手动闭环。本人配合确有局部必要。

**可证伪条件：** 提供当时逐用例、逐角色能力探测和安全限制，证明人工清单每个子项都没有合法自动路径，且可自动子项已另行覆盖。**置信度：高，限于分类过度扩大；不认定所有人工项均错。**

### H-QA-02：自动测试对实现细节过拟合，且某些替身主动补齐了真实宿主缺失

**关联 P 号：P-005、P-018、P-019、P-020、P-023、P-022、P-142、P-157、P-158、P-159、P-161。支持：** F 中固定异常顺序、排序名次、原已 achieved 的记录、转义文本、旧选择器均曾造成测试失败。Q `verify-isolation-fail-classification-20261020.md` 的 C1 绑定字面量 `return true`；更严重的是 `b8-packaging-fail-20261020.md` 的 FAIL2/P-158：旧 bundle 测试手动预载 schemas factory，补上了宿主不会提供的模块，形成假阳性。测试覆盖的是“补齐后的应用”，不是实际接缝。P-157 漏包内声明补丁、P-159 替换串破坏语法属于产品构建/交付缺陷；未检查声明资源、预载掩盖装载失败才是测试合同缺陷，不能混为一类。忠实的自动 entry-only 装载和语法检查能捕获这些问题，不必把所有检出责任都推给 GUI。

**反证：** Q 后来建立 entry-only 模块表门、禁预载，并对七项脚本重写逐条核对负例，见 `p2-2-independent-acceptance-20261017.md` §1.1。纠正测试不是天然“凑绿”。

**可证伪条件：** 证明旧契约明确要求固定顺序/旧选择器，或真实宿主同样预载 schemas；同时用故障注入证明替身仍能检出真实装载失败。**置信度：高，具体案例成立；尚无全测试套件误判率。**

### H-QA-03：角色名称不能独自证明独立性，但“普遍自签通过”目前证据不足

**关联 P 号：P-131、P-143、P-084、P-100。支持：** A-L00261/L00268 派“目视验证并修复”者，回传修 CSS 后 27/27 并推送；这是实现与自检合并。后期主端也亲自修上传路由并称主要验收完成，M-L01778–L01805。若汇总者再替正式签字，就可能失去独立门。

**反证：** 早期合并角色发生在后续独立门确立前，不能追溯定违规。Q 首轮验收明确测试者未改产品；R4 又区分作者自述、独立复跑。M-L02226 记录已读取独立专项报告且源码与冻结一致，不支持把该批直接指为自签。

**可证伪条件：** 每批提供实现者、采证者、正式审签者及原始审证记录；签字者未改产品、未照搬自报即可反驳该批指控。反向若只有开发口述 PASS，则提高怀疑。**置信度：中；合并角色事实高，后期违规自签未证实。**

### H-QA-04：对象与提交边界不明确，测试操作错误可能驱动无效产品返修

**关联 P 号：P-119、P-120、P-027、P-116、P-162。支持：** Q R1 §2 D-05 误取 Grid 占位列；R4 §4/§7 把删任务当删看板卡，又把仅 select 交付物当已关联。正确关联需 select→“关联交付物”→主保存→重开→反查。报告记录作者回退误判直连补丁，说明误判已影响修复方向。另须区分 P-162：Q `round3-gui-execution.md` S1-20 记录恢复演练后根本没有确认/取消按钮，这是用户提交路径缺失的已报告产品问题，不能套用“测试没点保存”的解释撤销。

**反证：** 测试撤回、禁用旧证据是有效纠错。若用户常误解选择即保存，产品也可能有提示不足；P-027 的“保存会议未保存行动项”是真实已记录问题，不能因本次 select-only 误操作就推翻。

**可证伪条件：** 用冻结用例证明原测试确实锁定正确实体并完成所有提交动作，重开仍无关联；或者合同原定选择即自动写。**置信度：高，误取/漏提交已记录；是否另有可用性缺陷为中。**

### H-QA-05：测试版本身份与正式运行身份可能混同，单写 HEAD 或 version 不够

**关联 P 号：P-119、P-124、P-125、P-100。支持：** R1 §1 撤回了“标记数量相同即前端相同”“启动时刻即后端冻结”的推断。Q `first-checkpoint-receipt-20261020.md` 明说 8dfed2d 是基线、v0.7.4 是历史 tag，新候选含未提交文件。M-L01824 又确认默认 OFF 的任务试点被表述为全页面落地。版本、构建、功能开关、页面部署分别成立才有用户可见结果。

**反证：** 未提交不等于无法测试：R3/R4 用 HEAD+tracked.diff+新增文件指纹建冻结树；R5 两文件另绑哈希，这是合理候选取证。包产物哈希用于认领字节，不应替代 tag/version 版本身份或要求跨 worktree 可复现哈希。

**可证伪条件：** 给出候选源清单、构建 manifest、运行解析路径、实际页面开关与部署审证的完整对应；证明用户所测与签字对象完全一致。**置信度：高，已有混同案例；不认定全部旧结论无效。**

### H-QA-06：失效规则欠缺受影响范围索引，既可能沿用旧证据，也可能触发无意义全重测

**关联 P 号：P-069、P-099、P-119、P-124。支持：** Q B8 报告明确模块表 PASS 发生在最终 inlineSync 改动之前，不能沿用；B1–B8 映射又串接多个冻结批次的拖缩、资料、报表证据。若只有“全绿计数”而没有代码接缝到用例的索引，汇总者难判断能继承什么。

**反证：** 同映射说明部分后续差异仅 CSS 尾部空行，并主动标旧候选 expired；纯空行不必让全部业务断言失效。规则本意是受影响结果过期，不是任何文档提交都全部作废。

**可证伪条件：** 展示每次差异的影响说明、受影响 CASE、重测证据及未重测理由；证明继承覆盖的装载链、共享样式和状态路径未变。**置信度：中高；局部失效成立，缺失索引的全局程度待查。**

### H-QA-07：门的可执行性受角色能力、认证和启服交接共同限制，不能归咎授权晚

**关联 P 号：P-123、P-140、P-141、P-143、P-144、P-145。支持：** Q R4 §3 的 Finder E2E 明确 Main-only；M-L01080 工具原文是“Subagent暂不支持操作电脑相关操作，请在MainAgent完成”。A-L00777–L00799 则出现反复启动、连接拒绝、无法向用户 Terminal 送按键，随后承认修复选择器根本不存在，重复重启并未补焦点断言。P-145 只是询问，A-L00904 明确否认授权晚。

**反证：** 休眠、真实服务退出、缺认证标签也是记录中的约束；已有主端采证成功案例。能力门并非不可解，也不是新建更多测试角色就会解。

**可证伪条件：** 时间线证明一次确切授权请求因负责人迟批直接卡住相应用例，并且批准后同一能力立即恢复。否则不能用“最高权限”解释角色能力门。**置信度：高，角色门事实；中，重复启服对总延误的贡献。**

### H-QA-08：合法 fixture 未在合同前准备，会把安全守卫误变成长期测试阻塞

**关联 P 号：P-122、P-118、P-139、P-149。支持：** R4 D-13 要验 >14 条历史折叠，现行回填仅过去两天；当天合法路径无法造足历史。不手改正式库正确，但“等真实多日”使这项门不可及时执行。慢响应、失败恢复若同样只等真实在线模型随机出错，也难稳定取证。

**反证：** 两天窗是安全/业务约束，不是产品缺陷；合法历史天然随时间累积。受控 fixture 能验证长列表渲染，却不能单独证明日常打卡写入和时间校验正确。

**可证伪条件：** 找到已批准的隔离时钟/种子生成入口，能产出通过 schema、关系、时间规则校验的合法历史，并有可重建步骤；或证明合同本就将长历史排除出本批。**置信度：高，当前缺口；改进收益中。建议研究隔离 fixture 合同，而非放宽生产回填或改系统时钟。**

### H-QA-09：隔离路径假设可能使测试门自己拒绝合法迁移场景

**关联 P 号：P-121、P-130、P-009。支持：** R4 §1.2 的 export 正则硬认 `/pm-tool/exports/`，冻结树换目录名即失败；settings 的空格路径子进程读源失败。A-L01313 还记录 guard 假定 exports 已存在，干净克隆会误红。这些首先是设施/可移植性问题，不能直接登记成候选业务回归。

**反证：** “七候选文件没碰脚本”不足以证明产品绝无缺陷；settings 的路径问题可能暴露真实命令解析风险。若合同只支持规范 cwd，偏离其布局也需先核是否有效环境。

**可证伪条件：** 在承诺支持的改名、含空格、干净克隆环境区分“实际行为错”和“断言位置错”，再与规范路径对照。若只有非承诺布局失败，则缩小指控。**置信度：高，路径假设存在；归属与支持边界为中。**

### H-QA-10：条件 PASS 容易在汇总中扩大范围，但机械全矩阵也可能成为不可执行门

**关联 P 号：P-077、P-084、P-094、P-100、P-127。支持：** M-L01095 同时写“全系统体验整治已完成”和四项待验；L01805 称主要验收完成，L01824 却撤回全页面落地。Q G3 工作表 G03/G06 明载窄屏只抽任务/抽屉/看板，G07 以 675 键盘行为替代 1440；`reachability-repair-20261018/final-review-20261018.md` 总称整体通过却保留多个未测子项。标题压缩了范围限制。

**反证：** G3 抽样理由公开、单行横滚有 M-L00849 负责人明示；R4/R5 逐子项、视口、主题限定 PASS，M-L02218 专项也明确不外推。P-127 的四视口×200%仍有待表决问题，不能追溯作为所有早期批次硬标准。

**可证伪条件：** 找到实施前获批的范围/抽样合同，证明摘要与放行均仅指该范围，未测项不含发布承诺；反向若本来逐页必验却无授权缩减，提升疑点。**置信度：高，摘要范围漂移；具体抽样违规为中低。**

### H-QA-11：负责人愿景缺少可测拆分，但严苛门的工程转译也应接受审视

**关联 P 号：P-041、P-066、P-067、P-074、P-143、P-146。支持：** “国际领先”“所有元素可配置”难直接形成验收终点。A-L00683 原意是找专职测试、全量回归、再报下一计划，L00684 执行方将其强化为新增功能五类全过再继续。若能力/fixture/审美参照未同时准备，规则更严格不等于交付更可靠。

**反证：** 负责人早在 P-131 要求先自行目视；P-149 的错误是具体可测的，不是审美反复。P-074 后来回答“国际领先”的参照是平台独特性，且多次给设计稿明确反馈。不能把基础控件错乱归咎用户不会写验收标准，也不能据上述转译推定所有者未批准规则。

**可证伪条件：** 证明每批开工前已有确认的可观察目标、非目标、体验样例和能力预算；或发现负责人明确拒绝缩小范围而坚持无界目标。**置信度：中；责任应分给提出愿景与负责可测转译双方，不下个人能力评价。**

### H-QA-12：验收未完时推进的风险取决于改动依赖，不能仅据“并行”归责负责人

### H-QA-13：空种子原子提交通过，不代表富历史编辑仍保持数据完整性

**关联 P 号：P-154、P-155、P-156。支持：** 已读 Q `b2-p3-destructive-draft-qa-20261020.md` §1–3：合法富种子有 at-1/at-2、pl-1 两次修订后软删、pl-2 active；编辑整区回传后 at-ID 重分配、软删历史消失、修订塌缩。此前 atomic 测试只在空数组首次提交，缺少“已有历史再编辑”的往返。因此原子性只证明一次事务内成功或失败，不能证明对象身份、软删和修订保全。这是可离线复现的真实数据完整性缺陷，不是 GUI 不足。F 的 P-155 跨项目/软删摘录与 P-156 wrapped 记录不显示提示同类风险：合法但不典型的既有数据未进入测试分母；两条具体报告本轮未进一步审读，仅作待交叉核验线索。

## 4. 第二轮需要回答的问题

目前较有力的机制假设包括“门分类扩大、对象/提交边界错误、候选身份混同、mock 装载不忠实、空种子漏富历史、测试副作用隔离不全”；不是单一“GUI 不足”“测试不严格”，也不是“负责人需求太多”。P-149 与后来的回归矩阵表明，严格门和分层门都可能工作，但前提是分类与证据真实。P-163/P-164 涉额度估算和工具效果归因，本轮只读事实、不抢占研究角色定案；尤其不能根据作者自述工具“防守型”就认定是 UI 差的根因。

第二轮宜要求其他角色分别反驳：

1. 协作架构/运维：当时哪项阻塞来自平台能力，哪项来自任务权限，哪项来自认证流程？可用 Main 为什么未及时接管？P-145 有无具体授权等待时间证据？
2. 开发：为哪些测试替身补了真实宿主没有的条件？空数组与富历史是否走同一个编辑入口？稳定 ID、修订、软删、跨项目引用如何保全？哪些路径失败可能是产品可移植性问题？未提交候选是否包含全部新增文件和声明的运行时资源？
3. 产品/设计：条件放行的范围何时获批？200% 是文本放大、原生浏览器缩放还是 Retina DPR？每页矩阵哪些是硬规则、哪些仍是提议？共享原语足以支持抽样吗？
4. 测试自身：P-149 人工清单由谁扩大，是否逐项复核能力？撤回误判前是否让开发返修？旧 GUI 证据如何证明对新候选仍有效？如何证实 mock 装载次序忠实、富种子合法，以及测试不会向备份/导出/附件根泄漏？
5. 负责人侧：是否愿意把愿景拆成批次目标与非目标，在浏览样稿时明确仅方向认可？这一点不能替代执行方自行验证基础交互和准确报告范围。

可供后续讨论的最小合同应同时写清：实体对象、初始 fixture、动作与提交点、可观察预期、被测候选、执行者能力、审签者、未测范围、失效条件。增加门前先验证能执行；缩门前先证明不丢掉承诺覆盖。以上仅是改进候选，本轮不新增仓库规则、不豁免既有门、不签产品通过。
