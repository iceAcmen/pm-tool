## 2. 跨角色质疑

### X-QA-01：质疑 H-PM-06 将“设计认可扩大”直接连到实现违约

**对应：** H-PM-06、H-OPS-05；P-098、P-100、P-101。

产品角色保留了“试点关闭可能正确”的反证，但仍将设计方向认可扩大列为主要机制。新读的 `main-first-journey-request-20261020.md` M-A1 明确要求未设置时默认未勾选、保留旧页面，切 ON 才新版生效，切 OFF 可回退，刷新与重启保持选择。该文件还把 B2 写未接、B5/B6 后续旅程单列 NOT_RUN。因此，B1 的 OFF 本身可以是实现忠实执行合同，而不是开发偷偷隐藏成果。

M-L01157 要“全部出设计图”，能证明设计覆盖期待；它不自动证明同一时点 B1 的生产迁移合同也是全页默认开启。M-L01805/01824 的完成表述与撤回，较直接证明交付摘要扩大或沟通失配，尚不能单凭助手事后自责证明每个实现者违反已分配范围。

**竞争解释：** 代表页试点按计划完成，但主端把底座、可达性、局部试点汇总为全页面视觉迁移。此时修正对象应是交付范围与汇总权，而非责令开发无条件打开风险开关。

**可证伪：** 找到 B1 开工前已确认、覆盖全部页且要求默认生效的迁移合同，或后续明确取消试点的指令，才能提高实现违约判断。现阶段 H-PM-06 的“表述冲突”保持高，“实现违约”降为待证；H-OPS-05 不宜继续仅查缓存来解释这组反馈。

### X-QA-02：质疑 H-OPS-06 把远端不可见升级为冻结过错

**对应：** H-OPS-06、H-PM-10；P-124、P-119。

运维原稿已经明确“冻结不等于失控”，该限制必须成为结论主体，而不能被“扩大迁移缺口”标题遮掉。17 ahead 只能说明本地记录与本地远端引用的差额；该角色未 fetch，不能写成 GitHub 实时落后，更不能证明有人丢成果、拒绝同步或违规不推送。

第一轮已读的 `first-checkpoint-receipt-20261020.md` 明确 HEAD 是基线、历史 tag 不含新候选，另有逐文件指纹；R3/R4 又记录冻结树、tracked.diff 和新增文件逐字节核对。未提交候选在授权冻结期可以被稳定取证，不必为满足“干净”而提前提交、推送。

**竞争解释：** 暂存是测试门的正确行为，真正风险只发生在接手方拿不到补丁、遗漏新增文件，或发布时没有把候选重新绑定到最终提交。17 这个计数本身不是质量指标。

**可证伪：** 需要一次具体迁移失败，证明接手者仅因缺少冻结包而无法恢复或错测版本；有完整可移植指纹和补丁时下调风险。测试方面必须问“验的是哪一份候选”，而不是催促“先清掉 17 个提交”。本轮不复核 Git 状态、不判断其当前授权。

### X-QA-05：质疑从“多角色”或“主端亲自修”推出普遍自签通过

**对应：** H-PM-12、H-PM-08、H-QA-03；P-131、P-143、P-119。

早期 A-L00261/L00268 的“目视验证并修复、27/27”证明开发与自检合并，但发生在后续独立门确立前，不能追溯违规。主端后期亲自修问题且汇报主要验收完成，也不自动证明正式签字者是同一个角色。

反向证据是历史 R3/R4 明确列作者自述与独立复跑，M-L02226 记录独立专项报告被读取、源码与冻结一致。没有各批审签链，就不能把所有 PASS 都定为自签，更不能用角色数量替独立性背书。

**应质疑的具体机制：** 签字者是否参与业务修改？采证者是否自改用例？审核是否只看作者 SUMMARY？有没有明确的被测版本和原始证据？这些均需要逐批事实。共同父代理可能造成汇总压力，但只是风险，不是已证串签。

**可证伪：** 拿出对应批次的实现、采证、审签身份及审证记录；若独立者确实审原始证据，则排除该批自签指控。H-QA-03 保留“普遍自签证据不足”，不因进入对抗轮而强化无证判断。

### X-QA-06：质疑 H-PM-10/H-PM-02 与 H-QA-10 混合矩阵提议和有效合同

**对应：** H-PM-10、H-PM-02、H-QA-10；P-067、P-127。

根规则 §6A.1 对四视口×浅深×100/200%、六状态及设计专家签字明确写“待所有者表决，表决前建议不生效”。这不能被另一文档的“新增要求”措辞直接升级成历史发布硬门。既有 ADL-045 的真实 GUI 和独立审证门仍有效，ADL-047 的必须本人协作分层也不能被抹掉。

同样，批次测试合同可以明确要求某个视口或键盘矩阵；本轮 `main-first-journey-request` 则清楚只先采 1440 浅深、抽 390，200% 和拖缩留 NOT_RUN。不能拿全局待表决矩阵反推该 first checkpoint 必须全过，也不能把 first checkpoint 的局部标准当成 B8 最终全量承诺。

**真正待查：** 某次“全门 PASS”究竟按当时何份批准合同？抽样是否事前获批、剩余项是否仍包含当前交付承诺？第一轮指出摘要与正文范围冲突有依据，但“未跑 200% 所以历史必违规”没有依据。

**可证伪：** 逐批列规则生效时间、批准人、适用范围及替代关系。更严全矩阵会增加取证成本和能力阻塞；在同样贫弱的种子或错误 mock 下，也可能只是重复采同一种假安全。

### X-QA-07：质疑 H-PM-07 的“旅程闭合”足以解释或解决数据完整性

**对应：** H-PM-07、H-PM-14、H-QA-13；P-154、P-155、P-156。

**可证伪：** 在同一个真实生产编辑入口使用合法富种子，比较稳定 ID、全部 revision 正文/顺序、deletedAt 与引用前后不变量。若已存在同等测试且绿，则追查不同入口或 fixture 忠实性；新建 raw draft 正确不能反驳编辑破坏。当前修复情况仍需新候选复验，不将历史红外推到现在。

### X-QA-08：质疑 H-OPS-14 把 P-158 仅停在“可能装载问题”

**对应：** H-OPS-14、H-PM-06、H-QA-02；P-157、P-158、P-159、P-161。

运维第一轮未读原件，保留机制置信限制正确。本轮 B8 原件明确给出四层区别：包根漏声明 patch 是交付不完整；profile patch 存在却被当成同一资源是静态合同误验；mock 手动 `loadChunkFactory` 并注入 `schemasFactory`，补上真实宿主不会同步注册的块，是主动改变被测装载环境；inlineSync `$&` 替换破坏字面量是修复引入的构建语法回归。

这里“主动掩错”指 mock 代码客观上提前提供了缺失依赖，不指人员有欺骗动机。原件记录真实宿主入口同步 require 失败，以及改为 entry-only、禁预载、异步 materialize 后静态复验闭环，足以比台账更具体地支持假阳性机制。

**可证伪：** 展示真实宿主当时确实同步预载 schemas 的机制，或证明出错块未被该入口引用；否则预载假阳性值得升为高置信历史机制。仍不认定这批试验回归已经进入正式服务，也不把 B8 故障当作 M-L01808“没改”的唯一原因。

## 4. 当前收敛与未决问题

“多 GUI 就够”遭 P-154/P-158 反驳：看见保存成功不证明修订史未损，mock 提前补依赖也不会因增加截图自动变忠实。反过来，只做离线域断言也不能证明 P-162 的确认入口存在、P-149 的键盘与等待反馈可用。需要的是不同合同回答不同问题，而不是哪一层吞并另一层。

“更严格全矩阵自然改善”同样不能成立。矩阵可补响应式和长内容证据，却不替代合法富种子、失败注入、装载顺序和准确候选。能力不足却不分配执行者，会让严格门长期不可执行；没有生效规则又事后提高标准，会制造无据违规。减少矩阵也非自然更好：若删掉当前承诺中的视口或旅程，风险只是被藏起来。

第二轮建议保留五类研究对象：数据不变量合同、宿主装载合同、用户操作合同、候选/部署身份合同、角色能力与审签合同。每类都说明预期、合法 fixture、实际执行者、证据边界、失效条件。它们是待讨论的合同框架，不是新增仓库规则，不以此豁免现有门。

尚需对抗的关键问题：B1 试点之后何时承诺全量默认开启？人工包是谁、何时、依据哪份能力探测扩大？可信按键恢复后为何没有同候选补全 Space/390？最终放行继承哪些旧证据、依据什么差异分析？ops 修复的富历史不变量是否真正通过生产入口复验？这些问题的答案可继续改变归因，不能用角色共识替代。

负责人侧评价亦保持有限：愿景与批量任务应由执行端转译为可测范围并回报，但基础交互、历史保全和忠实 mock 是工程责任，不能归咎负责人“国际领先”的措辞。要求并行、提供持续授权、认可设计方向，都不等于许可跳过具体门或承认实现完成。
