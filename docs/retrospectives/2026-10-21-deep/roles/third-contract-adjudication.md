# 第三轮独立合同审证裁决

日期：2026-10-21。

## 范围与证据身份

本轮仅阅读 `role-tester-r2.md`（下称 QA）与 `role-developer-r2.md`（下称 DEV），继承书面材料，不继承首轮作者身份。未读原合同、源码或其他档案，未测试、上网或操作服务；唯一写入为本文件。以下是对两报告论证边界的裁决，不是产品验收、原件核验或责任终案。同源历史报告经两角色转述，不能计为两次独立复现。

两稿没有形成已记录的直接互答：DEV 明示未读 QA 首轮，QA 也未声明读过 DEV 第二轮。这里裁决可逐条对照的实质质疑，不虚构角色已经回应或达成共识。

## 一、修订损失：观察与预测必须分栏

对应：QA §2「X-QA-07」、§3末行；DEV §3「Q-DEV2-02」、§4「C-DEV2-02」、§5 P154。

**接受：** DEV 对证明范围的收缩成立。其转述的 active pl-2 原本只有 rev1，保存后成为 pl-3/rev1，修订数量是 1→1。这能支持重新编号，不能直接证明 active 多修订压成一条。固定 `revisions:[rv-1]` 的代码定位支持机制预测，但不是多修订输入的往返观察。

**接受：** QA 对“旅程成功不能证明历史保全”的反质疑仍成立。两稿均报告软删 pl-1 原有两次修订，保存后整项消失；这属于已报告的直接观察，不因 active 种子不足而降格为纯预测。行动项 ID 改号也须独立保留，不能用修订计数争议冲淡。

**不接受：** 把 QA 的“进展重新发 ID 并缩为 rv-1”概括直接扩写为“active 多修订已实测塌缩”；也不接受据此断言正式数据永久受损或当前仍坏。QA 原文并未明确声称 active 多修订实验，本裁决限制解释，不追认其作过该断言。

**待澄清：** 故障候选上的 active 多修订观察及现行修复状态。本轮无权补实验。登记应分为“软删两修订随记录消失：历史观察”“active 单修订改号：历史观察”“active 多修订塌缩：机制预测”。

## 二、Rollback：登记合同歧义，不替专家改例

对应：DEV §3「Q-DEV2-03」；QA §1第三组材料、§2「X-QA-07」、§4合同分层讨论。

**接受：** DEV 转述的“同事务校验失败整体零写”与“整批零写，已成功项不回滚”在“已成功项”指本批新写入时互相冲突，足以登记验收文字歧义。QA 第二轮提及既有 atomic 覆盖，但未复述或消解这两句；不能以 QA 未反驳当作认可。

**不接受：** 开发自行选择保留本批前半段写入，或审证人把“已成功项”径直改成事务前既有事实。后者虽可使文本一致，仍只是解释候选。文字冲突也不直接证明实现发生部分写入，更不使稳定 ID 与历史保全要求失效。

**待澄清：** 登记对象应注明两句原文、DEV 所指原报告第30–33及49–52行、歧义术语、事务边界和两种解释。请原测试专家确认“已成功项”的时间归属及失败后预期状态；专家确认前，依赖该歧义的原子性判定保持待澄清。原用例不由执行端增改，历史结果不擅自改签。本轮登记不是新增仓库规则，也不宣布整批验收阻塞或通过。

## 三、Mock：限制补能力，不是全面禁止

对应：QA §2「X-QA-08」、§4；DEV §2、§3「Q-DEV2-04」、§4「C-DEV2-04」。

**接受：** 两稿共同限定的失效机制是：真实宿主入口前没有 schemas factory，旧验证器却提前装入并注入，替被测包补上缺失的业务装载条件。QA 已明确忠实静态检查有价值，DEV 的异议应理解为阻止推广，不是证明 QA 主张全面禁 mock。

**不接受：** 全面禁用替身或一切依赖注入；也不接受只要验证器能运行，就视为宿主等价。允许提供真实宿主确实预置的平台依赖，以及按真实装载序列取得的模块能力；不允许测试预先赠送产品本应自行取得、宿主实际未提供的注册。

**待澄清：** 私有宿主无法导入时，公开 bench 的等价范围仍未证明，必须保留其非真实宿主身份。两稿对历史预载的说明可支持局部假阳性机制，不能替新候选宿主激活或 GUI 签字。

## 四、GUI 旅程与数据不变量不能相互吞并

对应：QA §2「X-QA-07」、§4；DEV §2、§3「Q-DEV2-01」「Q-DEV2-09」。

**接受：** QA 指出的“打开、编辑、保存、重开可成功而历史仍丢失”，与 DEV 区分持久化结果、保存语义及进度含义的意见相互约束。真实 GUI 回答入口、操作和反馈是否成立；数据不变量回答合法既有事实是否保全。成功提示、截图数量或事务无部分写，均不能单独证明内容正确。

**不接受：** 用更多 happy-path 页面采证覆盖历史损坏，或反向用离线数据全绿证明键盘、等待态与确认入口可用。两稿没有主张抛弃另一层，不应制造方法之争。

**待澄清：** 后续审签须分别说明生产编辑入口、合法富种子、前后不变量和同候选 GUI 证据的覆盖边界。此处只保留证据问题，不追加用例、不安排测试、不关闭历史缺陷。

## 裁决收束

接受直接观察和窄机制，拒绝超出种子、时序及候选身份的推广；合同文字未定之处保持待澄清。报告之间的真实张力是“不能夸大证明”与“不能因证明不足否认已见损坏”，不是谁替谁签字。以上裁决立即落盘，不等待角色回复，不产生任何产品 PASS。
