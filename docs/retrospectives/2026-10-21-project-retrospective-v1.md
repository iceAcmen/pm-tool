# pm-tool 项目复盘：从立项到 2026-10-21

> 给项目所有者和接手平台阅读。依据实际 Git 历史、仓库档案、独立测试报告及可读的本机豆包工作项目材料。第一版尚未取得豆包工作完整聊天原文；不改产品代码、不启停服务、不签发测试结论。

## 1. 核心判断

项目从离线项目台账扩展为包含 AI 副驾、可配置看板、目标与习惯、文件工作流和本地启动器候选的工作台。独立插件、只读上游、JSON 持久化的架构，支撑了跨平台接续和多轮扩展。[1](#s1) [2](#s2)

后续主要困难已经转向：功能是否可发现、数据语义是否一致、用户旅程是否完整、被测代码是否对应运行版本。自动化数量持续增长，但最新候选仍有 GUI 未测、测试夹具限制和桌面验证缺口，不能宣布全系统完成。[3](#s3) [4](#s4)

建议先冻结现有候选、完成独立验收和版本收口，再扩大范围。这是复盘建议，不是新产品决策。

## 2. 证据覆盖与缺口

已读取仓库协作规则、进度、交接、需求、变更、决策、问题档案、产品评估、设计合同、发布说明；核对了完整本地 Git 提交链、tag 指向及远程 main 实际引用。

本机确有豆包工作项目会话目录。可读材料包含任务公告板、自治授权记忆，以及 `conversation/.../background_history_task/index.json` 中的后台命令和输出索引；这些不是完整的“用户消息—助手回复”。当前云历史只返回部分 TRAE 会话，浏览器连接未返回可读的豆包聊天结果。

因此，本文可以还原成果、缺陷、规则与关键转折，不能完整还原每次讨论的全部选项和用户当时的意图。平台记忆仅作辅助，不高于仓库、Git 和独立验收。未读取凭据、账号数据库或无关私人对话。

本文没有重新运行构建、测试或验证正式服务。所有历史测试数字来自档案，不代表当前候选重新通过。

## 4. 做得有效的部分

**最小验证优先。** 最初先用 ping、真实领域打开和 JSON 写盘确认框架链路，而不是立即编写全部业务。真实 API 与配置问题得以及早暴露。[1](#s1)

**仓库沉淀实际支撑了平台切换。** 没有完整聊天，仍能追到 R9 接收、独立测试门、客观进度裁决、正式服务事故和现有候选。这套机制应继续保留。[1](#s1) [2](#s2) [6](#s6)

**AI 创造与确定性写入分离。** 模型输出草稿，领域代码负责校验、确认和落盘；固定快照保留历史口径，稳定行动项 ID 支撑后续转任务。[6](#s6) [7](#s7)

**独立验收开始纠正不可靠结论。** ADL-045 要求专家判定，ADL-047 区分自动化与必须用户参与项。最新报告撤回误判、保留 NOT_RUN/BLOCKED，避免把观察或自测伪装为全量通过。[4](#s4) [6](#s6)

## 5. 反复返工的原因与改进

### 5.1 能力实现与完整旅程未始终同步

早期产品评估指出：任务树被分组打散、搜索和提醒不能直达、移动能力没有界面入口。后续又出现 OKR/习惯缺导航、收件区没有随 snapshot 注入、副驾切状态却没有挂载。共同点是业务能力存在，用户入口或上下文没有连通。[7](#s7) [9](#s9)

建议每项功能固定一条验收旅程：找到入口→录入→校验→确认→持久化→重开→失败恢复。schema、命令、按钮单独完成不能代替旅程完成。

### 5.2 数据坐标与真实视觉对象未充分绑定

看板卡体自然高度曾超过 slot 高度，仅检查网格坐标不能证明无叠压。即时数字夹紧、浮层压窄画布、被动布局回写又造成编辑和保存漂移。[9](#s9)

建议同时核对数据坐标、slot、真实卡体边界和交互后的持久化；区分主动布局修改与响应式展示投影，后者不能暗中写回。

### 5.3 错误测试对象与版本不清造成无效返工

独立报告撤回过三类误判：占位列当任务编号列、删任务当删看板卡、只选择交付物而未执行关联当关联失败。正式页面也不能直接等同当前 HEAD，需冻结被测版本。[4](#s4)

建议缺陷提交开发前核对对象、完整步骤和版本。不能将所有 FAIL 都归为产品问题，也不能因出现误判而忽略真实缺陷。

### 5.4 数据口径需要先于所有页面收敛

“客观进度”后续确定只根据非空 checklist 计算；无清单显示证据不足，验收状态独立，旧手填值不混入汇总。ADL-050 否决 done 自动记 100%、全勾封顶 90% 等方案。[6](#s6)

这属于产品语义变化。应先冻结公式、样例、兼容规则，再让任务、甘特、看板、汇报消费同一派生结果。

### 5.5 并行产出需要单独的集成责任

Git 中有分片、合并和共享组件迁移，最新工作树同时含 client 与 launcher 候选。豆包公告板的“完成”表示任务单元状态，不代表产品独立验收。[2](#s2) [3](#s3)

建议并行前明确接口、文件边界、集成负责人和接缝用例；最终验收对象是固定提交或可核对补丁包。

### 5.6 文档规模扩大后，当前状态漂移

AGENTS 快照仍主要描述早期 R1–R12，progress 已进入 13 类修复；onboarding 保留多个“当前”。v0.7.4 发布说明仍有“tag 将创建”措辞，但本地 tag 已存在。包 version 仍 0.7.4，开发 HEAD 已包括之后多轮功能。[2](#s2) [3](#s3) [10](#s10)

这不能直接证明运行服务版本错误，但说明需要单独区分开发头、验收候选、发布 tag、运行实例。建议一张最新状态表作为入口，其余流水标明历史。

## 7. 后续建议

| 顺序 | 工作 | 产物 |
| --- | --- | --- |
| 1 | 冻结交接 | 清点已提交未推送、未提交候选、独立测试产物；明确原执行端是否结束同文件修改 |
| 2 | 收口当前缺陷 | 专家维护用例，开发修确认缺陷和合法夹具，GUI 端按既定步骤采证 |
| 3 | 统一状态入口 | 开发 HEAD、候选指纹、独立结论、tag、运行 worktree/profile/端口单表 |
| 4 | 重新定范围 | PM 核心、个人成长、宿主融合、启动器分批；每批围绕一条高频旅程 |
| 5 | 补聊天复盘 | 豆包导出用户/助手消息，或在原会话生成有原消息出处的决策索引 |

补齐聊天后重点核对：需求变化与实现偏差各占哪些返工；已有授权为何重复询问；并行节省的等待与增加的集成成本；哪些功能每天实际使用。没有工时、使用记录和完整原文，不量化返工率、平台效率、满意度，也不直接归责平台。
