# 缺陷格式与严重度定义

> 用途：开发、产品、测试专家对「什么是缺陷、怎么记、先修哪个」用同一套语言。
> 核心原则（ADL-045）：**严重度只排修复先后，不自动豁免**；是否带病发布须项目所有者单独特批，不预设。

## 1. 严重度（仅决定修复先后，不豁免）

| 严重度 | 定义 | 例子 | 处理 |
|---|---|---|---|
| **S1 阻断** | 核心台账/写路径在真页面不可用、数据可能损坏或丢失、安全门（confirm/快照/预检）被绕过 | 甘特拖拽不落库；restore 无快照直接覆盖；真浏览器 bundle 崩溃 | 立即修，阻塞发布 |
| **S2 严重** | 高频主流程效率/正确性受损，但有命令行等绕行 | 行内编辑 UI 接线缺失；提醒/搜索点击不直达；新视图破版 | 发布前必修 |
| **S3 一般** | 边界、打磨、文案、空态、加载反馈 | 空态 CTA 缺失；窄屏轻微溢出；个别中文文案拗口 | 排期修；未经特批不带病发布 |
| **S4 观察** | 不影响功能的文档/一致性 drift、建议项 | 面板行数与文档不符 | 记录，不阻塞 |

> 注意：S3 不等于「可以带病发」。ADL-045 第 6 条——轻微问题不默认豁免；豁免须所有者明确特批并留痕。

## 2. 缺陷记录字段

每条缺陷必须包含以下字段（缺一不可，否则不算有效缺陷）：

```
编号：T-DEF-NNN
标题：一句话现象
严重度：S1 / S2 / S3 / S4
类别：功能 / 集成 / 网页实测 / 页面样式 / 用户体验
被测提交：<commit hash>
现象：实际观察到什么（含步骤/前置）
预期：按需求/验收应该是什么
证据：日志路径 / 代码行 / 截图（谁产生、何时）
根因初判：代码或流程层面最可能的原因（测试专家初判，最终以开发定位为准）
影响：哪些实体/视图/数据受影响
复现方式：可重复的最小步骤或缺失的测试
状态：OPEN / FIXED / RE-VERIFIED / WONTFIX(需所有者特批)
指派：开发修复（测试专家不改产品代码）
```

## 3. 生命周期

1. **OPEN**：测试专家在验收报告中登记，附证据。
2. **FIXED**：开发修复并提交（新 commit），说明改动文件。
3. **RE-VERIFIED**：测试专家对新提交复验该缺陷 + 受影响范围回归；通过则关闭。
4. 任何新提交使历史结论受影响 → 相关用例回退为「过期」，重测后方可再引用。
5. **WONTFIX**：仅当项目所有者明确特批方可标记，须留痕理由；测试专家不得自行豁免。

## 4. 有效缺陷 vs 无效投诉

- **有效**：可复现、绑定提交、有证据、与验收不符。
- **无效/不记**：个人偏好但不影响正确性；环境未按声明配置；把「未实测」当「有 bug」——未实测一律记 BLOCKED 而非 FAIL。
