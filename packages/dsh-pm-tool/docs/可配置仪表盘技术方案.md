## 1. 目标 / 本期范围 / 非目标

### 1.1 目标
把当前写死在 `src/client/panel.tsx`（`GlobalBoard`，约 L3611 起）的固定卡片，重构为**数据驱动的可配置 Widget 框架**：

1. 拖拽移动卡片 + 手柄拖拽改卡片长宽（不同 `w/h`）；
2. 卡片库抽屉：选择 / 添加 / 移除卡片；
3. 卡片内元素可配置、可自定义；
4. 卡片数据支持自定义数据源、公式/计算、筛选、排序。

**核心原则**：先做「可配置 widget 框架」，已确认的 7 卡作为**默认布局 JSON** 由配置渲染，**不再在 JSX 里写死任何一张卡的位置/尺寸/取数逻辑**。

### 1.2 本期范围（v0.8.x）
- 可配置 Widget 框架：Registry + 布局模型 + 编辑态/浏览态切换；
- 拖拽移动 + 手柄 resize（栅格对齐）；
- 固定卡片库（已确认 7 卡）+ 7 卡默认布局 JSON；
- 持久化：global/project/user 三作用域语义、恢复默认、`version` + 迁移；
- 卡片库抽屉增删（阶段二）、配置器（数据源/筛选/排序/显示元素，阶段二）；
- 公式引擎 + 自定义 KPI/文本卡（阶段三）。

### 1.3 非目标（本期不做）
- 任意用户自定义 JS / 任意脚本（**安全红线，见 §4.5**）；
- 实时多人协同编辑（仅做「未来共享」的数据结构预留与冲突合并占位）；
- 看板间互相引用 / 跨卡片联动过滤（下一阶段）；
- 历史趋势图（Task 无 `completedDate`，禁止画历史曲线，见 `progress-derivation.ts` 口径）。

### 2.1 一个必须知道的构建事实（本次实测发现）
tsdown **默认把 `package.json` 的 dependencies 当作 external（不打包）**。产品里 `lucide-react` 之所以能进 bundle，正是因为 `noExternal:[/^lucide-react/]` 显式把它拉回来。
**因此：任何新引入的运行库（RGL / dnd-kit / expr-eval）都必须显式写进 `noExternal`，否则 tsdown 会把它留成 `require("xxx")`，而宿主模块表答不出这个名字，运行时必崩。**

## 3. 技术选型结论（含隔离实测证据）

> 实测目录：`.tmp/widget-poc/`（gitignored，自建 package.json，**未动** `packages/dsh-pm-tool/package.json` / `pnpm-lock.yaml`）。
> 实测方式：与产品一致的 tsdown 配置（单 CJS / browser / es2022 / `__ModuleLoader__` banner），外加 jsdom + react-dom 烟雾测试。

### 3.1 拖拽布局

| 维度 | **react-grid-layout 1.4.4** | @dnd-kit/core 6.3.1 + sortable 10.0.0 + modifiers 9.0.0 |
|---|---|---|
| 安装（React18.3.1） | ✅ 无 peer 警告 | ✅ 无 peer 警告 |
| tsdown 单 CJS 内联打包 | ✅ 成功 | ✅ 成功（**但有前提，见下**） |
| gzip 体积（单独打包） | **≈ 44 KB**（含 react-draggable/resizable/resize-observer/clsx/fast-equals/prop-types） | **≈ 43 KB**（core+sortable+modifiers+utilities+tslib） |
| 内置栅格对齐 | ✅ 开箱即用（列数/行高/边距/紧凑排布） | ❌ 无，需自实现碰撞/换位算法 |
| 内置手柄 resize | ✅ 开箱（`se/e/nw…` 手柄） | ❌ 无，需自实现尺寸拖拽 |
| 断点响应式 | ✅ 内置 `Responsive` + `layouts:{lg,md,sm}` | ❌ 需自写 |
| 触摸 / 无障碍 | 一般（桌面鼠标为主） | ✅ 原生 pointer/键盘/触摸传感器、a11y 友好 |
| 自带 CSS | **需要**：`react-grid-layout/css/styles.css`（仅 **2.7 KB**） | 无 |
| jsdom 烟雾测试 | ✅ 渲染出 `.react-grid-layout` 网格 | ✅ `DndContext`+`SortableContext` 挂载成功 |

**实测踩到的坑（dnd-kit）**：在未复刻宿主 `define:{'process.env.NODE_ENV':'production'}` 与 `inputOptions.resolve.conditionNames:['production','browser','import','module','default']` 时，`@dnd-kit/utilities` 的入口按 `process.env.NODE_ENV` 分支做 CJS require，rolldown 内联后 `useLatestValue` 取不到，运行时抛 `utilities.useLatestValue is not a function`。**补上这两项后即通过**——这是宿主 `clientConfig` 里已经有的东西，本包 tsdown.config 目前**没有**，选型落地时必须一并补上。

**结论：推荐 react-grid-layout 1.4.4。**
理由：本场景是「桌面端、固定栅格、要 resize、要断点」的仪表盘，RGL 把最难的栅格/碰撞/resize/响应式全部做完，体积与 dnd-kit 打平（44 vs 43 KB gzip），而 dnd-kit 省不掉自写 grid+resize 的工作量（≈ 多 3–5 人日）。dnd-kit 的触摸/a11y 优势在鼠标为主的 PM 桌面工作台不是决定性因素。
- **备选**：@dnd-kit（若未来要做「自由画布/跨面板拖拽/触摸看板」再切）。

### 3.2 公式引擎

| 维度 | **expr-eval 2.0.2** | hot-formula-parser 4.0.0（=formulajs） | 自研安全子集 |
|---|---|---|---|
| 安装 | ✅ | ✅ | — |
| tsdown 打包 | ✅ | ✅（但体积大） | — |
| gzip 体积 | **≈ 10.5 KB** | **≈ 71 KB**（内置 ~400 个电子表格函数） | ≈ 0（自己写） |
| 是否用 `eval`/`new Function` | `new Function` **仅在 `.compile()` 路径**（且带 `with`）；默认 `parse().evaluate()` 走 **AST 解释**，CSP 安全 | formulajs 内部存在 `new Function` | 完全可控 |
| 模型 | 表达式 + 变量上下文 + 可注册函数 | **A1 电子表格模型**（`SUM(A1:A3)`） | 自定 |
| 对象数组字段聚合 | ✅ 注册 `count/sum/avg/pct` 等即可（实测 `pct(count(done),count(all))=66.7%` 正确） | ❌ A1 引用模型，不匹配「对象数组字段」语义 | ✅ |
| Lambda/箭头函数 | ❌ 不支持（`t => …` 报 `unexpected >`） | n/a | 可做也可不做 |

**实测**：
- `pct(count(doneTasks), count(allTasks))` → `66.7` ✅
- `avg(allTasks,"progress")` → `50` ✅
- `Parser.parse('1+2*3').evaluate()` → `7`（AST 路径，不触发 Function）✅

**结论：推荐 expr-eval 2.0.2。**
理由：10.5 KB、AST 解释（不暴露 `compile()` 即 CSP 安全）、可注册领域聚合函数，且天然匹配「对象数组字段」语义；hot-formula-parser 是 A1 表格模型（71 KB），与我们的数据模型错位。**筛选/过滤一律用外层结构化 DSL（见 §4.3），公式只做标量/已聚合数组上的算术与统计**——这样既绕开 expr-eval 不支持 lambda 的限制，又把安全面压到最小。
- **备选**：阶段三若需要更复杂的「类 Excel」公式，再评估 hyperformula（不引入 hot-formula-parser）。

### 3.3 react-dom 处理方式（只读核查结论）
- 宿主 `packages/client/web/src/platform.ts` 的 `PLATFORM_MODULES` 明确包含：
  `'react','react/jsx-runtime','react-dom','react-dom/client','@deepseek-ai/cordis', …`
  —— 即宿主把这四者**冻进模块表**，插件 bundle 里 `require("react-dom")` 在运行时由宿主注入的 `require` 解析。
- RGL 的 `peerDependencies` 声明 `react-dom >= 16.3`，其 CJS 入口确实会 `require("react-dom")`。
- **实测**：把 `react` / `react/jsx-runtime` / `react-dom` 加入 `external` 后，本 POC 产物的外部 require 恰好只有这三个，jsdom 烟雾测试（用本地 node_modules 模拟模块表）渲染成功。
- **落地动作**：`tsdown.config.ts` 的 `external` 从 `['react','react/jsx-runtime']` 扩为
  `['react','react/jsx-runtime','react-dom','react-dom/client']`。
  **不要**把 react-dom 打进 bundle（会出现第二个 React 渲染器、hooks 直接崩、体积 +30 KB gzip）。

### 3.4 RGL 的 CSS 如何处理
RGL 自带样式只有一个文件 `react-grid-layout/css/styles.css`（**2.7 KB**，仅 `.react-grid-layout` / `.react-grid-item` / `.react-resizable-handle` 等布局类）。本工程是单 `panel.css` 体系：
- **推荐做法**：把该文件内容**手动并入 `panel.css`**（类名加 `.pm-` 前缀作用域化，避免与宿主样式冲突），不引入 CSS import 管线；
- 备选：用产品已有的 `?raw` 自定义插件把 CSS 读成字符串、运行时注入 `<style>`。
- 无论哪种，都要过 `verify-web`：**禁 hex、用语义锚点类名**。

## 4. 架构设计

### 4.1 Widget Registry（TS 接口草图）

```ts
// 一个 Widget 类型的描述（注册时登记一次，运行时按 type 实例化）
interface WidgetDescriptor<TConfig = unknown> {
  type: string                 // 唯一键，如 'completionHero' / 'kpiNumber'
  name: string                 // 卡片库显示名
  category: 'overview' | 'list' | 'kpi' | 'progress' | 'text'

  // 栅格默认尺寸与下限
  defaultW: number; defaultH: number
  minW: number;     minH: number

  // 该卡片声明它需要哪些数据源（DataContext 的子集），框架据此喂数据
  requiredSources: Array<'projects'|'tasks'|'milestones'|'riskIssues'|'deliverables'|'meetings'|'reports'>

  // 配置 schema（zod）：配置器据此自动生成表单；存进布局 JSON
  configSchema: ZodSchema<TConfig>
  defaultConfig: TConfig

  // 纯渲染：吃 DataContext + 该卡 config，输出 ReactNode
  render(ctx: WidgetContext<TConfig>): ReactNode
}

interface WidgetContext<T> {
  data: DataContext            // §4.3
  config: T
  // 交互回调（打开记录、切项目等），与现有 onOpenRecord/onPickProject 对齐
  actions: { openRecord(projectId: string, type: string, id: string): void
             pickProject(id: string): void }
  isEditing: boolean
}
```

注册中心：`widgetRegistry: Map<type, WidgetDescriptor>`。框架启动时注册「已确认 7 卡 + 候选卡」；**新增卡片 = 新增一个 descriptor 并 `register()`**，布局 JSON 里只存 `type + config + layout`，不存渲染函数。

#### 4.3.3 筛选 DSL（结构化，不用表达式字符串）
```ts
interface FilterRule { field: string; op: 'eq'|'ne'|'in'|'gte'|'lte'|'contains'|'isEmpty'; value: unknown }
interface Filter { op: 'and'|'or'; rules: FilterRule[] }
```
作用对象是某数据源（如 `tasks`）；字段白名单见 §4.3.2，非白名单字段拒绝。

#### 4.3.4 排序 DSL
```ts
interface SortRule { field: string; dir: 'asc'|'desc' }
```

#### 4.3.5 公式求值上下文
- **可用变量**：当前卡片「筛选后的数组」`rows`，以及标量上下文 `today`（`YYYY-MM-DD`）。
- **可用聚合函数（白名单，注册到 expr-eval）**：
  `count(rows)`、`sum(rows, field)`、`avg(rows, field)`、`min/max(rows, field)`、`pct(part, all)`、`countIf(rows, field, value)`。
- 表达式只产出**标量数字/字符串**给 KPI/文本卡；不允许遍历写操作、不允许调用环境 API。

#### 4.3.6 安全沙箱
- **禁止 `eval` / `new Function`**：固定使用 expr-eval 的 `parse().evaluate()`（AST 解释路径），**不暴露 `.compile()`**（该路径会生成 `new Function` + `with`，CSP 下必崩）。
- 函数白名单：仅 §4.3.5 注册的聚合 + 四则/比较/逻辑运算；未登记标识符一律拒绝。
- 表达式长度上限（如 ≤ 200 字符）、求值超时（如 50ms）、输入数组条数上限（如 ≤ 5000）。
- 只读：上下文里不暴露任何可写对象/函数。
- **不允许用户自定义函数 / 任意 JS**（见 §9 拍板点）。

### 4.4 卡片配置器（zod 驱动）
配置器是一个侧抽屉，按 tab 组织，每个字段直接绑定该 widget 的 `configSchema`：

| Tab | 内容 | 字段绑定（zod） |
|---|---|---|
| 数据源 | 选数据源实体 + 项目范围（全部/单选项目） | `source: enum`, `projectScope` |
| 筛选 | 筛选规则行（字段/op/值，§4.3.3） | `filter: Filter` |
| 排序 | 排序字段 + 方向 | `sort: SortRule` |
| 公式/计算 | KPI 卡：标量公式输入（§4.3.5） | `formula: string(≤200)` |
| 显示元素 | 要显示哪些列/指标/进度条/标签、数字格式（%/万） | `display: {columns[], format}` |
| 外观 | 卡片标题、副标题、强调色（用语义 token，禁 hex） | `title, subtitle, tone` |

保存时 `configSchema.parse(config)` 校验，失败不写入。

### 4.5 编辑态 / 浏览态
- 全局一个 `isEditing` 开关（看板头部「布局编辑」按钮）。
- 浏览态：卡片静态、不响应拖拽；
- 编辑态：RGL `isDraggable/isResizable=true`，每卡右上角出现「配置 / 移除」手柄，顶部出现「添加卡片 / 恢复默认 / 完成」。
- **撤销/重做**：本期做最简版（栈深 20 的 `past/future` 布局快照），不做命令式 diff；若工期紧则降级为「恢复默认」单点，编辑态误操作用浏览器历史不兜底——取舍见 §8。
- 主题：深/浅由宿主 CSS 变量提供，卡片只用语义 token，不写死色值（过 verify-web）。

### 4.6 持久化

| 作用域 | 语义 | 默认 |
|---|---|---|
| **global** | 插件出厂默认布局（即 §4.2.1 这 7 卡） | 代码内置，随版本升级 |
| **project** | 某项目工作台的布局，覆盖 global | 未配置时回退 global |
| **user** | 当前用户在本机的个性化，覆盖 project/global | 未配置时回退 project→global |

- **存储位置**：优先走 `@deepseek-ai/dsh-storage` 的 JSON 记录（与现有 records 一致、离线、可备份/导出），key 形如 `dashboard-layout:<scope>:<projectId?>`；不滥用 `localStorage`（插件运行在受控宿主内，storage 才有备份/隔离）。
- **schema 版本化**：布局 JSON 带 `version`；加载时若 `version < current`，依次跑迁移函数 `migrate.v1→v2→…`，迁移失败回退 global 默认并记日志。
- **导入/导出**：导出为 `.json`（含 version + widgets）；导入时跑 schema 校验 + 迁移。
- **未来多人协作共享**：数据结构上预留 `{ updatedAt, updatedBy, revision }`；合并策略占位（local-wins / 手动选择 diff），本期不实现实时同步。

## 6. 性能与离线

- **bundle 体积预算**：在现有产物基础上，框架净增预算 **≤ 60 KB gzip**（RGL ≈44 KB + expr-eval ≈11 KB + 框架自身 ≈5 KB）。
  - 实测 POC 全量（RGL+dnd-kit+两个公式库）为 142.8 KB gzip；最终只选 RGL + expr-eval，按分库实测线性叠加约 **55 KB gzip**，达标。
- **widget 按需注册 / lazy**：7 张默认卡随主包注册；候选卡（列表模板、自定义卡）走动态 `import()`，由 `asyncChunkRequirePlugin` 同款机制拆 `client.<name>.js` 异步块，首屏不加载。
- **CSP**：不引入 eval/Function 热路径；无 CDN、无网络字体（继续用 base64 Inter）。
- **离线**：纯本地渲染，所有数据来自 `web snapshot`，不发请求。

## 7. 与现有 verify / 隔离契约的兼容

- `verify-web`：新卡片类名用语义锚点（`.pm-widget-*` / `.pm-rgl-*`），**禁 hex**（沿用现有 CSS 变量 token）；RGL 样式并入 `panel.css` 时同样作用域化。
- slot 注入：框架仍挂在现有 dsh slot，不新增宿主依赖。
- `build=0`：不得引入 tsc 报错；新增库必须先在 `.tmp` 实测、再以 `noExternal` 方式进 `package.json`。
- `verify-isolation` 64 目标：重构 GlobalBoard 时保持所有现有可点击元素的 `data-open-record` / `data-open-type` / 锚点行为不变，避免 `verify-web-*` 红。
- **落地风险**：
  1. RGL 与宿主已有全局样式冲突（用作用域前缀缓解）；
  2. dnd-kit 式的 `NODE_ENV`/`conditionNames` 缺失导致运行时错——必须把宿主 `define` 抄进本包 tsdown.config；
  3. 7 卡重构中，`BoardPeopleSection` 等现有派生逻辑要原样搬进对应 widget 的 `render()`，口径不能漂移。

## 9. 需用户拍板的取舍点

1. **拖拽库最终选哪个？** 推荐 **react-grid-layout**（自带栅格+resize+响应式，44KB gzip，与 dnd-kit 打平但省自写 grid 的 3–5 人日）；备选 dnd-kit（触摸/a11y 更好，但要自实现栅格与 resize）。
2. **公式能力开放到什么程度？** 推荐：**只开放「白名单聚合函数 + 算术」，筛选交给结构化 DSL，不开放 lambda、不开放任意 JS**；是否允许用户自定义函数？（建议否，降低安全面）
3. **配置作用域默认值**：默认落 `user` 还是 `project`？多人共用时谁的布局生效？（建议 user 个性化优先、project 做团队模板）
4. **是否允许任意 JS？** 建议**不允许**（CSP + 安全），只用 expr-eval AST 解释 + 函数白名单。
5. **本期是否做导入/导出 / 分享？** 建议阶段三做**本机 .json 导入导出**，多人实时共享只做数据结构预留。
6. **bundle 体积上限**：是否接受净增 ≈55 KB gzip？是否需要把 RGL 做成异步块（首屏只加载浏览态、编辑态才加载拖拽库）？
