**微信项目群消息采集与自动项目汇报：可行性调研**

调研日期：2026-10-21。适用场景：项目经理读取本人参与的工作群，整理项目进展、任务动态、风险与待跟进事项；重点考虑 macOS 和现有 pm-tool 的衔接。

本文件是调研参考，不代表功能已实现、已测试或已立项。公开文档核对与本机实测分开记录。

**1. 结论与选择建议**

可以实现“消息采集 → 项目进展提取 → 日报/周报 → 任务进度记录”，但读取消息的方式决定了可靠性与可用范围。

- **保留现有普通微信群**：优先小范围验证 Mac 桌面读取工具。WeChat-MCP 等项目提供现成基础，但需要保持微信运行、桌面可操作，并解决群身份、发言人识别、历史补采与漏消息问题。现阶段适合作为试点，不能承诺全部消息完整采集。[cite:12][cite:13]
- **追求长期常驻、可靠采集**：优先企业微信官方会话存档或数据与智能专区。前提是企业管理员开通、群与参与成员符合授权范围；外部联系人会话需要同意。它不等于读取任意个人微信群。[cite:1][cite:2][cite:4]
- **团队愿意主动报进度**：企业微信智能机器人可以接收群内 @机器人 的汇报，实时形成任务动态。它接收的是与机器人交互的消息，不能当作全群聊天记录接口。[cite:7]
- **最快验证汇报价值**：先复制本人有权处理的群消息，或导入已经取得的聊天记录文件，让 AI 生成带出处的汇报与任务变更草稿。采集自动化可在效果验证后接入。

截至本次核对，腾讯官方微信插件 `@tencent-weixin/openclaw-weixin` 的版本为 2.4.10，渠道代码明确声明 `chatTypes: ["direct"]`。它能接收 Bot 会话新消息，但不能据此声称已支持读取现有微信群或全部微信历史记录。[cite:8][cite:9]

**2. 同一维度比较各条路线**

下表中“稳定性”是依据接口性质、依赖与已公开限制做出的工程判断，不是本机测试成绩。“定时”频率由后续实现配置。

| 路线 | 可读取的范围 | 实时 / 定时 | 历史记录能力 | 部署与成本因素 | 本次建议 |
|---|---|---|---|---|---|
| 企微官方会话内容存档 | 已授权员工涉及的可存档内部/外部会话；受成员范围、版本权益与外部同意限制 | 新会话通知触发拉取，也可定时拉取 | 接口最多取最近 5 天；持续存储后可形成长期历史 | 管理员开通、存档权益、服务器、SDK、模型费用 | 长期自动化首选，先确认群与开通通道 |
| 企微数据与智能专区 | 授权范围内的企微会话 | 可通过通知和专区 SDK 处理 | 获取会话记录接口限制近 5 天 | 需部署专区程序/模型；原文出区受限制 | 可在专区分析并输出允许的结果，不能套用任意外部 LLM 流程 |
| 企微智能机器人 | 单聊机器人消息、群内 @机器人 的消息 | WebSocket 长连接或回调 | 不能由此补取全群历史 | 机器人配置、后台或本机服务、模型费用 | 适合主动提交任务进展 |
| Mac GUI / 辅助功能 / OCR | 本人微信客户端可显示、可加载的聊天 | 常驻轮询或定时顺序读取；属于近实时 | 部分工具支持滚动补采，完整性需验证 | Mac 常开、微信登录、系统权限、兼容维护 | 现有普通微信群的优先试点路线 |
| 本地数据库 / 调试 / 非官方协议 | 工具声称覆盖本人账号本地记录或新消息 | 某些工具声明支持流式监听 | 取决于已同步的数据、版本与解密能力 | 版本绑定、原生组件、账号与许可限制 | 不能直接选作项目生产基础 |
| 手动复制或已有文件导入 | 明确选取的群消息 | 采集需人工；整理可自动定时执行 | 可处理已经提供的历史文件 | 实施最简单；成本主要是整理与模型调用 | 先验证内容质量和任务匹配效果 |

“群成员列表”“获取客户群详情”“机器人 Webhook”“微信客服消息”也不等于“读取所有工作群聊天记录”。能力要按具体消息范围判断。[cite:6][cite:7][cite:8]

**3. 企业微信官方路线的实际边界**

**3.1 传统会话内容存档 SDK**

官方提供 `GetChatData` 获取会话数据，使用 `seq` 持续增量拉取，`msgid` 可用于去重；消息包含群 ID、发送者、时间和类型，媒体需要单独拉取。[cite:1]

官方“使用前帮助”要求管理员配置开启范围、调用 IP 和公钥。开启员工与未开启员工之间的会话可以获取，未开启员工之间的会话不能获取。内部员工需要告知，外部联系人需要同意。[cite:2]

可以使用新会话回调唤醒采集器，再拉取消息；传统存档的官方回调文档写明按 15 秒间隔检查是否有新会话并触发通知。这个数字是通知机制，不是完整“消息到汇报”的延迟保证。[cite:3]

当前官方文档明确：

- 最多拉取最近 **5 天**的会话内容，而不是许多旧教程所写的 3 天。[cite:1]
- 需要连续采集并保存游标；不能每周末才开始拉一整周。
- Linux 和 Windows 有官方 SDK 下载，当前获取会话内容页面未列出 macOS 原生 SDK。因此若走这条通道，建议把采集器放在 Linux 服务，Mac 使用报告与管理界面。[cite:1]
- 官方页面的存在不保证你的企业现在能直接开通同一通道；实际权益、收费与接口权限需以管理员后台为准。

不能把“加入一个企微账号”视为已完成采集配置，也不能承诺把现有普通微信群的旧记录自动迁移到企微存档。优先考虑建立符合存档条件的企微项目群或客户群，让后续工作在其中开展。

**3.2 数据与智能专区是另一种处理架构**

2026-09-10 更新的官方文档仍提供获取会话记录、搜索与模型分析能力，但要求依赖会话内容的任务在专区中完成，仅允许符合要求的脱敏分析结果或消息 ID 传到专区之外；分析结果不能包含会话原文。[cite:4][cite:5]

因此要先确认开通的是传统 SDK 路径还是专区路径：

- 传统 SDK：在授权条件下由企业持有密钥解密并处理。
- 专区路径：在专区中部署分析程序/模型，外部 pm-tool 接收允许输出的结果。

“会话内容导出”是用户通过会话展示组件发起的专门流程，需要组件给出的单次 code，结果也通过指定组件展示。它不是一个可随意定时调用、向本机返回全量明文的通用下载接口。[cite:20]

**3.3 智能机器人适合主动报进度**

官方长连接文档说明：群内 @机器人 或给机器人发单聊消息时，才推送消息回调。可以约定团队提交任务编号、进展、预计完成时间、阻塞事项，再整理成项目台账与汇报。[cite:7]

这条路线可以减少采集漏失和语义歧义，但前提是团队愿意采用该报进度方式；普通群内讨论不会自动成为机器人输入。

**5. 自动汇报与任务记录需要怎样处理消息**

推荐的逻辑结构：

```text
工作群消息来源
  ├─ 普通微信：经验证的 Mac 读取器 / 已有文件
  ├─ 企业微信：授权存档 / 专区内分析
  └─ 主动报进度：企微智能机器人
             ↓
按群与项目过滤 → 增量保存 → 去重 → 发言人与时间归一化
             ↓
结合既有任务、负责人、截止日期提取进展与风险
             ├─ 带出处的项目日报 / 周报草稿
             └─ 带出处的任务动态与变更建议
                              ↓
                      规则校验 / 有歧义时确认
                              ↓
                         正式任务台账
```

专区路径的原文处理与模型推理必须留在专区内，上图向外传递的是允许的结果；普通微信与传统存档路径则按具体授权选择本地或获准的模型服务。

消息输入至少保留：采集来源、群身份、项目映射、消息时间、采集时间、发言人、类型、内容或受控引用、可获得的消息 ID、采集完整性状态。GUI 无法拿到可靠 ID 时，不能假装存在平台 ID；可用来源与内容组合去重，并标记识别不确定。

任务动态至少保留：匹配到的任务、事件类型、进展描述、负责人、预计完成日、阻塞事项、来源引用、提取可信度、是否已确认。报告至少包含：已完成事项、进行中事项、风险/阻塞、下一步计划、需要负责人处理的事项、覆盖的消息时间段和采集缺口。

需要重点避免以下误记：

- “预计完成”“承诺完成”不能记为“已完成”。
- “开发完成”“已经提测”不能自动等于“验收完成”。
- 相对日期根据消息发出时间解释；不明确的时间保留待确认。
- 群昵称、转述与引用消息不一定代表责任人本人确认。
- 没有新消息只代表缺少新证据，不能据此标记任务停滞或延期。
- 没有明确进度比例时，不让模型自行编造完成百分比。
- 后续撤回或更正需要留下修正事件，旧汇报保持快照，避免悄悄改写历史。

**6. 与现有 pm-tool 的衔接**

本次只读取了本地需求文档的相关条目。文档列明现有 R9 固定快照汇报、R14 AI 叙述、R15 速记归纳、R17 行动项转任务能力；这说明可复用整理和管理能力，但不是本次对这些功能的运行验收。

新增工作主要在前半段：

- 微信/企微来源接入及增量采集。
- 群与项目、群成员与负责人、消息与既有任务的映射。
- 消息证据与任务动态的留存。
- 自动生成汇报草稿，以及可确认的任务变更建议。

不建议直接编辑 pm-tool 业务 JSON 文件。应通过项目服务/命令等已验证入口写入，保留校验、编号与一致性约束。新消息采集模块和原始数据不纳入公开 Git 仓库；模型 key 仍走本地配置或环境变量。

**7. 推荐试点**

如果当前是普通微信群，建议先选少量项目群，在自己的 Mac 上验证 **只读桌面采集 + 自动整理**。先验证文字，语音、图片和附件后续逐类补齐；这里的范围是试点建议，不是工具已验证范围。

建议试点安排：

1. 用一段已经取得的消息和现有任务表验证整理效果，核对任务匹配、负责人、截止日期与风险提取。
2. 再接入 Mac GUI 读取，设置建议的每 10–15 分钟采集；多群顺序操作同一微信窗口，防止并发串群。
3. 每日生成汇报草稿，汇总任务动态；初期对正式状态、负责人和截止日期变更做确认。
4. 连续观察一个工作周，人工对照消息覆盖率、重复、责任人误识别、断线补采以及对日常使用的干扰。
5. 只有采集和抽取稳定后，才将规则明确的低歧义动态自动入库；有歧义项仍保留确认入口。

GUI 试点要验证：Mac 锁屏/睡眠、微信掉线、窗口遮挡、群消息密集、同名群、群改名、长消息、历史延迟加载、引用与撤回。采集失败时报告必须注明缺口，不能输出看起来完整的结论。

如果公司已有企业微信并能开通相应权益，建议优先验证一个符合条件的项目群，再选择传统 SDK 采集或专区内分析。采购时要核实具体套餐覆盖的内部/外部会话、接口权限、结果可用范围、数据导出和自定义分析能力，不能只确认“有 AI 总结”。

**8. 成本、边界与未确认事项**

成本应分开估算：

- 企微：存档/专区权益 + 采集或专区程序 + 存储与备份 + 模型。
- Mac GUI：本机常开 + 系统权限 + 模型 + 版本兼容和采集维护。
- 文件导入：人工准备输入 + 模型；适合先验证投入产出。

本次没有找到可直接核验的当前官方存档价格表，因此不把服务商报价当作腾讯官方价格。实际费用以管理员后台和服务商正式报价为准。

原始消息与索引本地保存，不等于 AI 内容不出机。外部模型会收到处理所需的片段，视觉模型可能收到截图；需要按公司允许的服务和工作群范围设置输入。[cite:15][cite:16]

实施前仍需确定：群是普通微信群、企微内部群还是客户群；能否开通企微权限；本机微信实际版本与芯片；群数量和消息量；语音/图片占比；任务表是否已有固定编号；汇报保存到 pm-tool、文件还是其他工作工具。

本次未读取用户微信、未取得密钥、未安装工具、未修改系统配置、未创建常驻采集任务，也没有向任何群发送消息。以上结论属于公开资料调研，不能替代真实账号与群的试点验证。
